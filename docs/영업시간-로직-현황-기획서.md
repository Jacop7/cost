# 1부 · 현황 (as-is)

## 0. 영업시간은 세 가지 일을 한다

| # | 하는 일 | 왜 | 근거 |
|---|---|---|---|
| ① | **하루의 경계**를 정한다 | 새벽 1시 매출이 어느 날짜인가 | 0047 |
| ② | **그날 값을 굳힌다** | 장사 중 레시피를 고쳐도 오늘 장부가 안 흔들린다 | 0048~0050 |
| ③ | **언제 자동으로 닫을지** 정한다 | 마감을 깜빡해도 장부가 닫힌다 | 0049 |

셋 다 필요한 기능이다. 문제는 셋이 **한 화면·한 상태·한 버튼에 뭉쳐 있다**는 점이다.

## 1. 데이터

### 1.1 `settings` — 사장님이 정하는 것 (4개)

| 컬럼 | 뜻 | 비고 |
|---|---|---|
| `open_time` | 영업 시작 시각 | 30분 단위 (화면 제약) |
| `close_time` | 영업 종료 시각 | **하루의 경계이기도 하다** |
| `break_start` / `break_end` | 브레이크 | 둘 다 넣거나 둘 다 비워야 함 |

저장은 `save_settings`. 검증은 **하나뿐** — 시작과 종료가 같으면 거부(`22000`). 경계를 정할 수 없기 때문이다.

### 1.2 `business_days` — 하루 한 행

| 컬럼 | 뜻 |
|---|---|
| `business_date` | 그 영업일 (매장별 UNIQUE) |
| `status` | `open` · `break` · `closed` |
| `planned_close_at` | 예정 마감 — **시작할 때 계산해 얼려 둔다** |
| `closed_at` / `close_method` | 닫힌 시각 · `manual`·`auto` |
| `last_activity_at` | 마지막 판매 기록 시각 |
| `snapshot` | **그날 굳은 값 전부** (jsonb) |
| `auto_close_ack` | 자동 마감을 사장님이 확인했는가 |

부분 인덱스(`status <> 'closed'`) 덕에 **열린 날은 매장당 사실상 하나**다.

## 2. 시각이 다섯 개다 — 헷갈림의 뿌리

| # | 이름 | 정의 | 언제 정해지나 |
|---|---|---|---|
| 1 | `open_time` / `close_time` | 사장님이 고른 값 | 설정할 때 |
| 2 | `business_cutoff()` | 자정 넘김이면 `close_time`, 아니면 `0` | **매번 설정을 다시 읽는다** |
| 3 | `business_day(at)` | `(at@KST − cutoff)::date` | 매번 계산 |
| 4 | `planned_close_at` | 날짜 + `close_time` | **영업 시작 때 얼린다** |
| 5 | `auto_close_at` | `greatest(예정 마감, 마지막 활동 + 1시간)` | 매번 계산 — **미끄러진다** |

화면에는 4번과 5번이 **동시에** 나왔다 — `예정 종료 22:00 이 지났어요 · 22:47 자동 종료`. 둘이 왜 다른지는 어디에도 없었다.

### ⚠ 하루 경계가 설정을 실시간으로 읽는다 (실측)

```
변경 전:              경계 = 00:00:00
close_time → 02:00:   경계 = 02:00:00   ← 즉시 바뀐다
```

영업시간을 바꾸면 **과거 데이터의 날짜 해석까지 소급해서** 달라진다. 이미 쌓인 `business_date` 는 안 움직이므로 둘이 어긋난다.

### ⚠ 자동 마감이 영영 안 올 수 있다

`greatest(예정 마감, 마지막 활동 + 1시간)` 이므로, 50분마다 하나씩 적으면 마감 시각이 계속 밀린다. 상한이 없다.

## 3. 상태 기계

```
   [none] ──open_business_day──▶ [open] ◀──set_break(false)──┐
   시작 전                        기록 중                      │
      ▲                            │  └──set_break(true)──▶ [break]
      │                     close_business_day
      │                            ▼
      └──(다음 날)──────────── [closed] ──reopen_business_day──┘
```

| 전이 | 함수 | 거부 조건 |
|---|---|---|
| none → open | `open_business_day` | 미래 날짜 · 다른 날이 열려 있음 · 그날이 이미 종료됨(`23505`) · **스냅샷이 비었음** |
| open ↔ break | `set_break` | 열린 날 없음 → "영업 중이 아니에요" |
| → closed | `close_business_day` | 〃 |
| closed → open | `reopen_business_day` | 열린 날이 있음 · 그 날짜가 종료 상태가 아님(`P0002`) |

`none`(오늘 아직 안 시작) 과 `closed`(오늘 이미 끝냄) 는 다르다. 화면이 다른 버튼을 그린다.

## 4. 스냅샷 — ②번 일의 실체

`open_business_day` 가 `build_day_snapshot` 을 불러 **그 순간의 값 전부**를 행에 넣는다. 스냅샷이 비면 **영업 시작 자체를 거부**한다.

| 키 | 얼어붙는 것 |
|---|---|
| `fixed_rate` · `fixed_items` | 그 달 고정지출률과 항목 |
| `ingredients` | 재료별 이름·단위·**기준단가** (0058) |
| `recipes` | 판매가·재료·부자재·세금 |
| `closing` | 마감할 때 그날 손익 집계를 덧붙임 |

**이 스냅샷 위에 서 있는 것 — 9곳**
`day_unit_price` · `day_menu_basis` · `day_fixed_rate` · `day_fixed_items` · `range_menu_detail` · `sales_extra_usage` · `sales_tax_breakdown` · `build_day_snapshot` · `open_business_day`

폐기 손실·세금·재료비·부자재·고정지출 **되짚기가 전부 여기 위에 있다.** "영업 시작"을 없앨 수 없는 이유다.

스냅샷에 없는 레시피를 팔면 막지 않고 **그때 더한다**(`add_to_day_basis`, 0062).

## 5. 무엇이 막히는가

| 상황 | 오류 | 어디서 |
|---|---|---|
| 오늘 영업일이 없음 | `45001` | `e10_sale_recorded` |
| 그날이 이미 종료됨 | `45002` | 〃 |
| 미래 날짜 판매 | `22000` | 〃 |
| 열린 날 없이 마감·브레이크 | `22000` | `close_business_day` · `set_break` |

**판매 기록만이 영업 상태를 본다.** 발주·입고·재고 수정·레시피 수정은 영업일과 무관하다.

## 6. 자동 마감 — 스케줄러가 없다

`close_if_due` 를 부르는 것은 **서버가 아니라 앱**이다(상태 조회 때마다, 60초 주기).

- 앱을 안 켜면 **어제가 안 닫힌다.**
- 어제가 열린 채면 오늘 판매가 `45001` 로 막힌다.
- 실제로 이틀 열려 있었고, "메뉴 판매 저장이 안 되네" 가 이것이었다.

### 실측 흔적

```
8/22 행:  planned_close_at  8/22 22:00 KST   ← 닫혔어야 할 시각
          closed_at         8/23 08:25 KST   ← 실제로 닫힌 시각
          close_method      auto
```

10시간 반 뒤에 닫혔다. `closed_at = now()` 라서 **8/22 장사가 8/23 아침에 끝났다**고 기록됐다.

## 7. 알림과 화면

`unacked_auto_close` 가 확인 안 한 자동 마감 1건을 준다. 배너에서 **고치기**(다시 열기) 또는 **확인**(`ack_auto_close`).

# 2부 · 결정된 변경안 (to-be)

> 사장님과 정한 것. **아직 구현 전이다.**

## 결정 1 — 1매장 전제를 코드에 못 박는다

**고치지 않는다.** `business_cutoff()` 도 `business_day()` 도 인자가 없고, 매장을 실으려면 부르는 곳을 전부 고쳐야 한다. 1차 범위가 1매장이니 값이 없다.

**대신 전제를 시끄럽게 만든다.** 지금은 2호점이 생기면 오류가 나는 게 아니라 **조용히 남의 영업시간으로 계산**된다. `settings` 행이 2개 이상이면 예외를 던지는 가드 한 줄이면, 전제가 깨질 때 깨진 걸 안다.

## 결정 2 — 영업시간 변경은 **익일부터**

새 개념이 아니다. 0048~0050 이 "오늘 값은 하루 동안 고정"인데 영업시간만 그 규칙 밖에 있었다. 안으로 넣으면 일관된다.

| 상황 | 언제 적용 |
|---|---|
| 오늘 영업이 열려 있음 | **다음 영업일부터** — 저장 화면이 그렇게 말해 준다 |
| 오늘 아직 시작 안 함 | **즉시** — 아직 굳은 게 없으니 안전 |

하루 안에서 경계가 절대 안 움직인다. 1부 8-③ 소급 문제가 사라진다.

## 결정 3 — 자동 마감은 **종료 시각 + 3시간 고정**

```
auto_close_at = planned_close_at + 3시간      ← 영업 시작 때 확정
22:00 마감  →  01:00 자동 마감
```

| | 지금 | 바꾼 뒤 |
|---|---|---|
| 마감 시각 | 판매할 때마다 밀림 | **항상 종료 + 3시간** |
| 영영 안 닫힐 수 있나 | **있음** | 없음 |
| 영업 시작 때 확정되나 | 아니오 | **예** |
| 화면 | 시각 둘 | **시각 하나** |

`last_activity_at` 은 **마감 판단에서 빠진다**(기록용으로만 남긴다). `touch_business_day` 도 마감 로직에서 빠진다.

화면 신호는 둘로 준다.

| 때 | 화면 |
|---|---|
| 종료 시각 ~ 마감 시각 | `영업시간은 끝났어요 · 01:00 까지 적을 수 있어요` |
| 마감 30분 전 | `곧 자동으로 마감돼요 · 01:00` |

## 결정 4 — `closed_at` 을 **계산된 마감 시각**으로

마감 시각이 고정되면 **나중에 계산할 수 있다.** 며칠 뒤에 앱을 켜도 "8/22 는 01:00 에 닫혔어야 했다"가 딱 나온다.

```
지금:   closed_at = now()                     → 8/22 장사가 8/23 아침에 끝났다고 기록
바꿈:   closed_at = planned_close_at + 3시간   (자동 마감일 때)
        closed_at = now()                     (사장님이 직접 누른 마감일 때)
```

늦게 처리해도 기록은 정확하다. **서버 스케줄러가 필요 없어진다.**

## 결정 5 — 열린 영업일이 있으면 **그 날이 오늘이다**

⚠ 결정 3 때문에 **반드시 필요한 짝**이다.

22:00 마감 + 3시간 = **01:00 — 자정을 넘는다.** 그런데 하루 경계는 자정이라, `00:30` 에 앱이 보는 "오늘"은 벌써 다음 날이다. 8/22 는 아직 열려 있는데도 **"8/22 장사가 안 닫혔어요 · 오늘 판매를 못 적어요"** 가 뜬다. 마감 정리하며 매출 적는 바로 그 시간에.

`+1시간`(23:00)이면 안 만나지만 `+3시간`이면 **반드시** 만난다.

### 규칙

```
1. close_if_due 를 먼저 부른다        — 마감 시각이 지났으면 닫는다
2. 그러고도 열린 날이 있으면 → 그 날이 오늘이다   (아직 마감 전이니까)
3. 열린 날이 없으면 → business_day() 가 오늘이다
```

00:30 에 8/22 가 열려 있고 마감(01:00) 전이면 판매는 **8/22 로 들어간다.** 맞는 날짜다.

부수 효과로 `staleDay`(어제가 안 닫힘) 상태가 **거의 사라진다.** 1번에서 이미 닫혔으므로, 열린 날이 마감 시각을 지나 있는 일 자체가 없다.

## 결정 6 — 과거 날짜를 **처음** 열 때만 경고

뒤늦게 적는 경우는 둘로 갈린다.

| 그날 영업을 시작했었나 | 뒤늦게 적을 때 |
|---|---|
| 시작했다 (행 있음) | `다시 열기` → **그날 스냅샷 그대로. 정확하다** |
| 아예 안 열었다 (행 없음) | `build_day_snapshot()` 이 **지금 값**으로 만든다 → 그날 장부에 오늘 가격이 박힌다 |

`open_business_day(매장, 과거날짜)` 는 **되고**(미래만 막는다), 스냅샷은 날짜를 인자로 받지 않는다. 그래서 아래쪽 칸에서 조용히 틀어진다.

**막지 않고 알린다.** 수기 입력이 이 앱의 전제라 몰아서 적는 일은 자주 있다. 열기 전에 이렇게 묻는다.

> 8/23 은 영업을 시작한 적이 없어요. **지금 가격·원가로 계산돼요** — 그날 값이 아니에요.

되짚어 만드는 것(`price_trends` 로 그날 단가, `entity_change_events` 로 그날 레시피 복원)은 **2차**다. 지금 급한 건 틀린 걸 조용히 넘기지 않는 것이다.
