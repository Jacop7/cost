# 레시피 손익 변동 최종 기획

## 1. 목적

레시피의 순이익이 **언제, 무엇 때문에, 얼마만큼** 바뀌었는지 사용자가 빠르게 확인하게 한다.

현재 화면처럼 순이익률과 재료비율만 반복하지 않는다. 목록에서는 최종 순이익과 증감액을 먼저 보여주고, 상세에서는 변동의 대표 원인과 순이익 결과만 보여준다.

프로토타입: `docs/prototypes/recipe-profit-history.html`

근거:

- `docs/source-v3/레시피_상세로직_유저시나리오_v3.txt` 1장·3.8절
- `docs/구현-변경점.md` 14절·19절
- `packages/db/supabase/migrations/20260608000004_recipes_pl.sql`의 `profit_trends`
- `packages/db/supabase/migrations/20260820000053_tax_one_place.sql`의 `recompute_recipe`

## 2. 핵심 결정

1. `손익 변동`은 수정 내역과 비슷한 목록 형태를 사용한다.
2. 목록의 대표 값은 `순이익 금액`이고, 그 아래에 직전 대비 증감액을 표시한다.
3. 상세는 `변동 원인`과 `손익 결과` 두 영역만 사용한다.
4. DB에는 전체 손익 스냅샷을 저장하지만 화면에는 필요한 값만 선별해 표시한다.
5. 금액이 없는 기존 비율 기록은 손익 변동 목록에서 표시하지 않는다.
6. `현재 매출 반영·미반영` 배지는 표시하지 않는다. 이 상태는 수정 내역에서만 다룬다.
7. 손익 기록은 영구 보존한다. 화면 데이터가 많아지면 삭제하지 않고 페이지 단위로 불러온다.

## 3. 수정 내역·그래프와 역할 구분

| 화면 | 사용자가 확인하는 내용 | 보관 |
|---|---|---|
| 수정 내역 | 누가 무엇을 직접 수정했는지, 어떤 값이 갱신됐는지, 현재 매출 반영 여부 | 화면 7일·서버 30일 |
| 손익 변동 | 변경 결과 순이익이 얼마에서 얼마로 움직였는지 | 영구 |
| 순이익률 변동 추이 | 기간별 순이익률·재료비율 흐름 | 영구 |

- 수정 내역의 `직접 수정·자동 갱신` 갈래를 손익 변동 화면에 다시 표시하지 않는다.
- 손익 변동에서는 사건 제목으로 원인을 설명한다.
- 같은 사건이 두 화면에 나타날 수 있지만 질문이 다르므로 중복 기능이 아니다.

## 4. 진입 위치

레시피 상세(RCP-02)의 `손익 변동` 영역에서 목록 행 또는 `자세히 보기`를 누르면 RCP-16으로 이동한다.

레시피 상세의 축약 목록도 RCP-16과 같은 한 줄 구조를 사용한다.

## 5. 목록 화면

### 5.1 헤더

```text
‹  손익 변동
```

- 헤더에는 레시피 이름을 붙이지 않는다.
- 조회·정렬·검색 버튼을 두지 않는다.
- 최신순으로 고정한다.
- 월별 머리말로 기록을 구분한다.

### 5.2 목록 한 줄

```text
08/20 · 14:41
고춧가루 단가 반영                 4,046.69원  ›
재료비 32원 감소                       +32원
```

표시 항목:

1. 발생 날짜와 시각
2. 사건 제목
3. 대표 원인 한 줄
4. 변경 후 순이익
5. 직전 대비 순이익 증감액
6. 우측 화살표

목록은 개별 카드 여러 개가 아니라 하나의 그룹 카드와 행 구분선을 사용한다.

### 5.3 증감 표시

| 상태 | 표시 |
|---|---|
| 순이익 증가 | 초록색 `+32원` |
| 순이익 감소 | 빨간색 `-36원` |
| 순이익 동일 | 회색 `변동 없음` |

손익 값이 동일한 재계산 기록은 DB에 남을 수 있지만 `손익 변동` 목록에서는 표시하지 않는다.

## 6. 사건 제목과 대표 원인

| 발생 원인 | 사건 제목 | 목록 대표 원인 예시 |
|---|---|---|
| 식재료 기준 단가 변경 | `{식재료명} 단가 반영` | `재료비 32원 감소` |
| 고정지출률 변경 | `고정지출 반영` | `고정지출 36원 증가` |
| 레시피 직접 저장 | `레시피 수정` | `판매가 500원 증가` |
| 세금 항목 변경 | `레시피 수정` | `세금 45.46원 증가` |
| 부자재 변경 | `레시피 수정` | `부자재 200원 증가` |

대표 원인이 여러 개면 순이익에 가장 크게 영향을 준 항목 하나를 목록에 표시한다. 나머지는 DB 스냅샷에 보존한다.

사용자 화면에서 `자동 반영`, `자동 전파`, `연관 변경`이라는 표현은 사용하지 않는다.

## 7. 상세 하단 시트

목록 행을 누르면 하단 시트를 연다.

```text
고춧가루 단가 반영
2026.08.20 14:41 · 고춧가루

변동 원인
재료비       2,838.40원 → 2,806.40원

손익 결과
순이익       4,014.69원 → 4,046.69원
순이익률         33.46% → 33.72%

닫기
```

규칙:

- 별도 `변경 내용` 헤더를 두지 않는다.
- 사건 제목을 최상단에 둔다.
- 날짜·시각·원인 대상을 제목 바로 아래에 표시한다.
- `변동 원인`에는 목록에서 선택된 대표 원인 한 줄만 표시한다.
- `손익 결과`에는 순이익과 순이익률 두 줄을 항상 표시한다.
- 판매가·세금·재료비·부자재·고정지출 전체 손익표를 반복하지 않는다.
- 하단 설명 문구와 현재 매출 반영 배지를 표시하지 않는다.

전체 계산 구성은 레시피 상세의 `손익 미리보기`에서 확인한다. RCP-16은 전체 손익표가 아니라 변동 기록이다.

## 8. 표시하지 않는 항목

- `현재 순이익` 요약 카드: 레시피 상세에 이미 있으므로 반복하지 않는다.
- 최근 N일 건수와 직접 수정·자동 갱신 건수: 수정 내역의 정보다.
- 현재 매출 반영·미반영: 수정 내역에서만 판단한다.
- 변하지 않은 손익 구성 항목
- 금액이 없는 기존 비율 기록
- 계산 과정 설명과 동적 안내 문구

## 9. 손익 계산 기준

모든 금액은 최소단위 원가를 사용한 **1인분 기준**으로 저장한다.

```text
순이익 = 판매가 - 세금 - 재료비 - 부자재 - 고정지출
순이익률 = 순이익 ÷ 판매가 × 100
재료비율 = 재료비 ÷ 판매가 × 100
```

- 세금은 서버의 `tax_of()` 한 곳에서 계산한다.
- 고정지출은 해당 영업월의 고정지출률을 판매가에 적용한다.
- 서버 RPC가 확정값의 권위다.
- `packages/core`는 같은 공식으로 미리보기와 검산만 수행한다.

고정 검산값:

```text
제육볶음 · 판매가 12,000원
재료비 2,806.40원
부자재 300원
세금 1,090.91원
고정지출 3,756원
순이익 4,046.69원
순이익률 33.72%
```

## 10. DB 스냅샷 확장

현재 `profit_trends`는 다음 값만 저장한다.

```text
trend_date · profit_rate · material_rate · cause · created_at
```

서버는 전체 손익을 계산한 뒤 비율만 저장하고 금액을 버리고 있다. 신규 마이그레이션에서 다음 필드를 추가한다.

| 필드 | 의미 |
|---|---|
| `occurred_at` | 사건이 실제 발생한 시각 |
| `previous_snapshot_id` | 비교 기준이 되는 직전 완전 스냅샷 |
| `price` | 판매가 |
| `material_cost` | 1인분 재료비 |
| `extra_cost` | 1인분 부자재 |
| `tax_amount` | 1인분 세금 |
| `fixed_cost` | 1인분 고정지출 |
| `fixed_rate` | 당시 고정지출률 |
| `profit_amount` | 1인분 순이익 |
| `profit_rate` | 순이익률 |
| `material_rate` | 재료비율 |
| `source_type` | `ingredient`·`recipe`·`fixed_cost` |
| `source_entity_id` | 원인이 된 식재료 등 원본 ID |
| `source_label` | 당시 원인 이름 스냅샷 |
| `summary` | 목록 대표 원인 |
| `calculation_version` | 손익 공식 버전 |
| `is_baseline` | 비교 기준용 초기 스냅샷 여부 |

기존 행 때문에 신규 금액 컬럼은 처음에는 nullable로 추가한다. 이후 `recompute_recipe`를 통해 생성되는 모든 신규 행은 금액 필드를 반드시 채운다.

`profit_trends`는 append-only를 유지한다. 과거 행을 현재 값으로 고치거나 삭제하지 않는다.

## 11. 기준 스냅샷과 기존 데이터

기존 비율 기록에서 과거 금액을 역산하지 않는다. 당시 판매가·세금·고정지출을 알 수 없으므로 현재 값을 넣으면 거짓 기록이 된다.

전환 시점 처리:

1. 배포 시점의 현재 손익을 레시피별 `is_baseline=true` 완전 스냅샷으로 한 번 기록한다.
2. 기준 스냅샷은 목록에 표시하지 않는다.
3. 이후 첫 변경부터 기준 스냅샷과 비교해 정확한 전후 금액을 표시한다.
4. 기존 비율 행은 삭제하지 않고 RCP-10 순이익률 그래프에서만 사용한다.
5. RCP-16은 `profit_amount is not null`이고 `is_baseline=false`인 행만 조회한다.

따라서 사용자 화면에 `기존 손익 기록`, `금액 기록 없음` 같은 기술 문구는 나오지 않는다.

## 12. 기록 시점

다음 서버 경로에서 완전 스냅샷을 기록한다.

- E1 입고 확정·취소로 식재료 기준 단가가 바뀌고 연결 레시피 손익이 달라진 경우
- E2/E5 허용 경로에서 기준 단가가 달라지고 연결 레시피 손익이 달라진 경우
- E3 레시피 저장으로 판매가·재료비·부자재·세금·순이익이 달라진 경우
- E4 고정지출률 변경으로 레시피 고정지출과 순이익이 달라진 경우

같은 사건이 여러 레시피에 영향을 주면 레시피마다 스냅샷 한 건을 기록한다. 원인 식별자는 동일한 `correlation_id`로 묶을 수 있지만, RCP-16은 현재 레시피의 행만 표시한다.

## 13. 조회와 정렬

- `occurred_at desc, id desc`로 정렬한다.
- 날짜만으로 정렬하지 않는다. 같은 날 여러 번 바뀌어도 정확한 순서를 유지해야 한다.
- 한 번에 20건을 가져오고 커서 기반으로 다음 페이지를 불러온다.
- 월별 머리말은 앱이 조회 결과를 기준으로 만든다.
- 총 건수를 상단에 표시하지 않으므로 전체 건수 집계 쿼리는 필요하지 않다.

## 14. 화면 상태

### 기록 없음

```text
아직 기록된 손익 변동이 없어요
레시피나 원가가 바뀌면 여기에 기록돼요
```

기준 스냅샷만 있고 실제 변동이 없어도 기록 없음 상태로 본다.

### 로딩

- 목록 영역에 기존 kit 로딩 상태를 사용한다.
- 과거 목록을 불러오는 동안 기존 행은 유지한다.

### 오류

- `손익 변동을 불러오지 못했어요`와 다시 시도 버튼을 표시한다.
- 일부 필드가 빠진 불완전 신규 행은 조용히 0원으로 바꾸지 않고 오류로 기록한다.

## 15. 구현 범위

### DB

1. `profit_trends` 금액·출처·시각 컬럼 추가
2. 기준 스냅샷 적재
3. `recompute_recipe`가 전체 손익 스냅샷을 기록하도록 변경
4. RCP-16 전용 커서 조회 RPC 추가
5. 같은 날 다건 정렬과 이전 스냅샷 연결 테스트 추가

### Core

1. DB와 동일한 손익 공식 유지
2. 스냅샷 전후 비교와 증감값 검산 함수 추가
3. 고정 검산값과 원인별 테스트 추가

### 앱

1. `RecipeDetail.profitTrends`의 비율 전용 타입과 RCP-16 상세 타입 분리
2. 레시피 상세 축약 목록 수정
3. `ProfitHistoryScreen`을 단순형 목록·하단 시트로 교체
4. 금액 없는 기존 행 필터링
5. 페이지네이션과 빈 상태 연결

RCP-10 `ProfitTrendScreen`은 기존 비율 그래프 역할을 유지한다.

## 16. 검수 조건

### 식재료 단가 변경

- 고춧가루 단가 변경으로 재료비가 32원 줄면 목록에 `재료비 32원 감소`가 표시된다.
- 변경 후 순이익 `4,046.69원`과 증감 `+32원`이 표시된다.
- 상세에는 재료비·순이익·순이익률의 전후값만 표시된다.

### 고정지출 변경

- 고정지출이 36원 늘면 순이익 증감은 `-36원`이다.
- 재료비나 세금처럼 변하지 않은 항목은 표시하지 않는다.

### 레시피 수정

- 판매가를 500원 올려도 순이익 증감액을 500원으로 표시하지 않는다.
- 세금과 고정지출 재계산까지 포함한 서버 확정 순이익 증감액을 표시한다.

### 데이터 경계

- 같은 날 여러 번 수정해도 시각과 순서가 정확하다.
- 기존 비율 행과 기준 스냅샷은 RCP-16에 나타나지 않는다.
- 기존 비율 행은 RCP-10 그래프에서 유지된다.
- 전체 스냅샷을 삭제하지 않아 장기간 추이를 잃지 않는다.
- 금액 null을 0원으로 표시하지 않는다.

## 17. 완료 기준

- 프로토타입과 앱의 목록·상세 구조가 같다.
- 순이익 금액·증감액·순이익률 전후값이 서버 스냅샷과 일치한다.
