# 매출관리 작성 수명주기 전환 기획안

> 상태: 아스트라 울트라·페이블 최종 P1 반영 및 재검수 중
> 범위: 매출관리 피드, 날짜별 매출 초안·확정·정정, 재고·손익 전파, 계산 기준 적용일
> 현재 구현의 권위: 구현 완료 전까지 `ARCHITECTURE.md`와 현행 DB RPC
> 목표: 사용자가 조작하는 영업 시작·브레이크·재개·영업 종료 절차를 없애고 날짜별 매출 작성으로 교체한다.

## 1. 결정 요약

사용자 입력 수명주기는 다음 세 상태로 통일한다.

```text
미작성 → 작성 중 → 작성 완료
                    │
                    └─ 수정 초안 → 수정 완료(보정 원장 추가)
```

- `작성 중`은 서버에 저장된 초안이다. 확정 매출·손익·재고 원장을 만들지 않는다.
- `작성 완료`는 해당 날짜의 판매·기타 매출·추가 지출·조리 후 폐기를 한 트랜잭션으로 확정한다.
- 작성 완료된 날짜의 수정은 완료 상태와 기존 확정값을 유지한 채 별도 수정 초안을 만든다.
- 수정 완료는 기존 원장을 삭제하거나 날짜를 다시 열지 않고 차이만 보정 원장으로 추가한다.
- 판매에서 파생된 기간 요약과 분석에는 작성 완료된 판본만 포함한다. 입고·식재료 폐기처럼 별도 RPC에서 이미 확정된 원장은 작성 상태와 분리해 해당 사건의 귀속일에 포함한다.
- 사용자가 누르던 `영업 시작`, `브레이크`, `영업 재개`, `영업 종료`는 화면과 공개 쓰기 계약에서 제거한다.
- 기존 `business_days`의 `open/break`를 새 초안 상태로 재사용하지 않는다. 자동 마감 크론이 초안을 확정하는 사고를 막기 위해 새 저장 경계를 사용한다.

`휴무`는 작성 상태가 아니라 날짜 분류다. 작성 현황의 세 상태 수에는 포함하지 않는다. 판매가 0원인 실제 영업일도 사용자가 `매출 없음`으로 작성 완료할 수 있으며, 이 경우 휴무나 미작성과 구분해 확정 영업일 수에 포함한다.

## 2. 사용자 화면

### 2.1 매출관리 메인

상단부터 다음 순서로 구성한다.

1. 기간 필터
2. 기간 핵심 요약 카드
3. 작성 현황
4. 영업일 최신순 피드

기간 핵심 요약 카드는 다음 값을 표시한다.

- 매출
- 판매량
- 지출
- 순이익과 순이익률
- `자세히 보기`

판매 요약 값은 확정 판본만 합산한다. 작성 중 금액은 요약에 섞지 않는다. 초안이 있는 경우 카드 아래에
`작성 중 N건은 합계에서 제외했어요`를 보조 문구로 표시한다.

작성 현황은 `미작성 N일 · 작성 중 N일 · 작성 완료 N일`을 표시한다. 휴무일은 분모와 각 건수에서 제외한다.

### 2.2 날짜 카드

모든 날짜 카드는 날짜와 우측 화살표를 누르면 읽기 전용 날짜 상세로 이동한다. 상태별 본문과 행동은 다음과 같다.

| 상태 | 카드 표시 | 하단 행동 |
|---|---|---|
| 미작성 | 매출·순이익 `—`, 상태 `미작성` | `작성하기` |
| 작성 중 | 초안 매출·예상 순이익, 상태 `작성 중`과 `임시저장` | `이어서 작성하기` |
| 작성 완료 | 확정 매출, 순이익·순이익률, 상태 `작성 완료` | 허용 기간이면 `수정` |
| 작성 완료 + 수정 초안 | 확정 매출·손익은 그대로 표시, 보조 상태 `수정 중` | `이어서 수정하기` |
| 휴무 | 상태 `휴무` | 없음 |
| 미작성 + 기간 만료 | 상태 `미작성`, 보조 상태 `입력 기간 종료` | 없음 |
| 작성 완료 + 기간 잠금 | 확정 매출·손익, 상태 `작성 완료` | 없음 |
| 미래 예정일 | 상태 `작성 불가` | 없음 |

작성·수정 허용 기간은 **전월 매출은 당월 말일까지, 당월 매출은 추천 작성 영업일까지**다. 서버가 이를 `지난달 1일 ~ 추천 작성 영업일` 범위로 반환한다. 일반적으로 추천 작성 영업일은 매장 달력의 오늘이지만 밤샘 영업 규칙에서는 달력 날짜와 다를 수 있다. 기간 밖에서는 행동 버튼을 숨기고 상세만 제공한다. 잠금 7일 전과 1일 전에는 피드에서 남은 기간을 안내한다.

### 2.3 날짜별 매출 작성

현재 매출관리 홈의 판매 수량, 기타 매출, 추가 지출, 조리 후 폐기 입력을 날짜별 작성 화면으로 옮긴다.

- 새 날짜: `YYYY년 M월 D일 매출 작성`
- 완료된 날짜 수정: `YYYY년 M월 D일 매출 수정`
- `임시저장`: 초안만 저장하고 목록의 상태를 `작성 중`으로 바꾼다.
- `작성 완료`: 부족 재고와 확정 영향을 확인한 뒤 서버 확정 RPC를 한 번 호출한다.
- 추천 작성 영업일이 끝나기 전에 완료하면 이후 생기는 매출은 `수정`으로 추가해야 한다는 확인 문구를 표시한다.
- 완료 응답을 받지 못한 재시도는 같은 요청 키를 사용한다.
- 수정 화면을 나가도 원래 완료 판본은 기간 요약과 재고에 계속 남는다.
- 입력량이 현재 확정 재고나 최근 판매량에서 크게 벗어나면 상한으로 잘라 저장하지 않고 확인 경고를 표시한다. 사용자가 확인하면 부족 재고를 숨기지 않고 전체 필요량을 저장한다.

### 2.4 날짜 상세

- 작성 완료일: 기존 일 매출 분석을 표시한다.
- 작성 중: 확정 분석 대신 `작성 중인 매출`과 예상값을 표시하고 `이어서 작성하기`를 제공한다.
- 미작성: 빈 분석을 만들지 않고 `아직 작성하지 않았어요`와 `작성하기`를 제공한다.
- 기간 밖 미작성·만료 초안: 읽기 전용 사유만 표시한다.

## 3. 영업일 목록의 권위

모든 달력일을 미작성으로 만들지 않는다. 서버가 매장 시간대와 영업 규칙으로 날짜 원장을 만든다.

1. `sales_calendar_days`는 매장·판매 영업일별 `expected | closed` 분류를 보존한다.
2. 서버가 각 매장 로컬 날짜가 시작될 때 당시 시간대·영업 규칙으로 추천 판매 영업일과 그 날의 분류를 한 번 생성한다. 밤샘 영업에서는 `local_date`와 `sales_date`를 따로 보존한다.
3. 생성된 과거 날짜 분류는 이후 영업시간 설정 변경으로 다시 계산하지 않는다.
4. 임시 휴무는 `closed`로 바꾸며, 이미 초안이나 확정 장부가 있으면 휴무로 바꿀 수 없다.
5. 예정에 없던 영업일은 사용자가 날짜를 골라 작성을 시작할 때 `expected`로 생성한다.
6. 피드는 `expected` 날짜와 실제 초안·확정 장부가 있는 날짜를 표시한다. `closed`는 기본 목록에서 제외하고 필터로 확인할 수 있다.
7. 날짜 생성 작업이 누락돼도 조회 시 같은 순수 날짜 해석기로 필요한 범위를 멱등 보충한다. 미래 `expected` 날짜는 저장된 운영 규칙의 유효기간과 판본으로 해석하며 전 요일 휴무이면 다음 적용일을 다음 매장 날짜로 반환한다.
8. 한 번 설정 변경 응답으로 반환한 적용일은 이후 휴무 변경이나 규칙 변경으로 이동시키지 않는다.
9. 과거 이관 시 확정 장부가 있는 날은 `expected`, 명시적 휴무 기록이 있는 날은 `closed`로 보존한다. 나머지 편집 가능 날짜는 저장된 운영 규칙으로 `expected`를 생성하고 사용자가 실제 휴무였던 날을 `closed`로 확정한다. 휴무로 추정해 자동 제외하지 않으며, 날짜 분류 변경은 사유·실행자·시각·전후 판본을 감사 원장에 남긴다.

이 분류와 작성 상태를 분리해 휴무일이 `미작성` 건수를 늘리지 않게 한다.

`현재 추천 sales_date`는 매장 시간대와 저장된 운영 규칙으로 서버가 정한다. 오늘의 예정 시작 전이거나 오늘이 휴무이면 오늘의 달력상 전날 `business_date`, 그 밖에는 오늘 `business_date`다. 예정 시작 시각이 없는 날은 서버가 정한 날짜 전환 시각을 시작 경계로 사용한다. 이 값은 실사 가능일·작성 기본일·편집 만료 계산에 공통으로 쓰며 기기 시계로 다시 계산하지 않는다.

## 4. 계산 기준과 설정 변경

### 4.1 날짜 기준 버전

과거 날짜를 늦게 작성해도 그 날짜의 가격·원가·세금·고정 지출로 계산해야 한다. 다음 기준은 적용일이 있는 불변 판본으로 관리한다.

- 메뉴 판매가와 판매 상태
- 레시피 구성과 재료 기준단가
- 세금 프로필과 가격 기준
- 고정 지출률과 항목별 평균

각 판본은 `effective_from_business_date`, 기준 품질, 서버 판본 번호를 가진다. 설정 변경은 기존 판본을 덮어쓰지 않고 새 판본을 추가한다.

기준 판본은 메뉴 판매가·판매 가능 상태, 레시피 구성, 재료 기준단가와 평가 방식, 세금 프로필·가격 기준·구성 항목별 반올림, 고정 지출률과 근거 월을 하나의 매니페스트로 묶는다. 한 날짜의 계산 중 일부만 다른 판본을 사용하지 않는다. 하루 안에서 계산 기준은 하나이며 POS 거래 시각별 기준 변경은 1차 범위에서 지원하지 않는다.

기준 이력 보장이 시작되는 출시일을 `basis_history_start_date`로 둔다. 그 이전 날짜는 다음 규칙을 사용한다.

- 기존 작성 완료일의 수정 초안은 그 완료 판본의 스냅샷과 `basis_quality`를 그대로 상속한다.
- 이관 전 미작성일은 복원 가능한 날짜 기준만 사용하고, 부족한 값에 현재 기준을 사용했다면 `estimated_current`로 표시한다.
- `estimated_current`를 정확한 당시 기준처럼 숨기지 않으며 작성 완료 확인에서 사용자에게 알린다.
- 당시 기준에 없던 메뉴를 과거 날짜에 추가하면 같은 품질 정책을 적용하고 근거 없는 값을 0으로 채우지 않는다.

### 4.2 적용일 결정

- 서버 매장 시각을 기준으로 오늘이 예정 영업일이고, 오늘의 예정 시작 시각 전이며, 오늘 날짜에 고정된 초안·확정 판본이 없으면 오늘부터 적용한다.
- 그 밖에는 저장 시점 운영 규칙과 등록 휴무로 계산한 오늘 이후 첫 예정 영업일부터 적용한다.
- 30일 안에 예정 영업일이 없거나 예정 시간이 불확실하면 다음 매장 날짜부터 적용한다.
- 이미 시작한 초안과 작성 완료된 장부는 새 설정 때문에 움직이지 않는다.
- 매장 시간대 변경도 적용일 판본으로 저장한다. 활성 초안·미완료 이관이 있는 동안 현재 시간대를 즉시 덮어쓰지 않으며, 과거 날짜 원장은 생성 당시 시간대와 운영 규칙 판본을 유지한다.

저장 확인 화면은 서버가 계산한 적용일을 저장 전에 보여 주고, 저장 응답도 정확한 `effective_from_business_date`를 반환한다. 과거 적용일 지정과 사용자의 임의 적용일 변경은 1차 범위에서 지원하지 않는다. 같은 적용일에 여러 변경이 있으면 모두 불변 판본으로 남기고 `(effective_from_business_date, revision)`이 가장 큰 판본을 아직 고정되지 않은 날짜의 기준으로 사용한다. 이미 고정된 초안·확정 판본은 그대로다. 설정 이력의 적용 표시는 완료 여부에 의존하지 않는다.

판본 발행은 조회 해석기에 맡기지 않는다. **매니페스트 입력을 바꾸는 모든 쓰기 경계**가 자신의 원장 변경과 같은 트랜잭션에서 공통 `publish_sales_basis_version`을 호출한다. 아래 목록은 최소 필수 사례이며 새 입력 경로를 추가할 때 발행 여부를 명시하지 않으면 배포할 수 없다.

- 메뉴 판매가·판매 상태·레시피 구성의 등록·수정·복구·삭제
- 입고·입고 취소처럼 재료 평가단가를 실제로 바꾸는 E1/E11과 그 경제 정정, 호환 `save_ingredient`의 구매가격·용량·`cost_scope`·단가 override 변경
- 매장 세금 프로필, 가격 포함/미포함 기준, 메뉴별 세금 override의 등록·수정·복구
- 고정 지출 항목/평균기간 설정 완료와 대상 월 마지막 재입력·취소·정정으로 비율 근거가 바뀌는 시점
- 영업시간·휴무 규칙·시간대 설정의 적용일 판본
- 매장 월 경계에서 새 대상월의 고정 지출 표본을 고정하는 서버 작업 또는 최초 조회 전 멱등 준비 명령

발행기는 공통 매장 쓰기 잠금 아래 **대상 적용일에 유효한 각 source 판본**을 합성해 전체 계산 입력 매니페스트를 만들고, source kind·source ID·source revision·유효 시작일을 보존한다. 현재값을 그대로 복사해 미래 변경을 조기 적용하지 않는다. 더 이른 적용일의 새 변경이 이미 예약된 미래 적용일 경계에 영향을 주면 그 경계마다 새 합성 판본을 append한다. 기존 판본과 이미 고정된 초안·확정 판본은 바꾸지 않는다. 무변경 쓰기는 판본을 만들지 않으며 같은 source revision 재시도는 하나의 판본만 반환한다.

- 현재 활성 최신 판본: `현재 계산 기준에 반영 중`
- 미래 적용 판본: `M월 D일부터 반영 예정`
- 더 오래된 과거 사건: 적용 상태 배지를 표시하지 않음

`영업 종료 후 반영 예정`, `매출 작성 완료 후 반영 예정`은 사용하지 않는다.

### 4.3 초안 기준 고정

- 첫 서버 임시저장 시 해당 영업일에 유효한 기준 판본 ID를 초안에 고정한다.
- 첫 저장 전 미리보기도 서버의 같은 날짜 기준 해석기를 사용한다. 첫 저장 요청은 미리보기의 `basis_version_id`를 보내며 서버 최신 해석과 다르면 저장하지 않고 변경된 미리보기를 반환한다.
- 초안 작성 중 설정이 바뀌어도 기준을 자동 교체하지 않는다.
- 고정 뒤에는 같은 날짜의 기준을 교체하지 않는다. `새 기준으로 재계산`은 이관 전 근거가 없어 `legacy_unrecorded` 또는 `estimated_current`로 표시된 **최초 작성 초안**을 저장하기 전 서버가 복원한 더 정확한 기준을 발견한 경우에만 제공한다. 수정 초안은 원래 완료 판본의 기준을 항상 유지한다.
- 초안에는 사용자가 입력한 수량·채널·금액·메모와 기준 판본 ID를 저장한다.
- 작성 완료는 고정된 판본을 확정 스냅샷으로 복사하고 서버 공식을 실행한다.
- 고정 지출 기준은 설정 변경뿐 아니라 매장 월 경계에서도 새 대상월의 직전 N개 완료 월 표본으로 판본을 생성한다. 해당 N개월이 미완료이면 고정 지출률은 `null`이며 이후 월 입력 완료 때 같은 대상월의 새 판본을 추가한다.
- 컷오버 때 현재 계산 설정 전체를 매장 생성일에 적용된 기준선 판본 `v0`로 생성한다. 이관 전 과거 근거가 없는 날짜는 이 판본을 사용하되 `estimated_current` 품질을 유지한다. 구 구조의 대기 설정 변경은 저장 당시 의도를 보존해 컷오버 뒤 첫 예정 영업일에 적용되는 새 판본으로 변환한다.

## 5. 서버 데이터 모델

명칭은 구현 시 기존 스키마와 충돌 여부를 확인해 확정하되 역할은 분리한다.

### 5.1 `sales_calendar_days`

- `store_id`, `business_date`
- `day_kind`: 제품 경로는 `expected | closed`. DB enum의 `unclassified`는 전환 호환 예약값이며 현재 생성기·백필은 발행하지 않는다.
- `source`: `operating_rule | manual_extra | manual_closed`
- `operating_rule_id`, `scheduled_open_at`, `scheduled_close_at`
- `timezone_id`, `local_date`, `sales_date`
- `revision`, `created_at`, `updated_at`
- 매장·날짜 유일 제약

### 5.2 `sales_day_drafts`

- `store_id`, `business_date`, `draft_kind`: `initial | amendment`
- 클라이언트가 생성한 불변 `draft_id`
- `status`: `editing | expired | discarded | finalized`
- `base_ledger_revision`: 최초 작성은 `0`, 수정은 현재 확정 판본
- `basis_version_id`
- `draft_revision`
- `last_saved_by`, `last_saved_at`
- 날짜당 활성 최초 초안 하나, 최신 완료 판본당 활성 수정 초안 하나를 부분 유일 제약으로 보장한다.

메뉴 수량·채널, 기타 매출, 추가 지출, 조리 후 폐기는 초안 자식 행 또는 정규화한 JSON 계약으로 저장한다. 확정 원장 테이블과 섞지 않는다. 모든 배열은 **전체 목표값**이다. 수정 초안은 서버가 최신 확정 판본의 모든 행을 복제해 시작하며 클라이언트는 저장 때 전체 행 집합을 보낸다. 서버는 최신 판본의 line ID가 빠진 payload를 거부하고, 사용자가 명시적으로 `deleted=true` 또는 메뉴 목표 수량 0을 보낸 행만 삭제로 해석한다. 최초 작성에서 빈 배열은 항목 없음이지만, 수정에서 기존 행이 있는 배열을 `[]`로 보내는 것은 전체 삭제가 아니라 오류다. 전체 삭제도 기존 line별 tombstone을 보내야 한다. `미전송(null)`과 `빈 배열`을 같은 뜻으로 사용하지 않는다.

### 5.3 확정 판본

기존 `daily_sales`, `business_days.snapshot`, `business_day_revisions`, `inventory_events`의 감사 의미를 유지한다. 논리적 `sales_day_versions(store_id, business_date, version_no)`는 각 날짜의 확정 판본 전체를 불변으로 보존하며 현재 판본 포인터만 전진한다.

- 최초 작성 완료는 날짜당 확정 장부를 한 번 만든다.
- 수정 완료는 현재 확정 판본 `v(n)`을 잠그고 `v(n+1)` 전체와 전후 상세를 추가한다.
- 판매 증가분은 E8, 감소분은 E9로 추가하며 기존 이벤트를 삭제하지 않는다.
- 수정 보정은 항상 `v(n+1) - v(n)`으로 계산한다. 보정 사건은 `business_date`, `from_version`, `to_version`, `source_draft_id`, `source_line_kind`, `source_line_id`를 보존하고 `(source_draft_id, source_line_kind, source_line_id, ingredient_id, event_type)` 유일 제약으로 중복 게시를 막는다. 두 메뉴가 같은 재료를 써도 판매행별 사건이 충돌하지 않아야 한다. 재고 수량 변화에서 양수는 복원(E9), 음수는 차감(E8)이다.
- `source_line_kind`는 적어도 `menu_sale_consumption | menu_cooking_waste`를 서로 다른 값으로 강제한다. 같은 메뉴행·같은 재료에서 판매 수량과 조리 후 폐기가 함께 바뀌어도 한 사건이 다른 사건의 유일 키를 차지하지 않는다.
- 각 판매 소비 증분은 불변 `sales_inventory_delta_component` ID, 수량, `stock_effect=normal|absorbed|resolved_by_count`, 연결 count batch를 보존한다. 이후 목표 감소는 아직 상쇄되지 않은 소비 component를 최신 판본·component ID 역순으로 결정적으로 배정하고 각 component의 stock effect만 반대로 적용한다. 흡수·재실사 해소 component는 감소해도 재고 E9를 만들지 않고, 정상 component만 E9를 만든다.
- 같은 목표 수량 재호출은 새 재고 이벤트를 만들지 않는다.
- 완료 판본의 기준 스냅샷은 이후 설정 변경으로 다시 계산하지 않는다.

## 6. 서버 명령 계약

### 6.1 초안 저장 `save_sales_draft`

입력:

- 매장, 영업일, 초안 종류
- 전체 목표 입력값
- `base_ledger_revision`, `base_draft_revision`
- 클라이언트 요청 키
- 첫 저장에는 미리보기의 `basis_version_id`

동작:

1. 매장 소유권을 검사하고 요청 키와 공통 매장 쓰기 범위를 잠근다.
2. 기존 요청 영수증이 있으면 정규화 payload hash를 비교한다. 같으면 성공 영수증을 먼저 재전달하고, 다르면 요청 키 충돌로 거부한다.
3. 신규 요청만 서버 날짜의 편집 허용 범위와 날짜·초안 revision을 검사한다.
4. 첫 저장이면 날짜 기준 판본을 선택해 고정한다.
5. 초안 판본이 다르면 충돌로 거부하고 최신 초안을 반환한다.
6. 원장·재고·확정 요약을 변경하지 않는다.

요청 키는 명령 종류, 초안 ID, 정규화 목표 hash, 결과 판본에 결속한다. 최초 초안처럼 아직 잠글 행이 없는 경합도 공통 매장 범위 잠금으로 설정 저장·휴무 전환과 직렬화한다. `draft_revision` 충돌은 최신 서버 초안을 반환하고 클라이언트는 자동 병합하지 않는다.

### 6.2 최초 확정 `finalize_sales_day`

하나의 DB 트랜잭션에서 다음을 수행한다.

1. 소유권 확인 뒤 요청 키 영수증과 payload hash를 먼저 검사한다. 성공한 동일 요청의 재시도는 월 경계가 지나도 같은 영수증을 반환한다.
2. 신규 요청이면 매장·날짜·초안·기준 판본·편집 기간·revision을 검사하고 잠근다.
3. 초안 입력 무결성과 영업일 당시 메뉴 존재·판매 상태를 검사한다. 과거 판매의 늦은 작성이나 정정은 현재의 판매 중지·삭제만으로 막지 않는다. 현재 날짜의 신규 판매만 현재 판매 중지를 적용한다.
4. 고정된 기준 매니페스트의 세금 프로필·가격 기준·구성 항목·반올림 규칙으로 세금 스냅샷을 만든다. 완료 시점의 `store_market_profiles`나 `store_tax_profiles`를 다시 읽어 초안 기준을 바꾸지 않는다.
5. 고정된 기준으로 매출, 세금, 재료비, 고정 지출, 추가 지출, 순이익을 계산한다.
6. 판매·기타 매출·지출·폐기의 확정 원장을 기록한다. 최초 작성은 초안 전체 목표값을 그대로 확정한다. 수정은 서버가 복제한 기존 line과 신규 line의 전체 집합을 사용하고, 명시적 0/tombstone만 제거한다. 기존 `apply_sale_items`의 부분 patch 의미에 전체 목표 배열을 그대로 넘기지 않는다.
7. 판매 필요량 전량을 E8로 기록하고 음수 재고를 허용한다.
8. 일 요약과 스냅샷을 기록한다.
9. 초안을 `finalized`로 바꾸고 확정 판본을 증가시킨다.

중간 한 단계라도 실패하면 전체를 롤백한다. 요청 키와 매장·날짜의 유일 제약으로 연타와 응답 유실 재시도를 멱등 처리한다.

### 6.3 수정 확정 `finalize_sales_amendment`

- 소유권을 확인한 뒤 요청 키를 잠그고 payload hash를 검증한다. 기존 성공 영수증이 있으면 편집 기간과 `base_ledger_revision`을 다시 검사하기 전에 같은 성공 결과를 반환한다. 신규 요청에만 현재 편집 가능 기간과 최신 확정 판본을 검사한다.
- 완료 상태를 해제하지 않는다.
- `base_ledger_revision`이 최신이 아니면 충돌로 거부한다.
- 기존 `amend_ended_business_day`의 전후 감사와 E8/E9 차이 원칙을 계승한다.
- 성공 시 새 확정 판본과 수정 이력을 추가하고 수정 초안을 `finalized`로 바꾼다.
- 무변경 수정 완료는 원장·확정 판본·확정 수정 시각을 올리지 않지만 수정 초안은 `finalized`로 닫고 예약량을 제거한다.

### 6.4 조회 `sales_feed`

서버가 기간과 페이지 커서를 받아 다음을 한 응답으로 제공한다.

- 서버 매장 달력 날짜(`local_date`), 추천 작성 영업일(`sales_date`), 편집 가능 시작·종료일
- 확정 기간 요약
- 미작성·작성 중·작성 완료 건수
- 날짜별 분류, 작성 상태, 확정값, 초안 예상값, 수정 초안 여부, 행동 가능 여부
- 휴무일 수와 제외 사유

기존 `sales_range`의 확정 집계 공식을 재사용하되 빈 날짜를 확정 0원으로 만들지 않는다.

피드는 확정 판본이 있으면 최신 확정값을, 확정 없이 초안만 있으면 `잠정` 예상값을 표시한다. 기간 요약에는 최신 확정 판본만 포함한다. 전월 편집 창이 닫히기 전 월간 요약은 `잠정`, 닫힌 뒤는 `확정`으로 표시하되 E2처럼 독립 원장 취소가 생기면 귀속일 기준으로 갱신될 수 있음을 상세에 알린다.

## 7. 재고 표시와 부족 판정

공식 재고는 확정 원장만 반영한다. 작성 중 판매 때문에 사용자가 가용 재고를 과대평가하지 않도록 별도 예상값을 제공한다.

- `확정 재고`: `inventory_states.stock_total`
- `작성 중 차감 예정`: 활성 최초 작성 초안의 판매와 조리 후 폐기에 필요한 재료별 증가분 합계
- `예상 가용 재고`: 확정 재고 − 작성 중 차감 예정

예상값은 `inventory_events`와 `stock_total`을 수정하지 않는다. 부족 경고는 고정된 기준에서 계산한 재료별 예약량, 다른 활성 초안 예약, 과거 스냅샷의 `stock_tracking`을 함께 사용하며 판매 완료 자체는 막지 않는다. 초안 폐기·만료·완료 시 예약값은 같은 트랜잭션에서 제거한다.

완료된 장부의 수정 초안은 판매와 조리 후 폐기 각각의 고정 기준 재료 필요량을 **최신 확정 판본**과 비교해 재료별 순증가분만 예상 예약에 포함한다. 감소분은 예약 합계에서는 0으로 두고 수정 완료 전까지 확정 재고에 되돌리지 않는다. 다른 기기가 먼저 새 판본을 확정하면 `base_ledger_revision` 충돌로 완료를 거부한다.

입고(E1), 입고 취소(E11), 식재료 폐기(E2), 가감형 재고 조정은 작성 상태와 독립된 확정 원장으로 계속 처리한다. 초안에 들어 있는 판매 소진량을 다시 `재고 차감` 사유로 입력하지 않도록 예상 가용 재고와 확정 재고를 함께 표시한다. 여러 날짜 초안→가감 조정·폐기→부분 완료 순서를 별도 검산한다.

절대 목표 재고 설정(E5)은 1차 버전에서 **원장 컷오프**로 취급한다.

1. 새 재고 조정 명령은 서버 검증 출처로 `absolute_count | relative_adjustment`를 분리한다. `absolute_count`는 매장의 활성 재고 추적 식재료 전체를 한 시점에 세는 일괄 실사이며 누락 식재료가 있으면 확정하지 않는다. 일부 식재료만 고치는 화면은 `relative_adjustment`로 처리하고 컷오프를 만들지 않는다. 사용자 표시 사유 문자열만으로 둘을 판정하지 않는다.
2. 사용자가 실사를 시작하면 서버는 하나의 활성 `inventory_count_session`과 관측 토큰을 발급하고 `observation_started_at`, `expires_at`(4시간), 공통 매장 쓰기 revision, 대상 식재료 ID 집합, 재고별 revision, `inventory_event_sequence` 상한을 고정한다. 세션 상태는 `active | completed | cancelled | expired | invalidated`다. 시작 RPC는 날짜·초안·재실사 전제를 검사하고, 사용자는 명시 취소할 수 있다. 모든 관련 쓰기 RPC는 서버 시각이 `expires_at`을 지났으면 먼저 세션을 `expired`로 바꾼다. 따라서 앱 종료·네트워크 단절이 매장을 영구 차단하지 않는다. 화면은 `실사 중에는 입고·폐기·사용·이동을 멈춰 주세요`를 표시하고 시작·완료 때 사용자가 물리 변동이 없었음을 확인한다. 활성 세션 동안 서버는 일반 재고 쓰기와 판매 완료를 막는다. 사용자는 대상 목록 전체를 입력한다. 완료 시 서버는 같은 목록·revision·사건 상한을 다시 검사한다. CAS 실패는 트랜잭션을 예외 롤백하지 않고 세션을 `invalidated`로 보존한 구조화 결과를 반환하며 `재고가 변경됐어요. 다시 실사해 주세요`를 표시한다. 입력 확정 시각을 실제 계수 시각으로 간주하지 않으며 관측 구간 전체를 하나의 불확실 구간으로 취급한다.
3. 일괄 E5는 유효한 관측 토큰에서 불변 `inventory_count_batch`를 만들고 `counted_at`, 컷오프 영업일, 검증한 `inventory_event_sequence` 상한, 식재료별 실측값과 E5 사건을 원자 기록한다. `counted_at`은 사용자가 임의 입력한 과거 시각이 아니라 관측 세션 완료를 서버가 받아들인 시각이다. 1차 버전은 서버의 현재 추천 `sales_date`가 이미 작성 완료됐거나 휴무로 확정된 경우에만 절대 실사를 허용하고 그 날짜를 컷오프로 쓴다. 현재 추천 날짜가 미작성·작성 중·수정 중이면 예정 시작 전이어도 절대 실사를 막고 상대 조정만 허용한다. 이 제한으로 실사 전에 발생했지만 아직 초안에만 있거나 기록하지 않은 당일 판매가 실사 뒤 E8로 다시 차감되는 경로를 없앤다.
4. E5 확정 전 검사 범위는 `직전 매장 컷오프 < D <= 새 컷오프`이면서 `편집 가능 시작일 <= D`인 `expected`와 `manual_extra` 날짜로 한정한다. 이 범위의 날짜는 모두 작성 완료 또는 휴무로 확정돼야 하고 활성 최초·수정 초안이 없어야 한다. 현재 추천 날짜도 반드시 이 검사에 포함한다. 서버가 조건을 검사해 미완료 날짜를 반환하며 조건 미충족이면 실사를 막는다.
5. 편집 기간이 끝난 미작성일과 만료 초안은 실사 전제 검사에서 제외한다. 확인 화면에 `만료 미작성 N일 · 재고 미반영분은 이번 실사의 감모에 포함돼요`를 표시하고, 이 날짜는 이후 판매 재고 사건으로 확정할 수 없다.
6. 모든 재고 쓰기 진입점은 재고·발주·입고·판매 행을 잠그기 전에 같은 공통 매장 쓰기 잠금을 먼저 획득한다. 잠금 순서는 `매장 쓰기 범위 -> 날짜/원본 사건 -> 재고 상태 -> 발주·판매 상세`로 고정한다. 모든 재고 쓰기는 매장 쓰기 revision과 사건 sequence를 증가시킨다. E5는 이 잠금 안에서 날짜 상태와 관측 토큰 재검사, 모든 활성 식재료 재고 행 잠금, 일괄 절대 조정, 매장 단위 컷오프, 요청 영수증을 한 트랜잭션으로 기록한다. 컷오프 이하 날짜를 나중에 `expected`나 `manual_extra`로 바꾸는 분류 변경은 막고 `재고 반영 기간이 끝났어요`를 표시한다.
7. 컷오프 가드는 `inventory_events`를 쓰는 단일 서버 함수 또는 트리거에서 적용한다. 진입점에서 획득한 공통 매장 잠금을 같은 트랜잭션에서 재확인한 뒤 컷오프를 다시 읽어 `가드 통과 -> E5 커밋 -> 과거 사건 커밋` 경합을 차단한다. 트리거가 재고 행을 잡은 뒤 처음으로 매장 잠금을 획득해서는 안 된다. 판매 최초 확정·날짜 분류처럼 `sales_date`만으로 판정하는 쓰기는 컷오프 이하 신규 재고 게시를 거부한다. 완료일 amendment와 비판매 지연 사건은 발생일만 보지 않고 8·10항의 관측구간 전용 명령만 통과한다. 관측 완료 뒤 실제 발생했고 이후 실사가 없는 것으로 검증되면 business/sales date가 cutoff 이하라도 현재 재고에 정상 사건을 게시한다. 역분개·취소 사건은 `reverses_event_id`의 원본 행을 같은 잠금에서 읽고, 새 사건 날짜와 원본 사건의 귀속 영업일 중 하나라도 컷오프 이하이면 기존 재고를 되돌리지 않는다. 연쇄 역분개가 있으면 최초 원본까지 따라가 보호 귀속일을 판정한다. 또한 원본 사건이 뒤이은 실사 배치의 high-watermark 이하이고 해당 식재료가 그 배치에 포함됐다면, 원본·취소 날짜가 컷오프 뒤여도 기존 재고 역분개를 금지한다. 실제 반품·재입고처럼 지금 물리 수량이 바뀐 사건은 과거 취소가 아니라 현재 시각의 별도 사건으로 기록한다. 일괄 절대 실사 배치와 그 E5 사건은 생성 뒤 수정·취소·역분개하지 않으며 새 일괄 실사로만 전진 보정한다. 상대 조정과 어떤 실사에도 흡수되지 않은 일반 사건만 기존 취소 규칙을 따른다. 각 RPC의 사전 검사는 이 공통 가드를 대체하지 않는다.
8. 실사 전후에 늦게 입력한 입고·이동·상대 조정·폐기는 정확한 `occurred_at` 없이는 저장할 수 없고 입력 시각·영업일 자정 같은 기본값을 쓰지 않는다. 클라이언트는 최근 실사 관측 시작·완료 시각과 함께 실제 발생 시각을 기본 선택 없이 받는다. 서버는 같은 식재료의 실사 구간을 시간순으로 대조한다. 관측 시작 전 실제 발생했지만 실사 뒤 입력된 사건은 `event.seq > batch.event_sequence_high_watermark`와 해당 식재료 실측 행을 확인해 최초 후속 batch의 `absorbed_by_count_batch_id`로 자동 연결하고 `count_delta=0`으로 기록한다. 관측 완료 뒤 발생했고 이후 실사가 없으면 날짜가 cutoff 이하라도 정상 `count_delta`로 게시한다. `observation_started_at <= occurred_at <= counted_at`이면 자동 흡수하지 않고 경제·감사 정보만 `ambiguous_during_count`로 남겨 `inventory_recount_required`와 미해결 `ingredient_id` 집합을 만든다. 사용자는 배치를 고르거나 흡수 여부를 끌 수 없다. 이 상태에서는 일반 입고·폐기·이동·상대 조정을 막고 재고값을 `재실사 필요`로 표시한다. 단, 다음 실사 전제검사와 같은 범위인 `유효 cutoff < D <= 현재 sales_date`의 편집 가능 날짜 전체에서 최초 초안 저장·완료와 활성 수정 초안 완료·폐기는 복구 모드에서 허용한다. 부족 판정은 신뢰 불가 안내를 반환하며 새 판매 완료의 E8/E9는 그대로 원장에 남긴다. 컷오프 이하 신규 판매와 편집 기간 밖 판매는 계속 막되, 이미 완료된 날짜의 보고 정정은 10항 전용 amendment 경로만 허용한다. 모든 대상 날짜를 완료 또는 휴무로 확정하고 활성 초안을 없앤 뒤 새 전체 실사를 수행한다. 복구 실사의 대상은 활성 재고 추적 식재료와 미해결 `ingredient_id`의 합집합이므로 중간에 비활성화된 문제 재료도 포함한다. 새 배치가 이 집합 전부를 원자 실측한 경우에만 같은 트랜잭션에서 미해결 집합과 `inventory_recount_required`를 해제한다.
9. 흡수 사건은 구매·원가·폐기 손실·감사 기록을 보존하지만 현재 재고에는 다시 적용하지 않는다. `reported_count_delta`는 최소 기준단위의 부호 있는 실제 수량이며 입고·복원은 양수, 폐기·사용은 음수다. 일반 신규 사건은 `reported_count_delta=count_delta`, 흡수 사건은 `count_delta=0`과 실제 `reported_count_delta`를 저장한다. 기존 행은 열을 덮어쓰지 않고 `reported_count_delta`가 NULL이면 `count_delta`로 읽는다. E2 호환 `volume_delta`는 `abs(reported_count_delta)`를 유지하고, 입고 취득 원가는 구매단위 `received_qty × volume`을 기준단위로 환산한 실제량과 `order_records.amount`를 함께 보존한다. 폐기 손실과 취득 원가는 이 경제 수량을 사용하되 재고 합계는 `count_delta`만 사용한다. 수량을 바꾸는 수정·취소는 지원하지 않는다. 잘못 입력한 취득 수량·금액·폐기 손실·거래 메타데이터는 원본을 지우지 않는 별도 `absorbed_financial_correction` 사건으로 전진 보정한다. 정정 명령은 `원본 사건 ID, 전체 목표 경제 수량·금액·메타데이터, expected economic_revision, 요청 키`를 받고 공통 매장 잠금 다음 원본을 잠근다. 서버는 원본과 누적 정정의 최신 목표에서 새 전체 목표까지의 차이만 계산하고 `economic_revision` CAS로 두 기기 덮어쓰기를 거부한다. 같은 요청 키·같은 payload는 같은 영수증을 반환하고 다른 payload는 거부한다. 정정은 `count_delta=0`을 유지하고 E2 손익 귀속일은 원본 `business_date`로 고정한다. 현재 재고 차이는 새 일괄 실사로 전진 보정한다.
10. 판매 amendment는 일반 재고 역분개가 아닌 전용 명령으로 검증한다. 감소분은 5.3의 미상쇄 `sales_inventory_delta_component`에 최신순으로 배정한다. component가 `absorbed_by_count_batch_id` 또는 `resolved_by_count_batch_id`를 가지면 원본 seq와 무관하게 `count_delta=0`으로 상쇄하고, 연결 없는 정상 component만 후속 실사 watermark 포함 여부를 재검사해 덮이지 않은 양만 E9로 복원한다. 현재 제품은 판매 증가분의 실제 발생 시각을 신뢰할 수 있게 입력받지 않는다. 따라서 전체 재고 실사의 컷오프와 겹친 완료일 amendment의 증가분은 판매일·기존 원본 시각·입력 확정 시각으로 즉시 E8 여부를 추정하지 않고 모두 불변 `pending_sales_inventory_resolution`에 draft ID·line ID·base revision·basis ID·전체 target hash·delta·reported_at을 저장해 `inventory_recount_required`로 전환한다. exact 발생 시각을 받아 실사 전후로 나누는 판매 입력 경로는 현 판본에 제공하지 않는다.

보류 delta가 있는 amendment는 목표값을 더 수정할 수 없고 `재실사 후 완료` 또는 `초안 폐기`만 제공한다. 재실사 시작 검사는 이 보류 초안을 일반 활성 수정 초안 예외로 허용하되 읽기 전용으로 고정한다. 후속 전체 실사는 물리 수량을 설정하면서 동일 target hash의 보류 delta를 `resolved_by_count_batch_id`로 원자 연결하고 재고 변화 0으로 해소한다. 그 뒤 같은 초안 완료 재시도는 연결된 보류 delta를 다시 차감하지 않고 매출·세금·원가 판본만 확정한다. 목표 hash·base revision이 달라지면 해소 결과를 재사용하지 않는다. 초안을 폐기해도 보류 감사행은 `abandoned`로 남고 재실사 필요 상태는 전체 실사가 끝날 때까지 유지한다. 따라서 `10개 완료 → 당일 실사 → 실제 2개 추가 판매 → 당일 12개 수정`도 현재 제품에서는 발생 시각을 입력받아 즉시 E8로 분류하지 않고 보류 후 재실사로 한 번만 해소한다. 컷오프 이하 완료일도 편집 기간 안이면 매출·세금·원가 보고는 고칠 수 있지만 전용 경로 밖 재고 쓰기는 허용하지 않는다. 실사 수치 정정은 과거 E5를 다시 쓰지 않고 새 일괄 절대 실사로 전진 보정한다.
11. 예약·행동 가능 여부·확정 가드는 모두 `max(매장 inventory_cutoff_business_date, legacy_inventory_cutoff_business_date)`인 단일 매장 컷오프를 사용한다. 활성 초안 예약은 이 컷오프보다 뒤인 영업일만 포함한다.

이 규칙으로 실사가 이미 흡수한 과거 소비나 입고·폐기·상대 조정을 다시 게시하는 이중 반영을 막는다. 컷오프보다 뒤인 영업일의 입고·폐기·상대 조정은 계속 허용한다. 일반 취소·역분개·직접 재고 보정은 컷오프 이하에서 막고, 결제수단·메모 같은 비재고 정정과 10항의 완료일 전용 amendment만 예외다. 메뉴 수량·조리 후 폐기 수량·파생 금액은 amendment 한 트랜잭션에서 함께 정정하며 재고분은 실사 포함 여부와 새 증가분 발생 시각에 따라 흡수 또는 정상 게시한다. 과거 원장을 다시 쓰면서 이후 E5 조정량을 재계산하는 기능과 재료별 컷오프는 1차 범위에서 지원하지 않는다.

## 8. 기간 요약 공식

- 매출: 작성 완료된 메뉴·기타 매출의 `customer_total` 합계. 세금 미포함 가격에서는 고객이 추가 납부한 세금을 포함한다. 이는 현행 `sales_summary.revenue=listed_total`에서 바뀌는 계약이므로 새 피드만 단독 변경하지 않는다. 일/기간/메뉴/채널/매출 상세와 고정 지출 채널 배분의 분자·분모를 같은 `customer_total`로 함께 전환하고, `net_sales`는 별도 순매출 필드로 유지한다.
- 순매출: 작성 완료된 메뉴·기타 매출의 `net_sales` 합계
- 판매량: 작성 완료된 메뉴 판매 수량 합계. 조리 후 폐기와 기타 매출 수량은 별도 상세로 둔다.
- 지출: `고객 결제액 합계 − 순이익 합계`로 서버가 반환하는 조정 합계. 상세에서 세금 납부액과 재료비·고정 지출·추가 지출·폐기 손실을 분리한다. 세금 미포함가에서 세액을 순매출 비용으로 다시 빼지 않는다. 고정 지출 표본이 부족해 rate가 `null`이면 0%로 확정하지 않고 `미산출`로 유지하며 해당 판본의 메뉴 손익에는 고정 지출을 반영하지 않았음을 표시한다.
- 순이익: `net_sales − 재료비 − 부자재/추가비용 − 고정 지출 − 추가 지출 − 폐기 손실`의 확정 서버 합계
- 순이익률: `기간 순이익 합계 ÷ 고객 결제액 합계`; 날짜별 비율 평균을 사용하지 않는다. 고객 결제액이 0이면 `null`을 반환하고 화면은 `—`로 표시한다.
- 평균 일매출: 작성 완료된 `expected` 영업일 수로 확정 매출 합계를 나눈다. 0원 작성 완료일은 분모에 포함하고 휴무·미작성은 제외한다.

합계 불변식은 `day.customer_total = Σ channel.customer_total = Σ menu.customer_total + Σ 기타매출.customer_total`이다. 메뉴 집계는 기타 매출을 포함하지 않는다. 현재 입력 계약은 메뉴 수량과 0 이상 기타매출만 지원하며 주문 단위 할인·환불·음수 매출은 이번 전환 범위에 넣지 않는다. 통화 최소단위 반올림은 구성 항목별 서버 계산 결과를 합산해 일·채널·행 합계를 정확히 일치시킨다. `net_sales`는 `customer_total`에서 포함·추가 징수된 세금만 분리한 서버 확정값이다. 기간 합계는 각 날짜의 최신 확정 판본만 합산하고, 재료비율과 고정 지출 배분율의 분모는 별도 계약대로 각각 `customer_total`을 사용한다.

고정 지출률이 `null`인 날짜가 하나라도 포함되면 기간의 고정 지출·고정 지출 포함 순이익·해당 비율은 `null`이며 `미산출 N일`을 함께 반환한다. 이를 0원으로 합산하지 않는다. 이관 판본에 `customer_total`이 없으면 당시 계약상 동일했던 `listed_total`을 `estimated_current` 고객 결제액으로 사용하고, 해당 날짜 수와 `이관 추정 포함` 표시를 기간 응답에 넣는다. 정의 전환일 전후를 섞어도 매출이 0 또는 누락되지 않아야 한다.

독립적으로 이미 확정된 입고·식재료 폐기 같은 재고 사건은 초안에 넣지 않는다. 입고 금액은 재고 원가 취득값이며 매출 기간의 지출에 다시 합산하지 않는다.

E2 식재료 폐기 손실은 다음처럼 합산한다.

1. 판매 작성 완료 스냅샷의 순이익은 E2를 제외한 판매 확정 손익으로 정규화한다.
2. E2 순손실은 판매 작성 상태와 무관하게 원래 폐기 사건의 `business_date`에 귀속한다.
3. 폐기 취소는 감사 발생 시각을 현재 시각으로 보존하되 손익에서는 원래 폐기일의 E2를 제외한다. 따라서 원래 날짜와 그 날짜를 포함한 과거 기간 요약이 갱신된다.
4. 기간 순이익은 `E2 제외 판매 확정 손익 + 현재 유효한 E2 순손익`으로 결합한다.
5. 기존 완료 스냅샷에 E2가 포함돼 있으면 호환 어댑터가 저장된 E2 구성액을 먼저 더해 판매 확정 손익에서 분리한 뒤 현재 유효 E2 순손실을 한 번만 차감한다. 원본 스냅샷은 수정하지 않는다.
6. 구형 스냅샷에 E2 구성액이 없으면 원장으로 복원한 품질을 함께 반환하고 근거 없는 0으로 처리하지 않는다.

날짜 카드와 기간 요약, 폐기 상세는 이 귀속일과 결합식을 함께 사용한다. 미작성일 E2 발생, 작성 완료 후 E2 취소, 구형 완료 스냅샷의 중복 차감 방지를 회귀 검산한다.

## 9. 경합·만료·오류

- 두 기기 저장: `draft_revision` CAS로 늦은 덮어쓰기를 거부한다.
- 완료 연타·응답 유실: 같은 요청 키는 같은 확정 결과를 반환한다.
- 다른 기기 완료: 같은 요청 키·같은 payload면 이미 확정된 판본을 반환하고 재고를 다시 차감하지 않는다. 다른 payload면 충돌로 거부한다.
- 수정 중 다른 수정 완료: `base_ledger_revision` 불일치로 거부하고 최신 확정값을 다시 보여 준다.
- 여러 날짜 초안: 날짜별로 독립하며 하나의 초안이 설정 변경이나 다른 날짜 확정을 막지 않는다.
- 매장 날짜 경계: 기기 시간이 아니라 서버 매장 시간대와 영업일 규칙을 사용한다.
- `business_date`는 매장 시간대와 당시 주간 운영 규칙의 예정 영업 구간으로 서버가 계산한 판매 귀속일이다. 자정을 넘기는 구간에서는 종료 전 시각을 전날 영업일에 귀속한다. 적용 가능한 구간이 없거나 겹치면 `local_date`를 기본값으로 반환하고 사용자가 날짜를 확인하게 한다.
- 편집 기간 만료: 지난달보다 오래된 활성 초안은 삭제하지 않고 서버가 `expired` 읽기 전용 상태로 보존한다. 만료 7일 전과 1일 전에 목록에 안내한다. 서버 읽기와 쓰기는 배치 실행 여부와 무관하게 같은 매장 시각으로 만료 자격을 판정하고, `finalize` 트랜잭션 안에서 편집 기간과 재고 컷오프를 다시 검사한다.
- 만료된 최초 작성 초안은 예약량·기간 요약에서 제외하고 피드에서 `미작성`으로 집계하되 `입력 기간 종료`를 표시한다. 만료된 수정 초안은 기존 `작성 완료`를 유지하고 `수정 중` 표시와 예약량을 제거한다. 만료 미작성일의 판매 소비는 원장에 반영되지 않고 다음 절대 실사의 감모에 포함될 수 있음을 상세에 표시한다. 소유자용 `잠금 해제 작성`은 1차 범위에서 지원하지 않는다.
- 사용자가 폐기한 최초 초안도 `미작성`, 폐기한 수정 초안도 기존 `작성 완료`로 돌아간다. 폐기·만료 사건은 감사 메타데이터만 남기고 확정 원장을 바꾸지 않는다.
- 작성 완료 뒤 해당 날짜를 휴무로 바꾸거나 확정 자체를 취소하는 `void`는 1차 범위에서 지원하지 않는다. 잘못 완료한 날짜는 허용 기간 안에서 0원 목표값으로 수정할 수 있고 감사 판본은 유지한다.
- 자동 마감을 제거한 뒤 누락이 조용히 쌓이지 않도록 다음 예정 시작 시각에 `어제 매출 미작성` 알림을 보낸다. 홈·매출 탭 배지에는 미작성·수정 중 건수를 표시하고, 기간 요약에는 `작성 완료 n일 · 작성 중 n일 · 미작성 n일 · 기간 만료 n일 · 휴무 n일`을 함께 표시한다. 절대 실사 진입 화면은 조건을 충족하지 않은 날짜 목록과 만료 미작성 건수를 분리해 보여 준다.

## 10. 전환 순서

1. 매장별 `sales_lifecycle_cutover_state`와 공통 전환 잠금을 추가한다. phase는 `legacy_active | draining | freezing | active | blocked`로 고정하며, 허용 전이는 `legacy_active → draining`, 조건부 `draining → legacy_active|blocked`, `draining → freezing`, `freezing → active|blocked`뿐이다. 전환 중에는 구형 `save_sale`, `p_open_day`, 상태 전이, 정정, 자동 마감과 새 쓰기를 모두 가드한다.
2. 새 계산 기준 매니페스트·기준선 `v0`·날짜 기준 해석기, 날짜 분류 원장, 초안, 확정 판본, RPC를 기존 테이블과 구형 쓰기를 유지한 채 먼저 배포한다.
3. 기존 장부와 명시적 휴무를 날짜 원장으로 멱등 백필하고, 확정 `business_days`를 새 조회 모델의 작성 완료 `v1`으로 읽는 호환 계층을 추가한다. 이관은 기존 `inventory_events`를 추가·수정·삭제하지 않는다. 구형 E5는 식재료 단위 변경이어서 새 전체 관측 배치로 가장하지 않는다. 의미가 증명된 절대 E5만 보호 경계 근거로 쓰고, 의미가 불명확한 E5가 있는 매장은 컷오버 freeze 시작 시 서버 시각으로 계산한 추천일을 이관 영수증에 고정해 그 날짜까지를 보수적 legacy cutoff로 삼고 `inventory_recount_required` 격리 상태로 시작한다. 이 매장은 정상 재고·판매 쓰기를 열기 전에 유지보수 구간에서 활성 식재료와 미해결 재료 전체를 필수 실사하고, 실시간 추천일이 바뀌더라도 이 고정 기준일로 실사 전제를 판정한다. 그 batch가 원자 완료된 뒤에만 격리를 해제하고 오늘 날짜는 정상 작성 수명주기로 연다.
4. 데이터 컷오버는 매장별 예정 시작 전 유지보수 구간에 수행한다. 24시간 영업처럼 안전한 구간이 없으면 해당 매장의 쓰기를 잠깐 동결하는 공지 구간을 사용한다. 먼저 계획한 freeze 후보 시각의 추천일이 작성 완료 또는 휴무가 될 수 있는지 선검사한 뒤 phase를 `draining`으로 바꿔 새 `open`만 막고 이미 열린 `open/break`는 구형 앱에서 저장과 정상 종료를 계속 허용한다. 이 세션을 강제 종료하거나 초안으로 바꾸지 않는다. 24시간 매장도 합의한 전환 경계에서 마지막 구형 저장과 정상 종료를 한 번 수행한다. 마지막 세션 종료 뒤 다시 계산한 추천일이 미작성 상태이면 대기하지 않는다. 공통 전환 잠금에서 freeze 영수증·새 수명주기 원장·실사·컷오프 변경이 하나도 없음을 확인하고 phase와 구형 open/크론을 `legacy_active`로 원자 복귀한 뒤 컷오버를 연기한다. 이 조건을 만족하지 못하면 자동 복귀하지 않고 운영 차단 상태로 남겨 전진 복구한다.
5. 열린 세션이 0건이고 freeze 후보 추천일이 작성 완료 또는 휴무인 경우에만 phase를 `freezing`으로 바꾸고 모든 구형·신형 쓰기를 차단한다. 공통 전환 잠금 아래 현재 snapshot·편집 최신값·대기 설정 event ID와 source revision을 불변 전환 영수증에 봉인한다. 정상 종료된 마지막 영업일은 당시 snapshot과 이미 게시된 판매행·E8 연결을 그대로 가진 이관 완료판본으로 백필한다. 신규 초안이나 전량 E8을 만들지 않는다. 그 뒤 대기 설정 변경을 저장 당시 의도에 맞는 다음 예정 영업일 판본으로 변환한다. 대기 항목 ID와 source revision을 멱등 키로 삼고, 이관 전 당시 기준이 없는 완료일은 `legacy_unrecorded`, 미작성일은 `estimated_current` 품질로 표시한다.
6. 열린 세션 0건과 설정 변환을 확인한 직후 재료별 `inventory_events` 원장 합과 `inventory_states.stock_total` 체크섬이 전환 전과 같은지 다시 검증한다. 모호한 구형 E5가 있는 매장은 이 동결 구간에서만 허용되는 이관 실사 명령으로 전체 물리 수량을 확정하고 검산한 뒤 격리를 해제한다. 전 매장이 통과하면 자동 마감 크론을 비활성화하고 날짜 원장 보충 작업을 활성화한다. 구형 `open/break/close/save_sale/amend` 호출은 고정 `APP_UPDATE_REQUIRED` 오류를 반환한다.
7. 매출 피드와 날짜별 작성·상세 화면을 활성화하고 모든 저장 진입점이 새 초안·확정 RPC를 거치는지 확인한 뒤 영업 상태 바와 전이 호출 코드를 제거한다.
8. 첫 신규 판매 확정, 첫 `inventory_count_batch`, 첫 흡수 사건, 첫 컷오프 변경 중 하나라도 발생하기 전에는 기능 플래그와 구형 크론을 원복할 수 있다. 이 중 하나가 발생한 뒤에는 구형 수명주기로 자동 롤백하지 않고 새 전진 migration으로 복구한다.

## 11. 완료 조건

다음 조건을 모두 만족해야 새 구조로 전환한다.

- 임시저장 전후 `daily_sales`, `inventory_events`, `inventory_states`, 확정 손익이 변하지 않는다.
- 최초 완료 한 번에 매출·세금·재료·고정 지출·지출·E8·일 요약이 함께 생긴다.
- 같은 완료 요청을 반복해도 확정 판본과 E8이 한 번만 생기며, 다른 payload의 같은 요청 키는 충돌한다.
- 완료된 날짜의 수정 초안을 방치해도 기존 기간 요약과 재고가 유지된다.
- 수정 완료의 증가·감소·동일 수량이 각각 E8·E9·무이벤트 계약을 지킨다.
- 과거 날짜를 늦게 작성해도 해당 날짜에 유효한 계산 기준을 사용한다.
- 이관 전 당시 기준이 없는 과거 작성은 `estimated_current`를 반환하고 경고 없이 정확한 값으로 가장하지 않는다.
- 설정 변경이 미완료 초안 때문에 무기한 대기하지 않는다.
- 휴무일이 미작성 건수에 포함되지 않는다.
- 기간 요약에 초안 예상값이 섞이지 않는다.
- 서버 시간대, 월 경계, 편집 만료, 두 기기 경합, 완료 응답 유실을 DB 시험으로 검증한다.
- 판매 수량은 그대로이고 조리 후 폐기만 증가한 수정 초안의 예약량과, 월 경계를 지난 뒤 수정 완료 응답 유실 요청을 같은 요청 키로 재시도하는 경우를 검증한다.
- 두 메뉴가 같은 재료를 사용하는 완료·수정, 한 판매행의 판매 수량과 조리 후 폐기가 함께 바뀌는 수정을 검증해 사건 식별자 충돌과 중복 게시가 없음을 확인한다.
- 과거 날짜의 현재 판매 중지 메뉴 작성, 월 경계 고정 지출 판본, 미작성일 E2와 완료 후 E2 취소, 초안 예약 중 E5 절대 재고 설정 차단을 검증한다.
- 초안 없는 미작성·활성 초안·수정 초안이 있는 상태의 절대 실사 차단, 실사 뒤 편집 가능 완료일의 증가·감소 수량을 재고 0차이 흡수 보정으로 허용, 실사와 완료의 두 세션 경합, 구형 RPC 우회 차단, 일괄 실사 취소·역분개 거부, 이관 전 실사, 상대 차감 유지, 컷오프 이후 날짜 작성을 검증한다.
- 실사 도중 입고·폐기·판매·식재료 활성 상태가 바뀌면 관측 토큰 전체를 거부한다. 현재 추천 날짜가 미완료이거나 활성 초안이 있으면 실사를 막는다. 실사 시작 전 실제 발생했으나 실사 후 입력된 입고와 폐기는 exact 발생 시각과 함께 해당 식재료를 포함한 최초 후속 배치 흡수 사건으로만 기록돼 재고가 두 번 변하지 않는지 검증한다. 실사 관측 구간에 발생한 미기록 사건을 나중에 입력하면 `ambiguous_during_count`와 재실사 필요 상태가 생기고 일반 재고 쓰기는 차단되는지 검증한다. D0 실사 뒤 D1 미작성·최초 초안·수정 초안을 각각 둔 상태에서 D2 모호 사건이 생겨도 복구 모드가 컷오프 뒤 편집 가능 날짜 전체를 완료·폐기·분류하고 새 전체 실사로 상태를 해제할 수 있어야 한다.
- 전체 재고 실사의 컷오프와 겹친 판매 amendment 증가분은 현재 제품이 exact 발생 시각을 받지 않으므로 모두 pending으로 고정되는지 검증한다. +2는 보류 초안 예외로 전체 재실사한 뒤 같은 target hash에서 재차감 없이 완료되고, 목표/base revision 변경과 중복 요청은 이전 해소를 재사용하지 못해야 한다. 보류 초안을 폐기해도 감사행과 재실사 필요 상태는 전체 실사까지 남아야 한다.
- absorbed +2와 재실사 해소 +2를 각각 후속 -2로 정정해도 E9가 생기지 않고, 정상·흡수 소비가 섞인 감소는 불변 component 최신순 배정에 따라 정상 component 몫만 E9가 되는지 검증한다.
- 수요일 적용 메뉴 A가 예약된 뒤 화요일 적용 세금 B가 생겨도 A가 조기 적용되지 않고 수요일 판본에 B가 누락되지 않는지 검증한다.
- 구성 항목별 세금 반올림 결과에서 일=채널=메뉴+기타매출 합계, legacy `listed_total` 추정 표시, fixed-rate null 포함 기간의 `미산출 N일` 전파를 검증한다.
- draining 중 legacy 세션은 신규 open을 막은 채 기존 저장·정상 종료를 허용하고, 열린 세션이 0건이 되기 전이나 freeze 후보 추천일이 완료/휴무가 아니면 freezing/활성화하지 않는지 검증한다. 날짜 전환 뒤 추천일이 미작성으로 바뀐 24시간 매장은 새 원장·실사·컷오프·freeze 영수증이 없을 때만 컷오버를 원자 취소해 `legacy_active`와 open/크론을 복구하고, 다음 경계에서 새 draining 시도를 시작해야 한다. 복귀 도중 경합해 새 쓰기가 생기면 취소 전체를 거부한다. 마지막 정상 종료판본은 당시 snapshot·판매행·E8 연결을 보존해 같은 목표에서 중복 E8이 없어야 한다.
- 모호한 구형 부분 E5가 있는 매장은 freeze 시작 시 고정한 추천일로 실사 전제를 판정해 시간이 지나도 교착하지 않으며, 보수적 cutoff와 격리 상태에서 동결 구간 전체 실사를 완료하기 전 판매·일반 재고 쓰기를 열지 않는지 검증한다.
- 실사 high-watermark 전에 정상 기록된 사건의 사후 취소, 일괄 E5 자체 취소, 흡수 사건의 경제 수량·금액 오입력 정정과 두 기기 economic_revision 경합을 검증하고 원장합과 원본 귀속일 손익을 함께 검산한다.
- 실사 완료 응답 유실의 같은 요청 키 재시도와 다른 payload 충돌을 검증한다.
- 실사 세션 명시 취소·4시간 만료·CAS invalidated 결과가 일반 쓰기 차단을 해제하고 감사 상태를 남기는지 검증한다.
- 모호 사건의 문제 식재료가 비활성화돼도 복구 실사 대상에 포함되고, 미해결 집합 전부를 세기 전에는 재실사 필요 상태가 해제되지 않는지 검증한다.
- 같은 메뉴행·같은 재료의 판매 소비와 조리 후 폐기가 함께 증감할 때 서로 다른 `source_line_kind`로 E8/E9가 빠짐없이 생성되는지 검증한다.
- 0원 작성 완료와 휴무·미작성의 구분, 잠금 D-7/D-1, 자정 초과 영업의 추천 귀속일을 검증한다.
- 앱 화면은 서버가 반환한 상태·행동 가능 여부·금액을 표시하며 확정값을 다시 계산하지 않는다.

## 12. 구현 범위에서 제외

- 판매 거래 시각별 POS 수준 원장
- 종료된 편집 기간을 관리자가 임의로 다시 여는 기능
- 초안을 확정 재고로 간주하는 기능
- 설정 변경으로 과거 확정 장부를 소급 재계산하는 기능
- 여러 초안을 한 번에 자동 작성 완료하는 기능
- 주문 단위 할인과 환불·반품 매출 원장. 실제 반품의 재고 증가는 현행 허용 물리 사건으로 별도 기록한다.
