# 재료 일괄 수정 상세 계획안

> 상태: 기획·검수 후보 — 제품·DB 미구현
> 작성일: 2026-09-22
> 기준: [재료 일괄 입고 상세 계획안](./재료-일괄-입고-상세계획안.md)의 구현된 ING-12와 [재고 차감·폐기 계약](./기능정의서.md#13-재고-차감폐기내역취소-상세)
> 적용 범위: 현재 재고에 대한 여러 재료의 입고(E7+E1), 차감(E5), 재료 폐기(E2)

## 1. 목표와 제품 결정

기존 `재료 일괄 입고`를 `재료 일괄 수정`으로 확장한다. 여러 재료의 **한 종류 작업**을 한 번에 확인하고 저장한다. 화면 상단에는 `입고 / 차감 / 폐기` 탭을 두고, 탭 안에서는 현재처럼 카드를 추가·삭제한다. 한 배치에 서로 다른 종류를 섞지 않는다. 종류가 섞이면 카드마다 확인 정보·손익 영향·복구 문구가 달라져 한 번의 저장 의도를 설명하기 어렵다. 사용자는 탭을 바꿔 다음 종류의 배치를 따로 저장할 수 있다.

단건 `재고 수정` 화면과 경로는 유지한다. 일괄 수정은 그 위의 빠른 진입점이며 단건 계약을 우회하지 않는다. 기존 ING-12 화면 ID를 유지하고 사용자 표시명과 AppMap 이름을 바꾼다. `/ingredients/bulk-inbound`는 기존 북마크를 위해 새 `/ingredients/bulk-edit`로 이동시키는 호환 경로로 남긴다. 기존 일괄 입고 RPC·영수증·원장은 이관하거나 다시 쓰지 않는다.

## 2. 사용자 흐름

1. 재료 메인의 `+ 추가`를 누르면 `재료 일괄 수정`, `재료 등록`이 나타난다.
2. `재료 일괄 수정`을 누르면 ING-12가 열린다. 기본 탭은 `입고`이고 빈 카드 1개가 있다.
3. 각 탭에서 카드를 최대 20개까지 추가한다. 카드 선택 순서는 화면 순서이자 서버 미리보기·처리 순서다. 같은 재료를 여러 카드에 넣을 수 있고, 각 행은 별도 사유·원장 사건으로 남긴다.
4. 입력을 마치면 서버 미리보기에 각 카드의 처리 후 재고가 나타난다. `폐기`에는 예상 손실, `입고`에는 입고 후 단가도 나타난다.
5. `N건 입고 / 차감 / 폐기` 확인창에서 종류·재료·수량·최종 재고를 확인하고 저장한다. 저장 중에는 중복 제출, 탭 전환, 화면 이탈을 막는다.
6. 성공 시 `N건을 입고했어요`, `N건을 차감했어요`, `N건을 폐기했어요`를 표시하고 재료 목록으로 돌아간다. 실패하면 모든 카드 입력을 보존한다.

탭을 바꿀 때 입력한 카드가 있으면 `입력한 내용이 사라져요` 확인창을 거친다. 확인하지 않으면 현재 탭과 입력을 유지한다. 마지막 카드를 삭제하면 해당 탭의 빈 카드 1개로 교체한다. 카드에는 눈에 보이는 번호 헤더를 두지 않되 접근성 이름은 `입고 항목 1`처럼 제공한다.

## 3. 화면 구성

공통 헤더는 뒤로가기와 `재료 일괄 수정`이다. 카드 표면·입력 크기·색 역할 토큰은 현재 ING-12와 단건 `재고 수정`을 재사용한다. 결과 필드는 회색 읽기 전용으로 보이고 사용자가 입력한 수량·금액과 구별한다.

```text
〈  재료 일괄 수정
입고  |  차감  |  폐기                 ← 밑줄 탭, 기본은 입고

┌──────────────────────────────┐
│ 재료명      [재료 선택       ▾] │
│ 종류별 입력·결과               │
└──────────────────────────────┘
                         [삭제]
[+ 재료 추가]

[일괄 입고 완료 / 일괄 차감 / 일괄 폐기]  ← 고정 하단 버튼
```

입고 카드의 기존 4행은 유지한다. 차감·폐기 카드에서는 구매처·결제금액·단가를 숨기고 수량·사유와 처리 후 재고를 보여 준다. 폐기에만 예상 손실을 더한다.

| 탭 | 카드 필드(위에서 아래) | 카드 하단 결과 | 필수 조건 |
|---|---|---|---|
| 입고 | 재료명, 구매처(선택), `결제금액 │ 입고 후 단가`, 입고량 | 입고 후 재고 | 현재 일괄 입고의 입력·계산·E7+E1 계약 그대로 |
| 차감 | 재료명, 차감할 수량, 차감 사유 | 차감 후 재고 | 양수 수량, 현재 확인 재고 이하, 공백 아닌 사유 |
| 폐기 | 재료명, 폐기할 수량, 폐기 사유 | 폐기 후 재고, 예상 손실 | 양수 수량, 현재 확인 재고 이하, 공백 아닌 사유 |

- 각 카드의 `현재 재고`와 기준단위를 재료 선택 직후 표시한다. 0·음수 재고는 그대로 표시하며 차감·폐기 입력은 막는다. 기존 응답 미확인 요청을 확인하는 동작은 이 유효성 조건과 독립적으로 제공한다.
- 차감은 결제금액·구매처·단가 변경을 만들지 않는다. 폐기만 실제 식재료 손실 E2를 만든다. 예상 손실을 기준단가가 없는데 `0원`으로 표시하지 않는다. 확정 손실은 서버가 계산한 값이다.
- 차감·폐기 탭에는 선택적인 `공통 사유`를 카드 위에 둔다. 입력하면 비어 있는 카드 사유만 채우고 이미 사용자가 고친 카드 사유는 덮지 않는다. 저장 시에는 카드마다 확정 사유를 전송해 원장 사건별 설명을 잃지 않는다.
- 재료를 바꾸면 이전 카드의 구매처·금액·수량·사유·미리보기를 초기화한다. 카드 ID는 삭제·순서 변경 뒤에도 유지한다.
- 같은 재료를 여러 카드에서 선택하면 앞 카드의 가상 처리 후 재고를 다음 카드의 확인 재고로 사용한다. 총 차감·폐기가 최종 가용 재고를 넘는 순간 저장을 막으며 0으로 자르지 않는다.
- g/ml/개를 DB 최소 단위로 보낸다. kg/L 표시는 기존 형식을 쓰며 표시 단위나 단가 소수 자릿수 설정으로 저장 수량을 반올림하지 않는다.
- 최근 실사 때문에 `실제 발생 시점` 확인이 필요한 재료는 현재 버전의 일괄 저장에서 **차단**하고 `단건 재고 수정에서 발생 시점을 확인해 주세요`로 안내한다. 실사 전 사건을 현재 사건으로 기록하거나 0 효과 원장을 임의로 만들지 않는다. 실사 전/중/후 혼합 배치는 별도 설계·시험 뒤 확장한다.

## 4. 서버·원장 설계

### 4.1 유지할 계약

- 입고 탭은 이미 구현된 `quick_inbound_batch_preview`, `record_current_quick_inbound_batch`, `resolve_quick_inbound_batch`를 그대로 호출한다. 카드별 E7+E1, 가중 단가, 영수증, 닫힌 요청 키를 보존한다.
- 차감은 `change_stock_quantity`의 `deduct` 의미인 E5만 기록한다. 폐기는 `discard` 의미인 E2만 기록한다. 둘 다 판매 소진 E8이나 조리 폐기 `qty_waste`를 만들지 않는다.
- `inventory_events`는 append-only다. 실패한 배치를 보정용 새 이벤트로 되돌리지 않고 DB 트랜잭션 전체를 롤백한다. 이후 개별 취소는 현재 원본 사건별 취소 계약을 따른다. `배치 전체 취소`는 새 기능 범위에 넣지 않는다.
- 현재 재고·기준단가·예상/확정 손실·매장 날짜는 DB가 권위다. 앱 계산값은 입력 검증·표시 보조에만 쓴다. 과거 확정 매출과 영업일 원가 스냅샷은 재계산하지 않는다.

### 4.2 차감·폐기용 배치 RPC 후보

기존 입고 RPC의 이름·payload에 `kind`를 덧씌우지 않는다. 별도 `preview_current_stock_quantity_batch(p_store, p_kind, p_items)`와 `record_current_stock_quantity_batch(p_store, p_kind, p_items, p_request_key)`, `resolve_current_stock_quantity_batch(p_store, p_request_key)`를 새 migration으로 도입한다. `p_kind`는 `deduct|discard`만 허용한다.

각 카드: `client_item_id`, `ingredient_id`, `quantity`, `expected_stock`, `note`. `expected_stock`은 **서버 미리보기의 해당 카드 직전 재고**이며 앱이 임의로 만들지 않는다. 미리보기는 매장 재고 쓰기 revision을 함께 반환한다. 그 조회 중 revision이 바뀌면 미리보기 자체를 다시 요청하고, 저장할 때는 **첫 카드 처리 전** 같은 revision인지 잠금 안에서 검사한다. 이후 카드에는 배치 내부의 순차 처리 결과를 사용한다. 이는 미리보기 뒤 다른 재고 사건이 같은 수량으로 상쇄되더라도 오래된 손실 기준을 확정하지 않기 위한 보수적 충돌 판정이다. 최종 필드 이름과 잠금 순서는 migration 작성 전에 기존 `inventory_store_write_state` 및 `change_stock_quantity`의 계약과 맞춰 확정한다.

서버는 `assert_my_store` → `lock_store_write_scope` → 배치 요청 키 잠금 → 영수증/닫힌 키 확인 → 전체 카드 형식·매장·활성 재료·사유·수량·실사 문맥 검증 → 화면 순서대로 카드별 E5/E2 처리 → 배치 영수증 기록을 한 트랜잭션에서 수행한다. 동일 재료 반복 행은 앞 행 처리 후 재고로 검증한다. 한 행이라도 실패하면 원장·재고·손실·영수증이 모두 롤백된다. 현재 배치 중 다른 기기가 재고를 바꾸면 40001 성격의 충돌로 전체를 거절하고 최신 재고를 재조회해 **새 확인**을 요구한다.

요청 키는 배치 단위 UUID, 카드별 키는 배치 키와 `client_item_id`로 파생한다. 같은 키·같은 payload는 기존 결과만 반환하고, 다른 payload는 거절한다. `resolve`는 writer와 같은 잠금을 잡아 `recorded` 또는 `not_recorded`를 확정하며, 후자는 키를 닫아 늦은 쓰기를 막는다. 앱 대기 기록은 사용자·매장·종류·키·payload hash·카드 수만 보관하고 전체 카드의 수량·사유를 로컬 영속 저장하지 않는다. 미확인 키가 있으면 새 일괄 수정을 잠그고 결과 확인을 먼저 제공한다. 앱 재시작·전량 차감 후 0 재고에서도 수량 입력 없이 결과 확인이 가능해야 한다.

### 4.3 실사 및 발생 시점 경계

현재 단건 차감·폐기는 `InventoryOccurrenceFields`로 실사 전/후를 구분하고 지연 RPC를 호출한다. 현재 일괄 입고는 서버 현재 시각 배치다. 첫 일괄 수정 범위도 **현재 시점 사건만** 허용한다. 항목 중 하나라도 실사로 인한 발생 시점 확인이 필요하면 배치 전체를 저장하지 않는다. 서버가 이 조건을 최종 확인하고 앱은 단건 화면으로 이동할 수 있게 안내한다. 추후 지연 배치를 추가할 때는 카드마다 정확한 발생 시각, 실사 흡수 여부, 손실 귀속, 동일 재료 사건 순서와 현재 재고 영향이 모두 정의되어야 한다.

## 5. 오류·캐시·기록

- 미리보기는 입력 변경 후 지연 요청으로 갱신하되, 현재 카드 판본과 일치하는 결과만 표시한다. 미리보기 조회 실패·미완성·오래된 응답 중에는 저장 버튼을 막는다.
- 서버 오류는 안정 코드와 `client_item_id`로 해당 카드에 연결한다. 재고 충돌·실사 진행·매출 전환 잠금처럼 배치 전체 오류는 상단에 표시한다. 일부 성공처럼 표시하지 않는다.
- 성공과 `recorded` 복구 시 재료 목록·상세·내역·발주 후보·메뉴 부족·매출 손실 조회를 종류별 E1/E5/E2 범위로 한 번씩 무효화한다. 캐시 갱신은 과거 원장 값 수정이 아니다.
- 차감/폐기 카드의 사유는 각 원장 사건에 보존한다. 이력에는 날짜, 종류, 수량, 잔량, 사유를 기존 형식대로 표시하고 배치 소속은 추적용 ID로 연결한다. 구매처·결제금액은 차감/폐기 이력에 만들지 않는다.
- 배치와 단건이 같은 재료를 동시에 수정하는 경우 store write scope 및 재고 행 잠금으로 순서를 정한다. 저장 순서가 바뀌면 확인 재고 충돌로 명확히 거절한다. 같은 키와 다른 키의 2세션 경합을 각각 시험한다.

## 6. 변경 대상과 작업 순서

1. 이 계획의 제품·DB 독립 검수에서 원장 의미, 실사 문맥, 복구 및 UI 문구를 확정한다.
2. 새 migration에 차감/폐기 미리보기·원자 writer·resolver·receipt/closed-key·RLS/ACL을 추가한다. 기존 입고 RPC와 과거 스냅샷을 수정하지 않는다.
3. DB 타입을 재생성하고 수량/실사/손실/원장/동시성/멱등/롤백 시험을 먼저 만든다.
4. ING-12 화면을 `BulkStockEditScreen` 등 의미에 맞는 공통 화면으로 분리하고 세 탭·카드·확인창·복구 저널을 연결한다. 기존 `/ingredients/bulk-inbound`는 redirect다.
5. 재료 메인 메뉴, AppMap 모델·샘플·실제 Expo 경로, `features/README.md`, 기능정의서, 작업큐를 같은 판본으로 갱신한다.
6. 모바일 상호작용과 접근성 시험, `corepack pnpm verify`, 독립 구현 diff 검수를 거친다. 네이티브 기기 증빙은 현재 정책대로 별도 상태로 기록한다.

| BULK-05 | 두 번째 카드 실패 | 첫 카드의 원장·재고·손실·영수증도 없음 |
| BULK-06 | 미리보기 뒤 다른 기기 입고/판매/차감 | 전체 저장 거절, 초안 보존, 최신 재고·새 확인 필요 |
| BULK-07 | 요청 응답 유실, 앱 재시작, 전량 폐기 | `recorded`만 조회, 자동 재전송·중복 E2 없음 |
| BULK-08 | `not_recorded` 뒤 늦은 writer | 닫힌 키 거절, 새 확인은 새 키 사용 |
| BULK-09 | 실사 대상 또는 진행 중 실사 | 배치 전체 거절, 단건 발생 시점 확인으로 안내 |
| BULK-10 | 0·음수·과다·21개·타 매장 재료 | 쓰기 0건, 공개 가능한 오류만 표시 |
| BULK-11 | 영업 중 원가/과거 매출 | 현재 재고와 E2 손실만 반영, 열린 영업일·과거 확정 스냅샷 보존 |
| BULK-12 | 390px·글자 확대·긴 이름 | 탭·카드·확인창 읽기 순서와 44pt 조작 영역 유지 |

## 8. 이번 범위에서 제외할 것

- 입고·차감·폐기를 한 요청 안에 섞는 카드별 모드
- 실사 전/중 사건의 일괄 지연 입력, 과거 날짜 수기 백필
- 판매 취소·입고 취소·차감/폐기 취소를 묶어서 수행하는 기능
- 재고 실사(절대 수량을 목표로 하는 E5)를 일괄 차감으로 위장하는 기능
- 영수증 OCR·스프레드시트 가져오기

이 문서는 구현 승인 판정이 아니라 설계 검수 후보이다. 특히 **현재 사건만 허용할지**, **한 배치에 동일 재료를 여러 번 허용할지**를 독립 검수의 주요 확인 항목으로 둔다. 현재 제안은 각각 `현재만`, `여러 번 허용·순차 처리`다.
