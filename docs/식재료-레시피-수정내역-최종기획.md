# 식재료·레시피 수정 내역 최종 기획

## 1. 목적

식재료 상세(ING-03)와 레시피 상세(RCP-02)에서 사용자가 다음 내용을 같은 방식으로 확인하게 한다.

1. 최근 7일 동안 무엇이 바뀌었는가
2. 사용자가 직접 수정했는가, 다른 데이터 때문에 갱신됐는가
3. 현재 영업의 매출 기준에 들어간 최신 변경과 아직 들어가지 않은 최신 변경은 무엇인가

식재료 기준 단가가 바뀌면 연결된 레시피의 현재 재료비와 순이익은 즉시 다시 계산한다. 영업을 시작한 날의 매출 장부는 영업 시작 스냅샷을 유지한다.

근거: `docs/source-v3/레시피_상세로직_유저시나리오_v3.txt` 1장·3.8절, `docs/구현-변경점.md` 9·10·12·13절.

## 2. 공통 용어

화면에서 변경을 두 종류로만 구분한다.

| 구분 | 의미 |
|---|---|
| 직접 수정 | 사용자가 해당 식재료·레시피 화면에서 저장해 바뀐 값 |
| 자동 갱신 | 입고, 식재료 단가, 고정지출 등 다른 데이터의 변경으로 계산되거나 전달된 값 |

- 상단 집계와 상세 팝업 모두 `직접 수정`·`자동 갱신`을 사용한다.
- `연관 변경`, `자동 변경`, `자동 반영`, `자동 전파`는 사용자 화면 문구로 사용하지 않는다.
- 사건 제목에서는 원인을 구체적으로 보여준다.

| 원인 | 사건 제목 |
|---|---|
| 식재료 정보 직접 저장 | 식재료 수정 |
| 레시피 직접 저장 | 레시피 수정 |
| 입고 확정으로 기준 단가 변경 | 입고 단가 반영 |
| 입고 취소로 기준 단가 변경 | 입고 취소 반영 |
| 식재료 단가가 레시피 금액에 적용 | 식재료 단가 반영 |
| 고정지출이 레시피 금액에 적용 | 고정지출 반영 |

`수정`은 사용자의 직접 행동, `반영`은 사건의 원인, `자동 갱신`은 상세에 표시할 값의 성격을 뜻한다.

## 3. 상세 화면의 최근 수정 행

식재료·메뉴 상세, 부자재 관리·고정지출·세금 페이지의 최상단 별도 카드에 같은 공통 행을 사용한다.

```text
현재 매출에 반영 중                   최근 수정  ›
                                  26-08-20 14:32
⌛ 영업 종료 후 반영 예정             (대기가 있을 때)
```

- 라벨 아래 날짜·시간을 12px로 표시한다(기존 14px에서 2px 축소, 2026-09-09 사용자 결정). 식재료·레시피의 공통 `RecentChangeRow`와 `COMPONENT.recentChange.timestamp`가 이 배치를 소유한다.
- 행 전체와 우측 화살표를 누르면 `수정 내역` 화면을 연다.
- 날짜·시간은 5개국 공통 `YY-MM-DD HH:mm`(예: `26-09-07 07:05`)으로 표시한다(2026-09-09 사용자 결정). 오늘도 생략하지 않는다. `src/lib/date.ts`의 공통 포맷터가 서버 timestamp를 서버가 제공한 매장 IANA 시간대로 변환하며, 시간대 누락·오류는 `—`로 표시하고 기기 시간대로 추정하지 않는다. 식재료·레시피 등록/최근 수정·수정 내역·손익 변동에 동일 적용한다. 날짜만/시간만 표시하는 항목과 저장용 ISO 형식은 범위 밖이다.
- 사건의 `매출 계산과 무관`은 수정 내역에서만 구분한다. 최상단 카드는 마지막 사건의 분류와 별개인 현재 적용 상태와 대기 요약을 표시한다.
- 수정 기록이 없고 생성일이 있으면 `등록` 라벨과 생성일을 표시한다. 수정 내역 목록에 가짜 사건을 만들지 않는다. 설정 이력 자체가 없는 화면은 공통 빈 상태를 사용한다.

## 4. 수정 내역 공통 화면

식재료와 레시피가 같은 화면 컴포넌트를 사용하고 데이터만 바꾼다.

### 4.1 헤더와 대상

```text
‹  수정 내역

레시피
김치찌개
```

- 헤더는 대상 이름 없이 `수정 내역`으로 고정한다.
- 헤더 아래에서 `식재료·레시피` 유형과 대상 이름을 표시한다.
- 우측 조회 버튼은 두지 않는다.

### 4.2 기간과 집계

```text
최근 7일 기준                         5건
직접 수정 3건 · 자동 갱신 2건
```

- 화면에는 최근 7일만 표시한다.
- 최신순으로 고정한다.
- 기간·정렬 필터를 제공하지 않는다.
- 건수는 서버가 최근 7일 전체를 집계한다. 현재 받아 온 페이지 수로 계산하지 않는다.

### 4.3 목록 한 줄

식재료와 레시피 모두 같은 리스트 구조를 사용한다.

```text
26-08-20 14:41
[직접 수정] 메뉴 수정
판매가 외 3개 항목 변경       [현재 매출 미반영]  ›
```

- 시각
- 사건 출처 배지(`직접 수정`/`자동 갱신`)와 사건 제목
- 한 줄 요약
- 선택된 상태 배지
- 우측 화살표

대표 금액은 목록 우측에 표시하지 않는다. 식재료와 레시피의 단위가 다르고 한 사건에 여러 값이 섞일 수 있기 때문이다. 모든 전후값은 상세 팝업에서 확인한다.

목록은 개별 카드 여러 개가 아니라 하나의 그룹 카드와 행 구분선을 사용한다.

## 5. 현재 매출 상태 배지

과거 사건마다 `현재 매출에 반영 중`을 붙이면 현재 값이 여러 개인 것처럼 보인다. 매출에 영향을 주는 내역의 상태 배지는 목록 전체에서 최대 두 건만 표시한다.

| 배지 | 표시 대상 |
|---|---|
| 현재 매출 미반영 | 현재 영업 기준이 확정된 뒤 발생한 매출 영향 변경 중 가장 최근 1건 |
| 현재 매출에 반영 중 | 현재 매출 기준을 만든 변경 중 가장 최근 1건 |
| 일부 메뉴 미반영 | 식재료 변경 하나가 여러 레시피에 퍼졌고 반영 상태가 섞인 경우. 미반영 배지 자리를 대신함 |
| 매출 계산과 무관 | 이름·안전재고·구매 기본값 등 매출 금액을 바꾸지 않는 사건 |

규칙:

1. `현재 매출에 반영 중`은 최대 1건이다.
2. `현재 매출 미반영` 또는 `일부 메뉴 미반영`은 최대 1건이다.
3. 나머지 과거 매출 영향 사건에는 상태 배지를 표시하지 않는다.
4. 최신 사건이 매출과 무관하면 건너뛰고 최신 매출 영향 사건을 찾는다.
5. 미반영 변경이 없으면 `현재 매출에 반영 중`만 표시한다.
6. 영업 전에는 최신 매출 영향 변경 1건만 `현재 매출에 반영 중`으로 표시한다.
7. 해당 사건이 최근 7일 밖에 있으면 목록에 억지로 배지를 만들지 않는다.

서버는 목록의 모든 사건에 현재 상태 문구를 반복해서 내려주지 않고 다음 식별자를 반환한다.

```text
latest_reflected_event_id
latest_unreflected_event_id
```

`latest_unreflected_event_id`가 식재료의 혼합 상태라면 앱은 `일부 메뉴 미반영`으로 표시한다.

## 6. 변경 상세 팝업

목록 행을 누르면 공통 하단 시트를 연다.

```text
입고 취소 반영             [현재 매출 미반영]
26-08-18 16:20 · 식자재쇼핑몰 입고 취소

자동 갱신
기준 단가       5.20원/g → 4.95원/g

닫기
```

- 별도 `변경 내용` 헤더를 두지 않는다.
- 사건 제목을 최상단 주제목으로 표시한다.
- 선택된 최신 상태 사건일 때만 제목 우측에 상태 배지를 표시한다.
- 날짜와 변경 출처는 제목 바로 아래에 표시한다.
- 사용자가 바꾼 값은 `직접 수정`으로 묶는다.
- 계산되거나 전달된 값은 `자동 갱신`으로 묶는다.
- 직접 수정과 자동 갱신이 한 저장에서 함께 발생하면 두 영역을 모두 표시한다.
- 하단의 동적 설명·안내 문구는 표시하지 않는다. 항목이 많거나 영향이 섞이면 한 문장이 실제 상태와 어긋날 수 있다.

### 직접 수정과 자동 갱신 예시

```text
레시피 수정                [현재 매출 미반영]
2026.08.20 14:41 · 직접 수정

직접 수정
판매가       9,500원 → 9,000원
부자재         120원 → 320원

자동 갱신
세금        863.64원 → 818.18원
순이익    2,278.92원 → 1,780.88원
```

## 7. 기록 대상과 제외 대상

### 7.1 식재료

직접 수정:

- 이름, 카테고리, 최소단위
- 개당 용량, 안전재고, 최소 발주량
- 구매 링크(구매처·상품명·용량·금액·URL)의 추가·수정·삭제. 기본 거래처 지정 기능은 제외한다(2026-09-09 사용자 결정).

자동 갱신:

- 입고 확정·취소로 바뀐 기준 단가

제외:

- 메모
- 판매 소진, 재고 실사, 폐기 등 재고 수량 변동

재고 수량 변동은 기존 재고 원장이 단일 출처다. 수정 내역에 복제하지 않고 재고 내역 화면에서만 확인한다. 기준 단가는 입고 등 허용된 서버 경로에서만 바꾼다.

### 7.2 레시피

직접 수정:

- 이름, 판매가, 기준 인분, 목표 순이익률
- 재료 구성과 1인분 사용량
- 부자재, 세금 항목, 판매 상태

자동 갱신:

- 직접 수정으로 다시 계산된 재료비·세금·고정지출·순이익·순이익률
- 연결 식재료의 기준 단가 변경으로 다시 계산된 금액
- 고정지출률 변경으로 다시 계산된 금액

제외:

- 메모
- 단순 조회, 새로고침, 캐시 무효화
- 실제 전후값이 같은 저장과 재계산

## 8. 기록 단위

- 저장 한 번은 수정 내역 한 건이다.
- 입고 한 번과 그로 인한 레시피 갱신은 같은 `correlation_id`로 연결한다.
- 여러 필드를 바꿔도 사건을 필드별로 나누지 않는다.
- 사용자 입력값과 계산 결과는 한 사건 안에서 `change_kind`로 구분한다.
- 변경 원장은 append-only로 기록하고 계산 원장·추이·영업 스냅샷과 분리한다.
- 화면은 최근 7일만 보지만 수정 내역 데이터는 30일 보관한다. 재고·구매·가격·손익 원장과 스냅샷은 삭제하지 않는다.

## 9. 데이터 구조

```text
entity_change_events
  id
  store_id
  entity_type             ingredient | recipe
  entity_id
  source_type             direct | inbound | ingredient | fixed_cost
  source_entity_id
  correlation_id
  title
  changes                 [{ key, label, before, after, unit, change_kind }]
  affects_sales
  business_day_id
  actor_id
  occurred_at
```

`change_kind`:

- `direct`: 상세 팝업의 `직접 수정`
- `derived`: 상세 팝업의 `자동 갱신`

현재 매출 반영 여부는 저장하지 않는다. 현재 영업일 스냅샷의 기준 시각과 사건 시각을 사용해 읽기 RPC에서 계산하고, 최종적으로 표시할 두 사건 ID만 선택한다.

## 10. API와 앱 연결

### 상세 RPC

`ingredient_detail`, `recipe_detail`에 `last_change`를 제공한다.

```text
last_change
  occurred_at
  event_id
  display_state
```

### 수정 내역 RPC

```text
entity_change_history(
  entity_type,
  entity_id,
  cursor,
  limit,
  days = 7
)
```

반환값:

```text
items
next_cursor
summary
  days
  count
  direct_count
  auto_count
  latest_reflected_event_id
  latest_unreflected_event_id
  latest_unreflected_state
```

- `latest_unreflected_state`: `not_reflected | partial | null`
- 목록은 20건씩 커서 페이지네이션한다.
- 요약 건수와 배지 대상 ID는 최근 7일 전체를 기준으로 서버가 계산한다.
- 앱은 공통 `RecentChangeRow`, `ChangeHistoryScreen`, `ChangeDetailSheet`를 사용한다.
- 식재료와 레시피 화면은 엔터티 유형과 데이터만 전달한다.
- 저장 성공 시 해당 상세·수정 내역과 연관 레시피 쿼리를 함께 무효화한다.

## 11. 완료 조건

1. 식재료와 레시피 수정 내역이 같은 헤더·요약·목록·상세 팝업을 사용한다.
2. 헤더에는 `수정 내역`만 표시하고 대상 유형과 이름은 본문에서 표시한다.
3. `최근 7일 기준`과 전체 건수를 한 줄로 표시한다.
4. 상단 집계가 `직접 수정 n건 · 자동 갱신 n건`으로 표시된다.
5. 목록 우측에 대표 금액을 표시하지 않는다.
6. 현재 매출 반영 배지는 최대 1건, 미반영 또는 일부 미반영 배지는 최대 1건이다.
7. 상세 팝업은 사건 제목으로 시작하고 `변경 내용` 헤더와 하단 설명 문구가 없다.
8. 상세 전후값은 `직접 수정`·`자동 갱신`으로 나뉜다.
9. 메모와 재고 수량 변동은 수정 내역에 나타나지 않는다.
10. 식재료 단가 변경은 연결 레시피의 현재 재료비·순이익을 갱신하고 같은 상관 ID로 양쪽에 기록된다.
11. 동일값 저장과 단순 조회는 수정 내역을 만들지 않는다.
12. 대파 4.00원/g, 제육볶음 재료비 2,806.40원, 순이익 4,046.60원 기준 테스트가 유지된다(AGENTS.md 고정 검산값).

### 공통 전파 검증 계약

- 사용자 확정 요구: 식재료 구매 가격·개당 용량을 수정하면 현재 기준단가와 연결 메뉴의 식재료비·손익도 갱신되어야 한다. 메뉴 판매가를 자동 변경한다는 의미는 아니다. 직접 수정한 구매 가격÷용량을 현재 메뉴 단가로 사용하고, 다음 성공한 입고는 실입고 가중평균으로 자동 갱신한다. 입고 취소는 취소 건을 제외한 평균으로 갱신한다. 별도 사용자 선택 모드나 과거 원장 재평가를 추가하지 않는다.
- 적용 시점은 영업 전/종료 후 즉시, 영업 중/브레이크에서는 현재 영업 기준 보존 후 종료 시 적용이다. 서버 상태·날짜·영업일 ID 전환을 감지하면 금액과 수정 내역·대기 요약을 함께 갱신한다. 다른 기기의 상태 변경 감지는 현재 60초 폴링 주기를 따른다.
- 같은 금액의 식재료·부자재 구성 교체도 직접 수정 사건으로 기록한다. 금액 변화가 없어도 판매 소진 대상 또는 영업 기준 구성이 달라지면 대기 상태가 필요하다. 단순 이름·메모 변경과 구분한다.
- 같은 값 저장·중복 요청은 사건/추이/판본을 중복 생성하지 않는다. 금액이 같은 구성 변경과 정보 변경은 수정 이력에 필요에 따라 남기되 금액 변동 추이를 만들지 않는다.
- 부자재 단가 0원과 부자재 연결 제거는 다르다. `material_id`가 있고 수량이 양수인 선택 항목은 0원이어도 유지한다. 다른 메뉴 정보를 수정하거나 저장을 반복해도 연결이 사라지지 않으며, 이후 가격 복원은 다시 전파한다. 사용자가 항목을 명시적으로 제거한 경우에만 해당 연결을 없앤다.
- 검사 단위는 단일 화면이 아니라 `변경 입력 → 서버 계산 → 영향 메뉴 범위 → 영업 적용 시점 → 직접/자동 이력 → 화면 캐시` 전체 연결이다. 등록/수정/삭제/원복/재요청, 0/없음, 연결 없음/한 개/여러 개/판매 중지, 동시 수정/종료, 날짜·월 경계, 권한 격리와 과거 원장 보존을 교차 검증한다.
- 부자재 마스터 비활성화와 메뉴에서 해당 부자재를 제거하는 동작은 구분한다. 전자는 기존 연결을 보존하는 현재 계약이며 후자만 메뉴 구성에서 제거한다. 이를 임의로 같은 삭제로 바꾸지 않는다.
- 메뉴의 기준 인분·목표 순이익률만 변경해도 시작 기준과 구분하여 적용 대기를 표시한다. 실제 원가·손익이 같다면 금액 추이를 만들지 않는다.
- 고정지출의 항목 추가·제거·세부 금액 변경·매출 분모 변경은 당월 메뉴 전체에 자동 갱신 사유를 남긴다. 같은 총액인 구성 변경도 포함하며, 과거·미래의 다른 월 변경은 현재 메뉴의 대기 상태와 섞지 않는다.
- 세금은 항목·요율·계산 기준·과세 상태·매장/배달/포장 납부 주체의 전후를 기록한다. MY 저장은 가격 기준과 세금 설정을 한 번에 저장하며, 실패 시 어느 한쪽만 저장하지 않는다. 메뉴별 유효한 과세 예외는 프로필 교체 후에도 보존한다.

### 공통 적용 상태와 세금 선택 최종 규칙

- MY 세금과 국가·통화 진입은 같은 세금 설정 화면과 원자 저장을 사용한다. 메뉴별 과세 선택에서 ‘매장 기본값’은 이후 매장 기본 과세 상태도 따라간다. 명시 과세·면세·유효한 분류 선택은 그대로 보존하며 삭제한 분류는 매장 기본값을 따른다. 이전 기록의 선택 의도는 소급 추정하지 않는다.
- 세금 변경으로 실제 기준이 바뀐 메뉴만 `영업 종료 후 반영 예정`을 표시한다. 명시 면세 메뉴의 기준이 그대로라면 다른 메뉴의 세금 변경 때문에 대기 표시를 붙이지 않는다.
- 현재 영업 중/브레이크 중인 판매 기준은 종료까지 유지한다. 종료 후에는 최종 원가·순매출·손익을 함께 적용하며, 세액이 같아도 순매출이 달라지면 손익 변동을 남긴다.
- 식재료·메뉴·입고·취소 변경 이력의 전후 손익은 같은 적용 예정 세금 기준으로 비교한다. 세금 설정과 원가 수정의 입력 순서로 이력의 세금 기준이 갈라지지 않는다.
- 미래 세금 예약을 앞당겨도 그 프로필에 실제 저장한 메뉴 선택과 수정 판본을 잃지 않는다. 영업일 스냅샷과 세금 활성 경계는 보존한다.

- 메뉴 과세 상태에 적용되지 않는 세금의 요율·납부 주체 변경은 해당 메뉴 수정 내역에 넣지 않는다. 같은 과세 상태에서 매장 기본값으로 전환하거나 이름·표시 순서만 바꾸는 경우는 정보성 이력이며 매출 반영 대기를 만들지 않는다. 세금 구성과 계산·납부 규칙의 사유는 구분한다.
- 다른 월 고정지출을 처음 등록해도 당월 메뉴의 손익 변동을 생성하지 않는다. 해당 월 설정 원장은 그대로 기록한다.
- 과거월 고정지출 정정은 해당 월 손익과 설정 수정 내역에 반영한다. 현재 메뉴·식재료 가격으로 과거 날짜의 메뉴 손익 점을 합성하지 않으며 종료 영업일 스냅샷을 보존한다.
