# 식재료·레시피 수정내역 최종 기획

## 1. 목적

식재료와 레시피 상세에서 사용자가 다음 세 가지를 바로 확인할 수 있게 한다.

1. 마지막으로 언제 값이 바뀌었는가
2. 직접 수정인지 다른 데이터에서 자동 반영된 변경인지
3. 바뀐 값이 현재 영업의 매출·원가 계산에 반영됐는가

식재료 기준 단가가 바뀌면 연결된 레시피의 현재 재료비·순이익은 즉시 다시 계산한다. 다만 영업을 이미 시작한 날의 매출 장부는 영업 시작 스냅샷을 유지한다.

근거: `docs/source-v3/레시피_상세로직_유저시나리오_v3.txt` 1장·3.8절, `docs/구현-변경점.md` 9·10·12·13절.

## 2. 상세 화면 공통 표시

식재료 상세(ING-03)와 레시피 상세(RCP-02)의 첫 요약 카드 하단에 동일한 글로벌 행을 사용한다.

`최근 수정 08.20 14:32 · 현재 매출 미반영  ›`

- 반드시 한 줄로 표시한다.
- 왼쪽부터 `최근 수정`, 최근 변경 시각, 매출 반영 상태, 우측 화살표 순서다.
- 행 전체를 누를 수 있다.
- 누르면 해당 항목의 `수정 내역` 목록을 연다.
- 변경 기록이 없으면 생성일을 최근 수정일로 사용하고 목록에는 `최초 등록`을 표시한다.
- 날짜는 오늘이면 `방금`, `14:32`처럼 축약하고 이전 날짜는 `08.20 14:32`로 표시한다.

### 매출 반영 상태

| 표시 | 조건 |
|---|---|
| 현재 매출 반영 | 영업 시작 전이거나, 변경값이 현재 영업 기준에 포함된 상태 |
| 현재 매출 미반영 | 영업 시작 후 기존 영업 기준에 포함된 레시피의 금액 계산값이 변경됨 |
| 일부 메뉴 미반영 | 식재료 변경이 여러 레시피에 전파됐고 현재 반영 상태가 섞여 있음 |
| 매출 계산과 무관 | 카테고리·안전재고처럼 매출 금액을 바꾸지 않는 수정 |

`현재 매출 미반영`인 값도 식재료·레시피 상세의 현재 계산에는 즉시 보인다. 오늘 매출 장부만 기존 스냅샷을 사용하고 다음 영업일부터 새 값이 적용된다.

영업 중 처음 추가된 메뉴처럼 오늘 기준에 아직 없는 항목은 첫 판매 시 현재 값으로 기준에 추가할 수 있으므로 무조건 `미반영`으로 표시하지 않는다(`docs/구현-변경점.md` 13절).

## 3. 메모

- 식재료: 이름 아래에 기존 `ingredients.memo`를 표시하고 수정 화면에서도 편집한다.
- 레시피: 이름 아래에 메모를 표시한다. 현재 스키마에는 레시피 메모가 없으므로 `recipes.memo`를 추가하고 레시피 저장·상세 RPC와 폼을 함께 연결한다.
- 값이 없으면 상세에는 `메모 없음`을 약한 색으로 표시하고, 수정 화면에는 선택 입력으로 제공한다.
- 메모는 표시·저장만 하며 수정 내역 원장에는 남기지 않는다.

## 4. 수정 내역 목록

우측 화살표 또는 행 전체를 누르면 같은 화면 위에 전체 화면 목록을 연다. 상단은 `‹ 수정 내역`, 본문은 최신순 카드 목록이다.

각 변경 카드는 다음 정보를 표시한다.

- 변경 시각
- 현재 매출 반영 상태
- 변경 제목
- 변경 출처: 사용자 직접 수정, 입고 확정, 식재료 자동 전파, 고정지출 자동 전파 등
- 변경된 필드의 이전값 → 새값
- 자동 전파라면 원본 항목과 영향을 받은 결과

한 번의 저장·입고·전파는 카드 한 장으로 묶는다. 필드마다 카드를 따로 만들지 않는다. 실제 값이 달라지지 않은 재계산, 화면 새로고침, 캐시 무효화는 기록하지 않는다.

### 식재료 목록 예시

```text
08.20 14:32                         현재 매출 미반영
기준 단가 변경
입고 확정으로 자동 계산
기준 단가       4.00원/g → 4.80원/g
연결 레시피 2개의 원가와 순이익을 자동 재계산했어요.
```

### 레시피 목록 예시

```text
08.20 14:32                         현재 매출 미반영
대파 기준 단가 자동 반영
식재료 변경에서 자동 전파
재료비          2,806.40원 → 2,838.40원
순이익          4,046.69원 → 4,014.69원
```

## 5. 기록 대상

### 식재료

- 직접 수정: 이름, 카테고리, 최소단위, 개당 용량, 안전재고, 최소발주량, 기본 거래처
- 자동 변경: 입고 확정·취소로 인한 기준 단가 변경
- 재고 수정·폐기는 기존 재고 원장이 단일 출처이므로 수정내역에는 요약만 연결하고 원본 수량 내역은 기존 재고 변동 화면에서 확인한다.

### 레시피

- 직접 수정: 이름, 판매가, 기준 인분, 목표 순이익률, 월평균 판매량, 재료 구성·수량, 부자재, 세금 항목, 판매 상태
- 자동 변경: 연결 식재료의 기준 단가 변경, 하위 레시피 원가 변경, 고정지출률 변경
- 자동 변경 시 재료비·고정지출·세금·순이익·순이익률의 전후값을 함께 보존한다.

## 6. 데이터 구조

`updated_at`만으로는 무엇이 왜 바뀌었는지 알 수 없으므로 공통 변경 원장을 추가한다.

```text
entity_change_events
  id
  store_id
  entity_type             ingredient | recipe
  entity_id
  source_type             direct | inbound | ingredient | sub_recipe | fixed_cost
  source_entity_id        자동 전파 원본 ID, 직접 수정이면 null
  title
  changes                 [{ key, label, before, after, unit }]
  affects_sales           매출 계산 영향 여부
  business_day_id         변경 시 열려 있던 영업일, 없으면 null
  actor_id                자동 변경이면 null
  occurred_at
```

- 변경 원장은 append-only로 보존한다.
- 저장 RPC의 같은 트랜잭션 안에서 원본 수정과 변경 기록을 함께 처리한다.
- 식재료 단가 전파는 하나의 상관 ID로 식재료 이벤트와 여러 레시피 이벤트를 연결한다.
- `현재 매출 반영 여부`는 시간이 지나면 달라지는 값이므로 boolean으로 저장하지 않고, 현재 영업일 스냅샷과 변경 시각·상관 ID를 기준으로 읽기 RPC가 계산한다.
- RLS는 원본 엔터티와 동일하게 `store_id` 단위로 제한한다.

## 7. API와 앱 연결

- `ingredient_detail`, `recipe_detail`: `last_change` 객체를 추가한다.
- 공통 RPC `entity_change_history(entity_type, entity_id, cursor, limit)`: 최신순 페이지 조회와 반영 상태를 반환한다.
- 식재료 저장·입고 확정·입고 취소·레시피 저장·고정지출 저장 RPC에서 변경 원장을 기록한다.
- 앱은 공통 `RecentChangeRow`와 `ChangeHistoryScreen`을 사용하고 식재료·레시피 화면은 데이터만 전달한다.
- 저장 성공 시 해당 상세·수정내역과 연관 레시피 쿼리를 함께 무효화한다.
- 목록은 최초 20건, 아래로 스크롤하면 다음 20건을 불러온다.

## 8. 완료 조건

1. 두 상세 화면의 최근 수정 행이 같은 모양의 한 줄로 표시된다.
2. 두 화면 모두 메모가 표시·저장된다.
3. 우측 화살표와 행 전체 클릭으로 수정 내역 목록이 열린다.
4. 직접 수정의 필드별 전후값이 한 카드에 묶여 보인다.
5. 식재료 단가 변경 한 번으로 연결 레시피의 재료비·순이익이 갱신되고 양쪽 내역에 같은 전파가 기록된다.
6. 영업 중 기존 레시피를 바꾸면 상세는 새 값, 오늘 매출은 스냅샷 값이며 `현재 매출 미반영`으로 표시된다.
7. 다음 영업 시작 뒤에는 같은 변경이 `현재 매출 반영`으로 바뀐다.
8. 안전재고처럼 매출 계산에 영향 없는 변경은 `매출 계산과 무관`으로 표시된다.
9. 동일값 저장과 단순 조회는 수정 내역을 만들지 않는다.
10. 대파 4.00원/g과 제육볶음 순이익 4,046.69원 기준 테스트가 유지된다.
