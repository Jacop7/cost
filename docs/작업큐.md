## 상태와 우선순위

- `대기`: 시작 조건 또는 선행 작업을 기다림
- `진행`: 전용 브랜치에서 구현·검증 중
- `병합 대기`: 완료 조건을 충족하고 동일 SHA CI를 기다림
- `병합 완료`: `main` 반영과 후속 기록까지 완료
- `차단`: 권한·환경·외부 결정이 없어 안전하게 진행할 수 없음
- `즉시`: 다음 작업의 신뢰할 수 있는 검증을 막는 기존 결함으로, 새 기능보다 먼저 처리
- `P0`: 실데이터 또는 첫 운영 배포 전에 반드시 완료
- `P1`: 첫 원격 프로젝트 연결·운영 절차 확정 전에 완료
- `P2`: 안전성에는 직접 영향이 없지만 회귀 방지를 위해 계획적으로 보강

## 공통 실행 규칙

1. 모든 작업은 최신 `main`에서 짧은 세로 브랜치로 시작한다.
2. DB를 변경하는 브랜치는 동시에 하나만 연다.
3. feature HEAD의 workflow matrix job이 모두 `completed/success`가 되기 전에는 `main`을 이동하지 않는다.
4. 운영·스테이징 적용 이력은 실제 연결과 조회 전까지 `미확인`으로 유지한다.
5. 완료 시 커밋 SHA, 로컬 검증, 동일 SHA CI, 운영 적용 여부를 이 문서에 기록한다.
6. 원격 환경에 적용된 마이그레이션은 고치지 않고 새 마이그레이션으로 전진 복구한다.

## TEST-1 야간 DB 시험 시간 독립화

```yaml
status: 병합 완료
priority: 즉시
planned_branch: codex/test-late-open-time-independence
base: main
depends_on: []
touches: [packages/db/tests/_prelude.sql, packages/db/tests/09_business_day.sql, packages/db/tests/12_day_basis.sql, packages/db/tests/13_change_history.sql, packages/db/tests/27_amend_ended_day.sql, packages/db/tests/29_store_context.sql, packages/db/tests/30_state_transitions.sql, packages/db/supabase/seed.sql, packages/db/scripts/upgrade-check.sh]
migration: none
```

### 문제

`2026-08-27T22:04+09:00` 전체 검증에서 개발 DB와 새 DB 모두 `09`·`12`·`13`·`27`·`29`·`30`
시험이 26/32로 실패했다. 이 시험들은 영업시간이 지난 뒤 `transition_business_state(..., 'open')`을
종료 시각 없이 직접 호출해 `45015 LATE_OPEN`을 받는다. `_prelude.sql`의 공통 준비 경로는 보완됐지만
다른 날짜의 열린 장부를 닫고 오늘을 여는 두 번째 분기와 각 시험 안의 직접 호출이 남아 있었다.

### 완료 조건

- 여섯 시험의 직접 `open` 준비를 0162의 정식 늦은 개점 경로 또는 사후조건이 있는 공통 헬퍼로 통일한다.
- 제품의 늦은 개점 거부 규칙을 약화하거나 시험에서 `45015`를 무시하지 않는다.
- 영업시간 전·후와 자정 경계에서 개발 DB 32/32, 새 DB 32/32가 모두 통과한다.
- `pnpm verify` 6/6과 업그레이드 8/8을 같은 실행에서 확인한다.
- 시간 의존 코드를 옛 직접 호출로 되돌린 사보타주가 해당 시험을 실패시킨다.

### 완료 결과

- `05b0cce`에서 시험 전용 `pg_temp.open_for_test()`를 만들었다. 이 헬퍼는 제품이 요구하는
  `45015 LATE_OPEN`만 잡아 매장 현지 시각 기준 미래 종료를 넘기며, 다른 오류는 삼키지 않고 반환
  영업일의 매장·상태 사후조건을 확인한다.
- 여섯 시험의 준비 호출과 `_prelude.sql`의 첫 개점·다른 날짜 종료 뒤 두 번째 개점 경로를 같은 헬퍼로
  통일했다.
- `30_state_transitions.sql`은 오늘 규칙을 `00:01~00:02`로 강제하고 다른 날짜의 열린 장부를 만든 뒤,
  벽시각과 무관하게 두 번째 분기와 늦은 개점 폴백이 실제로 동작하는지를 검증한다.
- `3a9f2d1`은 `0150` 중간 상태 DB에 현재 seed를 재생하는 야간 경로를 보정했다. `seed.sql`은 0162
  이전 시그니처에서 오늘 장부의 종료를 미래로 보장하고, `upgrade-check.sh`가 그 조건을 직접 단언한다.
- 로컬 `pnpm verify` 6/6, 개발·새 DB 32/32, 업그레이드 8/8, 종료 후 임시 `fresh_*` DB 0개를 확인했다.
- [feature CI](https://github.com/Jacop7/cost/actions/runs/33081474853)와
  [같은 SHA의 `main` CI](https://github.com/Jacop7/cost/actions/runs/33081709783)에서 Node 20.19.4·24가
  모두 `completed/success`였다.

### 후속 보강 결과 (2026-08-28)

- 장부 정상화 뒤 전체 검증에서 `open_today()`가 오늘의 종료 장부를 먼저 되열면 다른 날짜의 열린
  장부와 둘이 동시에 열릴 수 있는 시험 준비 결함을 확인했다.
- `9fc4b47`에서 다른 날짜를 먼저 닫고 그 성공을 보존한 뒤 오늘을 열도록 순서를 고쳤다. 종료와
  재개점을 별도 예외 블록으로 나누고, 종료 단계는 예상 가능한 `22000`·`45002`만 처리한다.
- `30_state_transitions.sql`은 대상 영업일과 같은 현지 날짜이면서 `03:00~21:00`인 `Etc/GMT*`
  고정 오프셋 시간대를 골라 자정·DST에 기대지 않는다. 대상 날짜의 장부가 없는 경우와 이미 종료
  장부가 있는 경우를 모두 확인한다.
- 늦은 개점 폴백 제거, 다른 날짜 종료 제거, 종료·재개점 예외 블록 재결합의 사보타주 3종이 각각
  `LATE_OPEN`, 오늘 영업일 0개, 다른 날짜 열린 영업일 1개로 실패함을 확인했다.
- 두 SQL은 UTF-8 BOM 없는 LF로 정규화했다. 대상 시험 `1/1`, 개발 DB `32/32`, 전체 `pnpm verify`
  6단계와 업그레이드 경로 `8/8`이 통과했고 종료 뒤 임시 `fresh_*` DB는 `0개`다.

## P0-2 DB 전체 검증을 병합 필수 체크로 이전

```yaml
status: 대기
planned_branch: ci/full-db-required-check
base: main
depends_on: [TEST-1]
touches: [.github/workflows, github-ruleset, scripts, packages/db, docs]
migration: none
```

### 문제

현재 GitHub Actions의 `pnpm verify --no-db`는 DB 패키지 시험과 로컬 6단계 중 ④ 새 DB·경합·실 DB
parity, ⑤ 업그레이드 경로를 실행하지 않는다. 저장소 ruleset도 없어 로컬 보고나 workflow 추가만으로는
직접 push를 자동 차단할 수 없다.

### 완료 조건

- 새 DB 전체 마이그레이션·DB 시험·2세션 경합·실 DB parity가 자동 실행된다.
- 중간 버전 업그레이드 경로가 자동 실행된다.
- 어느 단계든 실패하면 `main` 병합이 차단된다.
- 실행 결과가 정확한 커밋 SHA에 연결된다.
- GitHub ruleset에 정확한 required check context를 등록하고, 성공하지 않은 SHA의 직접 push를 막는다.
- 실패하도록 만든 시험용 커밋이 `main`으로 이동하지 못하는지 실제로 확인한다.
- `--no-db` 결과를 전체 6단계 통과로 표시하지 않는다.

### 근거

- [운영 기획안 §4.3](./브랜치-DB-운영-기획안.md#43-로컬-전체-검증과-ci-범위), §5.3

- feature 브랜치 또는 승인되지 않은 SHA에서 운영 적용을 거부한다.
- project ref·배포 SHA·적용 마이그레이션을 배포 기록에 남긴다.

- 자동 백업 상태와 보존 기간을 확인한다.

- DB 백업과 별도로 Storage 객체의 복구 방법을 확인한다.
- Cron의 마지막 성공·실패·지연과 핵심 RPC 오류율을 관측하고 경보 경로를 검증한다.
- `P1-1` 감사 결과와 운영 `migration list`를 배포 기록에 남긴다.

## P1-1 원격 ACL 읽기 전용 감사

```yaml
status: 대기
planned_branch: security/remote-acl-audit
base: main
depends_on: []
touches: [packages/db/scripts/admin-acl.sh, packages/db/scripts/admin-acl.test.sh, docs]
migration: none
```

### 완료 조건

- `admin-acl.sh --remote audit` 모드를 추가하고 `supabase_admin` 전환 없이 실행한다.
- `current_user`·`rolsuper`·`pg_has_role(..., 'supabase_admin', 'member')` 원값을 출력한다.
- 원격 마이그레이션 이력에 ACL 보완 `0166`·`0167`이 있는지 확인한다.
- `postgres` 소유 프로브를 트랜잭션 안에서 만들고 검사 후 rollback한다.
- `anon`·`authenticated`의 유효 `TRUNCATE`·`TRIGGER`·`REFERENCES` 권한이 0건인지 확인한다.
- 애플리케이션 `public` 객체 중 `supabase_admin` 소유 객체가 0건인지 확인한다.
