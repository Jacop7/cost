## 상태와 우선순위

- `대기`: 시작 조건 또는 선행 작업을 기다림
- `진행`: 전용 브랜치에서 구현·검증 중
- `병합 대기`: 완료 조건을 충족하고 동일 SHA CI를 기다림
- `병합 완료`: `main` 반영과 후속 기록까지 완료
- `차단`: 권한·환경·외부 결정이 없어 안전하게 진행할 수 없음
- `즉시`: 다음 작업의 신뢰할 수 있는 검증을 막는 기존 결함으로, 새 기능보다 먼저 처리
- `P0`: 실데이터 또는 첫 운영 배포 전에 반드시 완료
- `P1`: 첫 원격 프로젝트 연결·운영 절차 확정 전에 완료
- `P2`: 안전성에는 직접 영향이 없지만 회귀 방지를 위해 계획적으로 보강

## 공통 실행 규칙

1. 모든 작업은 최신 `main`에서 짧은 세로 브랜치로 시작한다.
2. DB를 변경하는 브랜치는 동시에 하나만 연다.
3. feature HEAD의 workflow matrix job이 모두 `completed/success`가 되기 전에는 `main`을 이동하지 않는다.
4. 운영·스테이징 적용 이력은 실제 연결과 조회 전까지 `미확인`으로 유지한다.
5. 완료 시 커밋 SHA, 로컬 검증, 동일 SHA CI, 운영 적용 여부를 이 문서에 기록한다.
6. 원격 환경에 적용된 마이그레이션은 고치지 않고 새 마이그레이션으로 전진 복구한다.

## AI-REVIEW-2 페이블 소진 시 Opus 연속성 감사

```yaml
status: 병합 완료
priority: P1
base: main
depends_on: [AI-REVIEW-1]
touches: [scripts/fable-review.mjs, scripts/fable-review/schema-v1.json, docs/ai-review/README.md, docs/ai-review/templates/, docs/팀구성_상세기획안.md]
migration: none
```

### 목표

- 페이블의 모델 예산·사용량·속도·용량 소진만 감지해 Opus 신규 클린 컨텍스트로 독립 감사 역할을 이어간다.
- 검수 실패·인증 실패·권위 경로·hash·schema·의미 계약 오류는 대체 모델로 우회하지 않는다.
- 실패 run과 대상 판본을 고치지 않고 successor Task가 동일 Finding registry와 읽기 전용 권한을 승계한다.
- 모델 출처, 정확한 CLI·model·runner hash와 작업 전체 사용 상한을 감사 기록에 남긴다.

### 완료 조건

- 소진 사유 allowlist와 비승계 오류 denylist가 runner·schema·task template에 같은 의미로 정의된다.
- Opus successor가 predecessor run, target commit, input/artifact hash, Finding registry를 검증한 뒤에만 실행된다.
- Opus도 새 세션·빈 MCP·`Read/Glob/Grep`·restricted/safe mode를 사용하고 제품 파일을 직접 쓰지 못한다.
- 같은 Task의 과거 회차를 모델 변경으로 덮어쓰기, Finding 누락, 권한 확대, 상한 초과를 자체시험이 차단한다.
- 결과와 상태에 실제 reviewer engine을 표시하며 Opus 결과를 페이블 결과로 가장하지 않는다.
- `FABLE-SEC`·`FABLE-FINAL` 대체 결과는 페이블 복구 후 표본 재감사 규칙과 연결된다.
- Opus도 사용할 수 없을 때 연쇄 하향하지 않고 모델 결과 없는 `run_state=RUN_FAILED`와
  `FALLBACK_UNAVAILABLE` 구조화 사유로 종료한다. verdict `BLOCKED`를 합성하지 않는다.
- 소진 승계 handoff를 기존 `predecessor_review`의 FABLE-FINAL·commit 변경 경로와 분리하고, 모든
  reviewer role·동일 target·첫 회차 소진 `INITIAL`·성공 회차 뒤 `RECHECK`를 자체시험이 검증한다.
- `INITIAL`·`RECHECK`는 registry 승계 의미로만 사용하고 `SECURITY`·`FINAL` route successor의
  `task.review_mode`를 `INITIAL`·`RECHECK`로 발행하면 거부됨을 자체시험이 검증한다.
- successor 입력 범위를 route별로 자체시험한다. `FINAL_INDEPENDENT`는 registry 승계 여부와 무관하게
  predecessor 장부를 보내지 않고, 그 밖의 route는 registry 승계 시 장부 전체·성공 회차가 없으면
  `SOLAR_REQUEST`까지만 보낸다.
- protocol 1.1 장부의 `AI_DEPUTY_FALLBACK_HANDOFF` append는 명시적으로 거부하고 protocol 1.2
  successor 전용 경로에서만 수용함을 자체시험이 검증한다.
- `MANDATORY_MUTUAL`·`CONDITIONAL` successor는 `task.review_mode=INITIAL`을 유지하고 RECHECK 상태를
  inherited registry에서 파생한다. `task.review_mode=RECHECK` 직접 선언은 거부함을 자체시험이 검증한다.
- runner 회차 상한 `budget_exhausted`, 인증 실패, STALE, schema·의미 계약 거부 run은
  fallback-eligible로 표시되지 않고 구조화된 제공자 오류만 승계됨을 자체시험이 검증한다.
- `review.json`·`run.json`·`status.json`·장부 턴 헤더에 primary/fallback engine과 정확한 model ID가
  기록되며 엔진 누락·위장은 `VALIDATION_REJECTED`로 격리된다.
- 실패 run의 실제 사용액을 작업 전체 상한에서 차감하고, 초과 승계는 사람 승인 없이는
  `run_state=RUN_FAILED`와 `TASK_CAP_APPROVAL_REQUIRED` 사유로 남긴다.
- 모델 결과 없는 Opus 불가·비승계 오류는 review/verdict를 합성하지 않고 `RUN_FAILED`와 구조화된
  사유만 남김을 자체시험이 검증한다.
- predecessor 장부 bytes/hash, fallback handoff turn/entry/run hash, handoff 전용 source commit을
  봉인하며 장부 변조·handoff 누락·다른 source commit은 자체시험이 실패 폐쇄한다.
- 결과 `reviewer_role`은 원 역할을 유지하고 `OPUS-FALLBACK`은 role 값이 될 수 없다. Finding
  `VERIFIED` 권한은 원 reviewer role을 따르고 Opus 검증에는 `verified_by_engine`이 필수임을
  schema·자체시험이 검증한다.
- 사람 결정 완료: 공식 Claude Code CLI `2.1.250`의 Max 구독 세션에서 `claude-opus-5` 실행 증거를
  확인했고, 사용자가 작업 전체 기본 상한 `$4.00`을 승인했다. 별도 API 결제가 아니라 기존 CLI
  로그인 세션을 사용한다.
- protocol 1.2 task 버전과 결과 schema 승격은 이 작업이 소유한다.
- 모든 reviewer role의 보호 체크 후 closure successor 계약을 protocol 1.2에 구현한다. 원
  role·route·범위와 registry를 승계한 `COMMIT` Task만 허용하고, 정확한 decision SHA의 보호 체크
  성공·보호 ref 포함 증거가 없거나 target이 그 commit을 포함하지 않으면 `CLOSED`를 거부한다.
- 페이블 표본 재감사 기록 없이 `FABLE-SEC`·`FABLE-FINAL` Opus 결과를 참조한
  `AI_DEPUTY_GATE_DECISION`은 거부됨을 자체시험이 검증한다.
- `corepack pnpm fable:check`, `fable:self-test`, `corepack pnpm verify`가 모두 통과한다.

- `main-required-gates` ruleset을 실제 원격에 적용했다. bypass 없이 `protected-gate`를 required context로
  요구하고 삭제·force-push를 금지하며, 저장소 선언과 원격 설정을 `ruleset:check`로 대조한다.
- 첫 원격 실행 `33225720891`은 개발 DB의 `supabase_admin` 기본 ACL 정규화 누락을 잡았다. CI가
  `admin-acl.sh --local postgres fix → check`를 먼저 실행하도록 고친 뒤 전체 DB가 통과했다.
- 실제 부정 시험에서 GitHub가 선행 실패로 `skipped`된 required check를 허용한다는 구멍을 발견했다.
  `protected-gate`를 `if: always()`로 실행하고 선행 실패를 자신의 `failure`로 바꿨다. 최종 실패 SHA
  `185b18e`의 run `33227819652`는 `protected-gate=failure`였고 `main` push는 `GH013`으로 거부됐다.
- ruleset 적용 직후 전파 지연과 위 `skipped` 의미를 재는 과정에서 시험 commit 두 개가 잠시 `main`에
  들어갔으나 각각 선형 revert로 즉시 원복했다. 삭제·force-push·bypass는 사용하지 않았고, 최종
  `main` `1426d3c`의 feature run `33227546008`과 main run `33227812395`가 모두 전체 게이트를 통과했다.
- 옛 decision commit은 당시 정확한 SHA의 새 보호 check가 없으므로 소급 종결하지 않는다. P0-2 이후
  새 decision successor만 원격 check 증거를 물질화해 closure 계약에 사용할 수 있다.
