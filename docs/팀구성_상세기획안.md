## 0. 문서 목적과 적용 원칙

이 문서는 식자재 관리 앱을 기획·설계·구현·검증·출시·운영하기 위한 사람과 AI의 역할, 권한, 인수인계, 품질 게이트를 정의한다. 팀 이름만 나누는 것이 아니라 누가 무엇을 만들고, 누가 반박하고, 누가 실제로 검증하며, 누가 최종 위험을 승인하는지를 고정하는 것이 목적이다.

권위 작업 루트는 `C:\Users\jacop\프로젝트\식자재관리앱` 하나다. OneDrive에는 이 저장소를 복사·
동기화·미러링하지 않으며, OneDrive 파일·링크·작업공간과 외부 사본·다른 checkout은 작업, 공동
작성, 검수, 판정 또는 복구 입력으로 사용하지 않는다.
보호 원격 CI가 origin의 정확한 decision commit SHA를 임시 읽기 전용 checkout해 hash-chain과
게이트 조건만 검증하고 즉시 폐기하는 환경은 외부 게이트 전용 예외다. 공동 작성·Fable 입력·공식
작업본으로 사용하지 않는다.

다음 문서를 운영 기준으로 함께 사용한다.


AI는 문서 충돌을 임의로 해석하지 않고 사람 주 오케스트레이터에게 결정 요청으로 올린다.

`ARCHITECTURE.md`나 `source-v3`의 역사적 설명은 현재 `AGENTS.md`에서 제거되거나 예약된 기능을 다시 활성화하는 근거로 사용할 수 없다. 활성 이벤트·계산·원장·전파 범위는 이 문서에 복사하지 않고 검증 대상 commit의 `AGENTS.md`와 현재 아키텍처를 참조한다. 실제 migration과 회귀 테스트는 충돌을 발견하고 구현 상태를 입증하는 증거이며, 사람의 승인 결정이나 버전 고정 명세를 임의로 덮어쓰는 새 정책 출처가 아니다.

## 1. 운영 모델 요약

팀의 기본 분업은 다음 한 문장으로 정의한다.

> 솔라는 기획·설계·구현·운영 준비를 담당하고, Codex는 기능 정확성과 실제 생활 속 사용 가능성을 검증하며, 페이블은 보안과 조직 전체의 맹점을 독립적으로 감사한다. 사람은 제품 정책, 운영 위험, 배포와 복구를 최종 승인한다.

## 2. 공통 운영 원칙

1. **제작자·검증자·승인자를 분리한다.** 작성자가 자기 결과물을 최종 승인하지 않는다.
2. **역할별 AI 컨텍스트를 분리한다.** 같은 모델이라도 역할 이름만 바꿔 한 대화에서 계속 수행하지 않는다.
3. **AI의 기억은 공식 기록이 아니다.** 확정 결정은 문서로 남긴다.
4. **근거가 없는 완료를 인정하지 않는다.** 코드, 테스트 결과, 화면, 로그, DB 전후값 중 필요한 증거가 있어야 한다.
5. **사람은 고위험 결정을 소유한다.** 도메인 공식, 권한, 운영 데이터, 배포, 복구, 잔여 위험은 사람이 승인한다.
6. **현재 결함과 차기 아이디어를 분리한다.** v1.1 제안은 현재 릴리스의 결함 수를 부풀리지 않는다.
7. **AI 현장 시뮬레이션은 가설이다.** 오픈 후 실제 사용자에게 반복 확인된 후에만 현장 사실로 승격한다.
8. **구조 변경과 기능 변경을 섞지 않는다.** 디렉터리 재구성은 동작 동등성을 먼저 증명한다.
9. **Blocker·Critical에는 Stop-the-line을 적용한다.** 누구든 근거를 제시하면 릴리스를 동결할 수 있고 사람만 해제한다.
10. **현재 `AGENTS.md`를 매 작업 입력에 포함한다.** 이전 대화의 값으로 현재 정책을 덮어쓰지 않는다.
11. **컨텍스트 분리는 공식 산출물 분리가 아니다.** 독립성을 위해 역할별 대화는 분리하지만 요구사항·설계·UX·소스·테스트의 주제별 공식본은 하나만 유지한다.
12. **제안은 반영·검증 전까지 공식본이 아니다.** 페이블 수정안은 솔라가 같은 공식 파일에 반영하거나 반론하고 새 판본을 재검수해야 현재 기준 후보가 된다.
13. **감사 역할과 모델을 분리한다.** 페이블은 기본 감사 엔진이고 Opus는 페이블의 사용량·용량이 소진된 때만 소환하는 연속성 엔진이다. 모델이 바뀌어도 대상 SHA, Finding ID, 읽기 전용 권한과 검증 계약은 바뀌지 않는다.
14. **팀의 성장은 증거가 연결된 기록으로만 축적한다.** 채팅 기억이나 성공담을 곧바로 규칙으로 쓰지 않고, 반복 가능한 증거가 있는 교훈만 검증·승격해 다음 작업 패킷과 테스트에 재사용한다.

## 3. 역할 카드

### 3.1 사람 주 오케스트레이터

#### 미션

제품의 목표, 정책, 위험 허용 수준, 출시 여부를 최종 결정한다.

#### 주요 책임

- 제품 목표와 우선순위 확정
- 기능의 포함·제외·연기 결정
- 도메인 정책과 검산 기준값 승인
- 주요 아키텍처와 데이터 정책 승인
- 솔라·Codex·페이블 의견 충돌 조정
- Blocker·Critical 처리와 잔여 위험 수용
- 오픈 후 실제 사용자 검증 결과의 제품 반영 여부 결정
- 프로덕션 배포, 롤백, 데이터 복구 승인
- 고객 안내, 보상, 정책 예외 결정

#### 위임하지 않는 권한

- 재고·단가·원가·세금·손익 공식 변경
- RLS, 인증, 인가 정책 변경
- 파괴적 DB 마이그레이션
- 운영 데이터 삭제·병합·소급 보정
- Blocker·Critical의 예외 수용
- 프로덕션 출시·롤백·복구 결정
- 가격, BM, 약관, 개인정보 정책 변경

#### 핵심 산출물

- 승인된 목표와 범위
- 정책 결정 기록
- 위험 수용 또는 기각 기록
- 최종 Go/No-Go 기록

### 3.2 솔라 AI 부 오케스트레이터·문서 관리자

#### 미션

사람이 모든 세부 작업을 직접 추적하지 않아도 되도록 작업 흐름, 컨텍스트, 산출물과 품질 게이트를 관리한다.

#### 주요 책임

- 목표를 요구사항·작업 단위로 분해
- 요구사항 ID와 작업 ID 발급
- 선행 조건, 담당 컨텍스트, 허용 파일 지정
- 입력 패킷과 산출물 버전 관리
- 요구사항 → 설계 → 코드 → 테스트 추적
- QA와 감사 지적의 중복 제거·분류
- 미완료·차단·결정 대기 상태 관리
- 게이트 증거 확인과 미충족 작업 반려
- 사람에게 결정이 필요한 사항만 압축 보고
- 릴리스 후보 번들과 변경 이력 준비

#### 금지 사항

#### 실기기 실행과 판정의 분리

Codex는 테스트 시나리오, 사전 조건, 기대 결과와 필수 증거를 정의하고 수집된 증거를 바탕으로 통과·실패·`환경 미검증`을 판정한다. Codex가 직접 실기기를 조작했다고 간주하지 않는다.

실기기 조작과 원시 증거 수집은 다음 중 하나가 수행한다.

- 지정된 사람 기기 운영자
- Maestro 등 등록된 모바일 자동화 runner
- EAS로 만든 배포 빌드를 설치해 실행하는 기기팜·클라우드 테스트 환경

EAS Build는 설치할 빌드를 만드는 수단이며 그 자체가 실기기 기능 테스트는 아니다. 실행자는 앱 build ID, commit SHA, 기기 모델, OS 버전, 화면·영상·로그 위치를 남긴다. Codex가 원시 증거를 확인할 수 없거나 실제 실행자가 없으면 통과가 아니라 `환경 미검증`으로 기록한다. 실행자는 조작과 증거 수집의 책임자이고 QA 결과의 최종 판정자는 아니다.

#### 불변식·검산 기준의 단일 출처

이 문서는 검산 숫자, 계산 공식, 활성 전파 이벤트 또는 고정 회귀 항목을 복사해 보관하지 않는다. 각 작업과 QA 실행은 **검증 대상 commit의 저장소 루트 `AGENTS.md`** 및 사람이 승인하고 Git으로 판본 관리하는 결정 기록을 단일 기준으로 사용한다.

작업 입력 패킷과 QA 증거에는 다음을 기록한다.

- 권위 저장소와 baseline commit SHA
- 해당 commit의 `AGENTS.md` blob SHA 또는 content hash
- 적용한 절·결정 ID
- 각 활성 불변식에 대응하는 테스트 ID
- DB RPC와 `packages/core` 미러 양측 실행 결과

`AGENTS.md` 또는 승인된 결정 기록이 바뀌면 영향받는 작업 패킷, fixture, seed, 기대값과 추적표를 함께 갱신한다. 서로 다른 기준 판본으로 얻은 결과는 통과로 인정하지 않는다. 출시 불변식이 `AGENTS.md`나 Git 추적 결정 기록 어디에도 없다면 QA가 추측하지 않고 먼저 단일 출처에 등록하도록 결정 요청한다.

#### 필수 회귀군 생성 규칙

Codex 기능 QA는 작업 baseline의 현재 `AGENTS.md`, 승인된 결정 기록과 영향 요구사항에서 활성
불변식을 추출해 해당 `docs/작업큐.md` 작업 항목에 다음 연결을 만든다.

```text
현재 불변식·결정 ID
→ DB/RPC 테스트
→ Core 미러 테스트
→ 앱·E2E 테스트
→ 실행 증거
```

릴리스 후보에서는 현재 활성 불변식 전체를 실행한다. 영향 범위 테스트만 통과한 결과를 전체 회귀 통과로 표기하지 않는다. 수치 기대값은 실제 테스트와 fixture에 존재할 수 있지만 이 운영 문서에 두 번째 사본으로 만들지 않는다.

솔라는 같은 공식 산출물을 수정하고 공동 장부에서 Finding별로 답한다. 페이블은 다음 회차에 기존
Finding ID를 사용해 재감사한다.

### 3.10.1 페이블 소진 시 Opus 연속성 감사

Opus는 페이블의 판단을 덮어쓰는 상급 승인자가 아니라, 페이블을 호출할 수 없는 동안 같은 독립
감사 역할을 이어받는 예비 엔진이다. 다음 경우에만 자동 소환 후보가 된다.

- 페이블 모델의 회차 예산 소진
- 페이블 모델의 사용량·속도 제한 또는 일시적 용량 부족
- 페이블 모델이 공식 CLI에서 일시적으로 제공되지 않음

인증 실패, 권위 저장소·대상 SHA 불일치, hash-chain 변조, 허용 경로 위반, 결과 계약 위반은
`FABLE_EXHAUSTED`가 아니다. 이런 오류를 Opus로 우회하지 않고 해당 실행을 `BLOCKED` 또는
`RUN_FAILED`로 남겨 원인을 먼저 고친다.

승계 절차는 다음과 같다.

```text
페이블 소진 증거가 남은 불변 run
→ AI 부 오케스트레이터가 남은 작업별 사용 상한 확인
→ 동일 target commit·허용 경로·Finding registry를 후속 Task에 봉인
→ 새 Opus 클린 컨텍스트가 같은 읽기 전용 계약으로 검수
→ 결과에 primary/fallback 엔진·CLI 판본·실행 hash를 명시
→ Codex가 계약·테스트 증거를 검증
→ 고위험 보안·최종 감사는 페이블 복구 뒤 표본 재감사
```

Opus는 제품 파일, 공동 장부 또는 과거 페이블 원본을 직접 수정하지 않는다. 같은 실패 run을
덮어쓰지 않고 후속 Task에서 `fallback_from_task_id`, `fallback_from_run_sha256`, 대상 commit SHA와
Finding registry hash를 잇는다. 작업 접수 때 사람이 정한 **작업 전체 상한** 안에서는 매회 다시
묻지 않고 전환할 수 있지만, 상한을 올려야 하면 사람에게 승인 요청을 올린다. Opus도 사용할 수
없으면 더 약한 모델로 연쇄 하향하지 않고 `BLOCKED`로 사람에게 보고한다.

대체 엔진의 결과도 동일한 구조·의미 계약을 통과하면 로컬 `VERIFIED`까지 진행할 수 있다. 다만
모델 출처를 숨기거나 페이블 결과로 표기하지 않으며, 보호 원격 게이트와 사람의 위험 승인 규칙은
그대로 유지한다.

### 3.12 오픈 후 실제 사용자 검증단

실제 사용자 검증은 출시 전 필수 게이트로 두지 않고 **오픈 이후 실제 사용 데이터가 생긴 시점부터 시작한다.** 오픈 전에는 대상 모집, 동의, 관찰 항목, 지원·복구 절차만 준비한다.

#### 권장 구성

최소 3~5개 매장에서 다음 역할을 포함한다.

- 직접 조리하는 소규모 식당 사장님
- 주방장 또는 메뉴 원가 담당자
- 발주·입고 담당 직원
- 디지털 도구 숙련도가 낮은 사용자
- 가능하면 업종·영업시간·네트워크·기기 수준이 다른 매장

#### 운영 원칙

- 실제 영업 전에 동의와 데이터 처리 범위를 명확히 한다.
- 인터뷰의 호감도보다 실제 행동을 관찰한다.
- 종이, 메신저, 계산기로 돌아가는 순간을 기록한다.
- 사용자 발언, 관찰 사실, 제품 해석을 분리한다.
- 한 명의 요구를 즉시 공통 기능으로 만들지 않는다.
- 초기에는 기존 장부와 앱을 병행하는 섀도 모드로 검산한다.

#### 단계

```text
오픈 전: 대상 후보·동의·관찰·지원 체계 준비
→ 오픈 후 1일: 첫 사용과 핵심 업무 관찰
→ 오픈 후 2~7일: 기존 장부와 앱 병행 검산
→ 오픈 후 8~30일: 누적 재고·단가·손익 비교
→ 30일 이후: 반복 문제와 업종별 차이 검증
→ 회귀 시나리오와 정책으로 환류
```

### 4.3 RACI 핵심표

표기: `R` 수행, `A` 최종 책임, `C` 사전 협의, `I` 공유.

| 업무 | 사람 | AI 부 O | 솔라 제작 | Codex QA | 페이블 | 실사용자 |
|---|---:|---:|---:|---:|---:|---:|
| 제품 범위·우선순위 | A | R | C | I | I | C |
| 요구사항·인수 조건 | A | C | R | C | C | C |
| 도메인 정책·기준값 | A | I | R | C | C | I |
| DB/RPC/RLS 설계 | A | C | R | C | C | I |
| 기능 구현 | I | C | A/R | C | I | I |
| 비정책성 UX 설계 | I | C | A/R | C | C | C |
| 비정책성 UX 검증·게이트 종결 | I | A(종결 결정) | C | R(통과·실패 판정) | C | C |
| 정책·금전 의미가 있는 UX | A | C | R | C | C | C |
| 기능·데이터 검증 | I | C | C | A/R | C | I |
| Android·iOS 실기기 실행 | R* | C | C | A(증거 판정) | I | I |
| 생활주기 시뮬레이션 | I | C | C | A/R | C | C |
| 실제 현장 검증 | A | C | I | C | I | R |
| 보안 감사 보고서 | I | C | C | C | A/R | I |
| 미해결 보안 위험 수용 | A | C | C | C | R | I |
| 독립 종합 감사 보고서 | I | C | I | I | A/R | I |
| 릴리스 후보 준비 | I | C | A/R | C | C | I |
| 프로덕션 배포·롤백 | A/R | I | C | I | C | I |
| 운영 데이터 보정 | A/R | I | C | C | C | I |

AI의 `A`는 해당 실무 결과의 판정 책임을 뜻할 뿐, 제품 정책이나 운영 위험의 최종 승인을 뜻하지 않는다.

`R*`: 지정된 사람 기기 운영자 또는 등록된 자동화 runner가 실행한다. 사람 기기 운영자는 조작자일 뿐 QA 결과를 승인하지 않으며 Codex가 원시 증거를 판정한다.

### 4.4 필수 검수 경로와 폐쇄형 재검수 루프

RACI는 책임을 나타내고 작업 순서를 나타내지 않으므로, 다음 검수 경로를 별도로 적용한다. 사람 승인이 필요한 산출물도 제작 직후 사람에게 보내지 않는다. 제작, 반대 역할 검수, 수정, 재검수, 실행 검증과 쟁점 종합을 먼저 끝내고 사람에게는 결정 패킷을 한 번 올린다.

이 검수는 역할마다 별도의 완성 문서를 만드는 방식이 아니라 **하나의 공식 공동 산출물을 솔라와 페이블이 번갈아 개선하는 방식**으로 수행한다. 작업별 `collaboration.md` 한 곳에서 요청·반론·수정 답변·Codex 증거를 시간순으로 이어 쓰고, 페이블의 원본 검수와 구체 문구 제안은 회차별로 보존한다. 실제 디렉터리, hash, CLI 권한과 실행 명령은 [`ai-review/README.md`](./ai-review/README.md)를 따른다.

| 적용 유형 | 대상 업무 | 필수 경로 |
|---|---|---|
| 상호검수 필수 | 요구사항·인수 조건, 도메인 정책·기준값, DB/RPC/RLS 설계, 정책·금전 UX, 릴리스 후보, 운영 데이터 보정 | 솔라 제작 → 페이블 반례·위험 검수 → 솔라 수정 → Codex 실행 검증 → 페이블 재검수 ↺ → AI 부 O 종합 → 필요한 경우 사람 승인 |
| 페이블 선행 제안의 역방향 검수 필수 | 보안 Finding과 페이블이 먼저 제안한 수정 문구·패치·전략 | 페이블 Finding·수정 문구 제안 → 솔라가 구현 가능성·정책·통합 영향을 검토하고 같은 공식 산출물에 반영 또는 반론 → Codex 실행 검증 → 페이블이 같은 Finding ID로 재검수 ↺ → AI 부 O 종결 결정 → 외부 게이트 검증 |
| 조건부 상호검수 | 기능 구현, 비정책성 UX, 생활주기 시뮬레이션, 프로덕션 배포·롤백 | R0는 Codex 검증 중심, R1은 영향 범위에 따라 표본 검수, R2·R3 또는 보안·정합성 영향이 있으면 솔라↔페이블 폐쇄형 검수를 의무화 |
| 역할형 검수 | 기능·데이터 QA, Android·iOS 실기기 실행 | 실행자 증거 → Codex 판정 → 솔라 수정 → Codex 재검증 ↺. 페이블은 보안·테스트 누락만 별도로 감사 |
| 독립성 예외 | 독립 종합 감사 보고서 | 페이블이 클린 컨텍스트에서 원문을 먼저 확정한다. 솔라는 보고서를 사전 편집하지 않고 발행 후 수정·답변하며, 페이블이 해당 지적을 재감사한다. |
| 현실 검증 예외 | 오픈 후 실제 현장 검증 | 실사용자 실행 → Codex 증거 구조화 → 솔라·페이블 분석 → 사람 제품 반영 결정. AI 상호검수로 실사용 사실을 대체하지 않는다. |

검수는 다음 상태를 순환한다.

```text
OPEN
→ FIXING
→ READY_FOR_REVIEW
→ VERIFIED 또는 OPEN(재작업)
→ CLOSED
```

운영 규칙:

1. 공식 요구사항서·설계서·UX 문서와 소스는 역할별 사본으로 갈라놓지 않고 `artifact_paths`에 지정된 같은 파일을 매개형으로 공동 작성한다. `reference_paths`와 `evidence_paths`에는 수정 제안을 낼 수 없다.
2. 모든 역할은 하나의 `collaboration.md`에 새 턴을 추가한다. 비-Fable 역할은 공통 task lock을 쓰는 `pnpm fable:append`로만 턴을 추가하고, 페이블 턴은 검수 실행기만 추가한다. 직접 편집, 앞선 역할의 턴 수정·삭제, 장부 전체 교체는 금지한다.
3. 검수자는 지적마다 `finding_id`, 심각도, 근거, 수정 인수 조건과 필요한 증거를 기록하고, 공동 저작에 도움이 되는 실제 대체 문구를 `proposed_edits`로 제시한다.
4. 제작자는 제안을 같은 공식 산출물에 반영하거나 근거를 붙여 반박하고, 수정 파일·결정·테스트 증거와 정확한 commit SHA 또는 문서 hash를 같은 대화 장부에 붙여 `READY_FOR_REVIEW`로 되돌린다.
5. 최초 지적 역할만 해당 Finding을 `VERIFIED`·`CLOSED`로 바꿀 수 있다. 제작자는 자신의 수정으로 Finding을 스스로 닫을 수 없고, AI 부 O는 Finding이 아니라 전체 task/gate만 종결한다.
6. 재검수에서 미충족 또는 새 결함이 발견되면 다시 `OPEN`으로 보내며, 모든 필수 지적이 닫힐 때까지 고정 횟수 제한 없이 반복한다.
7. 코드·DB·RLS·실기기 관련 수정은 텍스트 답변만으로 닫지 않는다. Codex의 실행 가능한 회귀 테스트와 원시 증거가 함께 통과해야 한다.
8. `Blocker`, `Critical`, `Major`와 명세상 필수 지적은 미해결 상태로 게이트를 통과할 수 없다. 선택적 개선 제안은 결함과 분리하여 백로그 ID·책임자·재검토 시점을 기록한다.
9. 같은 지적이 세 차례 연속 실질적 진전 없이 반복되면 완료로 간주하지 않고 `DISPUTED`로 표시한다. AI 부 O가 쟁점과 선택지를 정리해 정책·범위·위험 결정권자에게 올리고, 결정 후 같은 검수 루프를 재개한다.
10. 사람은 매 왕복에 참여하지 않는다. 정책 선택, 범위 변경, 미해결 위험 수용, 운영 데이터와 프로덕션 권한 또는 `DISPUTED` 결정이 필요할 때만 개입한다.
11. AI 부 O는 모든 필수 finding의 `CLOSED`, 정확한 판본의 실행 검증 통과와 미해결 제안의 분리를 확인한 뒤, 마지막 review/run/장부/공식 산출물을 anchor commit에 고정하고 이를 참조하는 `AI_DEPUTY_GATE_DECISION` 턴을 별도 decision commit으로 발행한다.
12. 로컬 hash-chain은 부분 변조 탐지용 일관성 증거다. 공식 gate 종결은 decision commit과 동일한 SHA에서 보호 원격 필수 체크가 성공하고 보호 ref에 반영된 기록을 권위로 한다. 기능 CI 하나나 로컬 ref는 부족하며, 대체는 사람이 사전 승인한 외부 서명/attestation이 decision commit SHA 전체를 봉인한 경우뿐이다.
13. 로컬 `status.json`은 실행기만 갱신하고 `gate_state=OPEN`을 유지한다. 현재 `P0-2`의 ruleset·필수 체크가 완료되기 전에는 AI 부 O도 `VERIFIED`까지만 보고하며 공식 `CLOSED`를 선언하지 않는다.

검수 루프 상태, Finding 판정, CLI 실행 상태와 기능 QA 결함 상태는 서로 다른 필드다.
`workflow_state`는 위 폐쇄형 작업 루프, `finding.review_state`는 `OPEN | VERIFIED | CLOSED | DISPUTED`,
`run_state`는 CLI 성공·실패·`STALE`, `defect_state`는 §7.2의 재현·수정 수명주기를 나타낸다.
CLI 호출 성공이나 페이블 `PASS`를 task/gate 종결로 해석하지 않는다.

### 4.5 사람 승인 제거와 예외 기반 승인

사람은 모든 산출물을 다시 결재하지 않는다. 정상적으로 증명된 저위험 결과는 역할 책임자가 최종 승인하고, 예외·정책·데이터·보안·프로덕션 위험만 사람에게 올린다.

사람 승인 없이 종결 가능한 항목:

- AI 부 오케스트레이터의 작업 분해, 상태, 추적, 내부 문서
- Codex의 기능 QA 통과·실패 판정
- Codex의 Android·iOS 플랫폼별 테스트 판정
- Codex 현장 QA의 시뮬레이션 보고서
- lint·typecheck·자동 테스트 실행 결과
- 테스트 코드, fixture, 익명화 시드
- 페이블 보안·종합 감사 보고서 자체
- 릴리스 후보 번들, 변경 로그, 관측 보고서
- 수정 후 독립 재검증이 끝난 결함의 `RESOLVED` 처리
- R0와 조건을 충족한 R1의 개발·스테이징 완료

R0·R1 자동 종결 조건:

1. 도메인 공식에 영향이 없다.
2. DB 스키마·RPC·RLS와 운영 데이터 쓰기에 영향이 없다.
3. 개인정보·결제·권한·법적 문구에 영향이 없다.
4. 승인된 요구사항 범위 안이다.
5. 필수 자동 테스트와 Codex 독립 QA가 통과했다.
6. Blocker·Critical이 없다.
7. 변경을 쉽게 되돌릴 수 있다.
8. 프로덕션 배포가 아니라 개발·스테이징 완료이거나, 별도 사전 승인된 자동화 범위다.
9. 마지막 검수의 review/run/장부와 공식 산출물이 anchor commit에, AI 부 O 결정이 이를 참조하는 decision commit에 고정돼 있다.
10. decision commit의 정확한 SHA에서 보호 원격 필수 체크가 성공하고 보호 ref에 반영됐거나, 사람이 사전 승인한 외부 서명/attestation이 같은 SHA를 봉인했다.

사람 승인이 계속 필요한 항목:

- 제품 범위·우선순위와 도메인 정책
- 재고·단가·원가·세금·손익 공식
- 중요한 DB 스키마·RPC·RLS·migration
- 운영 데이터 삭제·병합·소급 보정
- 미해결 Blocker·Critical의 위험 수용
- 감사 권고와 다르게 출시하는 결정
- 실제 사용자 결과의 제품 정책 반영
- 프로덕션 배포·롤백과 보안 사고 종결
- 가격·BM·보상·약관·개인정보 결정

결함이 완전히 수정되고 최초 발견 팀이 동일 절차로 재검증했다면 심각도와 관계없이 기술적 `RESOLVED`는 AI가 처리할 수 있다. 수정하지 않은 결함을 `ACCEPTED_RISK`, `OUT_OF_SCOPE` 또는 심각도 하향으로 종결하는 것은 사람만 할 수 있다.

### 5.1 필수 컨텍스트 분리

```text
SOLAR-ORCH          부 오케스트레이터·문서 관리
SOLAR-PO            PO·도메인 정책
SOLAR-ARCH          아키텍처·데이터 무결성

SOLAR-DEV-APP       Mobile 개발

SOLAR-UX            UX·접근성
SOLAR-OPS           릴리스 준비·관측 보조
CODEX-FUNCTION-QA   기능·데이터 신뢰성 QA
  ├─ ANDROID-LANE    Android 테스트 설계·증거 판정 레인
  └─ IOS-LANE        iOS 테스트 설계·증거 판정 레인
```

### 5.2 작업 입력 패킷

모든 AI 작업에는 다음을 제공한다. 이 패킷은 역할별 제품 문서가 아니라 공동 작업의 범위·판본을
고정하는 기계 계약이며, 실제 운영에서는 `docs/ai-review/tasks/<TASK-ID>/task.json`으로 관리한다.

```md
# Task Packet
- Role ID:
- Task ID:
- Requirement IDs:
- Baseline commit SHA:
- Current AGENTS.md blob/content hash:
- Applicable invariant / decision IDs:
- Goal:
- In scope:
- Out of scope:
- Current AGENTS.md version:
- Relevant human decisions:
- Applicable VERIFIED Learning IDs:
- Excluded / RETIRED Learning IDs and reason:
- Domain invariants:
- Shared artifact paths (공동 편집 대상):
- Read-only reference paths (정책·설계 기준):
- Read-only evidence paths (테스트·증거):
- Excluded paths:
- Upstream dependencies:
- Required outputs:
- Required tests/evidence:
- Known risks:
- Questions requiring human decision:
```

### 5.3 공동 산출물 인계 턴

역할마다 별도의 인계 문서를 만들지 않는다. 아래 내용을 같은 작업의 `collaboration.md` 끝에 새
턴으로 추가하고, 다음 역할은 공식 공동 산출물과 이 대화 장부를 함께 읽는다. 비-Fable 턴은
`Get-Content -Raw .\turn.md | corepack pnpm fable:append -- --task TASK-ID`처럼 공통 append 명령으로만
추가한다. 이 명령과 Fable 검수 명령은 같은 task lock을 공유하므로 동시에 실행하지 않는다.

턴 형식은 [`ai-review/templates/collaboration.md`](./ai-review/templates/collaboration.md)를 단일
템플릿으로 사용한다. `SOLAR_REQUEST`, `FABLE_REVIEW`, `SOLAR_RESPONSE`, `CODEX_EVIDENCE`,
`HUMAN_DECISION`, `FABLE_RECHECK`, `BACKLOG_DISPOSITION`, `AI_DEPUTY_GATE_DECISION`을 구분하며
모든 응답에 앞선 turn/review hash, 대상 artifact hash, Finding별 disposition, 변경 경로, 실행
증거와 다음 요청을 연결한다. 마지막 턴만 task/gate 종결을 선언할 수 있으며 페이블 `PASS`만으로는
대체할 수 없다.

### 5.4 분리 규칙

1. 개발 컨텍스트를 기능 QA에 재사용하지 않는다.
2. 아키텍처와 구현 컨텍스트를 분리한다.
3. 기능 QA에는 개발자의 의도를 최소화하고 공개 명세와 diff를 제공한다.
4. 현장 QA는 블랙박스 수행 후 실패 분석에만 내부 구조를 본다.
5. 페이블 보안 감사와 최종 감사는 서로 다른 새 컨텍스트로 실행한다.
6. 최종 감사에는 과거 논쟁의 결론이나 자기변호를 제공하지 않는다.
7. 정책 버전이 바뀌면 영향받는 작업 패킷을 모두 새로 발행한다.
8. 실제 사용자 데이터는 익명화한 테스트 데이터로 대체한다.
9. 컨텍스트는 분리하되 공식 산출물은 분리하지 않는다. 솔라와 페이블은 같은 요구사항서·설계서·UX 문서·소스를 순차적으로 개선한다.
10. 페이블 원본 검수는 회차별로 보존하고, 수정·반박·검증은 같은 `collaboration.md`의 새 턴과 같은 공식 산출물의 다음 판본으로 남긴다.
11. 이 저장소의 필수·조건부 검수 경로에서는 2026-08-28 사용자 승인에 따라 AI 부 오케스트레이터가 매회 재확인 없이 공식 Claude Code CLI를 호출할 수 있다. 비밀정보·실사용자/운영 데이터·다른 저장소·제품 파일 직접 쓰기·commit/push/배포 권한은 이 승인에 포함되지 않는다.
12. `review.*`, `artifact-snapshot.json`, `input-snapshot.json`, `collaboration-entry.md`, `manifest.json`, `run.json`은 감사·복구 기록이며 편집 가능한 역할별 공식본으로 사용하지 않는다.

### 5.5 페이블→Opus 승계 패킷

대체 호출은 기존 Task의 모델 이름만 바꿔 재실행하지 않는다. 실행기·모델·예산과 실패 run이
불변으로 남도록 새 후속 Task를 만들며, 최소한 다음 값을 봉인한다.

```md
- Fallback reason: MODEL_BUDGET_EXHAUSTED | MODEL_RATE_LIMITED | MODEL_CAPACITY_UNAVAILABLE
- Fallback from task / round / run SHA-256:
- Primary reviewer engine and exact model:
- Fallback reviewer engine and exact model:
- Target commit SHA and artifact hashes:
- Finding registry SHA-256 and inherited finding IDs:
- Allowed / excluded paths:
- Remaining task-wide usage cap:
- Required tests and return-to-Fable sampling rule:
```

모델 변경 전후의 권한은 동일하게 읽기 전용이고, Opus에는 페이블의 숨은 대화나 자기변호를 추가로
주지 않는다. 최종 결과와 상태에는 실제 엔진을 기록한다. `FABLE-SEC`·`FABLE-FINAL`을 Opus가
이어받은 경우 페이블이 복구되면 다음 릴리스 게이트 전 동일 Finding 또는 위험 표본을 다시 감사해
대체 엔진 편향을 측정한다.

### 5.6 팀 성장 히스토리와 학습 승격 루프

업무 원본은 기존 단일 출처에 남긴다. 작업 상태·완료 기록은 `docs/작업큐.md`, 결정은
`docs/team/DECISIONS.md`, 결함·검수 원본은 해당 테스트와 `docs/ai-review/tasks/`, 운영 사고는
`docs/operations/POSTMORTEMS/`가 소유한다. 팀별로 이 원본을 복제한 보고서를 만들지 않는다.

팀의 재사용 가능한 교훈만 `docs/team/TEAM_LEARNING.md` 한 파일에 팀 레인별로 축적한다.

```text
ORCHESTRATION   작업 분해·인계·게이트 운영
SOLAR           PO·아키텍처·DB·Core·App·UX 제작
CODEX           기능·데이터·모바일·현장 QA
INDEPENDENT-AUDIT  Fable·Opus 보안·종합 감사
OPERATIONS      릴리스·복구·관측·고객지원
```

각 학습 항목은 다음 필드를 가진다.

```md
- Learning ID / Team lane / Status: CANDIDATE | VERIFIED | RETIRED
- Source task, decision, finding, test and commit SHA:
- Context and trigger:
- Previous approach and observed result:
- Reusable rule or checklist change:
- Scope and forbidden reuse:
- Validation evidence and independent verifier:
- Promotion target: task packet | test | template | runbook | canonical policy
- Owner, review date and invalidation condition:
- Reuse count, outcome and regressions:
```

성장 루프는 다음 순서를 지킨다.

```text
업무·실패·성공의 원시 증거
→ 팀 회고에서 CANDIDATE 작성
→ 반대 역할이 재현성·과잉 일반화 검토
→ 두 번째 작업 또는 회귀시험에서 효과 확인
→ VERIFIED 승격
→ 다음 관련 Task Packet에 Learning ID 주입
→ 테스트·템플릿·런북 또는 기존 공식 정책에 반영
→ 재사용 결과 측정
→ 환경·정책 변경 시 재검증 또는 RETIRED
```

`TEAM_LEARNING.md`는 정책과 제품 명세의 대체본이 아니다. 공식 규칙을 바꾸는 교훈은 사람 결정과
기존 권위 문서의 같은 주제 절에 반영돼야 효력이 생긴다. 근거 없는 채팅 요약, 모델의 자기평가,
개인정보·비밀정보, 운영 원문은 학습 항목으로 승격하지 않는다. 독립 종합 감사의 최초 회차에는
결론 편향을 막기 위해 학습 요약을 입력하지 않고, 승인된 명세·소스·원시 증거만 제공한다.

AI 부 오케스트레이터는 매 5개 완료 Task 또는 주요 게이트마다 먼저 도래한 시점에 학습 검토를
열고, 오래된 항목·서로 충돌하는 항목·재사용 뒤 악화된 항목을 `RETIRED` 또는 재검증 대상으로
돌린다. 팀의 성장은 문서량이 아니라 반복 결함 감소, 첫 재검수 통과율, 재작업 회차, 복구 시간과
검증된 학습 재사용 성공률로 측정한다.

## 6. 작업 수명주기와 품질 게이트

### 1인 운영의 R0·R1 통합 착수 게이트

사람이 1명인 운영에서 R0·R1 작업은 G0·G1·G2를 `통합 착수 패킷` 하나로 합치고 사람 승인도 한 번만 받는다. 이는 증거를 생략하는 제도가 아니라 세 게이트의 증거를 한 패킷에서 동시에 확인하는 제도다.

통합 패킷에는 다음을 모두 포함한다.

- G0의 목표·범위·기준선·영향 불변식
- G1의 요구사항·인수 조건·예외·복구 정책
- G2의 설계·의존성·호환·롤백 계획
- 변경 위험 등급과 판정 근거
- G3 이후의 필수 검증 계획

반복형 R0는 승인된 패킷 템플릿 안에서 AI 부 오케스트레이터가 종결하고 사람은 L0 규칙에 따라 표본 감사한다. R1은 사람의 통합 패킷 승인 한 번을 받는다.

진행 중 범위·정책·공식·DB/RPC/RLS·운영 데이터 영향이 새로 생기면 통합 승인은 즉시 무효가 되고 R2·R3로 재분류한다. G3 이후 실행 증거, QA, 보안 감사와 프로덕션 배포 승인은 이 조항으로 생략할 수 없다. R2·R3는 G0·G1·G2를 각각 적용한다.

- 동일 `head_sha`의 GitHub Actions `verify` run URL과 Node 20.19.4·24 matrix 전체 성공

로컬 `pnpm verify`는 DB 시험·새 DB·업그레이드 경로를 포함한 전체 검증이고, GitHub Actions는 `pnpm verify --no-db`로 Linux·Node matrix를 보완한다. CI 성공은 로컬 6/6을 대체하지 않는다. 현행 `pnpm verify`에는 `pnpm lint`가 포함되지 않으므로 이 문서는 lint 통과를 verify 결과라고 주장하지 않는다. lint를 공식 단일 게이트에 포함하기로 결정하면 별도 수동 명령을 늘리지 말고 `scripts/verify.mjs`에 편입한다.

판정: AI 부 오케스트레이터가 SHA 일치, 로컬 6/6과 CI 2/2를 확인한다. skip, 미실행, 다른 SHA, 진행 중 CI 또는 검증 후 파일 변경은 통과가 아니라 `환경 미검증`이다.

## 7. 결함과 장애 관리

### 7.1 결함 심각도

| 등급 | 정의 | 예시 | 출시 처리 |
|---|---|---|---|
| Blocker | 테스트·영업 불가능 또는 광범위한 데이터·보안 위험 | 앱 실행 불가, 매장 간 노출, 대량 원장 훼손, 롤백 불가 | 즉시 동결, 수정 후 전체 재검증 |
| Critical | 핵심 확정값 오류 또는 복구 곤란 | 중복 입고, 단가·손익 오류, 부분 커밋, 권한 우회 | 미해결 출시 금지 |
| Major | 핵심 업무는 가능하지만 반복 실패·우회 필요 | 입고 중단 후 복귀 불가, 중요한 오표시 | 원칙적으로 수정, 예외는 사람 승인 |
| Minor | 비핵심 불편·시각·카피 문제 | 정렬, 보조 문구, 제한적 화면 깨짐 | 담당·기한을 정해 출시 가능 |
| Improvement | 현재 요구 충족 후의 개선 | 터치 수 단축, 추가 자동화 | v1.1로 분리 |

### 7.2 결함 상태

```text
OPEN
→ EVIDENCE_READY
→ TRIAGED
→ OWNER_ASSIGNED
→ FIX_READY
→ RECHECK
→ RESOLVED
```

예외 상태:

- `ACCEPTED_RISK`: 사람만 지정 가능
- `DUPLICATE`: AI 부 오케스트레이터가 증거를 연결해 지정 가능
- `NOT_REPRODUCED`: 환경·재시도 기록 필요
- `OUT_OF_SCOPE`: 사람 승인 필요

이 `defect_state`는 §4.4의 `review_state` 및 Claude CLI의 `run_state`와 별도다. 예를 들어 CLI가
`RESULT_RECEIVED`여도 finding은 `OPEN`일 수 있고, 코드 수정이 `FIX_READY`여도 최초 발견 역할의
재검수 전에는 `CLOSED`가 아니다.

### 7.3 필수 결함 증거

- Finding ID와 요구사항 ID
- 환경·기기·앱/DB 버전
- 사전 조건과 테스트 데이터
- 재현 절차
- 기대 결과와 실제 결과
- 로그·화면·DB 전후값
- 영향 범위와 심각도
- 임시 우회 방법
- 수정 담당자
- 필수 회귀 테스트
- 재시험 결과

### 7.4 운영 장애 등급

| 등급 | 예시 | 기본 대응 |
|---|---|---|
| S0 | 매장 간 데이터 노출, 대규모 손상, 계정 탈취 | 즉시 확산 차단·사람 호출·배포 중지 |
| S1 | 입고·재고·원가 오염, 핵심 흐름 전체 중단 | 긴급 복구·영향 범위·사용자 안내 |

장애 처리 순서:


서비스가 다시 열렸다고 데이터 복구가 완료된 것은 아니다. 두 상태를 별도로 관리한다.

## 9. 오픈 전후 운영 전환

### 9.1 디렉터리 재구성 단계

팀 운영 모델을 처음 적용하는 시험 작업으로 사용한다.

#### 진행 중 브랜치 경과 규정

이 운영안 확정 전에 시작된 `codex/refactor-domain-boundaries` 브랜치를 디렉터리 재구성 파일럿 1차 묶음으로 소급 인정한다. 채택 시점의 base SHA와 head SHA, `businessDay`의 `features/business-day/` 이동, `HistoryLayout`의 `components/history/` 이동 등 실제 diff와 요구사항→설계→코드→테스트 연결을 `docs/작업큐.md`의 해당 작업 항목에 기록한다.

이미 완료된 이동을 게이트 순서에 맞추기 위해 되돌리거나 다시 수행하지 않는다. 대신 1차 묶음은 정확한 head SHA를 대상으로 다음 증거를 소급 수집한다.

- G3: 옵션 없는 `pnpm verify` 전체 결과와 동일 SHA의 GitHub Actions `verify` 결과
- G4: 동작 동등성, 도메인 경계 테스트와 이전 경로 잔존 검사
- 변경 전·후 import와 public API 대응
- 구조 변경에 기능 변경이 섞이지 않았다는 diff 근거

증거가 완성되기 전 상태는 `구현 완료·증거 대기`이며 파일럿 완료로 처리하지 않는다. 2차 이동 묶음부터는 적용 가능한 G0~G4를 순서대로 적용한다. 소급 검증에서 기능 변화가 발견되면 별도 요구사항과 별도 diff로 분리한다.

1. AI 부 오케스트레이터가 현재 디렉터리, import, 화면 ID, RPC 의존성을 목록화한다.
2. 솔라 아키텍처가 목표 경계와 이동 순서를 제안한다.
3. Codex 기능 QA가 이동 전 타입·테스트·E2E 기준선을 고정한다.
4. 페이블이 경계 누락과 순환 의존성 위험을 감사한다.
5. 솔라 개발이 DB → Core → 공통 UI → feature → route처럼 작은 묶음으로 이동한다.
6. 각 묶음 뒤 Codex가 동작 동등성과 이전 경로 잔존을 검사한다.
7. 기능 추가는 별도 요구사항과 변경으로 분리한다.
8. 최종적으로 페이블 클린 감사를 수행하고 사람이 구조를 확정한다.

완료 기준은 파일 이동량이 아니라 기존 데이터 동작 유지와 의존성 방향의 명확성이다.

## 11. 필수 운영 문서 구조

작업·담당·상태·차단 사유와 요구사항→설계→코드→테스트 연결은 기존 권위 문서
`docs/작업큐.md` 하나에서 관리한다. 이를 복제하는 `TASK_BOARD.md`나 역할별 추적 문서를 새로
만들지 않는다. 새 운영 문서는 기존 권위 문서와 주제 중복 여부를 먼저 매핑하고, 소유 문서가 없는
주제만 다음처럼 추가한다.

```text
docs/team/
├─ DECISIONS.md           사람 승인 정책·설계 결정
├─ RISKS.md               제품·데이터·보안·운영 위험
├─ RELEASE_GATE.md        릴리스별 증거·승인 인스턴스
├─ ROLE_CONTEXTS.md       현재 활성 역할/컨텍스트 ID·version·hash 레지스트리
└─ TEAM_LEARNING.md       팀 레인별 검증된 교훈·재사용·폐기 단일 장부
```

오픈 준비 단계에서 추가한다.

```text
docs/operations/
├─ RUNBOOK_RELEASE.md
├─ RUNBOOK_INCIDENT.md
├─ RUNBOOK_RECOVERY.md
├─ DATA_CORRECTION_POLICY.md
├─ MONITORING_CATALOG.md
├─ SUPPORT_PLAYBOOK.md
├─ PILOT_PLAN.md
└─ POSTMORTEMS/
```

AI 부 오케스트레이터가 문서를 갱신하지만 정책 결정과 위험 수용 항목에는 사람 승인자와 날짜를 기록한다.

`docs/team/`과 `docs/operations/`는 역할별 보고서 묶음이 아니라 주제별 단일 출처다. 같은 주제에
솔라본·페이블본·수정본을 따로 만들지 않고, 모든 역할이 같은 공식 파일에 제안·반영·검증 이력을
연결한다. `RELEASE_GATE.md`는 이 기획안의 게이트 정책을 복사하지 않고 릴리스별 적용 증거와 승인만,
`ROLE_CONTEXTS.md`는 역할 설명을 복사하지 않고 실제 활성 컨텍스트 식별자와 판본 hash만 기록한다.
`TEAM_LEARNING.md`는 작업 원본이나 정책을 복사하지 않고 Learning ID, 원본 증거 링크, 승격 상태,
재사용 결과와 폐기 조건만 기록한다.

솔라·페이블 공동 작성과 검수 원본은 다음 구조로 추가 운영한다.

```text
docs/ai-review/
├─ README.md               공동 작성·CLI·보존 규격
├─ templates/              작업·공동 대화 장부 템플릿
└─ tasks/<TASK-ID>/
   ├─ task.json            역할·범위·판본 계약
   ├─ collaboration.md     솔라↔페이블↔Codex 단일 상호작용 장부
   ├─ status.json          최신 상태
   └─ rounds/rNNN/         불변 manifest·원본 검수·실행 증거
```

`rounds`의 검수 파일은 감사 원본이고, 역할별 최종 산출물이 아니다. 최종 산출물은 항상 기존
`docs/`, 소스와 테스트 경로의 하나의 공동 파일이다.

## 13. 도입 순서

### 1주차: 거버넌스 기준선

1. 사람 주 오케스트레이터와 승인 대리자 지정
2. 역할 컨텍스트 생성과 금지 권한 입력
3. 기존 `docs/작업큐.md`에 담당·상태·차단·추적 필드를 적용하고, 주제 소유 문서가 없을 때만 `DECISIONS`, `RISKS`, `ROLE_CONTEXTS` 생성
4. 현재 기준 SHA의 `AGENTS.md` hash와 적용 불변식·결정 ID를 모든 역할 입력에 고정
5. 현재 SHA의 `pnpm verify`·동일 SHA GitHub Actions 상태와 화면·RPC·미검증 기준선 기록

### 2주차: 디렉터리 재구성 파일럿

1. 현재 import·라우트·RPC·이벤트 지도 작성
2. 목표 경계와 단계별 이동안 승인
3. 이동 전 회귀 기준 고정
4. 작은 파일 묶음 단위 구현·QA·재검증
5. 페이블 구조 감사와 사람 확정

### 3주차: 품질 조직 정착

1. 기존 60개 시나리오를 테스트 ID로 변환
2. 현재 `AGENTS.md`에서 추출한 불변식·결정 ID를 DB/Core 양측 테스트와 추적
3. 24시간 현장 시나리오 초판 실행
4. 결함 등급과 증거 템플릿 적용
5. 보안 감사와 최종 감사 입력 번들 시험

### 4주차 이후: 오픈 후 실사용 검증·운영 준비

1. 오픈 후 검증에 참여할 3~5개 초기 사용자·매장 후보 확보
2. 오픈 후 시작할 섀도 모드와 1일·7일·30일 계획 수립
3. 릴리스·장애·복구 런북 작성
4. 모의 릴리스와 백업 복원 훈련
5. 관측 지표와 사람 호출 기준 시험

## 14. 예상 실패 패턴과 예방책

| 실패 패턴 | 예방책 |
|---|---|
| 솔라가 작성하고 같은 컨텍스트에서 승인 | 개발·QA·오케스트레이션 컨텍스트 분리 |

| 전체 저장소 번들로 피상적 감사 | 작업 단위 diff 감사 + 최종 클린룸 번들 감사 |
| AI가 과거 정책을 현재 정책으로 사용 | 매 작업 패킷에 현재 `AGENTS.md` 버전 포함 |
| 현장 AI 시뮬레이션을 실제 사실로 간주 | 가설/검증됨 상태 분리, 오픈 후 실제 사용자 확인 |
| 구조 변경에 기능 추가가 섞임 | 별도 요구사항·diff·게이트로 분리 |
| 테스트 수치로 핵심 실패를 가림 | 핵심 불변식·E2E는 별도 100% 게이트 |
| v1.1 아이디어가 출시를 지연 | 결함과 Improvement 섹션 분리 |
| 서비스 복구를 데이터 복구로 착각 | 서비스 상태와 데이터 정합성 상태 별도 관리 |
| 사람 1명에게 승인·배포·복구가 집중 | R3 두 번째 검토자와 외부 복구 연락망 확보 |
| 페이블 소진을 검증 실패와 혼동해 Opus로 우회 | 소진 사유 allowlist와 불변 후속 Task 승계, 인증·hash·계약 오류는 원인 수정 |
| Opus 결과를 페이블 결과로 표기 | 실제 reviewer engine·모델·run hash를 상태와 보고서에 명시 |
| 팀별 채팅 요약이 새 정책처럼 굳음 | 증거 기반 `TEAM_LEARNING.md`와 CANDIDATE→VERIFIED→RETIRED 승격 루프 |
| 오래된 성공 공식을 계속 재사용 | review date·무효화 조건·재사용 결과를 확인하고 재검증 또는 RETIRED |

## 16. 최종 운영 선언

> AI 부 오케스트레이터는 흐름과 기록을 통제한다. 솔라는 제품을 기획·설계·구현하고 출시를 준비한다. Codex는 기능 정확성과 실제 영업 생활 속 사용 가능성을 증명한다. 페이블은 보안과 전체 산출물의 맹점을 공격한다. 실제 사장님과 셰프는 AI의 현장 가설을 현실에서 검증한다. 사람 주 오케스트레이터는 정책, 데이터, 위험, 배포와 복구의 최종 책임을 가진다.
