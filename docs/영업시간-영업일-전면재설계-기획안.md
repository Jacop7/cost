# 영업시간 · 영업일 전면 재설계 기획안

> 작성일: 2026-08-23  
> 범위: 기획 및 프로토타입. 앱·서버·DB 실제 구현은 포함하지 않는다.  
> 검토 원본: `docs/영업시간-로직-현황-기획서.md`, MY-09, 매출관리 영업 상태 UI, DB 0047~0057.

## 1. 결론

현재 문제는 영업시간 화면 하나가 불편한 것이 아니다. 아래 네 개가 하나의 `business_day()`와 수동 상태 버튼에 섞여 있다.

1. 매장 현지 달력 날짜
2. 판매 장부의 영업일
3. 그날 손익 기준값 스냅샷
4. 영업 상태와 지난 판매 입력 가능 기간

전면 재설계의 핵심은 다음과 같다.

- `business_day()`를 전역 날짜 함수로 쓰지 않는다.
- 일반 기록 날짜와 판매 영업일을 분리한다.
- 매출 화면에는 `영업 시작`, `영업 종료`, `브레이크 타임`, `영업 재개`만 두고 `다시 열기`는 제거한다.
- 판매 장부는 예정 영업 시작 또는 첫 판매 시 서버가 자동으로 준비한다.
- 영업 상태는 `영업 전`, `영업 중`, `브레이크 중`, `영업 종료` 네 단계로 관리한다. 다만 자동 종료된 영업일은 회색 상태 뱃지에 `자동 영업종료`로 표시해 직접 종료와 구분한다.
- 브레이크 타임은 영업시간 설정에 포함해 자동 판정하고, 필요하면 영업 중 `브레이크 타임` 버튼으로 직접 전환할 수 있다. 판매 기록은 막지 않는다.
- 영업 종료와 판매 기록 가능 여부를 분리한다. 종료된 날도 지난달 1일부터 오늘까지 판매를 추가·수정할 수 있다.
- 종료된 장부 수정은 “다시 열기”가 아니라 감사 기록이 남는 장부 정정으로 처리한다.
- 영업시간 변경은 버전으로 저장해 이미 시작된 영업일과 과거 날짜를 바꾸지 않는다.
- 앱은 날짜와 상태를 계산하지 않고 서버가 준 `business_context`만 표시한다.

## 2. 현 구현에서 확인된 구조적 문제

### 2.1 앱과 DB가 서로 다른 오늘을 계산한다

- 앱 `todayBusiness()`는 `@sikjae/core`의 KST 자정 기준 날짜를 사용한다.
- DB `business_day()`는 자정을 넘는 매장일 때 `close_time`을 경계로 사용한다.
- 예: 10:00~02:00 매장에서 01:00은 앱에서는 다음 날짜, DB에서는 전날 영업일이다.
- 매출 화면이 다음 날짜로 저장을 요청하면 이미 열린 전날 장부를 찾지 못해 시작 오류 또는 날짜 불일치가 발생할 수 있다.

확인 위치:

- `packages/core/src/businessDate.ts`
- `apps/mobile/src/features/sales/period.ts`
- `packages/db/supabase/migrations/20260820000047_business_hours.sql`

### 2.2 영업시간을 수정하면 과거 날짜 해석도 바뀐다

`business_cutoff()`가 매 호출마다 현재 `settings.close_time`을 다시 읽는다. 기존 `business_days.business_date`는 그대로인데 함수의 날짜 판정만 바뀐다.

결과:

- 이미 저장된 장부 날짜와 새 조회 날짜가 어긋난다.
- 입고·발주·추이처럼 판매 영업일이 아닌 데이터까지 영향을 받는다.
- 현재 열려 있는 영업일의 `planned_close_at`은 옛 값인데 상태 RPC의 `hours`는 새 값을 표시할 수 있다.

### 2.3 전역 함수가 매장을 모른다

`business_cutoff()`와 `business_day()`는 `store_id`가 없고 `settings limit 1`을 사용한다. 저장소 원 기획안은 1매장 가드만 추가하려 했지만, 글로벌 앱의 기반 로직으로는 유지하면 안 된다.

### 2.4 자동 마감이 앱 실행에 의존한다

`close_if_due()`는 앱이 상태를 조회할 때 60초 간격으로 호출한다.

- 앱을 열지 않으면 마감 처리가 실행되지 않는다.
- 판매 RPC 자체는 마감 예정 시각이 지났는지 확인하지 않는다.
- 조회와 판매 저장 사이에 상태가 바뀌는 경쟁 조건이 있다.
- 자동 마감 시각이 지나도 열린 행이면 판매를 계속 받을 수 있다.

### 2.5 자동 마감 시각이 계속 밀린다

현재는 `max(예정 종료, 마지막 활동 + 1시간)`이다. 판매를 계속 입력하면 마감이 끝없이 밀린다. 브레이크 버튼도 `last_activity_at`을 갱신해 마감을 미룬다.

### 2.6 기존 브레이크는 설정과 상태가 연결되지 않는다

- 설정한 `break_start/break_end`는 판매를 제한하거나 알리지 않는다.
- `set_break(true)` 상태에서도 판매 RPC는 판매를 허용한다.
- 브레이크 버튼은 자동 마감만 늦출 수 있다.
- 기존 버튼 로직은 제거하고, 설정 시간 자동 전환과 사용자 직접 전환이 동일한 서버 상태 규칙을 사용하도록 다시 설계해야 한다.

### 2.7 수동 시작이 사용자의 계산 책임이 됐다

사용자는 판매를 입력하려다가 “오늘 값을 굳힐까요?”라는 내부 데이터 구조 설명을 먼저 이해해야 한다. 스냅샷은 시스템이 지켜야 할 회계 규칙이지 사용자가 매일 눌러야 할 업무가 아니다.

### 2.8 과거 장부를 다시 여는 방식이 현재 영업과 충돌한다

현재 `reopen_business_day()`는 과거 장부를 다시 `open` 상태로 바꾼다.

- 현재 영업일이 열려 있으면 과거 장부를 고칠 수 없다.
- 과거 장부가 열린 동안 오늘 장부가 막힌다.
- 자동 마감 규칙과 과거 수정 시간이 충돌한다.
- 장부 수정과 실제 영업 상태가 같은 상태 기계를 공유한다.

### 2.9 복합 전이가 원자적이지 않다

앱의 `useCloseStaleAndOpen()`은 마감 RPC와 시작 RPC를 두 번 호출한다. 마감 성공 후 시작 실패가 발생하면 중간 상태가 그대로 남는다.

### 2.10 예상 가능한 상태를 한국어 오류 문장으로 판별한다

앱은 `아직 영업을 시작하지 않았어요`, `영업은 종료됐어요` 문자열을 포함하는지 검사한다. 서버 문구를 수정하거나 번역하면 분기가 깨진다.

### 2.11 서버 검증이 화면 검증보다 약하다

- 서버는 시작과 종료가 같은지만 막는다.
- 브레이크 시작·종료 쌍, 영업시간 안 포함 여부, 24시간 경계 충돌을 보장하지 않는다.
- 시간 선택은 48칸 그리드라 모바일에서 탐색 비용이 크다.

## 3. 기존 기획안에서 유지할 것과 바꿀 것

### 유지

- 영업일 경제 스냅샷: 오늘 판매가·재료비·부자재·고정지출·세금은 하루 동안 고정한다.
- 예정 영업 종료 시각은 판매 활동으로 계속 밀리지 않게 한다.
- 자동 종료의 `ended_at`은 앱을 연 시각이 아니라 **계산된 자동 마감 기한**을 기록한다.

  > **확정(2026-08-26, 마이그레이션 0137~0139)** — 세 시각을 구분한다.
  >
  > | 값 | 뜻 |
  > |---|---|
  > | `planned_close_at` | 영업시간의 종료 시각. 그날 규칙으로 영업 시작 때 고정된다 |
  > | 자동 마감 기한 | `planned_close_at + auto_close_grace()`(1시간, **고정**). 활동을 따라가지 않는다 |
  > | `closed_at` | 자동은 **자동 마감 기한**, 수동은 잠금을 얻은 그 시각(`clock_timestamp()`) |
  >
  > `closed_at`을 `planned_close_at`으로 적으면 장부에 모순이 생긴다 —
  > 유예 시간(22:00~23:00) 판매를 받아들이면서 종료를 22:00으로 적는 셈이다.
  > 화면의 `자동 종료 11:00–22:00`(§6.1)은 `closed_at`이 아니라 `planned_close_at`으로 그린다.
  > **두 값은 뜻이 다르다.**
- 기록 없는 과거 날짜는 현재 기준 추정이라는 사실을 저장 전에 알린다.

### 변경

- 1매장 가드로 전역 `business_day()`를 유지하지 않는다. 모든 날짜 판정을 매장·시간대 기반으로 바꾼다.
- `열린 날이 오늘`이라는 예외 규칙을 앱에 추가하지 않는다. 서버가 `active_business_day_id`를 직접 준다.
- 과거 장부를 `reopen`하지 않는다. 닫힌 상태를 유지한 채 정정 이벤트를 기록한다.
- 기존 `set_break()` 구현은 제거하고, 자동·직접 브레이크가 같은 상태 전이와 감사 기록을 사용하도록 교체한다.
- 앱 조회가 영업 종료 실행 주체가 되지 않는다.
- `영업 종료`를 판매 입력 잠금으로 사용하지 않는다. 입력 가능 기간은 매장 현지 날짜 기준으로 별도 계산한다.

## 4. 새 도메인 정의

### 4.1 매장 현지 날짜 `store_local_date`

발주·입고·재고·가격 추이·손익 추이의 날짜다.

- 입력: `store_id`, `occurred_at`
- 기준: 매장 IANA 시간대
- 영업 종료 시각과 무관하다.
- 예: 서울 매장 01:00 입고는 현지 달력의 오늘 입고다.

### 4.2 판매 영업일 `sales_business_day`

판매 장부 한 장을 가리키는 식별자다.

- 날짜를 클라이언트가 시간으로 역산하지 않는다.
- 서버가 현재 활성 영업일 ID와 표시 날짜를 함께 반환한다.
- 새벽 영업 중이면 `business_date`는 전날일 수 있다.
- 모든 판매·당일 추가 지출·판매 폐기는 `business_day_id`를 권위값으로 사용한다.

### 4.3 경제 기준 `day_basis`

해당 영업일의 판매가·원가·세금·고정지출 스냅샷이다.

- 영업일이 준비될 때 한 번 생성한다.
- 생성 이후 수정하지 않는다.
- 영업 중 새 메뉴를 처음 판매하면 해당 메뉴 기준만 추가하며 기존 항목은 바꾸지 않는다.

### 4.4 영업시간 규칙 `operating_rule`

요일별 영업시간·브레이크 타임과 시간대의 버전이다.

- `effective_from`을 갖는다.
- 영업시간을 수정해도 과거 규칙은 남는다.
- 영업일은 생성 당시 적용 규칙 ID와 계산 시각을 저장한다.

## 5. 사용자 경험 원칙

1. 사용자는 스냅샷을 시작하지 않는다. 첫 판매 또는 예정 시작 시 서버가 준비한다.
2. 화면은 `영업 전`, `영업 중`, `브레이크 중`, `영업 종료` 상태만 사용한다. 자동 종료된 경우에는 종료 상태의 표시 문구만 `자동 영업종료`로 바꾼다.
3. 모든 영업 상태 카드 상단 좌측에는 영업일을 공통 노출하고, 우측에는 현재 가능한 상태·행동을 배치한다.
4. 예정 종료는 정상 동작이므로 매일 확인 배너를 띄우지 않는다.
5. 과거 매출 입력은 오늘 영업 상태와 독립적으로 접근하며 `현재 월 + 직전 월`만 허용한다.
6. 날짜는 서버 응답을 그대로 사용한다. 앱이 자정·종료 시각으로 다시 계산하지 않는다.
7. 내부 용어인 스냅샷·cutoff·stale day는 사용자 문구에서 제거한다.
8. `기록 가능`은 사용자 상태가 아니라 서버 권한값이다. 날짜 선택 화면에서 허용 범위로만 표현한다.

## 6. 새 화면 흐름

### 6.1 매출관리 상단 상태

#### 영업 전

- 상태: `영업 전`
- 행동: `영업 시작`
- 판매 입력은 영업 시작 전에도 가능하며 선택 날짜가 허용 기간 안인지 서버가 검증한다.

#### 영업 중

- 상태: `영업 중`
- 카드 상단 좌측에는 영업일 `8월 24일 (월)`, 우측에는 현재 상태 `영업 중⌄` 셀렉터를 표시한다. 날짜는 굵게, 요일은 보조 텍스트로 표시한다.
- 셀렉터는 카드 상단 우측에 파란색 채움·흰색 텍스트로 표시한다.
- 누르면 하단 메뉴에 1번 `브레이크 타임`, 2번 `영업 종료`를 노출한다.
- `브레이크 타임`은 즉시 적용하고, `영업 종료`는 확인 후 직접 종료 상태로 이동한다.

#### 브레이크 타임

- 상태: `브레이크 중`
- 카드 상단 좌측에는 영업일, 우측에는 `브레이크 중⌄` 셀렉터를 표시한다.
- 하단 메뉴: 1번 `영업 재개`, 2번 `영업 종료`

#### 영업 종료

- 직접 종료 상태: `영업 종료`
- 자동 종료 상태: `자동 영업종료`
- 카드 상단 우측에 연한 회색 배경의 상태 뱃지로 표시한다.
- 상태 카드에는 추가 행동 버튼을 노출하지 않는다.
- 영업일 옆에는 실제 시작–종료 시간을 표시한다.
- 별도의 종료 원인 설명 문장은 노출하지 않는다. 직접 종료와 자동 종료는 상태 뱃지와 기록 데이터로 구분한다.

상태 카드 공통 규칙:

- 모든 상태에서 설명 문구·브레이크 시간·종료 원인 문구를 제거한다.
- 카드에는 `영업일 + 시간 + 상태/행동` 한 줄만 노출한다.
- 영업 전·영업 중·브레이크 중에는 예정 영업시간을 표시한다.
- 영업 종료에는 실제 시작–종료 시간을 표시한다. 예: 직접 종료 `11:00–21:30`, 자동 종료 `11:00–22:00`.
- 종료 원인을 설명하는 별도 문장은 노출하지 않는다.

### 6.2 영업시간 설정

- 화면은 `요일 설정`, `시간 설정` 두 영역만 노출한다.
- 요일 설정은 월~일 체크 방식으로 제공하며 선택하지 않은 날은 휴무로 본다.
- `매일 동일/요일별 설정` 모드 선택은 제거한다.
- `영업 시작 + 영업 종료`는 `영업시간 11:00–22:00` 한 행으로 묶고 하나의 팝업에서 함께 수정한다.
- `브레이크 타임`은 영업시간 아래의 별도 행과 별도 팝업으로 유지한다.
- 사용자는 영업 시작·종료 시각만 입력한다. 종료 시각이 시작 시각보다 이르면 서버가 다음 날 종료로 자동 판정한다.
- `오늘 / 다음 날` 선택 컨트롤은 제공하지 않고 결과만 `18:00–다음 날 02:00`처럼 표시한다.
- 시간 선택기는 앱에서 선택한 언어·로케일의 12/24시간 표기와 순서를 따른다.
- 언어는 표시 형식만 바꾸며 시간 계산 기준은 별도 매장 시간대를 사용한다. 매장 시간대는 이 화면에 반복 노출하지 않는다.
- 48칸 시간 그리드는 제거하고 네이티브 모바일 시간 선택기를 사용한다.
- 분 단위는 15분 단위 기본, 직접 입력을 허용한다.
- 브레이크 타임은 `사용/사용 안 함`, 시작, 종료를 설정한다.
- 1차는 선택한 모든 요일에 같은 영업시간과 브레이크 한 구간을 적용한다. 요일마다 서로 다른 시간 설정은 이후 범위로 둔다.
- 브레이크 타임은 해당 영업 구간 안에 있어야 하며 영업 시작·종료와 같거나 구간 밖이면 저장하지 않는다.
- 브레이크 시각도 같은 영업 구간 안에서 자동 해석한다. 자정 이후이면서 영업 시작 시각보다 이른 시각은 다음 날로 계산한다.
- `지난 판매 입력`은 영업시간 설정에서 삭제한다. 허용 기간은 판매 날짜 선택 화면에서만 안내한다.

### 6.3 설정 저장 결과

활성 영업일이 있으면:

> 오늘 영업일은 기존 시간으로 유지돼요. 새 영업시간은 다음 영업일부터 적용됩니다.

활성 영업일이 없고 오늘 시작 전이면 즉시 적용한다.

### 6.4 과거 매출 수정

- 입력 가능 범위는 매장 현지 날짜 기준 `지난달 1일~오늘`이다.
- 예: 2026년 8월 24일에는 7월 1일~8월 24일을 선택할 수 있다.
- 종료된 장부를 다시 열지 않는다.
- 판매 기록이 있는 날짜의 매출 상세 하단에는 `판매 내역 수정`을 표시한다.
- 판매 기록이 없는 날짜에는 중앙에 `판매 내역이 없습니다.`만 표시하고 하단에 `판매 내역 추가`를 표시한다.
- 추가·수정 화면 상단에는 `영업일`만 표시한다. `판매 채널 · 매장`처럼 채널을 고정하는 행은 두지 않는다.
- 메뉴 행에는 메뉴명과 현재 판매 수량만 표시한다. `판매가 · 재료비` 보조 문구는 표시하지 않는다.
- 메뉴의 `+ 판매`를 누르면 `매장 · 배달 · 포장` 중 판매 채널을 선택한다.
- 기존 판매 수정에서는 메뉴별·채널별 수량을 늘리거나 줄일 수 있어야 한다.
- `기타 매출`, `지출 추가`는 기존 매출 입력 흐름과 같은 입력 UI를 사용한다.
- 정정 RPC는 기존 `day_basis`로 수량과 금액을 다시 계산한다.
- 저장 후 판매 수량·매출 합계·채널별 매출·손익을 다시 조회해 매출 상세에 즉시 반영한다.
- 변경 전후 값과 사용자·시각을 감사 이벤트로 남긴다.
- 현재 영업일은 계속 열린 상태를 유지한다.
- 실제 판매일과 입력·수정한 시각을 별도로 기록한다.

기록이 없는 과거 날짜는 빈 화면에서 경고 카드를 먼저 노출하지 않는다. 사용자가 판매 내역을 입력하고 저장할 때 다음 확인을 노출한다.

> 당시 기록이 없어 현재 판매가와 원가를 기준으로 저장해요.

진행한 경우 `basis_quality = estimated_current`를 영구 저장한다. 정상 장부처럼 조용히 섞지 않는다.

#### 과거를 고칠 때 무엇을 기준으로 쓰는가 (0149)

`다시 열지 않는다`만으로는 부족했다. **고칠 때 어느 시점 값을 쓰는지**를 안 정하면
현재 설정이 과거 장부로 새어 들어간다. 실측으로 두 곳이 그랬다.

- **기타 매출 세금은 그날 세율로 매긴다.** 메뉴 세금은 스냅샷의 `recipes[].tax` 로 굳어
  있지만 기타 매출은 굳는 곳이 없어서 현재 세율로 다시 계산됐다 — 저장된 2,636.36원이
  세율을 9.0909%→20% 로 바꾸자 5,800원이 됐다. 사장님은 아무것도 안 고쳤는데 과거
  세금과 손익이 움직였다. 규칙은 셋이다.
  - 기타 매출 **내용이 같으면 계산 자체를 안 한다.** 화면은 고친 칸만 보내지 않고 화면에
    있는 값을 통째로 보내므로, 이 경우가 가장 흔하다.
  - 금액을 고칠 때는 **그날 스냅샷의 `etc_tax_rate`** 로 매긴다.
  - 그날 세율이 기록에 없으면(0149 이전 장부) 현재 세율을 쓰되
    `basis_quality = estimated_current` 로 내린다. 조용히 현재값을 쓰지 않는다.
- **`판매 중지`는 과거 정정에 걸리지 않는다.** 지금 파는지를 묻는 스위치인데 과거에
  실제로 판 기록의 수량 수정까지 막았다 — 제육볶음을 중지하니 3일 전 수량이 안 고쳐졌다.
  과거 정정은 지금 파는지가 아니라 **그날 무엇이 있었는지**를 따른다. 같은 이유로 전역
  `business_day()` 미래 검사도 정정 경로에는 걸지 않는다(정정 RPC 가 이미 매장 현지
  날짜로 걸렀다).
- 그날 기준에 **없던 메뉴**는 `판매 내역 추가` 의 정상 경로다. 종료된 장부에도 더하되
  더한 값은 지금 값이므로 그 장부를 `estimated_current` 로 내린다. 이미 있는 기준은
  정정 경로라도 안 건드린다. 그날에도 없고 지금도 없는 메뉴만 `BASIS_NOT_AVAILABLE`
  (45013)로 돌려보낸다.

#### 정정의 경계 셋 (0150)

`무엇을 기준으로 쓰는가`(0149)를 정하고 나니 **누구 것을, 언제 만드는가**가 남았다.
셋 다 실측으로 재현했다.

- **기준은 그 매장 메뉴만 더한다.** `recipe_snapshot_entry()`는 매장을 안 가리고,
  정정 RPC 는 `security definer` 라 RLS 도 지나간다. 실측: 매장 A 의 과거 장부에 매장 B 의
  메뉴가 판매가 7,777로 저장됐다. `assert_my_store(p_store)` 로는 못 막는다 — 그건
  "이 사람이 이 매장 사람인가"지 "이 메뉴가 이 매장 것인가"가 아니다. 경계를 지킬 곳은
  `add_to_day_basis` 한 곳이고, 남의 매장 메뉴는 `BASIS_NOT_AVAILABLE`(45013)로 거절한다.
- **기준은 바꿀 판매가 있을 때만 더한다.** 그날 기준에 없는 메뉴를 **0개**로 보내면
  수량을 보기도 전에 기준부터 더했다 — 실측: `changed=false` 인데 `basis_quality` 가
  `exact → estimated_current` 로 내려가고 감사 기록은 0건. 합계가 0이고 기존 판매행도
  없으면 `skipped` 로 돌려보내고 기준을 안 만든다.
- **`basis_quality` 가 바뀌었으면 그것만으로도 `changed=true` 다.** 판매 숫자가 그대로여도
  그날 손익을 무엇으로 계산했는지가 바뀌었다. 감사 기록에
  `before_basis_quality → after_basis_quality` 를 남긴다.
- **이미 열려 있던 장부에도 세율을 한 번 굳힌다.** 0149 는 앞으로 만드는 스냅샷만 고쳐서,
  그전에 열린 오늘 장부는 같은 영업일 안에서도 설정을 바꾸면 세금이 따라 움직였다 —
  실측: 1,000원 → 100원(10%), 세율을 20%로 바꾼 뒤 2,000원 → 400원.
  ⚠ **종료된 장부는 안 채운다.** 그날 세율이 얼마였는지 지금은 알 수 없다. 비워 두면
  위 규칙이 `현재 세율 + estimated_current` 로 정직하게 처리한다 — 지금 값으로 채우면
  그게 그날 값인 척하게 되고, 그게 더 나쁘다.

#### 문은 두 겹이고, 채움은 기록을 먼저 본다 (0151)

- **교차 매장 방어는 두 곳에 둔다.** `add_to_day_basis` 하나로는 못 막는다 —
  그날 기준에 그 메뉴가 **이미 있으면** `e10_sale_recorded` 가 그 함수를 아예 안 부른다.
  판매 경로(`e10`)의 첫 문과 기준 함수 안, 두 곳에서 끊는다. 기준 함수에서는 검사를
  `이미 있으면 그대로 둔다` **보다 앞**에 둔다.
  ⚠ **지운 메뉴와 구별한다.** `recipes` 에 아예 없는 것은 안 막는다 — 그날 기준이 남아
  있으면 과거 판매를 계속 고칠 수 있어야 한다. 끊는 것은 **다른 매장 것으로 존재하는**
  경우뿐이다.
- **열린 장부에 세율을 굳힐 때, 기록이 있으면 추측하지 않는다.** 처음에는
  `etc_tax ÷ etc_revenue` 로 되짚었는데, `etc_tax` 는 소수 둘째 자리로 반올림돼
  저장되므로 나눗셈으로 나오는 건 그때 세율이 아니라 **저장된 합계를 재현하는 유효
  세율**이다. 실측: 실제 9.0909%·기타매출 1원 → 세금 0.09원 → 역산 9.0000%,
  그 뒤 10,000원에서 909.09원 vs 900.00원으로 9.09원 어긋난다. 매출이 작을수록 커진다.
  ⚠ `estimated_current` 를 붙여 넘길 수도 없다 — 그건 "현재 기준으로 계산했다"는 뜻이고
  화면 문구도 그렇게 나가는데, 역산 세율은 현재 기준도 아니다. 붙이면 거짓말이 된다.
  규칙은 하나다(0152):
  - 굳은 세율로 그날 기타매출 세금이 **재현되면 그대로 둔다**
  - **재현되지 않으면 마이그레이션이 멈춘다.** 사람이 그날 세율을 확인해 직접 넣는다
  - 기타 매출 기록이 **없는** 열린 장부는 지금 세율을 굳힌다 — 아직 아무것도 안 팔았으니
    추측이 아니다

  ⚠ 이 규칙은 **업그레이드 순서로 검증한다.** 최종 스키마만 보는 시험으로는 못 잡는다 —
  한때 앞 마이그레이션이 역산값을 써 놓고 뒤 마이그레이션이 그 값으로 검사해서
  스스로 통과했다(`0150 → 0151 → 0152`, 실측: mismatch=true 였던 장부가 0151 뒤
  mismatch=false 가 되어 통과). `packages/db/scripts/upgrade-check.sh` 가 그 순서를
  실제로 태워 ① 어긋난 장부는 막히고 ② 멀쩡한 장부는 통과하며 ③ 옛 helper 는 지워지는지
  잰다. `fresh-db.sh --until <14자리>` 로 중간 상태 DB 를 만든다.

### 7.2 서버 함수 분리

#### 날짜

- `store_local_date(p_store, p_at)` — 일반 기록 날짜
- `resolve_sales_business_context(p_store, p_at)` — 판매 장부 상태

#### 상태

- `sync_business_context(p_store, p_at)`
  - 예정 시작 시 필요한 장부를 준비한다.
  - 영업시간과 브레이크 구간을 기준으로 현재 영업 상태를 계산한다.
  - 자동 마감 기한이 지났으면 서버 트랜잭션 안에서 영업 종료를 기록한다.
    ⚠ 구현은 **pg_cron 1분 스윕**(`close_due_business_days`)이다(0137). 앱은 관여하지 않는다.
    판매 저장도 영업일 행을 잠근 뒤 같은 기한을 다시 본다 — `clock_timestamp()`로 본다.
    `now()`는 트랜잭션 시작 시각에 고정돼, 잠금을 기다리는 동안 기한이 지나도 통과한다.
  - 화면 상태와 판매 입력 가능 기간을 한 번에 반환한다.
- `transition_business_state(p_store, p_business_day, p_action)`
  - `start | start_break | resume | end`만 허용한다.
  - 현재 상태에서 가능한 행동인지 서버가 검증한다.
  - 직접 전환 시 사용자·시각·이전 상태·이후 상태를 감사 기록으로 남긴다.

#### 판매

- `save_sales(p_store, p_business_day, ...)`
  - 행 잠금 후 요청 판매일이 `지난달 1일~오늘`인지 다시 검증한다.
  - 영업일이 없고 허용 기간 안이면 원자적으로 장부와 기준값을 생성한다.
  - 영업 종료 상태여도 판매 추가·수정을 허용하고 revision을 남긴다.
  - 허용 기간 밖이면 문자열 예외 대신 안정된 결과 코드를 반환한다.

#### 영업 종료

- `end_business_day(p_store, p_business_day, p_method)`
  - 자동 종료 기간 경과는 `ended_at = scheduled_close_at + auto_close_grace()`(= 자동 마감 기한).
    ⚠ 초안은 `ended_at = scheduled_close_at`이었으나, 유예 시간 판매가 종료 시각보다
    뒤에 남는 모순이 생겨 **기한으로 확정**했다(0138·0139). 화면 표기는 `scheduled_close_at`을 쓴다.
  - 수동 종료는 `ended_at = now()`.
  - 중복 호출은 같은 결과를 반환한다.

#### 과거 정정

- `amend_ended_business_day(p_store, p_business_day, p_changes, p_reason)`
  - 영업 상태를 다시 열지 않는다.
  - 기존 스냅샷으로 재계산한다.
  - revision과 감사 이벤트를 남긴다.

### 7.3 영업 종료와 판매 기록 분리

1. 서버 스케줄러는 예정 종료 대상을 `영업 종료`로 기록한다.
2. 모든 판매 쓰기 RPC는 영업 상태가 아니라 요청 판매일의 허용 기간을 검증한다.
3. 브레이크 타임에는 화면 상태만 바뀌며 판매 저장을 차단하지 않는다.

앱을 열지 않아도 영업 상태는 서버에서 정리되며, 종료된 날짜의 누락 판매는 허용 기간 안에서 감사 기록과 함께 추가할 수 있다.

### 7.4 상태 응답 예시

```json
{
  "business_day_id": "uuid",
  "business_date": "2026-08-23",
  "state": "open",
  "display_state": "open",
  "can_record": true,
  "recordable_from": "2026-07-01",
  "recordable_to": "2026-08-24",
  "scheduled_open_at": "2026-08-23T02:00:00Z",
  "scheduled_close_at": "2026-08-23T13:00:00Z",
  "break_start_at": "2026-08-23T06:00:00Z",
  "break_end_at": "2026-08-23T08:00:00Z",
  "basis_quality": "exact",
  "end_reason": null,
  "available_actions": ["end_business_day", "start_break"]
}
```

상태 enum:

- `before_open`
- `open`
- `break_time`
- `ended`

`ended`일 때 `end_reason = manual | auto_timeout`을 함께 반환한다. 서버의 `display_state`는 직접 종료 `ended_manual`, 자동 종료 `ended_auto`로 구분한다. 앱은 이 코드를 다시 판정하지 않고 현재 언어로 각각 `영업 종료`, `자동 영업종료`에 해당하는 문구를 표시한다.

### 7.5 예상 가능한 결과 코드

PostgREST 는 `errcode` 를 `code` 로, `detail` 을 `details` 로 실어 보낸다(실측).
앱은 **`code` 로만 분기한다** — 한국어 문구는 바뀔 수 있고 실제로 바뀌었다.

| SQLSTATE | `details` | 뜻 |
|---|---|---|
| `45001` | `BEFORE_OPEN` | 그날 장부가 아직 없다 |
| `45002` | `DAY_CLOSED` | 영업이 종료돼 판매 경로로는 못 쓴다 |
| `45009` | `REVISION_CONFLICT` | 다른 기기가 먼저 저장했다 |
| `45010` | `SALE_DATE_OUT_OF_RANGE` | 지난달 1일~오늘 밖이다 |
| `45011` | `DAY_IS_LIVE` | 아직 영업 중인 날이라 이 문이 아니다 |
| `45012` | `NO_CHANGES` | 고칠 내용을 아무것도 안 보냈다 |
| `45013` | `BASIS_NOT_AVAILABLE` | 그날 기준에도 없고 지금도 없는 메뉴다 |

⚠ 초안의 `BUSINESS_DAY_MISMATCH`·`SCHEDULE_CONFLICT` 는 만들지 않았다 — 앞의 코드들로
갈렸다. `HISTORICAL_BASIS_MISSING` 은 `BASIS_NOT_AVAILABLE` 로 구현됐다. 같은 것에
두 이름을 두지 않는다.

한국어 문구는 앱 번역 계층에서 코드별로 관리한다.

## 8. 상태 전이

```text
영업 전 ── 영업 시작/예정 시작 ───▶ 영업 중
                                      │
                                      ├─ 직접/예정 브레이크 시작 ─▶ 브레이크 타임
                                      │                    │
                                      │◀─ 영업 재개/예정 종료 ───┘
                                      │
                                      ├─ 직접 영업 종료 ─────┐
                                      └─ 자동 종료 기간 경과 ─▶ 영업 종료

영업 종료 ── 허용 기간 내 판매 정정 ──▶ 영업 종료 + revision 증가
```

브레이크는 설정 시간에 자동 전이하거나 버튼으로 직접 전환한다. 두 경로 모두 같은 서버 상태를 사용하며 재오픈은 제거한다.

## 9. 시간 설정 검증

- 시작과 종료는 같을 수 없다.
- `종료 < 시작`이면 `close_day_offset = 1`, 아니면 `0`으로 서버가 자동 계산한다. 사용자가 오프셋을 직접 입력하지 않는다.
- 자동 판정 결과는 저장 전 `18:00–다음 날 02:00`처럼 화면에 표시한다.
- 계산된 영업시간이 20시간 이상이면 입력 반전 가능성이 있으므로 총 시간을 확인한 뒤 저장한다.
- 24시간 영업은 시작과 종료를 같게 입력하는 방식으로 처리하지 않는다. 향후 별도 `24시간 영업` 옵션으로 제공한다.
- 브레이크 시작과 종료는 같을 수 없고 같은 영업 구간 안에 있어야 한다.
- 브레이크의 날짜 오프셋도 영업 시작 시각과 비교해 자동 계산한다.
- `18:00–다음 날 02:00` 영업에서 `23:00–00:30` 브레이크는 `23:00–다음 날 00:30`으로 계산한다.
- 요일별 영업 구간끼리 겹치면 저장을 막는다.
- 시간대 변경은 과거 데이터에 소급하지 않는다.
- 활성 영업일 중 시간대 변경은 다음 영업일부터 적용한다.
- 요일별 휴무는 시간 null 쌍으로 저장한다.
- 글로벌 시간대와 DST에서는 고정 24시간을 밀리초로 더하지 않고, 매장 현지 날짜·시각과 IANA 시간대로 `scheduled_open_at`·`scheduled_close_at`을 생성한다.

## 10. 테스트 필수 경우의 수

### 날짜·시간대

- KST 10:00~02:00의 01:00 판매
- 뉴욕 DST 시작일과 종료일
- 시간대 변경 전후의 과거 장부 불변
- 자정 전후 앱 표시 날짜와 서버 영업일 ID 일치

### 상태

- 예정 시작 후 첫 판매 자동 준비
- 영업 중 → 브레이크 → 영업 중 자동 전환
- 브레이크 중 판매 입력 허용
- 예정 종료와 수동 종료의 `ended_at` 정확성
- 직접 종료는 `영업 종료`, 자동 종료는 `자동 영업종료` 회색 뱃지로 표시
- 앱을 며칠 열지 않아도 영업 종료 시각 정확
- 스케줄러와 판매 쓰기가 동시에 실행되는 경쟁 조건

### 설정

- 활성 영업 중 시간 변경은 다음 영업일부터
- 시작 전 변경은 즉시
- 선택한 요일에는 공통 영업시간과 공통 브레이크 적용
- 선택하지 않은 요일은 휴무
- `11:00–22:00`은 당일 종료로 자동 판정
- `18:00–02:00`은 다음 날 종료로 자동 판정하고 결과 문구 표시
- 시작과 종료가 같으면 저장 거부
- 20시간 이상 영업시간 확인
- 브레이크 사용 안 함
- 자정을 넘는 브레이크의 날짜 자동 판정
- 브레이크가 영업시간 밖이거나 다음 영업과 겹치는 설정 거부

### 과거 정정

- 오늘 영업 중 어제 장부 수정
- 8월 24일 기준 7월 1일 허용, 6월 30일 거부
- 기존 스냅샷 유지
- revision 증가와 전후 합계 기록
- 기록 있는 날짜에는 `판매 내역 수정`, 기록 없는 날짜에는 `판매 내역 추가` 표시
- 기록 없는 날짜는 빈 상태를 표시하고 저장 시 현재 판매가·원가 사용 확인
- `+ 판매`에서 매장·배달·포장 채널 선택
- 기존 판매의 메뉴별·채널별 수량 증가·감소
- 저장 후 판매 수량·매출·채널 구성·손익 즉시 재계산

## 11. 단계별 전환 계획

### 1단계 — 날짜 분리 ✅ (0121~0125)

- 일반 기록을 `store_local_date`로 이동한다.
- 판매 화면의 `todayBusiness()` 사용을 제거하고 서버 `business_date`를 사용한다.

### 2단계 — 영업시간 버전 ✅ (0129~0132 · 0156)

- `operating_rules`와 시간대 컬럼을 추가한다.
- 기존 settings 값을 첫 규칙으로 이관한다.
- (0156) 의미 검증 `assert_weekly_schedule` — 시작=종료·브레이크 범위·다음 날 겹침.
  시간대는 `set_store_timezone` RPC 한 문(영업 중 45011, confirmed 기록).

### 3단계 — 상태 RPC 교체 ✅ (0154·0155·0157)

- ~~`sync_business_context` 한 번으로 교체~~ → 실제 구현은 **읽기와 쓰기를 갈랐다**:
  읽기는 `resolve_sales_business_context`(매장 시간대·현지 날짜·판매 영업일·규칙·
  열린 영업일 한 번에), 쓰기 전이는 `transition_business_state` 한 문.
  자동 마감은 크론(`close_due_business_days`)이 이미 맡고 있어(0137·0139) 날짜
  조회에 종료를 섞지 않는다 — "화면을 여니 영업이 끝났다"를 되살리지 않기 위해서다.
- 판매 쓰기: 첫 판매 = 영업 시작 + 저장 한 트랜잭션(`save_sale p_open_day`),
  기한 지난 옛 영업일 = 마감 + 오늘 열기 한 트랜잭션(`open_business_day`).
- 전역 `business_day()`·`business_cutoff()` 삭제(0155).

### 4단계 — UX 교체 ✅

- 매출 상단 상태 카드 교체 — 카드 영업시간은 장부에 굳은 규칙(0154).
- 내부 스냅샷 확인과 자동 종료 확인 배너 제거(0141·0142).
- MY 영업시간: 요일 선택 + 공통 적용 + 브레이크 토글 + 15분/직접 입력 +
  기기 시간대 제안(0156).

### 5단계 — 과거 정정 ✅ (0144~0153)

- `reopen_business_day` 사용을 중단한다(0140 삭제).
- 영업 종료된 장부 정정(`amend_ended_business_day`)과 revision UI 연결(SALES-21).

### 6단계 — 기존 함수 제거 ✅

- `business_cutoff()` — 0155
- 매장 인자 없는 판매용 `business_day()` 의존 — 0154·0155
- `set_break()` — 0157 (`transition_business_state` 로)
- `touch_business_day()` 기반 자동 연장 — 밀림 제거는 0139, 함수·기록 제거는 0158
- `reopen_business_day()` — 0140
- 앱의 한국어 오류 문자열 판별 — 0144·0145 (SQLSTATE 분기)

### 7단계 — 검토 반영 ✅ (0159~0162)

- 영업시간 규칙 판본(예약 변경 유실 방지, 45009) — 0159
- 시작·종료 몸통 앱 롤 차단(과거 직접 열기 봉쇄) — 0160
- 열린 장부가 밤을 소유(휴무일·연장 영업의 새벽 귀속) — 0161
- 늦은 개점(45015 — 오늘만, 종료 시간 선택, 다음 영업과 겹침 거부) — 0162
- 요일 값 로드·혼합 표시, 매장 현지 시각 표시(P2)
- **2세션 경합 시험**(`tests/concurrency.mjs`) — 판매 저장 ↔ 크론(마감·브레이크)을
  실제 연결 두 개로 동시 실행: 교착 없음 · 중복 차감 없음 · 평시 무해 ·
  마감 원자성(정확히 1회, 경계 뒤 45002, 마감 뒤 판매 이벤트 0). verify ③ 이 돌린다.
