## 1. 왜 지금인가

프로토타입과 문서는 `DS-20260904-011`까지 정합을 맞췄다. 다음 목표는 **"프로토타입과 문서를
확정해 실제 앱에 한 번에 적용"** 이다. 그런데 지금 앱에는 옮길 수단이 없다.

### 1.1 앱의 토큰 사용 실태 (2026-09-04 실측)

`apps/mobile` 소스 187개 파일 기준.

| 토큰 | 정의 | 실사용 |
|---|---|---:|
| `T` (색상) | 25종 | **1,827회** |
| `tnum` | 1종 | 61회 |
| `STATUS` | 3종 | 12회 |
| `cardShadow` | 1종 | 5회 |
| `space` | 6단계 | **3회** |
| `TYPE` | 7단계 | **0회** |
| `radius` | 5단계 | **0회** |

색상만 토큰이 살아 있고 나머지는 사실상 죽어 있다. 그 자리를 인라인 값이 채운다.

| 인라인 하드코딩 | 건수 |
|---|---:|
| `fontSize: <숫자>` | 822 |
| `fontWeight: '<숫자>'` | 671 |
| `padding·margin·gap: <숫자>` | 1,657 |
| `borderRadius: <숫자>` | 162 |
| hex 색상 리터럴 | 44 |

`TYPE`은 **정의된 지 오래됐는데 한 번도 쓰인 적이 없다.** 토큰을 더 만드는 것이 문제가 아니라,
**만든 토큰이 쓰이게 하는 것**이 문제다. 이 기획안의 성패는 거기서 갈린다.

### 1.2 공통 컴포넌트 실태

`src/components/kit`에 12개가 있고 사용 범위가 갈린다.

| 컴포넌트 | 사용 파일 |
|---|---:|
| `Icon` | 65 / 187 |
| `AppHeader` | 46 / 187 |
| `Button` | 40 / 187 |
| `Sheet` | 36 / 187 |
| `SearchBar` | 9 / 187 |
| `Txt` | **3 / 187** |

`Txt`는 `fontVariant: tabular-nums`만 선택 적용하는 얇은 래퍼다. 타이포 역할을 갖지 않는다.
**`TYPE`이 0회 쓰이는 이유가 이것이다** — 타이포 토큰을 받아 줄 컴포넌트가 없다.

### 1.3 프로토타입의 실제 값 분포 (185 target 전수 computed 측정)

`full-page-flow-prototype-render-audit.mjs`와 같은 방식으로 `.phone` 안 모든 요소의
computed 값을 수집했다. 문서가 아니라 **렌더 결과**다.

| 항목 | 고유 종류 | 앱 토큰 단계 |
|---|---:|---:|
| 글자 크기 | **17** | 7 (`TYPE`) |
| 글자 굵기 | 5 | 3 |
| 글자 색 | 14 | — |
| 배경색 | 21 | — |
| 테두리(색+두께) | 10 | — |
| 반경 | **20** | 5 (`radius`) |
| padding 값 | **25** | 6 (`space`) |
| gap 값 | **21** | 6 (`space`) |
| 그림자 | 6 | 1 (`cardShadow`) |

**중요 — 숫자 타이포 통일은 절반만 끝났다.** `PRT-179`~`PRT-183`은 *숫자를 담은 요소*만
정리했다. 위 17종은 전체 요소 기준이며, `20px`(3,729회) · `11px`(553회) · `12px`(256회) ·
`15px`(237회) · `10px`(187회) 등 숫자가 없는 텍스트는 손대지 않았다. 이 기획안이 나머지 절반이다.

굵기 `900`(195회)은 `b·strong`의 브라우저 `bolder` 파생이며 렌더 face는 `800`과 같다.
선언값이 아니므로 위반이 아니다(`PRT-189`에서 확정).

## 2. 목표와 비목표

**목표**

1. 기본 → 의미 → 컴포넌트 3계층으로 토큰을 재배치해 **중복 정의를 없앤다.**
2. 프로토타입의 실측 값을 토큰으로 **수렴**시킨다. 발명하지 않는다.
3. 앱의 인라인 하드코딩을 토큰·컴포넌트로 치환할 수 있는 **경로를 만든다.**

**비목표 (이번 범위 아님)**

- 화면 구조·문구·업무 흐름 변경. 현재 확정안이 이미 권위다.
- 다크 모드·테마 전환. 구조는 막지 않되 값은 만들지 않는다.
- 앱 전체 치환 완료. 이번엔 **구조 확정 + 시범 화면 치환**까지다.

## 3. 3계층 구조

검수자가 제안한 구조를 따른다. 두 가지만 조정한다.

### 3.1 기본 토큰 — 재사용되는 최소 재료

```ts
primitive = {
  color,        // brand · surface · text · border · positive · negative · caution · scrim
  typography,   // family · size · weight · lineHeight · letterSpacing
  space,        // 4 · 8 · 12 · 16 · 20 · 24
  size,         // controlHeight · iconSize · touchTarget
  borderWidth,
  radius,
  shadow,
  opacity,
  motion,       // duration · easing
  breakpoint,
  zIndex,
};
```

**조정 1 — `color.status`를 색 이름으로 바꾼다.** 원안의 기본 `color.status`와 의미 `state`는
이름이 겹쳐 "성공 색을 어디서 고치나"가 모호해진다. 기본은 **색 이름**(`positive` · `negative` ·
`caution`), 의미는 **역할 이름**(`success` · `danger` · `warning`)으로 나눈다. 그러면
`semantic.state.success = primitive.color.positive` 한 줄로 연결이 드러난다.

**조정 2 — `lineHeight`·`letterSpacing`은 값을 만들되 지금은 비운다.** 프로토타입이 대부분
브라우저 기본을 쓰고 있어 실측 근거가 없다. 자리만 두고 값은 근거가 생길 때 채운다.
**근거 없는 값을 토큰으로 만들지 않는다.**

### 3.2 의미 토큰 — 역할 부여

```ts
semantic = {
  text,           // body · caption · title · monetaryValue · unit
  spacing,        // screenPadding · sectionGap · contentGap
  line,           // divider · fieldBorder · focusedBorder
  surface,        // cardSurface · raisedSurface · modalSurface
  state,          // success · warning · danger · disabled · selected
  layout,         // headerHeight · rowHeight · contentMaxWidth
  layer,          // sticky · dropdown · sheet · modal · toast
  accessibility,  // minimumTouchTarget · focusRing
  media,          // 반복이 확인될 때만 추가
};
```

`text.monetaryValue`와 `text.unit`은 **이미 확정돼 있다.** `PRT-179`가 정하고 `PRT-183`까지
검수를 마친 계약을 그대로 승격한다.

| 역할 | 크기·굵기 | 색 | 정렬 | 숫자 폭 |
|---|---|---|---|---|
| `monetaryValue` | 16 / 700 | `text.primary` | 우측 끝선 | tabular |
| `unit` | 14 / 600 | `text.secondary` | 값 뒤 8px | – |

### 3.3 컴포넌트 규격

```ts
component = { button, icon, input, select, checkbox, switch, chip, card, header, sheet, tab };
```

여기서 **지금 열려 있는 결정 두 개가 함께 풀린다.**

| 미해결 | 실제로는 무엇의 문제인가 |
|---|---|
| `KD-001` 글자 200%에서 `.header-icon`의 `＋` 글리프가 박스를 5px 넘침 | `component.icon` + `component.header` 규격 |
| `KD-002` CSS 200%에서 `option_more` 팝오버가 화면 밖으로 나감 | `component.sheet` / `semantic.layer` 규격 |

따로 결정할 항목이 아니라 이 단계의 산출물이다.

## 4. 결정이 필요한 것

솔라가 정하지 않는다. 확정 없이는 P1을 시작할 수 없다.

### 4.1 색 충돌 — 프로토타입과 앱의 값이 다르다 (실측)

| 역할 | 프로토타입 | 앱 `tokens.ts` | 같은가 |
|---|---|---|---|
| 초록 | `#0E9F6E` | `#15B374` (`T.green`) | **다름** |
| 앰버(글자) | `#B76E00` | `#E07A00` (`T.amberText`) | **다름** |
| 파랑 틴트 | `#EAF3FF` | `#EBF3FE` (`T.blueTint`) | **다름** |
| 앰버 틴트 | `#FFF4E5` | `#FFF4E5` | 같음 |

추가로 프로토타입 안에서만도 갈라진 값이 있다.

- 앰버 계열이 **셋** — `#B76E00`(12회) · `#E07A00`(18회) · `#E97900`(3회)
- 초록 틴트가 **둘** — `#E7F7F0`(11회) · `#E8F8F1`(6회)
- 빨강 틴트가 **둘** — `#FEECEC`(38회) · `#FFF0F1`(29회)

**결정 D-1: 색의 정본을 어디로 둘 것인가.**
- (가) 앱 `tokens.ts` — 실제 사용자에게 이미 나간 값이다. 프로토타입을 맞춘다.
- (나) 프로토타입 — 더 최근 판단이다. 앱을 맞춘다. 회귀 검수 범위가 커진다.
- (다) 역할별로 각각 판단.

솔라 의견: **(가)를 기본으로 하고 예외만 (나)로 올린다.** 색 차이는 대부분 미세하고
(`#EAF3FF` vs `#EBF3FE`는 육안 구분이 어렵다) 앱 쪽이 이미 배포된 값이다. 다만 초록은
`#0E9F6E`와 `#15B374`가 실제로 다르게 보이므로 눈으로 확인 후 정하는 편이 낫다.

**결정 D-2: 프로토타입 내부 중복(앰버 3 · 초록 틴트 2 · 빨강 틴트 2)을 각각 하나로 합칠 때
어느 값을 남길 것인가.** 사용 빈도만으로 정하면 `#E07A00` · `#E7F7F0` · `#FEECEC`이지만
시각 확인이 필요하다.

### 4.2 스케일 결정

**결정 D-3: 글자 크기 17종 → 몇 단계로 줄일 것인가.**
`TYPE`은 7단계(22·20·18·16·14·13)다. 실측 17종 중 `19px`(135) · `17px`(80) · `15px`(237) ·
`12px`(256) · `11px`(553) · `10px`(187)이 스케일 밖이다. **`11px`·`10px`은 대부분 프로토타입
셸(상태바 시각·화면 ID 배지)이라 제품 UI가 아니다.** 나머지를 7단계로 흡수할지, 단계를
추가할지 정해야 한다.

**결정 D-4: 반경 20종 → 5단계, padding 25종 → 6단계로 줄일 때 허용 오차.**
예: `11px`·`13px`·`14px`를 `12px`로 흡수하면 최대 2px가 움직인다. 화면당 몇 px까지 허용할지
기준이 있어야 기계적으로 수렴시킬 수 있다.

솔라 의견: **±2px 이내는 자동 흡수, 초과는 개별 판단.** 타이포 때와 같은 방식이다.

## 5. 단계와 순서

### P0 · 감사기 거짓 음성 2건 제거 (선행, 짧음)

토큰을 실측으로 확정하려면 측정이 먼저 정확해야 한다. `PRT-189` 검수에서 나온 6건 중
**진짜 결함을 가리는 2건만** 먼저 고친다.

- `F04` — `inScrollableX()`가 조상의 `scrollWidth > clientWidth`만으로 조기 반환한다.
  `overflow-x: auto|scroll` 확인 전에 탈출하므로 **`overflow: hidden`에서 잘리는 실제 결함이
  정상 스크롤로 제외된다.**
- `F03` — shell 예외 `SPAN 11px`가 클래스 없는 모든 `<span>`을 뜻한다. **제품 UI에 클래스 없는
  숫자 `<span>` 11px이 생겨도 예외로 흡수된다.** DOM 경계로 한정한다.

나머지 4건(`F01`·`F02`·`F05` 변조 방어, `F06` 완료)은 뒤로 미룬다 — 근거는 §7.

### P1 · 기본 토큰을 실측으로 확정

1. 색·간격·반경·그림자·타이포를 185 target 전수 computed로 수집한다(이미 도구가 있다).
2. `tokens.ts`와 대조해 충돌표를 만든다 — §4.1이 그 초안이다.
3. D-1~D-4 결정을 받아 스케일을 확정한다.
4. `primitive` 레이어를 코드로 만든다. **`tokens.ts`의 기존 export는 지우지 않고 유지한다** —
   1,827곳이 `T.`를 참조하고 있어 한 번에 끊으면 앱이 멈춘다. `T`는 `primitive.color`의
   별칭으로 남긴다.

### P2 · 의미 토큰 배정

역할을 붙인다. 이 단계에서 프로토타입 CSS를 의미 토큰 이름으로 치환해 **프로토타입 자체가
토큰 구조의 참조 구현**이 되게 한다. 프로토타입은 이미 185 target 회귀 검수 아래 있으므로
치환 사고를 바로 잡을 수 있다.

### P3 · 컴포넌트 규격 + `KD-001`·`KD-002` 해소

`Txt`에 타이포 역할을 부여하는 것이 **가장 큰 지렛대**다. `TYPE`이 0회 쓰인 원인이므로
여기를 풀면 `fontSize` 822건 치환 경로가 열린다.

### P4 · Expo 적용

`RecipeDetailScreen`(114건) · `RecipeAddScreen`(77) · `SalesHomeScreen`(65)에 하드코딩이
몰려 있다. 이 셋을 시범으로 먼저 치환해 규격의 실효성을 확인한 뒤 확대한다.

## 6. 완료 조건과 검증

**측정으로 판정한다.** 아래는 전부 `full-page-flow-prototype-render-audit.mjs`가 이미 재고
있거나 항목을 추가하면 재는 값이다.

| 단계 | 완료 조건 |
|---|---|
| P0 | 두 거짓 음성 정정 후 재측정. 새로 드러난 위반은 원인과 함께 `known.json`에 등록 |
| P1 | 프로토타입 실측 고유 종류가 목표 단계 수 이하 — 색은 충돌 0, 반경 ≤ 5, padding·gap ≤ 6, 그림자 ≤ 3 |
| P2 | 프로토타입 CSS의 색·크기 리터럴이 의미 토큰 참조로 치환. 185 target 회귀 무변화 |
| P3 | `KD-001`·`KD-002`가 `known.json`에서 사라진다(게이트가 낡은 예외를 강제로 지우게 한다) |
| P4 | 시범 3화면의 인라인 `fontSize`·`borderRadius`·spacing 0건 |

**회귀 기준선** — P1~P4의 각 단계에서 185 target × 4 패스 결과가 이전 단계와 같아야 한다.
달라지면 의도한 변경인지 사고인지 target 단위로 설명한다. 타이포 통일(`PRT-179`~`183`)에서
face 대조로 썼던 방식과 같다.

## 7. 미루는 것과 그 이유

`PRT-189` 검수 지적 중 셋은 이번에 다루지 않는다. **거짓 음성이 아니라 변조 방어**이기 때문이다.

| 지적 | 내용 | 미루는 근거 |
|---|---|---|
| `F01` | 게이트가 합계 산식만 봐서 화면·팝업이 함께 줄면 통과 | 대상이 줄면 다음 감사의 target 목록에서 드러난다. 누가 몰래 지우는 상황이 아니다 |
| `F02` | 위반 대조가 `pass\|metric\|target`뿐이라 이탈 요소가 3→20개가 돼도 통과 | 악화는 P1~P4의 회귀 기준선 대조에서 잡힌다 |
| `F05` | face "구분"만 보고 Pretendard identity 미확인 | `fonts.check` 4종 + 실측 폭 4종 구분을 이미 통과한다. fallback이 우연히 4단계를 만들 확률은 낮다 |

**단, 이 판단은 조건부다.** 토큰 값을 이 감사 결과로 확정하는 이상 측정 신뢰도가 곧 토큰
신뢰도가 된다. P1에서 색·간격 수집 항목을 추가할 때 `F02`의 지문(fingerprint) 단위 대조를
함께 넣는 것이 자연스럽다면 그때 처리한다.

## 8. 위험

| 위험 | 완화 |
|---|---|
| **토큰을 만들어도 안 쓰인다** — `TYPE`이 0회인 전례가 있다 | 토큰만 만들지 않고 **받아 줄 컴포넌트를 같이 만든다**(P3). 완료 조건을 "토큰 정의"가 아니라 "인라인 0건"으로 잡는다 |
| 1,827곳의 `T.` 참조를 끊으면 앱이 멈춘다 | `T`를 별칭으로 유지하고 점진 치환. 한 번에 끊지 않는다 |
| 값 수렴이 화면을 미세하게 바꾼다 | ±2px 허용 오차를 명시하고, 초과분은 target 단위로 승인받는다 |
| 프로토타입과 앱의 색이 갈린 채 굳는다 | D-1을 P1 시작 전에 확정한다. 미확정이면 P1을 시작하지 않는다 |
| 범위가 계속 커진다 | 비목표(§2)를 지킨다. 다크 모드·테마·앱 전체 치환은 이번이 아니다 |

## 9. 검수자에게 묻는 것

솔라가 스스로 의심하는 지점이다. 근거가 약하면 지적해 달라.

1. **§5 P0의 판단** — 감사기 6건 중 2건만 먼저 고치고 나머지를 미루는 구분(거짓 음성 vs 변조
   방어)이 타당한가. §7의 근거가 충분한가.
2. **§4.1 솔라 의견** — 색 정본을 앱 `tokens.ts`로 두자는 제안이 타당한가. 프로토타입이 더
   최근 판단인데 앱을 정본으로 두는 것은 "최신 결정을 되돌리는" 것 아닌가.
3. **§3.1 조정 2** — `lineHeight`·`letterSpacing`을 자리만 두고 비우는 것이 옳은가,
   아니면 아예 넣지 않는 것이 옳은가.
4. **§5 P2의 순서** — 프로토타입 CSS를 의미 토큰으로 먼저 치환하고 앱을 나중에 하는 순서가
   맞는가. 앱을 먼저 하면 프로토타입은 버려도 되는 것 아닌가.
5. **§6 완료 조건** — "고유 종류 수 ≤ 단계 수"가 좋은 판정 기준인가. 수는 줄었는데 역할
   배정이 엉망인 상태를 이 기준이 통과시키지 않는가.
6. **§1.3의 함의** — 숫자 타이포만 통일하고 나머지 텍스트 17종을 남긴 것이 `PRT-179`~`183`의
   범위 설정 실수였는가, 아니면 단계적 접근으로 정당한가.
