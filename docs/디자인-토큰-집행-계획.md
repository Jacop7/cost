## 0. 초판 철회 기록

이 문서의 초판(커밋 `7f34139`, 제목 "디자인 토큰 3계층 재배치 기획안")을 철회하고 다시 쓴다.
두 가지가 틀렸다. 남겨 두는 이유는 같은 실수를 반복하지 않기 위해서다.

**틀림 1 — 이미 있는 것을 새로 제안했다.** 3계층 구조는 실행서 §3과 UI 가이드 §1~5에 이미
확정돼 있다. 초판은 그 문서들을 읽지 않고 새 구조를 제안해, 두 번째 경쟁 표준을 만들 뻔했다.
`AGENTS.md`가 요구하는 단일 정본 원칙에도 어긋난다.

**틀림 2 — 수치가 재현되지 않았다.** 초판의 앱 실측은 임시 grep 결과였고 세는 규칙을
적지도 스크립트로 남기지도 않았다. 검수에서 전부 어긋났다.

| 초판 표기 | 실제 (AST 측정) |
|---|---|
| `T` 25종 | **24종** |
| `TYPE` 7단계 | 역할 **7개**, 고유 크기 **6개** |
| `T.` 1,827회 | **1,816회** |
| `Txt` 사용 3파일 | JSX 사용 **1파일 3곳** |

`PRT-188`에서 "측정값은 저장소에 보존된 산출물에서만 인용한다"고 재발 방지까지 적어 놓고
바로 다음 문서를 임시 grep으로 썼다. **재발 방지는 적는 것으로 지켜지지 않는다.**
그래서 이번에는 `scripts/token-adoption-audit.mjs`를 먼저 만들고 그 출력만 인용한다.

## 1. 이 문서가 하려는 것

**토큰을 설계하지 않는다. 이미 있는 토큰이 실제로 쓰이게 만든다.**

`TYPE`은 정의된 지 오래됐는데 **한 번도 쓰인 적이 없다.** `radius`도 0회다. 문제는 설계 부재가
아니라 집행 부재다.

---

## 2. 3계층은 이미 어디에 있는가

검수자가 제안한 기본 → 의미 → 컴포넌트 3계층은 이 저장소에 다른 이름으로 이미 존재한다.
**새로 만들지 않고 이 자리를 정본으로 쓴다.**

| 제안된 계층 | 이미 있는 곳 | 성격 |
|---|---|---|
| 기본 토큰 | `apps/mobile/src/theme/tokens.ts` (`T`·`TYPE`·`space`·`radius`·`STATUS`·`FONT`·`cardShadow`·`tnum`) | 코드가 정본 |
| 기본 토큰 서술 | UI 가이드 §1 기초 토큰 (§1.1 권위·§1.2 대비·§1.3 타이포·§1.4 간격·§1.5 그림자·레이어·모션·§1.6 아이콘) | 문서 |
| 의미 토큰 | UI 가이드 §1.1 매핑표 — "가이드의 의미 역할은 Expo 원시 토큰의 **별칭**이며 새 팔레트가 아니다" | 문서 |
| 컴포넌트 규격 | UI 가이드 §3~5 각 절의 "공통 계약과 kit 대응" + 실행서 §3 `C-01`~`C-21` 21개 잠금 | 문서 |
| 확정 값 표 | 실행서 §3.1 색상 역할 · §3.2 타이포 · §3.3 간격·크기·모서리 · §3.4~3.9 | 문서 |

**권위 순서도 이미 정해져 있다.** 가이드 §1.2 — "접근 가능한 진한 전경색은 실제 대비 검산 후
`tokens.ts`에 추가한다. **이 문서가 임의 색을 확정하지 않는다.**" 즉 값의 정본은 코드이고
문서는 역할을 설명한다. 초판이 "색 정본을 어디로 둘 것인가"를 열린 결정으로 남긴 것은
**이미 답이 있는 질문을 다시 물은 것**이다.

따라서 이 계획의 문서 작업은 **새 문서 추가가 아니라 위 자리의 정정과 보강**이다.

결과 JSON의 `manifest`에 함께 남긴다. 정규식을 쓰지 않는 이유는 문자열·주석·import·타입 위치를

## 4. 진단

**설계가 없어서가 아니라, 제품 화면이 공용 계층을 우회하고 있다.**

제품 화면 170개가 `T.`를 1,667회 직접 참조하면서 크기·간격은 인라인으로 박는다. 공용 컴포넌트
14개의 인라인은 각 94건인데 제품은 1,461·1,558건이다. **비율이 아니라 자릿수가 다르다.**

`TYPE` 0회 · `radius` 0회는 원인이 아니라 결과다. 화면이 kit을 거치지 않으니 kit이 들고 있는
타이포·반경 계약이 화면에 닿지 않는다.

그러므로 이 계획의 축은 토큰 목록이 아니라 **제품 화면의 공용 계층 경유율**이다.

**초판의 원인 단정은 철회한다.** 초판은 "`Txt`에 타이포 역할이 없어서 `TYPE`이 0회"라고
단정했다. 화면은 `Txt` 없이도 `<Text style={TYPE.body}>`로 토큰을 쓸 수 있으므로 그 단정은
성립하지 않는다. `Txt` 개선은 여러 수단 중 하나이지 원인 제거가 아니다.

## 5. 발견한 문서 오류

실행서 §3.1이 토큰 이름 옆에 프로토타입 실측값을 적어 뒀는데 코드와 어긋난다.
가이드 §1.2가 값의 정본을 `tokens.ts`로 못박고 있으므로 **틀린 쪽은 실행서 표기다.**

| 실행서 §3.1 표기 | 실제 `tokens.ts` |
|---|---|
| `T.green` = `#0E9F6E` | `#15B374` |
| `T.amberText` = `#B76E00` | `#E07A00` |
| `T.blueTint` = `#EAF3FF` | `#EBF3FE` |

읽는 사람은 `T.green`이 `#0E9F6E`인 줄 안다. 열린 결정이 아니라 정정 대상이다.

프로토타입 내부에서도 같은 역할의 색이 갈려 있다 — 앰버 `#B76E00`·`#E07A00`·`#E97900` 3종,
초록 틴트 `#E7F7F0`·`#E8F8F1` 2종, 빨강 틴트 `#FEECEC`·`#FFF0F1` 2종. 이쪽은 프로토타입을
`tokens.ts`로 수렴시키면 함께 해소된다.

## 6. 결정이 필요한 것

초판은 4건을 열린 결정으로 남겼다. **그중 하나는 이미 답이 있었다.**

| | 초판 | 이번 |
|---|---|---|
| D-1 색 정본 | 열린 결정 | **철회.** 가이드 §1.2가 `tokens.ts`를 정본으로 이미 정했다 |
| D-2 프로토타입 내부 중복 색 통합 | 열린 결정 | **불필요.** `tokens.ts`로 수렴하면 자동 해소 |
| D-3 타입 단계 수 | 열린 결정 | **유지 → 아래 D-1′** |
| D-4 수렴 허용 오차 | ±2px 일괄 | **철회.** 속성별로 나눈다 → D-2′ |

**D-1′ · 스케일 밖 텍스트 크기를 어떻게 처리할 것인가.**
프로토타입 전체 요소 기준 글자 크기는 17종이고 `TYPE`은 6단계다. 스케일 밖은
`19px`(135) · `17px`(80) · `15px`(237) · `12px`(256) · `11px`(553) · `10px`(187)이다.
`11px`·`10px`은 대부분 프로토타입 셸(상태바 시각·화면 ID 배지)이라 제품 UI가 아니다.
나머지를 6단계로 흡수할지, 단계를 추가할지 정해야 한다.

**D-2′ · 값 수렴의 판정 기준.**
초판은 반경·padding·타이포에 같은 `±2px`를 제안했으나 잘못이다. `15→13px` 타이포는 약 13%
축소이고 `14→12px` padding은 밀도와 터치에 영향을 주며 반경 2px과 의미가 다르다.
숫자 근접성으로 판정하는 방식은 `PRT-181`에서 굵기를 잘못 정규화했던 것과 같은 유형이다.
**속성별로 다른 기준을 쓴다.**

| 속성 | 판정 기준 |
|---|---|
| 간격 | 무엇과 무엇 사이인가(관계 역할). 화면 gutter·Section·Card·Field 소유권 |
| 타이포 | 위계상 어느 역할인가 + 큰 글꼴 확대에서의 결과 |
| 반경 | 컴포넌트 형태(Field·Card·Sheet·Badge) |
| 크기 | 터치 영역 최소 44px 충족 여부 |

각 기준을 누가 정할지는 §7 단계별로 나눈다.

## 7. 단계

### P0 · 감사기 거짓 음성 정정 (선행)

`PRT-189` 검수 지적 6건 중 `F06`은 처리했다(커밋 `f2efe1e`). 남은 5건을 **전부** 먼저 고친다.

초판은 이 중 `F01`·`F02`·`F05`를 "변조 방어"로 분류해 미루자고 했으나 **철회한다.** 셋 다
정상 변경에서도 발생한다.

- `F01` — 화면이 실수로 레지스트리에서 빠지면 다음 감사도 그 화면을 보지 못한다.
- `F02` — 같은 target의 넘침이 악화돼도 target 단위 비교는 통과한다.
- `F05` — 폰트 경로·descriptor 변경으로 fallback이 선택되는 것은 일반적인 회귀다.
  "우연히 네 단계를 만들 확률이 낮다"는 확률 판단은 검증 근거가 아니다.

**이 감사 결과로 토큰 값을 확정할 것이므로, 측정 신뢰도가 곧 토큰 신뢰도가 된다.**
잘못된 측정 기준이 토큰 정본으로 승격되는 것을 막는다.

### P1 · 값 매핑표 확정 (치환하지 않는다)

프로토타입·앱의 현재 값 각각을 어느 토큰 역할에 매핑할지 표로 확정한다. 예외는 근거와 함께
남긴다. **이 단계에서 렌더 종류 수가 줄기를 요구하지 않는다** — 치환은 P2다.
같은 단계에서 실행서 §3.1의 색 3건을 정정한다.

### P2 · 프로토타입 치환

매핑표대로 프로토타입 CSS를 치환한다. 회귀 기준은 **"무변화"가 아니라 "승인된 target별 변화만
존재하고 비의도 변화 0"** 이다. 20종 반경과 25종 padding을 줄이면 의도된 시각 변화가 생긴다.

프로토타입은 **참조 구현이 아니라 시각 회귀 fixture**다. `tokens.ts`가 정본이고 프로토타입이
두 번째 토큰 체계가 되면 안 된다.

### P3 · 컴포넌트 규격과 채택 수단

`C-01`~`C-21`을 코드 계약으로 내린다. 여기서 `KD-001`(큰 글꼴 아이콘 글리프)과
`KD-002`(팝오버 독립 레이어)가 함께 풀린다 — 각각 `component.icon`·`component.header`,
`component.sheet`의 문제다.

채택 수단은 하나로 단정하지 않고 셋을 두고 고른다 — (가) 타이포 역할을 가진 텍스트 컴포넌트,
(나) `TYPE`을 직접 쓰는 규약 + lint 규칙, (다) 화면별 StyleSheet를 토큰 참조로 강제.
**어느 쪽이든 완료 판정은 인라인 건수로 한다.**

### P4 · 제품 화면 치환

인라인이 몰린 `RecipeDetailScreen`(247) · `RecipeAddScreen`(174) · `SalesHomeScreen`(152)을
먼저 치환해 규격의 실효성을 확인한 뒤 확대한다.

## 8. 완료 조건

**단순 종류 수는 보조 지표로만 쓴다.** 종류가 줄어도 역할 배정이 엉망일 수 있기 때문이다.
주 판정은 **매핑 충족**으로 한다.

| 단계 | 완료 조건 |
|---|---|
| P0 | `PRT-189` 지적 5건 정정. 새로 드러난 위반은 원인과 함께 `known.json`에 등록 |
| P1 | 프로토타입·앱의 모든 현재 값이 **허용 토큰 또는 승인 예외에 매핑**된다. 미매핑 0건. 실행서 §3.1 색 3건 정정 |

## 9. 검수자에게 묻는 것

솔라가 스스로 의심하는 지점이다.

1. **§2의 판단** — 3계층이 이미 실행서 §3·가이드 §1~5에 있다고 보고 새 구조를 만들지 않는
   것이 옳은가. 아니면 기존 문서의 어휘가 실제로 3계층을 이루지 못하고 있어 재배치가
   필요한가. 재배치가 필요하다면 어느 자리를 고쳐야 하는가.
2. **§4의 진단** — "제품 화면이 공용 계층을 우회한다"가 `TYPE` 0회의 원인이라고 볼 근거가
   충분한가. 다른 원인(예: kit이 화면이 필요로 하는 변형을 못 담아 우회가 합리적 선택이었을
   가능성)을 배제하지 않았는가.
3. **§5** — 실행서 §3.1을 `tokens.ts`에 맞추는 것이 옳은가. 반대로 프로토타입 검수를 거친
   값이 더 최신 판단이므로 `tokens.ts`를 바꿔야 하는 경우는 없는가.
4. **§7 P3의 채택 수단** — 셋 중 하나로 단정하지 않고 열어 둔 것이 실행 계획으로 충분한가,
   아니면 지금 정해야 하는가.
5. **§8 완료 조건** — "매핑 충족"이 "종류 수"보다 나은 기준이라는 판단이 맞는가.
   매핑표 자체가 잘못 만들어진 경우를 이 기준이 통과시키지 않는가.
6. **§0·§3.5의 함의** — 측정 도구를 만들자마자 그 도구의 결함이 두 번 나왔다. 이 계획이
   그 도구의 출력에 의존하는 구조가 안전한가. 도구를 검증할 별도 수단이 필요한가.
7. **범위** — P0~P4가 한 계획으로 묶일 만한 단위인가. `AGENTS.md`의 단일 정본·서버 확정값
   원칙과 충돌하는 지점이 있는가.
