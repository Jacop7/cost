## 4. Task·권한·상태 계약

Task에는 task_id, correlation_id, mission_id, canonical root 참조, 요청 출처 포인터, 목표,
완료조건, 범위, 제외 범위, owner, 참여 역할, 의존성, task_revision, 권한 Decision 포인터를 둔다.
원시 대화·비밀·provider endpoint ID는 넣지 않는다. 짧은 답변용 QUESTION은 Task를 만들지 않는다.
자유 문장 분류는 AI 판단이며, 모호한 요청·운영·권한 확대는 결정 대기로 남긴다. 정규식만으로 승인하지 않는다.

권한은 `사람의 명시 범위 ∩ 원 Task 범위 ∩ 역할 권한 ∩ 활성 Router 계약`이다.
각 Decision·Task 권한·edit lease에는 issued_at, not_before, expires_at, revoked_at/revision과 적용 action이 필요하다.
신뢰된 host UTC가 not_before 이상·expires_at 미만이고 폐기되지 않았을 때만 유효하다. 시계 출처가 없으면 차단한다.
권한은 send/효과 실행 직전에 재검증하며, 과거 유효 권한의 늦은 결과 수신은 감사 기록일 뿐 새 실행 권한이 아니다.
기존 무만료 Decision은 자동 무기한 연장하지 않고 read-only 조사 또는 새 명시 Decision으로 처분한다.
READY/PREPARED 중 만료·폐기는 AUTH_EXPIRED/AUTH_REVOKED 차단과 pending action/lease 취소로 전이한다.
SENT/EXECUTING 중 만료·폐기는 신규 send/effect를 금지하고 이미 소비된 fence/effect를 pending으로 조정한다.
안전 STOP/취소/보고는 별도의 최소 safety capability로만 허용하며 업무 실행 권한을 되살리지 않는다.
새 Decision으로만 RESUME 가능하다. 실행 당시 유효하고 내용·출처가 맞는 늦은 receipt는 AUDIT_ONLY,
실행 당시 무효/위조 receipt는 REJECTED다. 수신 시각 만료만으로 둘을 혼동하지 않는다.
추가 설명·팀 협업·CEO 직접 지시는 이 교집합을 넓히지 않는다. 수정 지시는 원 Task revision을 올리고
총괄에게 변경 diff를 보내므로 경쟁 Task와 중복 구현을 만들지 않는다. 파일 편집에는 별도 edit lease가 필요하다.
최초 파일럿은 read-only 권한만 갖고, 이후 제품 수정 권한 계약은 별도 검수 후 부여한다.

### 안정 식별자·협업 범위

`subtask_id`는 논리 업무 단위, `assignment_id`는 그 업무의 책임 배정 단위,
`effect_key = SHA256(task_id, subtask_id, work_spec_revision, effect_kind)`는 중복 외부 효과 방지 키다.
Task의 보고/집계 revision이 바뀌어도 work_spec_revision과 effect_key는 바꾸지 않는다.
CEO/총괄의 같은 일에 대한 지시는 기존 subtask/assignment를 조회해 CAS로 변경하며 새 route를 새 일로 보지 않는다.
다른 effect_key를 발급하는 것은 실제 업무 명세 변경을 승인하고 기존 효과의 취소/대체를 처분한 경우뿐이다.
수신 업무도 effect_key의 CLAIMED/EXECUTED/RESULT_RECORDED 상태를 원자적으로 확인한다.
effect의 영속 PK/UNIQUE는 (task_id, effect_key)이며 run_generation은 claim metadata다.
세대별 별도 effect entity를 만들거나 PK에 run_generation을 넣어 같은 효과를 다시 청구하지 않는다.

협업은 parent_subtask_id, ancestor_subtask_ids, 참여자 집합이 있는 DAG다. 자기/조상 재참조를 거부하며
최초 상한은 협업 깊이 3, 각 subtask의 직접 자식 4, 한 Task의 총 subtask 20이다. 초과는 결정 대기다.
협업은 미리 승인된 참여 팀만 사용하며 자동 전 팀 broadcast나 권한 확대를 하지 않는다.

### 기본 전이

- REQUEST_ACCEPTED → READY → DISPATCH_PREPARED → SENT_UNCONFIRMED → ACKNOWLEDGED.
- 요청/배정 수신의 ACCEPTED와 실제 작업 결과 RESULT_VERIFIED를 구분한다.
  중간 라우팅 hop은 접수 완료 뒤 다음 actor로 진행할 수 있으나 업무 전체 완료로 승격하지 않는다.
- 담당 팀은 EXECUTING → RESULT_SUBMITTED → RESULT_VERIFIED, 총괄은 종합 → CEO는 최종결과 → 사람01 수신.
- 업무 완료 조건은 필수 subtask 결과·별도 Quality 검증·사람에게 결과 전달 영수증 충족이다.
  ACK, send 도구의 queued/success, 포인터 존재만으로 업무를 COMPLETED 처리하지 않는다.
- 알 수 없는 필드·타입·event·scope·actor·revision·receipt 불일치는 fail-closed.
- id는 문자열 선검사. canonical JSON은 NFC·정렬 key·compact UTF-8, 비JSON/중복 정규화 key 거부.
  hash 대상은 명시 schema의 의미 필드다. 도착 시각·프로세스 metadata를 중복 판정에 넣지 않는다.

### 차단 보고와 사람 결정

BLOCKED는 정당한 Task 참여 역할이 발생시킨다. 현재 foreground leg의 양끝으로만 제한하지 않는다.
상황실·게이트 등 다른 역할의 escalation은 Task intake/권한 검증기가 요청 출처·Task 연결·역할을 검사한다.
권한 검증기는 Router bridge의 검증된 caller/Task 계약을 소비하며 상황실이나 요청자 자신의 승인으로 처리하지 않는다.
알려진 10개 비사람 역할의 안전 보고는 가능하지만 보고만으로 Task 실행 참여·편집 권한을 얻지 않는다.

BLOCKER_OPEN → REPORT_PENDING → REPORT_SENT_UNCONFIRMED → REPORT_ACKED → WAITING_HUMAN_DECISION.
DECISION은 decision_id, task/correlation, blocker_id, expected_revision, 허용 행동·범위, 실제 사람 출처가 필요하다.
선택은 RESUME / RETRY / AMEND / STOP이다. 역할명이 human인 합성 event를 사람 승인으로 인정하지 않는다.

- RESUME: 차단 전 checkpoint로 복원, 기존 token/미확인 send를 보존하고 먼저 receipt를 회수한다.
- RETRY: 실제 transient failure로 확인된 동일 논리 전송에 한해 동일 route/token/payload 유지.
- AMEND: 새 Task revision으로 변경, 기존 실행/결과는 superseded 이력으로 보존, 총괄·담당에게 차이만 공유.
- STOP: 아직 실행 안 한 send/child task를 막고 이미 실행 중인 참여자에 취소 신호를 전달한다.
  취소 확인 전에는 STOP_REQUESTED, 모든 참여자 확인 또는 미확인 목록 확정 뒤 STOPPED_WITH_PENDING/STOPPED.
  이미 일어난 외부 효과를 되돌렸다고 주장하지 않는다. 정지 뒤 늦은 ACK/결과는 감사 기록으로만 수용한다.

root Task만 stop_epoch와 command_seq를 소유한다. fence의 stop_epoch는 항상 root Task 값이다.
자손의 독립 epoch 발급·입력은 CHILD_STOP_EPOCH_FORBIDDEN으로 거부한다. 최종 send fence는 `task_revision, stop_epoch, run_generation, assignment_id,
effect_key, activation_epoch, lease_nonce, decision_id, authority_revision, not_before, expires_at`에 결속한다. STOP의 CAS가 선형화 시점이며 이전 stop_epoch의
아직 소비되지 않은 action/lease를 무효화한다. send fence 소비와 STOP CAS는 동일 Task 잠금 아래 순서를 정한다.
fence 소비가 먼저 완료된 send는 이미 허가된 in-flight로 분류하므로 STOP 뒤 실제 도착할 수 있다.
그 효과까지 사라졌다고 주장하지 않으며 취소/조회 대상으로 회수한다. 외부 앱이 fence를 집행하지 못하면
로컬 잠금만으로 외부 STOP 경합을 완전히 막았다고 하지 않고 §5 PH-FEASIBILITY의 실전 제약으로 차단/보고한다.


### STOP과 협업 DAG

v0.4의 STOP은 Task 전체에만 적용한다. subtree/특정 팀만 중지하는 부분 STOP은
`PARTIAL_STOP_NOT_SUPPORTED`로 거부하고 범위 명확화 Decision을 요구한다.
모든 자손은 별도 stop_epoch를 발급하지 않고 root Task의 stop_epoch를 상속·조회한다.
STOP CAS는 DAG 확장과 동일 root lock을 사용해 기존 모든 비종결 subtask를 cancellation set에 넣고
새 자손 생성/새 lease를 금지한다. 이미 승인된 in-flight는 별도 pending set에 남긴다.

취소 전파 메시지는 root Task/stop_epoch/subtask_id로 멱등 처리하며 각 자손의 ACK를 별도로 수집한다.
부모 ACK가 자손 ACK를 대신하지 않는다. 팀의 효과 claim은 send fence와 별도로 같은 root lock에서 authority/epoch/run_generation을 확인하고 CAS로 소비한다.
STOP CAS가 먼저면 effect claim을 거부하며, effect claim이 먼저면 in-flight 효과로 기록하고 조회/취소한다.
lock 밖의 단순 epoch 읽기는 이 선형화를 대신하지 않는다. 외부 효과를 원자 취소할 수 없으면 불확실성을 pending으로 유지한다.
미확인 자손이 있으면 STOPPED_WITH_PENDING과 정확한 pending 목록을 유지한다.
늦은 완료는 root STOP을 취소하지 않고 `LATE_RESULT_AFTER_STOP`로 기록한다.
재개가 승인되면 새 run_generation을 열고 옛 effect_key의 실제 효과를 reconcile한 뒤 필요한 업무만 재배정한다.
action/lease/prepared route/receipt/result에 run_generation을 결속한다. 옛 세대 receipt는 옛 delivery의 감사/조정만 갱신하며 새 실행 완료를 충족하지 않는다.
외부 tool이 해당 필드를 주지 않으면 보호된 immutable intent와 provenance로 결합하며 provider 발급값으로 가장하지 않는다.

### 상태 소유자와 roll-up

후보 단일 계약은 `docs/team/service-flow-state-contract.json`이다. Task·subtask·assignment·delivery·
effect·blocker는 각자 revision과 상태를 소유한다. 한 delivery의 ACK가 Task 전체 상태를 덮지 않는다.
ACKNOWLEDGED 뒤 전달 leg는 다음 hop을 READY로, 최종 담당 leg는 해당 assignment를 EXECUTING으로 진행한다.
sibling 결과/차단은 keyed entity event로만 갱신하며 다른 sibling을 종결하거나 덮어쓰지 않는다.
Task COMPLETED는 현 run의 모든 필수 subtask 검증 결과 + 독립 Quality 결과 + 사람 최종 전달 receipt를
동시에 요구한다. 미해결 blocker/pending/STOP이면 완료 불가다. AC-18에서 이 조건을 기계 검증한다.

## 5. 실제 실행·전송·수신

자동 실행 주체는 **각 역할의 활성 Codex agent**다. Node/Python 프로세스가 앱 도구를 호출할 수 있다고 가정하지 않는다.
driver는 다음 한 건의 typed action을 반환하고, agent bridge가 앱의 send_message_to_thread/wait_threads 도구를 호출한다.
source_endpoint는 현재 실제 활성 역할에 결속돼야 하며 CEO가 다른 역할 ID를 사칭해 대신 보내지 않는다.

### Host 신뢰 경계 v1 — PH-FEASIBILITY에서 구현 가능성부터 검증

  못하면 PH-FEASIBILITY 결과를 HOST_BINDING_UNAVAILABLE_IN_SCOPE로 기록한다. 새 ACTIVE dispatch와
  P6 host 통합은 차단한다. host 없는 로컬 코어는 §6의 LC-ADMISSION을 따르며 PH 양성을 요구하지 않는다.
  필요한 플랫폼 최소 요구와 미충족 시 축소 계약을 분리 제시하며 false를 묵시적으로 true로 바꾸지 않는다.

1. 01 사용자 turn: 분류→Task 저장→driver tick→Router prepare→정확한 target/prompt로 02에 전송.
2. 수신 agent turn: canonical root·activation·model plan·manifest·endpoint·payload scope 검증.
   기존 채팅의 무관한 미완료 일은 재개하지 않는다. ACK-only는 ACK만 반환하며 child route를 만들지 않는다.
3. 검증된 envelope/결과를 실제 tool provenance와 함께 수신 영수증으로 저장한다.
   검증된 target ACK 뒤에만 record-delivery로 inbound scope를 닫고 원 Task를 한정해 다음 일을 수행한다.
   APP_QUEUED/도구 접수 receipt는 전송 감사만 기록하며 DELIVERED/ACKNOWLEDGED 또는 scope close로 승격하지 않는다.
   현재 CLI가 app receipt와 target ACK를 구별하지 못하는 부분은 P6 adapter/CLI 계약에서 변경해야 한다.
   rejected target은 record-rejection으로 종결하고 queued 결과를 ACK로 합성하지 않는다.
4. source는 bounded wait로 해당 대상의 ACK/결과를 회수한다. 기다릴 때 새 사용자 STOP을 즉시 우선 처리한다.
5. actor마다 이번 turn의 미확인 수신/송신부터 조정한 뒤 다음 action을 수행하고 진행/차단 증거를 남긴다.

§6의 PH-FEASIBILITY에서 API와 신뢰 경계의 가능성을, 승인 후 PH-LIVE-PROBE에서 최초/수신 turn과 재개 시 실제 실행 진입점을
검증해야 한다. runbook을 써 둔 것만으로
자동 적용됐다고 하지 않는다. role skill/hook 연결이 필요하면 설치 가능성과 현재 host hook API를 먼저 확인한다.
새 incoming task 메시지가 수신 agent를 깨우고 이후 다음 actor를 깨우는지 실증 전까지 자동 서비스 완료가 아니다.

### 시계 신뢰와 소유자 결정

조사는 기존 strict 기준으로 가용성을 판정하며, 대안의 위험 수용 전에도 caller/receipt/fence를 조사할 수 있다.
UTC 값을 반환하는 도구의 존재와 조작/역행/drift 경계를 보장하는 신뢰 시계 계약은 다르다.
로컬 host UTC + monotonic elapsed + 허용 drift 기록 대안은 OWNER_DECISION_REQUIRED이며 자동 채택하지 않는다.
그 대안을 채택하려면 정확한 scope, 최대 drift/lease, 재부팅/역행/큰 시간 점프 시 차단,
동일 사용자·관리자 시계 조작을 방어하지 못한다는 잔여 위험과 유효기간을 사람이 승인해야 한다.
선택하지 않으면 strict 요구를 유지한다. 시계 외 필수 입력도 빠져 있으면 시계 승인만으로 PH를 승격하지 않는다.
모든 source 읽기를 완료한 뒤 결정적인 MISSING이 있으면 UNAVAILABLE이며, 결정적 부재 없이 미확인만 있으면 INCOMPLETE다.

static 필수 입력은 caller provenance, raw receipt provenance, source/send/effect fence 집행 경로, trusted UTC다.
live-only 항목은 실제 wake/ACK/재개 관측이다. static UNVERIFIED를 LIVE_PROBE_REQUIRED로 바꾸어 통과하지 않는다.
새 FEASIBLE_STATIC 판정은 새 scope ID와 plan/acceptance/state의 requirements bundle SHA,
host tool-catalog 원출력 hash 및 실제 조회 성공 출처, 모든 static 필드의 양성 증거를 결속해야 한다.
HOST-SCOPE-001 음성 기록을 편집하거나 source hash가 같다는 이유만으로 양성 판정에 재사용하지 않는다.
FEASIBLE_STATIC도 실제 wake/ACK 성공은 아니다. phase depends_on과 허용 outcome은 acceptance catalog에 고정한다.

### 중단·재시도와 crash window

intent는 prepare 전에 영속화한다. prepare 성공 결과를 보호 runtime에 저장한 뒤 전송한다.
현재 CLI는 호출마다 새 route/token을 만들므로 blind prepare 재호출은 금지한다.
동일 intent_key의 prepare 조회/재사용과 exact prepared payload 복원을 지원하는 CLI 보완이 선행돼야 한다.
prepare 성공 직후 checkpoint 전에 죽은 경우에도 intent_key로 기존 route를 되찾을 수 있어야 한다.

P2b의 비활성 prepare 저장소는 `intent_key = SHA256(task_id, run_generation, assignment_id, leg_id, work_spec_revision,
logical_source, logical_target, message_kind)`에 UNIQUE/CAS를 적용한다. 같은 key·같은 payload면 최초 route/token을
반환하고 다른 payload면 INTENT_CONFLICT다. key 예약, envelope/route/token 생성, recoverable commit marker를
한 intent 잠금/트랜잭션에 묶고 Router event chain과 scope 생성의 부분 성공도 marker로 재생한다.
같은 run_generation의 재시도/endpoint successor 복구는 같은 intent key와 route/token을 유지한다.
RESUME으로 run_generation이 바뀌면 새 intent key와 새 route/token을 발급하며 옛 route는 감사/조정에만 쓴다.
effect_key는 run_generation과 별개로 유지하여 이미 발생한 업무 효과를 중복 실행하지 않는다.
새 UUID를 발급한 뒤 key를 나중에 쓰는 구현은 금지한다. 이 계약 시험이 P3 전체/P4 진입의 선행조건이다.
§6의 C1/C2 한정 수정은 예외이며 실제 Router runtime 대신 격리된 fixture만 사용한다.

send 성공 후 기록 전 crash는 UNKNOWN_DELIVERY다. token으로 대상 결과·Router 원장을 조정하기 전 재전송하지 않는다.
운송 계층의 exactly-once를 주장하지 않고 at-least-once + 수신 token dedupe + 업무 idempotency를 사용한다.
transport에 token 조회/중복 억제 기능이 없으면 해당 ambiguous send는 자동 retry 대신 사람에게 보고한다.
REJECTED는 terminal, retry는 정책 retryLimit 이내에서만, timeout은 업무 실패와 구분한다.
같은 업무 실행 세대의 endpoint successor 이동은 endpoint만 바꾸고 in-flight route/token을 유지한다.
이동 자체로 run_generation을 올리지 않는다. 사람 승인 RESUME은 이와 다른 업무 실행 세대 전환이다.

## 7. 기계 판독 수용 시험 계약

## 8. 모델·검수·토큰

주담당은 구현/실행 시험, Sol ultra는 계획과 중요 통합 checkpoint의 독립 교차검수에만 사용한다.
Sol 검수는 한 담당자, 추가 하위 agent 없음. 동일 finding의 후속 확인은 diff·시험을 재사용하되, 최종 계획 승격 전에는 전체 문서의 절 간 일관성을 별도 확인한다.
검수자 수나 재독 범위는 이 문서가 스스로 승인하지 않으며 사용자 지정과 저장소 검수 규격을 따른다.
이번 계획은 Fable/Opus를 호출하지 않는다. Sol 결과를 Fable/Opus 공식 게이트로 가장하지 않는다.
기존 필수 gate 대체는 별도 사람의 명시적 정책 결정과 문서/기계 계약 변경 없이는 수행하지 않는다.
새 외부 유료 회차에는 기존 정책의 정확한 soft-cap 위험 승인이 필요하다.

구현 모델/추론 변경은 기존 model-plan.json의 후속 후보 판본에 명시하고 기존 SHA 소비자를 조사한 뒤
재봉인한다. 계획 hash를 조용히 바꿔 기존 ACTIVE_DISPATCH가 깨지는 배포를 하지 않는다.
모델 가중치는 실측/명시 보수 추정의 근거 없이는 만들지 않는다. Sol ultra가 미보정이면
MULTI_MODEL_CALIBRATION_REQUIRED로 경제성 rollover만 보류하고 승인된 읽기/시험 결과는 기록한다.
단, 구현을 위한 P2 model gate는 별도다. 보정 누락으로 후속 계획 자체를 봉인하지 못하면 구현 역시 보류한다.
이번 Sol 자문을 이유로 기존 Fable/Opus 역할을 지우거나 새 gate PASS를 만들지 않는다.

## 9. 활성화·복구·완료 게이트

후보 변경을 별도 stage에서 모아 검증하고 기존 운영 원본과 충돌하지 않는 전환 창을 잡는다.
검수 전 candidate_manifest에 plan/acceptance/state schema/runner/assertion verifier/구현/시험/policy/design/model/manifest/plugin/수신 절차 hash를 먼저 봉인한다.
formal review receipt는 candidate_manifest SHA, engine/route, risk_class, Findings와 종결 상태, protocol 판본,
Fable 기본 또는 자격 증거가 있는 Opus 승계를 typed 필드로 결속한다. Sol advisory나 timeout은 거부한다.
R2/R3 위험등급은 Opus 승계만으로 닫지 않고 공식 정책의 Fable 표본 재감사 또는 exact SHA 사람 위험 수용도 요구한다.
사람 Decision은 candidate SHA + formal receipt SHA의 approval_target과 범위를 지정한다.
최종 activation envelope는 epoch_id/previous_epoch, candidate SHA, formal receipt SHA, Decision SHA를 묶는다.
Decision이 자기 SHA를 포함한 envelope를 서명하는 순환 참조는 만들지 않는다.
기존 사람 승인을 새 SHA 승인으로 재사용하지 않는다.

신규 send를 닫고 in-flight 목록/캡처 epoch를 보존한다. 모든 send adapter가 runtime의 단일
`current_epoch`를 읽고 expected_epoch CAS/fence를 집행하는 것이 배포 선행조건이다. bundle 전체를 검증한 뒤
동일 프로젝트 잠금에서 current_epoch를 atomic CAS로 바꾸고 P8은 PROBE_ONLY capability만 연다.
PROBE_ONLY에서는 exact 승인된 ACK-only source/target/kind/token 범위만 허용하며 업무 child route와 일반 신규 send를 거부한다.
AC-16 실제 통과 후에도 candidate/receipt/Decision의 일반 pilot 권한을 다시 검증해야 P9 제한 dispatch를 연다.
probe 권한만 승인됐다면 일반 dispatch는 계속 닫는다.
부분 파일 교체가 원자적이라고 주장하지 않는다. fixed canonical 경로만 읽는 구 CLI는 epoch-capable adapter/CLI로
이관되기 전에는 신버전 전환에 참여할 수 없다. 혼합 판본 호출자는 거부한다.

새 send는 새 epoch만, 기존 in-flight ACK/결과는 발송 당시 캡처한 immutable bundle과 verifier 판본으로 검사한다.
옛 epoch는 기존 route 수신/감사에만 허용하고 신규 route·retry 권한을 부활시키지 않는다. 이전 runtime 형식이
새 verifier와 호환되지 않으면 outbox를 격리하고 전환을 중단한다. epoch CAS 실패 시 send gate는 닫힌 채 유지한다.

11 endpoint를 실재 작업과 대조한다. 이미 맞는 endpoint는 유지하고, 최초 결속과 successor를 혼동하지 않는다.
필요한 역할만 실제 handoff→RESTORE_VERIFIED→요구 Study Gate→generation CAS로 교체한다.
ID 직접치환, 가짜 영수증, 검수 생략으로 연결을 맞추지 않는다.

신규 계약 검증 실패 시 신규 dispatch는 차단한다. 이전 계약으로 복구할 때도 저장된 정확한 bytes와
호환 runtime을 함께 확인하며 새 generation을 임의 역행시키지 않는다. 기존 미확인 결과 수신은 보존한다.

정상 완료에는 코드/시험 PASS만 아니라 **11 actor 연결 검증, 실제 비운영 요청 왕복, 협업·직접 보고·재개·
중단·crash/reconcile·successor 증거, 필수 검수/승인, 현재 verify 실패의 처분**이 필요하다.
P9 결과를 기존 AI 팀 운영 스타터 키트에 역반영하되 새 경쟁 키트를 만들지 않는다.

## 10. 실행 상태의 단일 출처

최신 판정·allowed actions·검수 이력·PH 결과·각 gate 상태는
[TEAM-SERVICE-FLOW-CURRENT.json](ai-review/evidence/TEAM-SERVICE-FLOW-CURRENT.json)만 소유한다.
계획 본문에는 현재 판정과 실행 체크박스를 복제하지 않는다. 과거 검수 원본은 각 입력 hash와 함께 보존한다.
이 계획이나 후보 계약 파일의 존재 자체는 구현·검수·활성화 성공 증거가 아니다.
