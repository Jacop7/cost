## 1. 출시 범위

### 1.1 출시 국가와 기본값

| 국가 | 국가 코드 | 통화 | 업무 로케일 | 기본 세금명 | 기본 가격 기준 | 하위 관할 |
|---|---|---|---|---|---|---|
| 한국 | `KR` | `KRW` | `ko-KR` | 부가세 | 세금 포함 | 불필요 |
| 미국 | `US` | `USD` | `en-US` | Sales tax | 세금 미포함 | 주·카운티·도시 필요 |
| 영국 | `GB` | `GBP` | `en-GB` | VAT | 세금 포함 | 1차 불필요 |
| 호주 | `AU` | `AUD` | `en-AU` | GST | 세금 포함 | 1차 불필요 |
| 캐나다 | `CA` | `CAD` | `en-CA` | GST/HST | 세금 미포함 | 주 필요 |

국가 기본값은 입력을 돕는 제안이며 법정 세율을 영구 보증하는 카탈로그가 아니다. 세율은 매장이
관할과 적용 대상을 확인해 저장하고 이후 변경할 수 있다.

### 1.2 언어·국가·통화 경계

- 앱 언어는 `ko`와 `en` 두 가지이며 사용자 표시 선호다.
- 국가·업무 로케일·통화·세금·매장 시간대는 매장 계약이다.
- 영어 UI를 쓰는 한국 매장도 `KRW`와 한국 세금 계약을 유지할 수 있다.
- 같은 영어 UI라도 미국·영국·호주·캐나다의 통화와 금액 형식은 각각 다르다.
- 1차는 국가당 통화 하나만 지원한다. 매장 다중 통화, 환전, 환율 손익은 범위 밖이다.
- 매장 시간대는 국가만으로 확정하지 않는다. 기존 서버 시간대 설정을 별도로 유지한다.
- 1차에서 지원하는 판매는 등록 매장의 관할 안에서 발생한 매장·배달·포장 판매다. 미국·캐나다의
  타 주·도 배송처럼 주문별 공급 장소 판정이 필요한 판매는 자동 판정하지 않고 범위 밖으로 둔다.

### 1.3 현재 로케일 계약 이관

현재 `packages/core`와 `locale_defaults()`는 `ko`, `en-US` 외에 `ja`, `de`, `ar-SA`, `ar-AE`,
`vi`, `es-ES`, `es-MX`, `pt-BR`도 안다. 새 계약은 이 값을 통화 권위로 사용하지 않는다.

- `ko`는 앱 언어 `ko`, 업무 로케일 `ko-KR` 후보로 자동 이관한다.
- `en-US`는 앱 언어 `en`, 업무 로케일 `en-US` 후보로 자동 이관한다.
- 나머지 여덟 값은 임의의 출시 국가·통화로 추정하지 않는다. 기존 표시는 유지하되 시장 프로필
  활성화 전에 사용자가 국가·통화·업무 로케일을 확인해야 한다.
- 기존 값을 삭제하거나 `en`으로 조용히 합치지 않는다. 이관 전후 행 수와 값 대응표를 upgrade 시험에
  고정한다.

## 3. 세금 의미와 계산 계약

### 3.0 계산 결과의 제품 경계

현재 앱은 영수증·주문 한 건씩 저장하지 않고 `영업일 × 메뉴` 행에 매장·배달·포장 수량을 누계한다.
따라서 1차 세금 결과는 **영업 관리와 손익 계산을 위한 확정값**이며 세금 신고서·법정 영수증의
거래별 세액을 대신하지 않는다. 영수증 단위 반올림·배송지별 세율·복합 공급 배분이 필요해지면
주문/거래 원장을 별도 schema version으로 먼저 추가한다.

세금 계산선은 `영업일 × 메뉴 × 판매 채널`이다. 현재 `daily_sales_items` 한 행에 있는 세 채널 수량은
계산할 때 세 개의 독립 계산선으로 펼치며, 판매 스냅샷도 채널별로 남긴다.

### 3.1 저장하는 세율

- 사용자는 법정 표면 세율을 퍼센트 포인트로 입력한다. 한국 10%는 `10`으로 저장한다.
- 포함 가격이라고 해서 사용자가 `10/110 = 9.0909…`를 입력하지 않는다.
- 빈 추가세 목록은 추가세 0원이다.
- 플랫폼·배달 수수료는 세금이 아니며 기존 고정 지출 계약을 유지한다.

### 3.2 과세 상태

| 값 | 의미 | 계산 금액 |
|---|---|---|
| `taxable` | 일반 과세 | 설정 세율 적용 |
| `zero_rated` | 0% 과세 | 0원이지만 과세 공급 의미 보존 |
| `exempt` | 면세 | 0원이지만 면세 공급 의미 보존 |

`zero_rated`와 `exempt`는 금액이 같아도 신고 의미가 다르므로 하나로 합치지 않는다.

### 3.3 추가세 계산 기준

| 값 | 추가세 과세표준 |
|---|---|
| `primary_tax_exclusive` | 세금 제외 판매가 |
| `primary_tax_inclusive` | 세금 제외 판매가 + 기본세 |

선택 중인 추가세 자체와 다른 추가세는 해당 항목의 과세표준에 포함하지 않는다. 다른 추가세를 선택적으로
포함하거나 순서대로 중첩하는 특수세는 1차 범위 밖이며 별도 schema version으로 추가한다.

### 3.4 공통 공식

다음 기호를 사용한다.

- `N`: 모든 세금 제외 판매가
- `r0`: 기본세율
- `ri`: 추가세 `i`의 세율
- `r0_effective`: `taxable`이면 `r0`, `zero_rated`·`exempt`이면 `0`
- `A(treatment)`: 해당 과세 상태에 명시적으로 적용되는 추가세 집합
- `bi`: 기본세 미포함이면 `1`, 기본세 포함이면 `1 + r0_effective`
- `M = 1 + r0_effective + Σ(i ∈ A(treatment))(ri × bi)`

가격이 세금 미포함이면:

```text
N = 레시피 판매가
기본세 = N × r0_effective
추가세 i = N × ri × bi  (i ∈ A(treatment))
고객 결제액 = N × M
```

가격이 세금 포함이면:

```text
고객 결제액 = 레시피 판매가
N = 고객 결제액 ÷ M
기본세 = N × r0_effective
추가세 i = N × ri × bi  (i ∈ A(treatment))
```

세율은 계산할 때 `rate_pct / 100`으로 바꾼다. DB RPC가 확정 금액을 만들고 `packages/core`는 같은
공식의 입력 미리보기와 SQL 대조 시험만 제공한다.

### 3.5 금액 정밀도와 반올림

- 세율과 중간 계산은 PostgreSQL `numeric` 풀정밀도로 유지한다. 앱의 JS 부동소수점 결과를 확정값으로
  저장하지 않는다.
- 통화 메타데이터가 `minor_unit`을 소유한다. 1차는 `KRW=0`, `USD/GBP/AUD/CAD=2`다.
- 계산선의 `listed_total = unit_price × 해당 채널 최종 수량`을 먼저 만든다.
- 기본세와 추가세 **각 구성 항목의 계산선 금액**을 풀정밀도로 계산한 뒤 각각 통화 minor unit으로
  반올림한다. 양수 금액의 정확한 절반은 PostgreSQL `round(numeric, minor_unit)`과 같은 방향으로
  올린다.
- `tax_total`은 반올림한 구성 항목의 합이다. 포함가는 `net_sales = customer_total - tax_total`,
  미포함가는 `customer_total = net_sales + tax_total`로 마지막 등식을 맞춘다. 반올림 잔차를 이름 없는
  세금 항목에 넣지 않는다.
- 저장은 현재 목표 수량으로 계산한 목표 세액과 기존 목표 세액의 차이만 반영한다. 같은 목표 수량
  재호출은 세금 원장·판본을 늘리지 않고, 일부 감소는 새 목표와의 차이를 환입하며, 수량 0 취소는
  원래 확정 세액을 정확히 0까지 되돌린다. 국제 세금 스냅샷·이벤트가 생긴 판매행은 수량 0에서도
  물리 삭제하지 않는다. 수량 0인 판매행 tombstone과 스냅샷을 남기고 반대 부호 이벤트 합을 0으로
  맞춘다. 화면·집계는 수량 0을 판매 없음으로 취급하되 감사 원장은 보존한다.

`zero_rated`와 `exempt`는 모두 기본세의 유효 세율을 0으로 만들지만 신고 의미는 그대로 보존한다.
따라서 기본세 포함 기준 추가세도 `bi = 1 + 0 = 1`이 된다. 추가세는 과세 상태만 보고 임의로
면제하거나 부과하지 않는다. 각 추가세가 `taxable`·`zero_rated`·`exempt` 중 어디에 적용되는지
`applies_to_treatments`로 명시하고, 비어 있거나 판정할 수 없으면 저장을 실패 폐쇄한다. 유효 과세
상태는 판매 확정 전에 매장 기본값과 향후 허용할 메뉴·채널 override 우선순위로 하나를 결정해 판매
스냅샷에 고정한다. override 소유 단위와 우선순위는 §10의 확정 결정을 따른다.

### 3.6 납부 주체

납부 주체는 세액과 고객 결제액을 바꾸지 않는다. 확정 세액을 다음 부채로만 나눈다.

- `merchant`: 매장 납부 예정 세금
- `marketplace`: 플랫폼 대납 예정 세금

납부 주체는 `세금 구성 항목 × 판매 채널` 단위로 확정한다. 매장 기본값은 입력 편의를 위한 제안이고,
매장·배달·포장 채널별 override를 허용한다. 판매 전체에 단일 `remittance_owner`를 저장하지 않으며
판매 시점 스냅샷의 각 구성 항목이 자기 납부 주체를 가진다. 1차에는 판매 한 번만을 위한 임시 override는
두지 않는다.

## 4. 개념 데이터 계약

### 4.1 매장 시장 프로필

```text
country_code
region_code nullable
currency_code
business_locale_code
price_basis
effective_from
revision
```

앱 언어는 인증 사용자별 `user_preferences.app_language`가 소유한다. 매장 시장 프로필과 같은 값으로
묶지 않으며 한 매장의 여러 사용자가 서로 다른 앱 언어를 선택할 수 있다. 로그아웃 상태의 최초값은
기기 언어에서 `ko/en`만 제안하고, 인증 뒤에는 서버의 사용자 선호가 권위다.

### 4.2 세금 프로필

```text
country_code
region_code nullable
default_treatment
primary_component
additional_components[]
effective_from
revision
market_profile_id
```

세금 구성 항목은 최소한 다음 값을 가진다.

```text
id
kind: primary | additional
name
rate_pct
jurisdiction_level
calculation_basis: primary_tax_exclusive | primary_tax_inclusive
applies_to_treatments: [taxable | zero_rated | exempt]
sort_order: display only
```

기본세의 `calculation_basis`는 항상 세금 제외 판매가이므로 저장하지 않거나 고정값으로 검증할 수 있다.
`sort_order`는 화면 표시 순서일 뿐 계산 순서가 아니다. INTL-1D 계산 몸통은 `sort_order`를 읽지 않고
구성 항목 ID·`kind`·`calculation_basis`로 계산하며, 표시 순서 변경은 계산 판본을 바꾸지 않는다.
`price_basis`의 소유 원본은 매장 시장 프로필 하나다. 세금 프로필은 이 값을 중복 저장하지 않고
`market_profile_id`로 적용 시장 프로필을 참조한다. 두 프로필은 불변 ID와 적용 구간을 가지며 같은
매장·현지 날짜에 겹치는 활성 구간을 허용하지 않는다. 판매 RPC는 영업일 행을 잠근 뒤 그 날짜에 유효한
시장·세금 프로필을 같은 트랜잭션에서 선택한다. 판매 스냅샷도 그 두 ID와 revision을 함께 굳힌다.

세금 프로필 변경은 이미 열린 영업일을 바꾸지 않는다. 서버가 계산한 **다음 미개장 영업일**부터 적용하고,
예약 변경끼리의 충돌은 프로필 revision으로 거부한다.

### 4.3 과세 상태와 관할 소유

- 매장 세금 프로필은 기본 `treatment`를 제안한다.
- 메뉴는 1차부터 `tax_category` 또는 명시적 treatment override를 가진다. 국가별 음식·음료의 서로 다른
  과세 상태를 매장 기본값 하나로 합치지 않는다.
- 1차에는 채널별 treatment override와 판매 1회성 override를 두지 않는다. 채널은 납부 주체만
  override한다.
- `region_code`는 임의 문자열이 아니라 `country_code`와 함께 검증되는 제품 소유 관할 코드다.
  가능하면 ISO 3166-2를 사용하고, 카운티·도시처럼 ISO로 표현되지 않는 단계는 국가별 검증 카탈로그와
  상위 코드 관계를 저장한다.

### 4.4 판매 시점 스냅샷

판매 계산선(`영업일 × 메뉴 × 판매 채널`)에는 최소한 다음 의미를 당시 값으로 보존한다.

```text
market_profile_id · tax_profile_id
country_code · region_code · currency_code · minor_unit
price_basis · treatment · tax_category · sales_channel
market_profile_revision · tax_profile_revision · calculation_version
unit_price · final_quantity · listed_total · net_sales · customer_total
기본세와 추가세별 ID·종류·이름·세율·계산 기준·적용 과세 상태·납부 주체·확정 금액
merchant_tax_liability · marketplace_tax_liability
```

설정을 바꾸거나 국가 기본값이 변경돼도 과거 판매·손익·세금 상세는 변하지 않는다.

## 5. 현재 DB에서 새 계약으로 이동

### 5.1 확인된 현재 계약

- 현재 `tax_of()`는 `판매가 × (Σ tax_items.rate ÷ 100)`로 계산한다. `rate`는 퍼센트 포인트다.
- 포함가 한국 부가세는 법정 세율 10이 아니라 판매가 대비 유효 세율 `9.0909…`로 저장한다.
- `tax_mode`는 호환용 자리만 남고 계산에서 사용하지 않는다.
- 현재 언어 설정이 통화와 금액 자릿수를 강제로 결정한다.
- 현재 영어 기본은 `en-US/USD` 하나라 `GBP`, `AUD`, `CAD` 매장을 표현할 수 없다.

### 5.2 migration 원칙

1. 기존 migration을 수정하지 않고 새 migration을 추가한다.
2. 시장·세금 프로필과 새 계산 함수를 확장형으로 먼저 배포한다.
3. 기존 RPC와 새 RPC를 구 앱 소멸 전까지 호환하거나 최소 앱 버전으로 쓰기를 차단한다.
4. 기존 매장은 기본적으로 `KR/KRW/ko-KR/세금 포함` 후보로 이관하되 실제 값 감사를 먼저 수행한다.
5. 이름이 `부가세`이고 유효 세율이 허용 오차 안에서 `10/110 × 100`인 항목만 기본세 법정 세율 10으로
   미래 적용 프로필에 자동 변환한다.
6. 그 밖의 기존 항목은 임의로 의미를 추정하지 않고 수동 확인 대상으로 표시한다.
7. 기존 판매·영업일의 저장 세액은 `legacy_effective_rate_v1` 계산 판본과 당시 합계 그대로 보존한다.
   과거 구성 항목·과세 상태·납부 주체를 역산해 만들지 않는다.
8. `etc_tax_rate`와 기타 매출의 저장 세액도 같은 원칙으로 보존한다. 반올림된 `etc_tax ÷ etc_revenue`로
   과거 세율을 되짚거나 법정 세율로 가장하지 않는다.
9. 새 앱 전환과 관측 후 구 필드·구 함수 제거는 별도 정리 migration으로 수행한다.

### 5.3 갱신 대상 RPC와 스냅샷

- 세금 항목 검증과 저장
- `tax_of`와 `tax_breakdown`
- 레시피 손익·권장 판매가·전파 계산
- 영업 시작 스냅샷
- E10 판매 저장과 판매 정정
- E9 판매 감소·취소와 종료 영업일 정정의 당시 세금 환입
- 일·기간·메뉴·채널별 손익과 세금 상세
- 설정 revision 충돌과 무변경 저장

판매 감소·취소와 과거 정정은 원판매 스냅샷의 프로필·구성 항목·반올림 결과를 사용한다. 현재 프로필로
다시 계산하지 않는다. 변경되지 않은 판매 계산선은 UPDATE하지 않으며, 목표 수량 대조로 세금 증감만
기록한다.

## 6. 서버와 외부 서비스

### 6.1 1차 구조

- 기존 Supabase 중심 모듈러 모놀리스를 유지한다.
- 세금 확정 계산은 Postgres RPC에 둔다.
- 국가·통화·세금 지원만으로 Queue, Edge Function, 외부 Worker를 추가하지 않는다.
- 세율은 수동 확인·저장을 기본으로 하며 자동 세율 서비스와 법률 판정 엔진을 두지 않는다.

### 6.2 향후 분리 검토 조건

다음 중 하나가 실제 요구로 확인될 때만 외부 세금 서비스를 별도 검토한다.

- 주소 단위 미국 세율 자동 조회가 제품 필수 기능이 됨
- 세율·면세 규칙 변경을 사람이 유지할 수 없는 규모가 됨
- 외부 POS·마켓플레이스가 세금 판정 근거와 버전 반환을 요구함
- 법정 신고·전자영수증·세금계산서 연동이 제품 범위에 포함됨

외부 서비스를 도입하더라도 공급자 응답·적용 시각·규칙 버전을 판매 스냅샷에 남기고, 외부 서비스가
업무 테이블을 직접 수정하지 않게 한다.

## 8. 배포 단위와 복구

- 앱·core·types·DB·시험·문서를 `codex/international-launch` 한 세로 기능 브랜치에서 완결한다.
- DB 변경 브랜치는 동시에 하나만 연다.
- 스키마 확장 → 데이터 이관 → 새 RPC → 앱 전환 → 관측 순으로 배포한다.
- 구 계약 제거는 같은 배포에 넣지 않는다.
- 실패 시 새 경로를 비활성화하고 구 읽기 계약을 유지하며, 이미 적용한 migration은 새 migration으로
  전진 복구한다.
- 새 세금 쓰기를 켜기 전 서버 capability와 최소 앱 버전 게이트를 먼저 배포한다. 구 앱의 세금 쓰기는
  `CLIENT_UPGRADE_REQUIRED`로 실패 폐쇄하며 새·구 계산을 양방향 dual-write하지 않는다.
- 새 계약으로 판매가 한 건이라도 확정된 뒤에는 구 계산 경로로 rollback하지 않는다. 결함은 새
  migration과 새 계산 판본으로 전진 수정한다.
- 운영 적용 전 5개국 합성 매장으로 스테이징 검산을 통과한다.

## 10. 구현 전 확정 결정

1. **계산선·반올림**: `영업일 × 메뉴 × 판매 채널 × 세금 구성 항목`별로 minor unit 반올림하고
   반올림한 항목 합으로 총세액을 만든다. 신고용 영수증 단위 계산은 범위 밖이다.
2. **적용 시점**: 프로필 변경은 다음 미개장 영업일부터 적용한다. 열린 영업일 스냅샷은 불변이다.
3. **플랫폼 대납**: 구성 항목×채널 단위. 매장 기본값과 채널 override만 두고 판매 1회성 override는 없다.
4. **국가·통화 변경**: 매출뿐 아니라 발주·입고·고정지출 등 금액 원장이 하나라도 생기면 변경을
   금지한다. 1차에는 환율 없는 혼합 통화 기간 장부를 만들지 않는다.
5. **앱 언어**: 인증 사용자별 선호가 소유하며 시장 프로필과 분리한다.
6. **구 앱**: 최소 앱 버전/capability 게이트로 세금 쓰기를 차단한다. 양방향 dual-write는 하지 않는다.
7. **과세 상태**: 매장 기본값보다 메뉴 `tax_category`/override가 우선한다. 채널·판매 override는 1차
   범위 밖이다.

이 결정과 아래 스키마 초안·검산 예시는 기준선 WORKING 검수
`INTL-LAUNCH-CONTRACT-HARDENING-001/r002`와 COMMIT 검수
`INTL-BASELINE-COMMIT-001/r001`을 통과했다. 구현은 `INTL-1A`부터 순서대로 진행하고 각 단계의
변경물도 필수 로컬 게이트와 당시 승인된 독립 검수 엔진을 다시 통과해야 다음 단계로 넘어간다.
사용자가 Fable 재개를 명시하기 전까지는 Opus를 별도 대체 게이트로 사용하며 결과를 Fable로 표기하지 않는다.

## 11. 구현 스키마와 검산 최소안

구현 migration은 이름이 달라질 수 있지만 다음 의미를 분리해야 한다.

```text
store_market_profiles
  id · store_id · country_code · region_code · currency_code · business_locale_code
  price_basis · effective_from · effective_to · revision

store_tax_profiles
  id · store_id · market_profile_id · default_treatment
  effective_from · effective_to · revision

store_tax_components
  id · tax_profile_id · kind · name · rate_pct · jurisdiction_level
  calculation_basis · applies_to_treatments · sort_order(display only)

menu_tax_overrides
  recipe_id · tax_profile_id · tax_category · treatment

channel_tax_remittance
  tax_component_id · sales_channel_code · remittance_owner

daily_sales_item_tax_snapshots
  daily_sales_item_id · sales_channel_code · market_profile_id · tax_profile_id
  calculation_version · final_quantity · input_snapshot · amount_snapshot

daily_sales_item_tax_component_snapshots
  sales_tax_snapshot_id · component_id_snapshot · remittance_owner · unrounded_amount · rounded_amount

sales_tax_events (append-only)
  daily_sales_item_id · sales_channel_code · component_id_snapshot · delta_amount
  target_quantity · calculation_version · business_day_revision_no · reverses_event_id nullable
```

구성 항목 snapshot의 합은 계산선의 `tax_total`과 같아야 하고, 구성 항목별 `sales_tax_events`의 합은
현재 구성 항목 snapshot 금액과 같아야 한다. 취소·정정은 기존 이벤트를 지우지 않고 반대 부호 또는
새 목표와의 차이 이벤트를 추가한다. 이 합계 불변식은 국제 세금 쓰기 capability를 켜기 전에 DB가
강제한다. `reverses_event_id`는 INTL-1D에서 같은 매장·판매 계산선의 원 이벤트만 가리키는 필수 계약으로
만들거나 제거하며, nullable·미검증 상태로 쓰기 경로에 사용하지 않는다.

`profile_id + revision`이 가리키는 계산 내용은 불변이다. 기존 시장·세금 프로필 행은 하위 프로필을
범위 밖에 남기지 않는 `effective_to` 마감만 허용하고, 국가·통화·가격 기준·기본 과세 상태·구성 항목
세율·카테고리 과세 의미·채널 납부 주체 변경은 새 프로필 행과 새 revision으로 만든다.

세금 이벤트는 일반 판매행 삭제나 직접 DELETE로 없애지 않는다. 수량 0 취소도 반대 부호 이벤트를
남기고 세금 원장이 연결된 판매행은 보존한다. 예외는 기존 `purge_archived_store`가 보존 종료·운영자
승인·백업 근거를 모두 확인한 매장 물리 삭제뿐이며, 이때만 해당 매장의 세금 이벤트도 cascade로
제거한다. 매장 FK가 없는 `store_lifecycle_events`의 물리 삭제 승인 감사는 계속 남는다.

필수 숫자 검산:

- KR 포함가 12,000원·기본세 10%·추가세 없음 → 순매출 10,909원, 세금 1,091원,
  고객 결제 12,000원(KRW 항목 반올림 후 등식 유지).
- USD 미포함 10.00·기본세 10%·추가세 5%가 기본세 포함 기준 → 기본세 1.00,
  추가세 0.55, 고객 결제 11.55.
- 같은 11.55가 포함가이면 순매출 10.00, 기본세 1.00, 추가세 0.55.
- 위 판매를 같은 수량으로 다시 저장하면 세금 이벤트 0건, 절반 감소하면 새 목표와의 차이만 환입,
  0으로 취소하면 세금 합계와 두 납부 부채가 모두 0으로 복귀한다.

## 12. 공식 근거와 검토 경계

- 한국 공급가액은 부가가치세를 포함하지 않는다:
  [국가법령정보센터 부가가치세법 제29조](https://www.law.go.kr/LSW/lsLinkCommonInfo.do?lsJoLnkSeq=1032157099)
- 미국의 일반 지역 판매세는 주·지방 관할별로 달라질 수 있다:
  [California Department of Tax and Fee Administration 지역세 안내](https://www.cdtfa.ca.gov/industry/local-and-district-retailer-taxes/district-tax.htm)
- 영국 VAT는 VAT 제외 tax value와 포함가 VAT fraction을 구분한다:
  [HMRC VAT Guide, Notice 700](https://www.gov.uk/guidance/vat-guide-notice-700)
- 호주 GST는 과세 공급가의 10% 또는 GST 포함 가격의 1/11로 설명된다:
  [Australian Taxation Office GSTR 2001/8](https://www.ato.gov.au/law/view/document?LocID=%22GST%2FGSTR20018%2FNAT%2Fft50%22&PiT=20251112000001)
- 캐나다 계산기는 모든 GST/HST·PST 적용 전 금액을 기준으로 받는다:
  [Canada Revenue Agency GST/HST 계산기와 주별 세율](https://www.canada.ca/en/revenue-agency/services/tax/businesses/topics/gst-hst-businesses/charge-collect-which-rate/calculator.html)

위 링크는 제품 계산 구조의 공식 근거이지 세무 자문이나 영구 세율 카탈로그가 아니다. 실제 출시 전에는
대상 관할·메뉴 유형·판매 채널에 맞는 최신 규정을 사업자 또는 세무 전문가가 확인해야 한다.
