## 1. 대화의 출발점과 목표

디렉터리 재구성에 앞서 사람과 AI의 팀 구조를 먼저 정하고, 기획·설계·개발·UX·QA·보안·릴리스가
서로 독립적으로 검증되면서도 하나의 공식 산출물을 함께 개선하는 운영 체계를 만드는 것이 목표였다.

초기 제안은 다음 구조였다.

- 솔라 울트라가 PO, 아키텍처, 개발, UX 초안을 제작한다.
- 페이블 5가 솔라의 모든 결과물을 수석 테크 리드·프로덕트 전략가 관점에서 스트레스 테스트한다.
- 페이블은 정책 누락, DB 병목, 보안, 코드 결함, UX 이탈 지점을 찾고 테스트·리팩터링·차기 기획을
  제안한다.
- 운영 방식은 일괄 번들 감사와 파트별 실시간 핑퐁 중 선택한다.

논의를 거치며 이 구조는 다음 원칙으로 발전했다.

1. 한 AI가 제작과 최종 승인을 동시에 하지 않는다.
2. 사람 주 오케스트레이터는 최소 오픈 후 6개월 안정화까지 유지한다.
3. AI 부 오케스트레이터가 문서·작업·게이트를 관리하되 정책과 운영 위험은 사람이 소유한다.
4. 기능 QA와 현장 생활주기 QA를 분리한다.
5. Android와 iOS는 별도 조직이 아니라 별도 검증 레인과 증거로 관리한다.
6. 솔라와 페이블은 역할별 완성본을 각각 만들지 않고 하나의 공식 파일을 반복 개선한다.
7. 검수 지적은 수정 후 최초 검수자에게 다시 보내며, 충족될 때까지 횟수 제한 없이 반복한다.
8. 사람 승인이 필요한 업무도 AI 상호검수와 실행 검증을 먼저 끝낸 뒤 결정 패킷 한 번으로 올린다.
9. 실제 사용자 검증은 오픈 후 수행하고, 오픈 전 AI 생활주기 시뮬레이션은 가설로만 취급한다.
10. OneDrive는 작업·검수·복구·문서 기준에서 완전히 제외한다.

## 2. 최종 팀 구성

### 2.1 지휘·조정

#### 사람 주 오케스트레이터

- 제품 목표, 범위, 우선순위와 위험 허용 수준을 최종 결정한다.
- 도메인 정책, 금전 공식, 중요한 DB/RPC/RLS, 운영 데이터, 프로덕션 배포·롤백을 승인한다.
- AI 간 의견 충돌과 `DISPUTED` 쟁점을 결정한다.
- 오픈 초기 고객지원과 실제 사용자 피드백을 직접 담당한다.
- 최소 오픈 후 6개월까지 주 오케스트레이터를 유지한다.

#### AI 부 오케스트레이터·문서 관리자 — 솔라 전용 컨텍스트

- 목표를 요구사항과 작업 ID로 분해한다.
- 선행 조건, 담당 역할, 허용 파일, 입력 판본과 품질 게이트를 관리한다.
- 요구사항 → 설계 → 코드 → 테스트 추적성을 유지한다.
- AI 간 반복 검수를 조정하고 사람에게 필요한 결정만 압축해 올린다.
- 저위험 기술 게이트를 종결하지만 제품 정책과 운영 위험은 승인하지 않는다.

페이블은 AI 부 오케스트레이터의 하위 조직이 아니다. 조정 조직 자체를 독립 감사할 수 있도록 사람
주 오케스트레이터에게 직접 보고한다.

### 2.2 제작 조직 — 솔라 울트라

역할별 컨텍스트를 분리한다.

- PO·도메인 정책: 페르소나, 목표, 요구사항, Given–When–Then 인수 조건, 예외·복구 정책
- 아키텍처·데이터 무결성: DB 관계·제약·인덱스, RPC, RLS, 트랜잭션, 멱등성, 동시성, 롤백
- DB/RPC 개발
- Core 개발
- Mobile 개발
- Integration 개발
- UX·접근성: 화면 흐름, 한국어 마이크로카피, 로딩·실패 상태, 접근성, 반응형

솔라가 만든 산출물은 솔라가 최종 검수하지 않는다. 페이블 또는 Codex가 역할에 맞게 독립 검증한다.

### 2.3 기능·데이터 신뢰성 QA — Codex 전용 컨텍스트

- 요구사항과 구현의 일치 여부를 검증한다.
- 단위·통합·E2E·회귀 테스트를 실행하거나 생성한다.
- DB 원장, RPC, `packages/core` 공식 미러, 동시성, 중복 요청, 오류·재시도를 검증한다.
- `pnpm verify`와 동일 SHA의 CI 증거를 판정한다.
- Android·iOS 원시 실행 증거의 통과·실패를 판정한다.
- 코드·DB·RLS 지적은 텍스트 답변만으로 닫지 않고 실제 실행 증거를 요구한다.

### 2.4 현장 생활주기 QA — Codex 별도 전용 컨텍스트

이 역할은 일반적인 앱 화면 시나리오가 아니라 실제 사용자 하루의 시간 압박과 업무 전환을 반영한다.
전 세계의 다양한 사용 패턴과 반례를 넓게 구성하는 데 Codex를 활용하되, AI 결과를 실제 현장 사실로
간주하지 않는다.

대표 페르소나:

- 직접 조리하는 식당 사장님
- 셰프 또는 메뉴 원가 담당자
- 발주·입고 담당자
- 피크타임에 여러 업무를 동시에 처리하는 1인 운영자

대표 생활주기:

```text
새벽·아침 재고 확인
→ 부족 품목 판단과 발주
→ 납품 도착·검수·입고
→ 조리 중 폐기·대체 재료·긴급 구매
→ 점심 피크 판매와 재고 부족
→ 거래처 연락·네트워크 불안·중복 입력
→ 저녁 피크와 직원 교대
→ 마감 실사·손익 확인·다음 날 준비
```

검증 항목은 인지 부하, 한 손 조작, 장갑·젖은 손, 밝은 주방, 알림 방해, 오프라인·지연, 실수 복구,
직원 교대, 시간대와 영업일 경계 등을 포함한다.

### 2.5 페이블 보안·권한 감사

- 인증·인가·RLS·매장 격리와 개인정보 노출을 독립 감사한다.
- 공격 경로, 권한 상승, 데이터 유출, 비밀정보 포함, 로그 노출을 점검한다.
- 보안 Finding과 구체적인 수정 문구·패치를 제안한다.
- 솔라 수정과 Codex 회귀 증거를 같은 Finding ID로 재검수한다.
- 보고서 자체는 페이블이 확정할 수 있으나 미해결 위험 수용은 사람만 한다.

### 2.6 페이블 독립 종합 감사

- 새 클린 컨텍스트에서 기획·설계·코드·UX·QA·릴리스 준비 전체를 교차 감사한다.
- 솔라는 독립 감사 원문을 발행 전에 편집하지 않는다.
- 발행 후 솔라가 같은 공식 산출물을 수정하거나 반론하고, 페이블이 다시 감사한다.
- 감사 보고서 확정은 페이블, 최종 Go/No-Go는 사람 책임이다.

### 2.7 운영 조직

- 릴리스·복구: 사람 + 솔라 보조
- 관측·데이터 신뢰성: 사람 데이터 책임자 + 솔라 분석 보조 + Codex 검산
- 실제 사용자 검증: 오픈 후 파일럿 사용자
- 고객지원: 오픈 초기 사람이 직접 담당하고 솔라는 분류·답변·문서화를 보조

|---|---:|---:|---:|---:|---:|---:|
| 제품 범위·우선순위 | A | R | C | I | I | C |
| 요구사항·인수 조건 | A | C | R | C | C | C |
| 도메인 정책·기준값 | A | I | R | C | C | I |

| 기능 구현 | I | C | A/R | C | I | I |

| 비정책성 UX 검증·게이트 종결 | I | A(종결 결정) | C | R(통과·실패 판정) | C | C |

`R*`는 지정된 사람 기기 운영자 또는 등록된 자동화 runner가 실기기를 조작한다는 뜻이다. Codex는
기기를 물리적으로 조작하는 주체가 아니라 원시 증거의 QA 판정자다.

AI의 `A`는 기술 결과의 판정 책임이며 제품 정책·운영 위험의 최종 승인을 뜻하지 않는다.

## 4. 필수 상호검수 경로

### 4.1 모든 업무를 동일하게 핑퐁하지 않는 이유

모든 업무를 무조건 솔라↔페이블 왕복시키면 비용과 지연이 커지고 독립 감사의 초점이 흐려진다.
따라서 위험과 역할에 따라 필수·조건부·역할형으로 나눈다.

| 유형 | 업무 | 경로 |
|---|---|---|
| 상호검수 필수 | 요구사항·인수 조건, 도메인 정책·기준값, DB/RPC/RLS, 정책·금전 UX, 릴리스 후보, 운영 데이터 보정 | 솔라 → 페이블 → 솔라 수정 → Codex 증거 → 페이블 재검수 ↺ → AI 부 O → 필요 시 사람 |
| 페이블 선행 역검수 필수 | 보안 Finding, 페이블이 먼저 낸 패치·전략 | 페이블 → 솔라 구현·정책·통합 영향 검토 → 같은 공식본 반영/반론 → Codex 증거 → 페이블 재검수 ↺ |
| 조건부 상호검수 | 기능 구현, 비정책성 UX, 생활주기 시뮬레이션, 배포·롤백 | R0는 Codex 중심, R1은 표본, R2·R3 또는 보안·정합성 영향 시 폐쇄형 검수 필수 |
| 역할형 검수 | 기능·데이터 QA, Android·iOS 실기기 | 실행 증거 → Codex 판정 → 솔라 수정 → Codex 재검증 ↺. 페이블은 보안·테스트 누락 감사 |
| 독립성 예외 | 독립 종합 감사 | 페이블 원문 선행 확정 → 솔라 수정·답변 → 페이블 재감사 |
| 현실 검증 예외 | 오픈 후 현장 검증 | 실사용자 실행 → Codex 구조화 → 솔라·페이블 분석 → 사람 반영 결정 |

### 4.2 완료될 때까지 되돌려 보내는 폐쇄형 루프

```text
OPEN
→ FIXING
→ READY_FOR_REVIEW
→ VERIFIED 또는 OPEN(재작업)
→ CLOSED
```

운영 규칙:

1. 검수자는 `finding_id`, 심각도, 근거, 수정 인수 조건, 필요한 증거를 남긴다.
2. 제작자는 같은 공식 파일에 반영하거나 근거를 붙여 반박한다.
3. 수정 완료 후 반드시 최초 검수 역할에게 다시 토스한다.
4. 최초 검수자만 자기 Finding을 `VERIFIED`·`CLOSED`로 바꿀 수 있다.
5. 미충족 또는 새 결함이면 다시 `OPEN`으로 보낸다.
6. 필수 Finding이 닫힐 때까지 고정 횟수 제한 없이 반복한다.
7. 세 차례 연속 실질적 진전이 없으면 완료가 아니라 `DISPUTED`로 올린다.
8. `PASS`는 검수 결과일 뿐 전체 게이트의 `CLOSED`와 같지 않다.

### 4.3 사람 승인이 필요한 업무도 먼저 AI 검수한다

사람은 각 왕복마다 결재하지 않는다. 제작·반대 역할 검수·수정·재검수·실행 증거·쟁점 종합을 먼저
끝내고 다음 경우에만 결정 패킷을 한 번 받는다.

- 제품 범위·우선순위 또는 도메인 정책 선택
- 재고·단가·원가·세금·손익 공식
- 중요한 DB 스키마·RPC·RLS·migration
- 운영 데이터 삭제·병합·소급 보정
- 미해결 Blocker·Critical 위험 수용
- 감사 권고와 다르게 출시하는 결정
- 실제 사용자 결과의 제품 정책 반영
- 프로덕션 배포·롤백·보안 사고 종결
- 가격·BM·보상·약관·개인정보 결정

## 5. 사람 최종 승인을 뺄 수 있는 범위

다음은 증거와 역할 분리가 충족되면 사람의 매건 최종 결재 없이 기술적으로 종결할 수 있다.

- AI 부 오케스트레이터의 작업 분해·상태·추적·내부 문서
- Codex 기능 QA 및 Android·iOS 플랫폼별 판정
- Codex 현장 생활주기 시뮬레이션 보고서
- lint·typecheck·자동 테스트 결과
- 테스트 코드·fixture·익명화 시드
- 페이블 보안·종합 감사 보고서 자체
- 릴리스 후보 번들·변경 로그·관측 보고서
- 수정 후 최초 발견 팀의 재검증이 끝난 결함의 기술적 `RESOLVED`
- R0와 조건을 충족한 R1의 개발·스테이징 완료

단, 현재 외부 보호 게이트 작업 `P0-2`가 끝나기 전에는 AI 부 오케스트레이터도 공식 `CLOSED`를
선언하지 않고 `VERIFIED`까지만 보고한다.

사람 1명 운영에서는 저위험 R0·R1의 G0·G1·G2를 하나의 통합 착수 패킷으로 승인한다. 정책·공식·
DB/RPC/RLS·운영 데이터 영향이 새로 생기면 통합 승인은 무효가 되고 R2·R3 경로로 전환한다.

## 8. 페이블 활용 방식

페이블은 단순한 마지막 문서 감수자가 아니라 세 가지 역할로 쓴다.

1. 파트별 반대 역할 검수: 정책 반례, 아키텍처 병목, 코드·테스트 누락, UX 맹점
2. 별도 보안 회차: 인증·인가·RLS·비밀정보·데이터 격리
3. 최종 독립 종합 감사: 기존 대화의 결론에 끌려가지 않는 클린 컨텍스트 감사

기본 운영은 위험 업무의 파트별 폐쇄형 검수이고, 큰 마일스톤에서는 번들 종합 감사를 추가한다.
페이블이 제시하는 차기 기능·BM·리팩터링은 현재 결함과 분리해 백로그로 관리한다.

## 9. 솔라·페이블 단일 공식본 공동 작성

### 9.1 별도 역할 문서를 만들지 않는다

요구사항서, 설계서, UX 문서, 소스와 테스트는 주제별 공식 경로 하나만 유지한다.
`solar-*`, `fable-*`, `revised-*` 같은 경쟁 공식본을 만들지 않는다.

입력은 다음 세 종류로 구분한다.

| 입력 | 용도 | 페이블 수정 제안 |
|---|---|---|
| `artifact_paths` | 함께 개선할 유일한 공식 산출물 | 허용 |
| `reference_paths` | `AGENTS.md`, 아키텍처, 결정 기록 | 금지 |
| `evidence_paths` | 테스트·fixture·로그 | 금지 |

### 9.2 공동 작성 흐름

```text
SOLAR_REQUEST + 공식본 수정
→ FABLE_REVIEW + Finding·대체 문구
→ SOLAR_RESPONSE + 같은 공식본 반영 또는 반론
→ CODEX_EVIDENCE + 실행·회귀 증거
→ FABLE_RECHECK(같은 finding_id)
↺ 필수 Finding 종결까지 반복
→ AI_DEPUTY_GATE_DECISION
→ 외부 보호 게이트
```

페이블은 제품 파일을 직접 쓰지 않는다. 페이블 결과를 버리지 않고 회차별 원본으로 보존하며, 솔라는
그 원본을 보고 같은 공식 파일을 수정한다.

### 9.3 공통 상호작용 장부

작업별 `collaboration.md`를 append-only 장부로 사용한다.

- `SOLAR_REQUEST`
- `FABLE_REVIEW`
- `SOLAR_RESPONSE`
- `CODEX_EVIDENCE`
- `HUMAN_DECISION`
- `FABLE_RECHECK`
- `BACKLOG_DISPOSITION`
- `AI_DEPUTY_GATE_DECISION`

비-Fable 턴은 `pnpm fable:append`만 사용하고, Fable 턴은 검수 실행기만 추가한다. 과거 턴 수정·삭제,
직접 편집, 장부 전체 교체를 금지한다.

## 12. 검토 과정에서 발견하고 반영한 중요 수정

### 12.1 폐기된 검산값 복사 문제

초기 팀 기획안의 QA 절에 과거 검산값이 복사돼 있었다.

- 과거: 대파 로스 15% 반영 `4.71원/g`
- 현재: 로스로 나누지 않는 `4.00원/g`
- 과거: 제육볶음 순이익 `4,014원 · 33.4%`
- 현재: 재료비 `2,806.40원`, 순이익 `4,046.69원 · 33.72%`

해결 원칙은 팀 문서에 기준값을 또 복사하지 않고 최신 `AGENTS.md`를 참조하는 것이다. 이 문서에
위 값을 적은 목적도 역사적 오류를 설명하기 위한 것이며 현재 테스트의 별도 기준을 만드는 것이 아니다.

### 12.2 G3 검증 명령

`typecheck`, `test`, `lint`를 각각 요구하면 DB 새 설치·업그레이드·번들 검사가 빠질 수 있다.
G3 증거는 옵션 없는 `pnpm verify` 전체 결과와 동일 SHA의 GitHub Actions 결과로 정리했다.

### 12.3 UX RACI 모순

비정책성 UX 설계의 최종 책임이 검증자에게 있던 모순을 수정했다.

- 솔라 UX: 설계 `A/R`
- Codex: 통과·실패 판정 `R`
- AI 부 오케스트레이터: 기술 게이트 종결 `A`

### 12.4 디렉터리 재구성 경과 규정

이미 시작된 `codex/refactor-domain-boundaries` 작업을 1차 파일럿으로 소급 인정하고 G3·G4 증거를
수집하는 경과 규정을 추가했다. 구조 변경과 기능 변경은 분리한다.

### 12.5 실기기 실행 주체

AI가 실제 기기를 물리 조작하는 것으로 적지 않는다. 사람 기기 운영자 또는 등록 자동화가 실행하고
Codex가 증거를 판정하도록 정리했다.

### 12.6 1인 운영 병목

R0·R1은 G0·G1·G2를 통합 착수 패킷 한 번으로 승인할 수 있게 했다. R2·R3와 운영·보안·데이터 위험은
기존 사람 승인 경로를 유지한다.

### 12.7 실행기 공격 검토

검수 실행기에는 다음과 같은 공격·장애 시나리오를 반복 점검했다.

- 과거 필수 Finding 누락·ID 재사용·심각도 하향
- reference 파일에 대한 수정 제안
- task·schema·runner·입력 판본 변조
- 장부 prefix 변조와 비인가 tail
- Fable 요약을 통한 역할 heading·marker 주입
- 비밀 경로·내용과 넓은 glob 우회
- symlink·junction·hardlink·OneDrive 경로 우회
- 죽은 lock과 동시 stale-lock 회수 경쟁
- 회차 공개 전 중단과 UTF-8 다중바이트 partial append
- 공개 회차 뒤 `status.json` 재조정
- Fable 회차와 수동 턴 사이 통합 hash-chain 단절

이 중 수동 턴 durable prepared record와 통합 chain 보강은 구현됐으나, 마지막 보강 직후 채팅이
중단됐으므로 최종 전체 자체 테스트와 실제 Claude 스모크를 다시 실행해야 한다.

## 15. 남은 작업

정확한 순서와 상태는 [`작업큐.md`](./작업큐.md)가 단일 권위다. 이 문서를 갱신한 시점의 다음
작업은 다음과 같다.

1. `P1-1` 브랜치의 공식 문서 반영과 로컬 커밋 정리
2. 동일 SHA CI를 확인한 뒤 승인 범위에서 병합·원격 감사 수행
3. 사람 R3 승인 뒤 `P0-5` authenticated RPC·원장 직접 쓰기 최소 권한
4. `AI-REVIEW-2` 페이블 소진 시 Opus 연속성 감사

`P0-2` 전까지 공식 상태는 최대 `VERIFIED`이며 `CLOSED`가 아니다.
