# 앱 현재 207개 표면·과거 별칭·전체 로직 전수조사 및 수정 계획

상태: **진행 중**  
기준일: 2026-09-20  
범위: AppMap 현재 207개 표면(화면 75, 팝업·상태 132) + 과거 판매 작성 별칭, 실제 Expo 라우트 66개, 화면 ID 74개

## 목적

AppMap에서 열리는 것과 제품 기능이 완성된 것을 구분한다. 각 화면·팝업·상태가 실제 제품 진입점,
도메인 훅, 서버 RPC, 원장 전파, 오류·재시도, 과거 시점 보존, 회귀시험까지 연결됐는지 확인한다.
UI만 존재하거나 샘플 데이터만 보이는 표면은 완료로 세지 않는다.

## 완료 판정

각 표면은 적용되는 항목을 모두 충족해야 `검증 완료`가 된다.

1. 실제 Expo 경로 또는 제품 안의 명확한 진입점이 있다.
2. 로딩·빈 값·오류·재시도 상태가 구분된다.
3. 입력값 검증과 저장 전 확인이 제품 계약과 맞는다.
4. 화면은 Supabase를 직접 호출하지 않고 도메인 훅을 사용한다.
5. 확정 계산과 원장은 DB RPC가 만들며 앱이 재계산해 덮어쓰지 않는다.
6. 재시도·중복 요청·동시 요청이 원장을 중복 생성하지 않는다.
7. 취소·정정은 반대 부호 사건과 판본을 남기고 과거 스냅샷을 보존한다.
8. 저장 뒤 관련 목록·상세·분석 캐시가 함께 갱신된다.
9. 웹 화면 시험과 실제 RPC 또는 DB 계약 시험이 같은 기대값을 증명한다.
10. 320px·390px, 글자 확대, 키보드·터치, 접근성 이름에서 핵심 동작이 막히지 않는다.

`ready`, 라우트 존재, AppMap 샘플 표시만으로는 완료 판정을 내리지 않는다.

## 실행 순서

### 1. 인벤토리와 계약 충돌 고정

- 215개 표면을 `검증 완료 / 검증 필요 / 부분 구현 / 껍데기 / 끊긴 연결 / 의도적 호환·미지원`으로
  분류한다.
- 화면 ID·경로·구현 상태는 `apps/mobile/src/features/README.md`, 실행 순서는 `docs/작업큐.md`에
  반영한다. 별도 경쟁 기능정의서는 만들지 않는다.
- 사용자 최신 결정과 `AGENTS.md`·`ARCHITECTURE.md`·기능정의서·DB 계약 충돌을 먼저 해소한다.

### 2. 재료와 메뉴

- 재료 등록→초기 입고→구매 옵션→입고/차감/폐기/실사→이력·취소를 E1·E2·E5·E7·E11로 추적한다.
- 메뉴 등록·수정→재료 사용량→판매가·세금·고정 지출→손익·수정 이력을 추적한다.
- 단위 환산, 기준단가, 음수 재고, 판매 중지, 삭제 제한, 카테고리·정렬 캐시를 반례로 검증한다.

### 3. 발주

- 후보→구매 옵션→발주(E7)→부분 입고(E1)→완료→취소(E11/E12)를 실제 RPC와 두 세션 경합으로
  검증한다.
- 발주는 재고·단가를 직접 바꾸지 않는다는 불변식을 모든 저장 경로에서 확인한다.
- E7 다건 저장은 요청 키로 중복 제거하고 한 트랜잭션으로 처리한다. 응답 유실은 저장된 키의 결과를
  먼저 조회하며, 부분 실패·같은 키 경합·다른 payload 재사용 거절을 DB와 앱에서 함께 검증한다.

### 4. 매출 작성

- 미작성은 사용자가 작성 확인 전까지 작성 중으로 바뀌지 않아야 한다.
- 초안 생성·임시저장·완료·수정·초기화·휴무 처리와 메뉴 수량·기타 매출·추가 지출을 추적한다.
- 재고 부족은 저장을 막지 않고 전량 E8로 기록해 음수 재고를 허용하며, 판매 중지만 차단한다.
- 판매 채널 manifest, 판본, 요청 키, 수량 증가 E8·감소 E9, 같은 목표 재호출 0건을 검증한다.

### 5. 손익과 분석

- 일별 손익·기간 분석·메뉴·채널·재료·세금 상세가 동일한 서버 확정값에서 파생되는지 대조한다.
- 하루/기간, 세금 포함/별도, 고정 지출 입력/미입력, 삭제 메뉴, 과거 채널을 조합한다.
- 합계 퍼센트를 다시 더하지 않고 금액 합계와 해당 합계 기준 비율을 서버 응답으로 표시한다.

### 6. MY와 공통 상태

- 국가·통화·시간대·세금·단위·영업시간·알림·계정 기능을 검사한다.
- 명시적 준비 중 기능은 실제 제공 범위와 안내를 맞추고, 제품 범위라면 구현한다.
- 공통 카드 여백·행 높이·화살표 예약 공간·시트·확인창·접기 버튼을 전 화면에서 검사한다.

### 7. 수정과 회귀

- P0 원장 훼손·권한·중복 저장, P1 손익 오산·기능 단절, P2 복구·표시 불일치, P3 정리 순서로 수정한다.
- 결함마다 실패 재현→최소 수정→해당 회귀→도메인 전체→`corepack pnpm verify` 순서로 확인한다.
- 운영·스테이징 migration은 고치지 않고 새 migration으로 전진한다.

### 8. Fable 독립 검수와 종료

- 계획 기준선, 각 수정 묶음, 최종 전체 결과를 같은 Task의 회차 또는 정확한 successor Task로 검수한다.
- Fable 필수 Finding은 반영·재검증 후에만 완료한다. 실행기가 제공자 한도로 호출 전에 막히면 실패
  원문을 보존하고 검수 완료라고 표시하지 않는다.
- 새 작업으로 넘길 때는 Mission Relay 1.7 판정, 봉인 handoff, 저장소·미션 복원과 Study Gate를 먼저
  통과한다.

## 핵심 데이터 연결 경우의 수 기준선

- `scripts/core-data-linkage-case-audit.mjs`가 기능정의서의 ING·RCP·ORD·SALES 관계와 시나리오를
  `core-data-linkage-cases.json`으로 생성하고 `verify` 단계 ③에서 문서 드리프트를 차단한다.

  보존하며 증거가 불명확한 행은 완료 합계에서 제외한다.
- 첫 보강 묶음은 FN-ORD-003~006이다. 직접 입고, 발주 입고, 미입고 취소, 입고 취소의 순차·재시도·

  208개 시나리오를 만들었다. 현재 196개는 단위·화면·DB·실제 2세션 시험과 정확한 기능정의서
