# 마스터 중심 심플 팀 운영 — 상세 기획안 001

- 작성일: 2026-09-09
- 상태: PROPOSED / 자체 문서 점검 대상 / 외부 독립검수 미실행
- 요청: 역할별 상세 MD·스터디 자료를 갖추고 마스터가 업무를 지시하는 심플 버전. 작업 유형에 따라 검수 강도를 구분하고, 개발·마케팅 마스터를 분리한다.
- 범위: 기획 및 실행계획 작성. 실제 채팅 생성·재배정·전송·자동 예약·제품 변경은 이번 문서 작성에 포함하지 않는다.

## 1. 목표와 완료 모습

사람이 한 곳에 요청하면 개발 마스터가 요구사항을 정리하고 담당 역할을 지정한다. 담당 역할은 업무지시서와 원본 자료를 읽고 실행 결과를 반환한다. 마스터는 검수 단계와 파일 충돌을 관리하며 필요한 경우에만 사람 결정을 요청한다.

첫 버전의 목표는 역할별 업무 수행을 시작할 수 있는 운영 기본형이다. 다음 버전에서 지시 전달·완료 감지·독립검수 회수·재작업 지시를 자동화한다. 첫 버전에 별도 웹 대시보드, 벡터 DB, 다중 PC 상시 서비스, 채팅 간 자율 협상을 넣지 않는다.

### 사용자 결정 반영

1. 작은 문구·스타일·비정책 문서 수정: 자체검수 → 마스터 검수.
2. 작은 CS 수정: 재현·수정·관련 회귀시험 → 마스터 검수.
3. 중장기 기획·여러 기능 변경: 자체검수 → Fable/Opus 독립검수 → 마스터 최종검수.
4. DB·계산·권한·운영 데이터·배포·복구: 관련 시험 + 독립검수 + 필요한 사람 승인.
5. 개발 마스터와 마케팅 마스터는 별도 역할이다. 사람 결정·공통 우선순위 창구는 하나다.
6. 마케팅은 후속 단계에서 연결한다. 현재 마케팅 방이나 실행 기능은 만들지 않는다.

## 3. 조직과 권한

아래는 마케팅 제외 14개 논리 역할이다. 첫날부터 물리 채팅 14개를 만들 필요는 없다. 기존 채팅에 역할별 업무 양식을 적용해 시범 운영하고, 분리가 필요한 역할부터 전용 채팅으로 연결한다. 새 채팅 생성은 별도의 사용자 요청 범위에서 수행한다.

| 번호 | 역할 | 책임 | 지시·완료 권한 |
|---|---|---|---|
| 01 | 사람 결정·총괄 | 요구사항, 공통 우선순위, 정책·예산·배포 결정 | 사람 최종 결정. 개발 요청을 개발 마스터에 인계 |
| 02-1 | 개발 마스터·단기 업무 | 개발 도메인 전체 접수·배정·상태 관리, 단기 지시서 | 개발 업무의 단일 배정자·통합 작업 상태 작성자 |
| 02-2 | 중장기 기획 | 요구사항·설계·단계·수용 기준, 계획 자체검수 | 계획 제출. 실행 배정은 02-1 |
| 03-1 | 마스터 최종검수 | 요구 충족·시험·독립검수·잔여 문제 종합 | 기술 완료 판정. 배포·정책 사람 승인 대체 불가 |
| 03-2 | Fable/Opus 검수 인계 | 정확한 대상과 참고 자료 전달, 원문 결과 회수 | 검수 실행 관리. 자체 의견을 독립검수로 기록 불가 |
| 04-1 | 개발·스테이징 | 배포 계획·검증·결과 보고 | 이번 프로필에서는 해당 배포의 사람 최종 확인 후 실행 |
| 04-2 | 운영 배포·복구 | 운영 배포·복구 계획, 백업·복구 근거 | 승인된 대상·환경·범위에 한해 실행 |
| 05-1 | 프론트 CS | 화면·입력·표시 오작동 재현·수정 | 배정된 수정 범위 수행 |
| 05-2 | 백엔드 CS | API·계산·데이터 처리 오류 재현·수정 | 배정된 수정 범위 수행. 운영 데이터 직접 보정은 별도 승인 |
| 06 | Product·Mobile | 앱 기능·UX·한국어/영어 기능 구현 | 업무별 계획과 수용 기준 수행 |
| 07 | Data·Backend | 도메인·RPC·DB·계산 기능 | 업무별 계획과 수용 기준 수행 |
| 08 | Server·Supabase·Operations | 서버·인프라·DB 운영 준비 | 개발 작업과 실제 운영 변경을 구분 |

01과 02-1은 초기 같은 채팅에서 운영 가능하다. 사람 의사결정과 AI 배정 기록을 구분한다. 02-2가 계획을 작성해도 두 번째 배정 마스터가 되지 않는다. 제작자가 마스터 역할로 자신의 작업을 단독 최종 승인하지 않도록 03-1 검수 컨텍스트를 구분한다.

팀 간 협업이 필요하면 담당자가 의존 업무 요청을 마스터에게 제출한다. 마스터가 하위 업무를 배정한다. 담당자가 다른 팀을 직접 깨우거나 독자적으로 업무 범위를 늘리지 않는다.

## 4. 검수 등급

아래 S0~S3는 심플 프로필의 운영 분류이며 기존 R0~R3의 의미를 자동 재정의하지 않는다. 구현 시 기존 위험 판정과 연결하되 여러 조건이 있으면 높은 등급을 적용한다.

| 등급 | 적용 조건 | 검증·검수 | 완료 조건 |
|---|---|---|---|
| S0 | 비정책 문구, 국소 스타일, 링크·오탈자 | 자체 점검 + 마스터 검수. UI는 표시 확인 | 요청 충족·변경 범위 확인 |
| S1 | 범위가 작고 재현 가능한 일반 CS, 고위험 조건 없음 | 실패 재현 → 수정 → 관련 회귀시험 → 마스터 검수 | 오류 해소·관련 기능 정상 |
| S2 | 중장기 기획, 여러 기능·공유 컴포넌트 변경, 광범위 CS | 계획 자체검수·독립검수, 구현 자체검수·필요 시험·독립검수, 마스터 최종검수 | 단계별 대상에 결속된 검수 통과 |
| S3 | DB/스키마/RPC, 원장·계산·세금, 권한·보안, 운영 데이터, 배포·복구 | 관련 시험 + 독립검수 + 영향에 맞는 사람 결정 | 기술 게이트 및 필요한 실행 승인 충족 |

### 상향 기준

- 파일 수가 적어도 가격·세금·재고·권한·SQL을 바꾸면 S3이다.
- MD라도 승인 규칙·자동 라우팅·검수 생략을 바꾸면 S0가 아니다. 본 기획은 정책 영향을 포함하므로 S3 검수 대상으로 취급한다.
- 번역이라도 금액 의미·동의·권한·중요 오류 안내가 달라지면 영향에 맞춰 상향한다.
- 작은 CS에서 원인이 공유 모듈·여러 화면으로 확장되면 S2 이상으로 재분류한다.
- 분류 근거와 제외 조건을 업무에 기록한다. 불확실하면 상위 등급으로 시작해 근거 확인 후 재판정한다.

### Fable/Opus 사용

독립검수 단계의 표시명은 Fable/Opus로 통일한다. 실제 엔진·검수 역할·대상 commit 또는 snapshot SHA·회차·결과·Finding을 기록한다. 같은 목적의 Fable과 Opus 동시 호출은 하지 않는다.

현재 공식 실행 경로의 Fable 기본/조건을 만족한 Opus 승계 규칙을 재사용한다. 사용자의 “Fable/Opus 검수” 선택을 임의의 직접 Claude 채팅 자문을 공식 PASS로 바꾸는 승인으로 해석하지 않는다. 최초 엔진 선택을 자유롭게 바꾸는 별도 요구가 생기면 규격 변경으로 다룬다.

최초 독립검수에는 요구사항·정확한 산출물·시험 증거를 제공한다. 제작자의 PASS 결론을 정답으로 주입하지 않는다. 재검수에는 기존 Finding과 변경 근거를 연결한다. 수정된 파일과 그 영향 범위를 검수하며, 다른 SHA의 이전 PASS는 현재 PASS가 아니다.

문서·스타일 변경에 구현을 그대로 따라 쓰는 불필요한 시험은 추가하지 않는다. 기존 저장소 필수 게이트와 독립검수 생략은 별개다. `corepack pnpm verify`와 보호 CI 요구는 이번 차등 검수안으로 자동 면제되지 않는다.

## 5. 업무 생명주기

```text
요청 → 분류·범위 확인 → 필요 시 기획 → 담당 배정 → 실행 → 자체검수
  → 등급별 시험/독립검수 → 마스터 최종검수 → 기술 완료
  → 배포 필요 시 사람 승인 → 배포 → 결과 확인 → 종료
```

최소 상태는 REQUESTED, PLANNING, READY, RUNNING, SELF_REVIEW, INDEPENDENT_REVIEW, REWORK, MASTER_REVIEW, TECHNICALLY_DONE, WAITING_HUMAN, DEPLOYING, CLOSED, BLOCKED, CANCELLED다. 단계 생략은 S0/S1의 독립검수 면제처럼 정책과 근거를 가진 경우에만 기록한다.

- 수행자는 상태 변경을 결과보고로 요청한다. 개발 마스터가 통합 작업 상태를 갱신한다.
- S2/S3 계획 검수 통과는 구현 검수 통과가 아니다. 서로 다른 산출물을 검수한다.
- 수정 필요 시 동일 Task ID에 새 판본으로 재지시한다. 기존 검수 기록은 보존한다.
- 2회 연속 같은 Finding이 해결되지 않거나 정한 시간·예산이 소진되면 BLOCKED로 원인을 보고한다. 실패를 완료로 바꾸거나 무한 호출하지 않는다. 해소 후 같은 Task로 계속한다.
- 미회신과 실패를 구분한다. 전송 결과가 불명확하면 먼저 수신·실행 흔적을 조회하고 재전송을 결정한다.
- 기술 완료와 실제 배포 완료를 따로 기록한다. 취소나 일시 중단은 실행 중 담당자에게도 전달되어야 한다.

## 6. 파일 충돌·CS 처리

업무마다 담당 1명, 기준 SHA, 수정 가능 경로, 의존 Task, 작업 순서를 고정한다. 경로가 겹치면 선행 업무를 기다리거나 마스터가 통합 담당자 한 명을 지정한다. 팀 이름이나 채팅 분리만으로 병행 수정이 안전하다고 판단하지 않는다.

예: 신규 매출 화면과 같은 화면 CS가 겹치면 긴급도·배포 범위를 확인한다. 기존 기능 담당자가 CS까지 처리하거나, CS를 먼저 완료한 기준으로 기능 작업을 재개한다. 새로운 기준에서 관련 회귀시험을 다시 실행한다.

현재 프로토타입 작업의 파일은 담당 작업과 소유권을 확인하기 전까지 구현 대상으로 삼지 않는다. 문서·양식 신규 초안은 먼저 작성할 수 있다. 기존 Dirty 문서나 공용 검증기를 임의로 덮어쓰지 않는다.

## 7. 문서와 스터디 구성

공식 제품 문서는 기존 경로를 유지한다. 역할별 문서는 해당 원본을 읽는 안내서다. 공식 본문을 복사해 별도 최신본으로 관리하지 않는다.

각 역할에는 다음 항목을 갖춘 상세 MD 1개와 스터디 안내 1개를 마련한다. 실제 경로·기존 manifest 연결은 실행계획에서 확정한다.

1. 목적·책임·입력·산출물·허용 작업·마스터에게 돌려야 하는 상황.
2. 필독 문서, 역할별 원본 링크, 읽는 순서, 이번 작업에 필요한 추가 자료.
3. 업무 전 체크, 자체검수, 결과보고, 다음 담당자 인계 기준.
4. CS/기능개발 경계, 파일 소유권, 한국어·영어와 시장별 확인 항목.
5. 모델 컨텍스트를 새로 열 때 복원할 Task·결정·근거 목록.

공통 필독은 AGENTS·작업지시·관련 아키텍처·작업 상태다. 개발은 해당 코드·migration·시험, QA는 재현·수용 기준, 운영은 배포·복구 계획, Knowledge는 공식 문서 관계를 추가한다. 모든 역할이 매번 모든 문서를 다시 읽지 않는다.

스터디 완료에는 읽은 문서 경로·판본/해시·업무에 적용되는 규칙·확인하지 못한 항목을 남긴다. 서명만으로 이해를 입증하지 않고 역할별 대표 사례 1건에 규칙을 적용해 확인한다.

### 최소 업무 기록

| 양식 | 필수 정보 |
|---|---|
| 업무지시 | Task ID, 요청 근거, 목표, 제외 범위, 등급·이유, 담당, 기준 SHA, 수정 경로, 수용 기준, 검수 경로 |
| 실행계획 | 단계, 의존 업무, 예상 시간, 단계별 산출물·시험·완료 기준 |
| 결과보고 | 변경 요약·대상, 실행 명령·결과, 미실행 검사, 남은 문제, 검수할 정확한 판본 |
| 검수기록 | 실제 검수자/엔진, 대상, Finding, 판정, 재검수 연결 |
| 사람결정 | 대상·환경·행위·범위, 승인/보류, 승인 시점, 변경 시 재판정 조건 |
| 인계 | 현재 상태, 결정, 완료·남은 작업, 수정 경로, 근거와 다음 행동 |

통합 작업 목록은 기존 작업큐를 사용한다. 후속 자동화에서 기계 상태를 도입하면 한 원본에서 목록을 생성한다. MD와 JSON에 같은 상태를 각각 수동 기록하지 않는다. 검수 원장은 기존 append 도구와 원본 보존 절차를 따른다.

## 8. 마케팅 연결

추후 사람 결정·총괄 아래 마케팅 마스터를 추가한다. 개발 마스터는 개발 배정, 마케팅 마스터는 마케팅 배정만 소유한다. 각 Task에는 도메인과 담당 마스터를 하나씩 기록한다.

공통 출시 자료에는 출시 기능·실제 준비 상태·공개 가능일·가격·지원 국가/언어·공개 승인 여부를 둔다. 개발 완료를 공개 승인으로 취급하지 않는다. 마케팅에 필요한 개발 수정은 총괄의 우선순위 결정 후 개발 마스터가 배정한다.

외부 게시·광고비·구매·계정 권한은 해당 사람 승인 범위에서 실행한다. 마케팅 연결 시 역할·스터디·수용 기준만 추가할 수 있게 하고 지금 콘텐츠 자동화·채널 API는 만들지 않는다.

## 9. 자동화의 최소 범위

기본형에서는 마스터가 업무 패킷을 준비하고 검증된 기존 전달 수단으로 운영한다. 자동형은 다음만 추가한다.

- 하나의 활성 개발 마스터, Task 판본 기반 배정 및 상태 변경.
- 대상 확인 후 지시 전달, 수신 확인, 실행 결과 회수.
- Task ID + 판본 + 담당 역할 기반 중복 방지.
- 재시작 후 진행 상태 복원, 불명확한 전송의 재조회.
- 필요한 Fable/Opus 검수 요청, 결과 검사, 재작업 루프.
- 사람 결정이 필요한 단계에서 대기하고 승인 대상이 바뀌면 이전 승인을 재사용하지 않음.

서비스 P6의 미완성 기능을 심플 버전에서 다시 만드는 것을 기본 전략으로 삼지 않는다. 기존 연결을 사용할 수 있는지 먼저 확인하고, 사용할 수 없으면 기본형까지의 완료와 자동형 연결 차단을 분리해 보고한다. 기존에 꺼 둔 예약은 다시 켜지 않는다.

## 10. 공식 정책 반영안

사용자가 이번 요청으로 선택한 차등 검수 방향은 계획 입력으로 확정한다. 이를 다시 선택하도록 반복 질문하지 않는다. 운영 적용 전에 다음 파일의 관련 조항과 검사 기대값을 일관되게 바꾸는 구체적 후보를 준비한다.

| 대상 | 반영할 변경 |
|---|---|
| AGENTS·팀 구성·품질 정책·검수 README | S0/S1 외부검수 면제 조건, S2/S3 필수 검수, 상향 기준 |
| 오케스트레이션·역할 컨텍스트 | 개발 마스터 단일 배정, 기획·시험·최종검수 역할 구분 |
| Router·chat manifest | 기존 11개와 14개 논리 역할 매핑, 프로필별 허용 경로 |
| 실행 모델 계획 | 실제 실행·검수 모델, 역할·단계·호출 예상 및 비용 근거 갱신 |

현재 오케스트레이션 문서는 머리말 ACTIVE와 본문 DRAFT 표현이 함께 있어 적용 기준 정리 항목으로 기록한다. 현행 전역 정책을 이 제안 파일 하나로 덮어쓰지 않는다.

기존 model-plan은 CLI에서 MODEL_PLAN_VERIFIED, SHA `60d7cb6a85cc43a76532f9047bcc5c4ed5113ebc3fd1708b0c954da91f85d96e`로 확인했다. 이는 기존 계획 검증이며 심플 버전의 모델 배정·예산 승인이나 사용 가능성의 신규 실측이 아니다. 구현 전 해당 범위를 반영할 후보를 작성한다.

## 11. 소요 기간과 제외 범위

작업일은 하루 약 6시간의 유효 개발·점검 시간으로 계산한 설계 추정이다. 벤치마크나 완료일 보장은 아니다. 기존 문서·검수기·채팅 연결을 재사용하고 주요 검수 수정 1~2회를 가정한다.

| 완료 수준 | 착수 후 누적 추정 | 결과 |
|---|---|---|
| 문서 구성 | 1~2작업일 | 역할·스터디·양식 초안 |
| 운영 기본형 | 3~5작업일 | 정책 연결·분류·수동 시범 업무·검수 절차 사용 가능 |
| 자동형 포함 전체 | 10~15작업일 | 마스터 지시·회수·재검수·재시작 시범 통과 |

자동형 포함 전체는 약 60~90시간, 통상 2~3주 정도의 작업량이다. 기존 P6 연결이 막히거나 새로운 상시 서비스·ACL·다중 PC 지원이 필요하면 재산정하며 이 범위보다 길어질 수 있다. 사람 승인, 프로토타입 겹침 해소, 모델 한도, 외부 검수 회신 대기는 별도다.

마케팅 실행, 제품 신규 기능, 기존 대형 조직 솔루션 전체 완성, Directory Discovery 구현, 실제 운영 배포는 이 기간에 포함하지 않는다. “전체”는 본 문서 §9의 심플 자동형 범위다.
