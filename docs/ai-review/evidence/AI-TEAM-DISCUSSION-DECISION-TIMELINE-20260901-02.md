## 3. 사람 요청을 듣고 업무로 바꾸는 오케스트레이션

### D-05 · `CURRENT`

- 사용자는 단순 실행자가 아니라 “사람의 요청을 듣고 업무를 정의·지시하는 오케스트레이션 입장”을

- 오케스트레이션은 요청을 그대로 복사하지 않고 목표·범위·제외·완료 조건·위험·사람 결정 항목으로
  정규화한다.

  판정해 기존 Task와 연결한다.
- 담당 팀 채팅은 사용자의 요청을 독자적으로 정책 확정하지 않고 마스터 오케스트레이션으로 반송한다.
- 공식 연결: 온톨로지의 요청 판정 enum, 오케스트레이션의 요청 수신·Task Graph.

### D-06 · `CURRENT`

- 채팅은 공식 기억이 아니며, Task·Decision·Finding·HANDOFF·Learning이 저장소에서 맥락을 보존한다.
- 새 채팅은 전체 대화를 복사하지 않고 계층형 컨텍스트를 복원한다.

## 5. Context & Token Steward와 새 채팅 전환

### D-09 · `CURRENT`

- Steward는 현재 채팅의 길이·중복·검색 실패·맥락 손실 위험을 관측한다.
- 새 채팅이 필요하다는 신호를 줄 수 있지만 범위·비용·정책·검수·배포를 결정하지 않는다.
- 팀 그룹마다 별도 토큰 관리자를 복제하지 않고 Knowledge · Orchestration과 부 오케스트레이션이
  공통으로 운용한다.

### D-10 · `REFINED`

- 사용자 비유: 여러 신경망으로 둘러싸인 구가 다른 구와 연결되고, 위성이 지구를 도는 입체 구조.
- 구현 해석:
  - 구의 중심: 중앙 권위와 현재 Task
  - 신경망: typed edge와 검색 가능한 Markdown 링크
  - 위성: 역할별 얇은 컨텍스트·현장 증거·외부 검수
  - 구 사이 연결: 검증된 HANDOFF와 Learning
- 새 채팅 전환은 `rollover → checkpoint → HANDOFF → 복원 검증 → lease 인계`다.
- 이번 새 채팅은 우선 읽기 전용 스터디이므로 edit lease를 자동 인수하지 않는다.

## 6. 히스토리를 성장판으로 바꾸는 규칙

### D-11 · `CURRENT`

- 실제 작업 이력과 대화 맥락은 새 채팅에서 즉시 검색 가능해야 한다.
- 원시 이력을 무조건 주입하지 않고 L0~L4 계층으로 조립한다.
  - L0: 바뀌지 않는 헌법·안전 규칙
  - L1: 현재 Task·상태·다음 행동
  - L2: 해당 주제의 공식 권위
  - L3: 직접 연결된 시험·Finding·결정
  - L4: 필요할 때만 여는 원시 역사
- 반복 관측만 Learning 후보가 되며, 독립 검증·적용 범위·폐기 조건을 거쳐야 재사용한다.
- 실패 기록도 삭제하지 않지만 성공 규칙으로 자동 승격하지 않는다.

### D-12 · `CURRENT`

- 실제 구조 구현 후 `AI 팀 운영 스타터 키트`를 만든다.
- 스타터 키트는 제품 고유 정책을 그대로 복사하지 않고 공통 엔진과 project profile/adapter를 분리한다.
- 이후 브랜치·DB·서버 운영 변경도 검증 후 스타터 키트에 환류한다.
- 다른 프로젝트는 문서 묶음을 던지는 것만으로 끝내지 않고 빈 저장소 이식 시험과 예제 Task 완주를
  통과해야 한다.

## 7. 실행·검수 과정에서 나온 역사적 교훈

### H-01 · `HISTORICAL`

- 큰 묶음 Fable 입력은 비용을 소진했지만 유효 판정을 내지 못한 회차가 있었다.
- 교훈: 동일한 큰 입력으로 상한만 올려 반복하지 않는다. 로컬 검증 후 문서별 의미 축을 나누고 마지막
  네트워크 검수에서 해시를 결속한다.

### H-02 · `HISTORICAL`

- Fable 실행 실패 회차는 비용 0의 실패로 보존됐다. 당시 작업 기록에는 rate limit 진단이 남았지만,
  보존된 원시 `run.json`에는 구조화된 `terminal_reason`·`provider_error_code`가 없으므로 원인을
  저장소 증거만으로 확정하지 않는다.
- 교훈: 실행 실패를 PASS나 검수 완료로 바꾸지 않는다.

### H-03 · `HISTORICAL`

- 검수 Task의 `agents_sha256`을 CRLF 작업 폴더 기준으로 계산해 commit blob과 어긋난 사례가 있었다.
- 교훈: Git blob OID와 SHA-256은 반드시 target commit의 원시 blob 바이트에서 계산하고, append 전에
  commit/tree/blob/path를 정적으로 검증한다.

### H-04 · `HISTORICAL`

- 역할별 검수 기록이 커져도 `collaboration.md`를 직접 편집하지 않는다.
- 비-Fable 턴은 `pnpm fable:append`, Fable 턴은 공식 실행기만 추가하며 당시 runner와 전후 hash를
  보존한다.

## 9. 새 채팅에 전달할 최소 결론

1. 사용자의 핵심 목표는 “AI 팀·문서·과거 작업이 연결돼 시간이 갈수록 더 잘 일하는 시스템”이다.
2. 채팅 수를 늘리는 것이 목표가 아니라, 얇은 채팅과 저장소 권위를 연결하는 것이 목표다.
3. 토큰 절감은 맥락 삭제가 아니라 계층형 복원·중복 제거·필요시 원시 이력 조회로 달성한다.

5. 과거 대화는 의도와 시행착오를 설명하는 참고 자료이고 현재 공식 계약을 대체하지 않는다.
6. 새 채팅은 이 타임라인을 읽은 뒤 반드시 실제 공식 문서·작업큐·커밋·시험과 대조해야 한다.
