# 식재료 편집 충돌 복구 — 2026-09-10

기준 커밋: `9dd2b3db711703276e788c0862c4795306c64cfc`.
사용자 요청: 반복 보고되던 메모·식재료 수정 폼의 충돌 후 갱신·재시도를 실제 수정한다.
옛 데이터 삭제나 원장 초기화 요청으로 처리하지 않았다. DB/RPC/migration/재고/원장은 변경하지 않았다.

## 변경

- 두 저장 mutation에서 서버 SQLSTATE 보존. `40001`만 충돌 복구로 분류한다.
- 도메인 공용 복구 훅/안내: 최신 상세 조회 → 명시적 확인 → 다시 편집·저장.
- 조회 중·실패·대상 없음에는 확인/저장 금지. 초안 보존, 조회 재시도 가능.
- 확인 자체는 mutation을 호출하지 않는다. 메모는 현재 초안으로 변경됨을 알린다.
- 전체 폼은 최초값/입력값/최신값을 비교해 수정하지 않은 항목만 최신값을 반영한다.
  숨겨진 메모·기본 구매처는 사용자가 확인한 서버값을 보존한다.
- 확인 뒤 또 다른 변경이 생겨도 DB CAS가 다시 거절하며 같은 복구 절차를 따른다.
- ID별 편집 컴포넌트와 조회 세대 구분으로 늦은 응답을 분리한다.
- 조회가 null이어도 열린 메모 초안을 유지한다. null→조회 오류에서도 폼 복구 안내가 가려지지 않는다.
- 공용 MemoEditSheet에는 기본값이 있는 선택적 children/saveDisabled만 추가했다.
  레시피 등의 기존 소비처는 새 동작을 opt-in하지 않는다. 복구 UI는 같은 시트 안에 놓아 중첩 Modal을 만들지 않는다.

## 재현과 시험

수정 전 추가한 두 회귀시험은 실제로 실패했다: mutation의 `40001` 코드 없음, 충돌 후 refetch 호출 0회.
기존 시험은 오류 전에 최신 mock 데이터를 제공하므로 해당 조건을 검증하지 못했다.

최종 로컬 확인:

- 모바일 타입 검사 PASS.
- 관련 4파일 59/59 PASS.
- 모바일 전체 83파일 799/799 PASS. `.codex/ingredient-conflict-mobile-20260910.log`.
- `git diff --check` PASS (Windows 줄바꿈 경고만 존재).
- 실제 화면 + 실제 도메인 조회/저장 훅 + QueryClient 통합시험 5개 PASS:
  사전 캐시 갱신 없는 복구 성공, 조회 실패, 반복 충돌, null 결과의 초안 보존,
  다른 대상 진입 후 이전 저장 성공 응답.

통합시험의 RPC 전송부는 fixture이며 실제 DB CAS 검증이나 네이티브 UI 인증으로 간주하지 않는다.
폼 시험은 캐시 없는 복구·미수정 필드 갱신·지연/실패·대상 변경·null→오류를 검증한다.

## 검수와 잔여 게이트
