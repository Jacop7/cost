# 마스터 중심 심플 팀 운영 — 실행계획 001

- 작성일: 2026-09-09
- 상태: PROPOSED / 실행 전 / 외부 독립검수 미실행
- 기획 근거: [상세 기획안](./MASTER-CENTERED-SIMPLE-PLAN-001.md)
- 이번 산출물은 기획과 실행계획이다. 완료 상태는 아래 단계마다 실제 증거로 갱신한다.

## 1. 단계와 기간

| 단계 | 작업 | 담당 역할 | 완료 기준 | 추가 작업일 |
|---|---|---|---|---|
| L0 | 기존 자산·소유권·역할 연결 및 검수 변경 후보 | 개발 마스터 + Knowledge | 수정 경로·정책 delta·기존/신규 역할 대응 확정 | 0.5~1 |
| L1 | 14개 역할·스터디와 업무 양식 | Knowledge + 역할별 담당 | 역할 안내 14개·스터디 안내 14개, 6종 양식·공통 시작 안내 | 1~1.5 |
| L2 | 차등 검수 정책 적용·기본형 시범·독립검수 | 개발 마스터 + Quality + Fable/Opus | 분류·충돌·검수·사람 승인 시범 및 기획/정책 검수 통과 | 1.5~2.5 |
| L3 | 마스터 상태·지시·결과 회수 연결 | 개발 마스터 + Backend | 대상 확인·중복 방지·수신/결과 판정 자동화 | 3~4 |
| L4 | 독립검수·재작업·재시작·승인 대기 연결 | 개발 마스터 + Quality | 검수 판본·실패·재시작 시나리오 통과 | 2~3 |
| L5 | 통합 시범·필수 검사·독립검수·인계 | Quality + Fable/Opus + 최종검수 | 자동형 수용 기준 통과, 미완료·지원 범위 명시 | 2~3 |

L0~L2 합계 3~5작업일, L3~L5 추가 7~10작업일, 총 10~15작업일이다. 문서 초안은 L0~L1 진행 중 1~2일 시점부터 검토할 수 있다. 실제 추정은 L0의 연결 기능 확인 후 한 번 갱신한다.

## 2. L0 — 연결·충돌표

다음 매핑은 제안이며 실제 기존 방의 담당 업무를 옮긴 상태가 아니다.

| 기존 논리 채팅 | 심플 역할 연결 후보 |
|---|---|
| MASTER-01-HUMAN-DECISIONS | 01 사람 결정·총괄 |
| MASTER-02-ORCHESTRATION | 02-1 개발 마스터 |
| MASTER-03-DEPUTY-CONTEXT | 02-2 중장기 기획, 기존 인계 기능 유지 검토 |
| MASTER-04-DEVELOPMENT-STAGING | 04-1 |
| MASTER-05-PRODUCTION-RECOVERY | 04-2 |
| DEPARTMENT-00-ALL-TEAMS-ROOM | 현황 조회용 유지, 별도 배정 권한 없음 |
| DEPARTMENT-01-PRODUCT-MOBILE | 06, 초기 05-1 CS 레인 |
| DEPARTMENT-02-DATA-BACKEND | 07, 초기 05-2 CS 레인 |
| DEPARTMENT-03-SERVER-OPERATIONS | 08 |
| DEPARTMENT-04-QUALITY-REVIEW | 09, 별도 컨텍스트의 03-1 최종검수 연결 검토 |
| DEPARTMENT-05-KNOWLEDGE-ORCHESTRATION | 10 |

14개 논리 역할을 11개 기존 방에서 운영할 수 있지만 제작과 최종검수의 컨텍스트는 구분한다. 과부하가 생긴 CS·기획 역할만 추후 전용 채팅으로 분리한다. 새 방이 실제로 생기면 manifest와 허용 route를 함께 갱신한다.

파일별로 현재 소유 작업, tracked/dirty 상태, 수정 범위, 적용 순서, 통합 담당을 기록한다. 특히 AGENTS.md, docs/ai-review/README.md, docs/team/ROLE_CONTEXTS.md, docs/team/DECISIONS.md, docs/작업큐.md, package.json, scripts/verify.mjs는 공유 파일이므로 기존 편집과 결합 전에 확인한다.

현재 요청은 문서 작성이므로 신규 evidence 문서 두 개만 추가한다. 프로토타입·P5/P6·Directory Discovery의 기존 승인이나 봉인을 이번 범위에 재사용하지 않는다.

## 3. L1 — 문서 구성 상세

아래 경로는 구현 시 만들 후보다. 현재 존재한다고 주장하지 않는다. 기존 역할 manifest가 같은 책임을 갖는 경우 본문은 그 파일에 반영하고 안내는 링크만 둔다.

- 시작 안내 후보: `docs/team/simple/README.md`
- 상세 역할 후보: `docs/team/simple/roles/<role-id>.md`
- 스터디 후보: `docs/team/simple/study/<role-id>.md`
- 양식 후보: `docs/team/simple/templates/{task,plan,result,review,decision,handoff}.md`
- 역할 연결은 기존 `docs/team/ROLE_CONTEXTS.md`·chat manifest에 합류한다.
- 업무 상태는 기존 `docs/작업큐.md`의 Task와 연결하고 별도 경쟁 작업큐를 만들지 않는다.

role-id 14개:

`human-chief`, `development-master`, `project-planner`, `master-review`, `independent-review-coordinator`, `staging`, `production-recovery`, `frontend-cs`, `backend-cs`, `product-mobile`, `data-backend`, `server-operations`, `quality-review`, `knowledge-orchestration`.

## 4. L2 — 차등 검수 적용

기획안의 S0~S3 기준을 한 곳에서 정의하고 안내·검사기는 해당 정의를 참조한다. 기존 R0~R3와 연결할 때 의미를 임의로 같다고 보지 않는다. 테스트 기대값과 실제 정책을 함께 변경한다.

실행 순서:

1. 기존 “모든 작업 독립검수” 조항을 사용자 선택에 맞게 바꾸는 변경안을 작성한다.
2. 고위험 상향 조건·작은 작업 면제 조건·필수 로컬/CI 시험 유지 조건을 반영한다.
3. 정책 후보를 자체 점검하고 Fable/Opus 공식 경로로 검수한다. 문서라고 S0 면제하지 않는다.
4. 선택된 방향 자체의 재승인을 요구하지 않고, 실제 배포·권한·예산 등 별도 결정이 필요한 범위만 구체적 대상과 함께 제시한다.
5. 기존 편집 작업과 합류해 공식 정책·실행 검사기·문서의 적용 판본을 일치시킨다.

## 5. L3~L4 — 자동형 구현 범위

첫 연결 점검은 기존 Task 조회·전달·결과 회수 기능의 실제 이용 가능성, 대상 바인딩, 공식 검수 실행기의 성공/실패 응답을 확인한다. 제공되지 않는 기능은 문서 속 명령으로 존재하는 것처럼 처리하지 않는다.

최소 구현 단위:

1. Task 판본·단계·담당·수정 경로·검수 대상 저장 및 상태 전이 검사.
2. 마스터만 지시를 제출하는 단일 경로, 대상 역할/실제 채팅 매핑 검증.
3. 전송 전 기록·수신 확인·결과 회수. 전송 불명확 시 재조회.
4. 중복 Task/payload 거부, 오래된 결과 거부, 동시 마스터 상태 갱신 충돌 거부.
5. Fable/Opus 요청·회신을 해당 대상과 연결, 미해결 Finding 재지시.
6. 재시작 후 마지막 확인 상태부터 복원, 승인 대기·취소 존중.

자동 반복은 유효한 실행 세션이나 명시적으로 구성된 서비스 범위에서만 동작한다. 예약을 끈 현재 상태에서 상시 감시가 계속된다고 표시하지 않는다. 상시 운영이 필요하면 호스트·시작/종료·재시작 방법을 별도 명세로 추가하고 기간을 재산정한다.

### 자동형 수용시험

| ID | 시험 | 기대 결과 |
|---|---|---|
| A01 | 정상 지시 → 결과 | 정확한 담당·Task·판본으로 한 번 수행 |
| A02 | 동일 지시 중복 요청 | 두 번째 실행 생성 없음 |
| A03 | 전송 직후 응답 유실 | 조회로 실제 상태 확인, 맹목 재전송 없음 |
| A04 | 다른 채팅/잘못된 역할 대상 | 전송 거부 |
| A05 | 결과 도착 중 Task 범위 변경 | 옛 판본 결과로 완료하지 않음 |
| A06 | Fable/Opus CHANGES_REQUIRED | Finding을 보존해 같은 Task 새 판본으로 재지시 |
| A07 | 코드 변경 후 과거 검수 PASS | 새 대상 검수까지 완료 거부 |
| A08 | 검수 엔진 한도/회신 오류 | 공식 승계/실패 계약 적용, 동시 중복 호출 없음 |
| A09 | 프로세스 종료 후 재시작 | Task·수신·검수 상태 복원, 중복 작업 없음 |
| A10 | 같은 파일 두 업무 | 마스터가 직렬화 또는 통합 담당 지정 |
| A11 | 두 마스터가 같은 판본 갱신 | 하나만 수용, 다른 갱신은 충돌 처리 |
| A12 | 사람 승인 대기·대상 변경 | 대기 유지, 대상이 다른 승인 거부 |
| A13 | 취소된 Task의 늦은 결과 | 기록만 보존, 다음 단계 실행 없음 |
| A14 | 검수 반복 무진전/예산 소진 | BLOCKED와 이유 보고, 무한 호출 없음 |
| A15 | 직접 Opus 자문만 존재 | 공식 검수 칸을 PASS로 만들지 않음 |
| A16 | 승인된 모의 배포 및 실패 | 실행 결과 검증, 실패 시 승인된 복구 범위만 적용 |

B01~B12와 A01~A16은 수용 명세이며 현재 미구현·미실행이다. 자동형 통과를 증명하려면 실제 시험 코드·입력·명령·대상 SHA·로그를 연결한다.

## 6. L5 — 종합 검증과 인계

- 역할 안내·스터디 14쌍, 양식 6종, 공식 원본 링크 확인.
- 정책과 분류기의 S0~S3 및 기존 위험 등급 연결 확인.
- 기본형 12개, 자동형 16개 수용 시나리오 실행 근거 확인.
- 구현 변경에 맞는 로컬 시험 및 `corepack pnpm verify` 실행. 선택 실행은 선택 범위로 표시.
- 검수 대상과 실제 산출물 동일성 확인, Fable/Opus 지적 반영·재검수.
- 사람 승인 대상과 배포 준비 상태는 별도 기록. 운영 실제 배포는 이번 솔루션 검증 완료에 필수로 실행하지 않는다.
- 지원 호스트·실제 전달 경로·재시작·실패 대응·사용법 인계.

## 7. 일정 운영과 위험

일정 기준은 기획안과 같은 하루 약 6시간의 작업량이다. 3~5일 기본형을 먼저 사용하고 자동형은 총 10~15일 목표로 진행한다. 이는 설계 추정이며 실제 P6 연결·검수 소요 확인 전의 확정 납기는 아니다.

| 변동 요인 | 대응 |
|---|---|
| 프로토타입과 파일 겹침 | 신규 문서부터 진행, 공유 파일은 작업 순서 합의 후 적용 |
| P6 연결 미완성 | 기본형 완료와 자동형 차단을 분리, 중복 플랫폼 개발 전 재산정 |
| 검수 지적 반복 | Finding 단위 수정, 무진전 시 근본 설계 확인 |
| 모델 한도·승인 대기 | 작업량과 대기 시간을 분리 보고 |
| 14개 역할의 과도한 물리 분리 | 11개 기존 방에서 레인으로 시범 운영 후 필요한 방만 분리 |

## 8. 현재 산출물 점검 기록

작성 시 원칙: 기존 공식 문서와 작업본은 수정하지 않고 기획·실행계획 신규 두 파일만 작성한다. 기존 모델 계획 검증 결과는 MODEL_PLAN_VERIFIED이며 새 모델 배정 계획을 승인한 결과는 아니다.

작성 후 수행할 자체 점검: 상대 링크 존재, 14개 role-id 중복 없음, B01~B12/A01~A16 누락 없음, 일정 합계 일치, 기획안과 실행계획의 검수·권한·범위 일치. 이 점검은 외부 독립검수나 솔루션 구현 시험을 대신하지 않는다.

외부 Fable/Opus 검수·정책 적용·채팅 재구성·자동화 구현·전체 verify는 이 문서 작성 시점에 미실행이다. 다음 실행 단위는 L0의 정책 변경 후보와 경로별 작업 순서 확정이다.
