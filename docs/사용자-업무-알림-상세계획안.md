# 사용자 업무 알림 상세 기획안

> 상태: 6종 매장 선호·기기 권한·token 등록/교체/로그아웃 폐기 구현 완료, 후보 생성·전달 인프라 구현 전
> 기준일: 2026-09-21
> 적용 범위: 모바일 점주 앱의 재료·발주·입고·메뉴 손익·매출 작성·고정 지출 푸시 알림
> 관련 기능: `FN-MY-021`, `FN-MY-022`

## 1. 문서 책임

이 문서는 사용자 업무 알림의 **대상 판정, 발송 시점, 묶음·중복 제거, 문구, 이동 목적지,
저장·전달 구조와 검수 기준**의 단일 기준이다. 현재 구현 상태는
[`기능정의서`](./기능정의서.md)와 [`작업큐`](./작업큐.md), 서버 공통 비동기 구조는
[`서버 확장 아키텍처 기획안`](./서버-확장-아키텍처-기획안.md)이 소유한다.

현재 앱은 MY-06에서 아래 6개 매장 공통 선호를 저장하고, 사용자의 명시 동의 뒤 Expo token을 현재
사용자·매장·설치에 등록한다. token 원문은 앱 role이 직접 읽지 못하며 token 회전과 로그아웃 폐기를
지원한다. 서버 후보 생성·예약·전송·영수증 확인 경로는 아직 없다. 따라서 **기기 수신 준비와 실제
푸시 전달 구현을 구분**하며,
아래 전달 단계와 합격 기준을 모두 통과했을 때만 `FN-MY-022`를 완료로 바꾼다.

## 2. 제품 목표와 원칙

알림은 사장님이 지금 처리해야 할 누락이나 상태 변화를 알려 앱의 원장을 완성하도록 돕는다.
조회수를 늘리기 위한 홍보 알림은 범위 밖이다.

1. 판정은 기기 시각이 아니라 서버의 매장 시간대·영업일·예정 시작/종료 시각을 사용한다.
2. 알림은 원장을 수정하지 않는다. 사용자가 알림을 열고 기존 RPC로 처리해야 상태가 바뀐다.
3. 예약할 때와 실제 전송 직전에 조건을 다시 확인한다. 이미 처리된 항목은 보내지 않는다.
4. 같은 원인·대상·판본·발송 구간에는 한 번만 보낸다.
5. 미산출, 0원, 미작성, 작성 중, 작성 완료를 서로 바꾸어 해석하지 않는다.
6. 잠금 화면 문구에는 매출액·순이익액·재고 수량 같은 민감한 숫자를 기본 노출하지 않는다.
7. 푸시가 실패해도 입고·판매·손익·재고 원장의 저장 성공 여부에는 영향을 주지 않는다.

## 3. 공통 용어와 상태 판정

| 용어 | 판정 |
| --- | --- |
| 매장 현지 시각 | `store_time_settings`와 영업 규칙을 적용한 서버 시각 |
| 다음 영업일 | 휴무·임시 휴무를 제외한 다음 `sales_calendar_days` 기대 영업일 |
| 예정 시작·종료 | 해당 영업일에 서버가 계산한 시각. 자정 통과 영업의 종료일 오프셋 포함 |
| 미작성 | 기대 영업일이며 확정 판본과 활성 초안이 없음 |
| 작성 중 | `sales_day_drafts.status = editing` |
| 전체 재고 실사 대기 | `sales_day_drafts.status = pending_inventory_resolution`. 다음 전체 재고 실사가 판매 증가분을 흡수해야 완료 가능 |
| 작성 완료 | 현재 확정 판본이 있음. 합계가 0원이어도 작성 완료 |
| 고정 지출 미입력 | `fixed_cost_basis_result.missing_months`가 비어 있지 않음 |
| 손익 미산출 | 필요한 고정 지출 월 또는 계산 기준 매출이 없어 서버 손익이 `null` |
| 재료 부족 | 활성 재료의 발주 후보가 `pending`이고 이미 발주 처리되지 않음 |
| 재고 확인 대상 | 알림 발송 시점에 재고 추적 중인 활성 재료의 `stock_total < 0` |
| 예상 입고일 경과 | 매장 현지 날짜가 `expected_at`보다 뒤이고 발주 상태가 `ordered` 또는 `partial` |

고정 지출 미입력 상태에서는 순이익을 0원이나 추정값으로 만들지 않는다. 목표 순이익률 미달
알림도 손익이 `null`인 경우 만들지 않는다.

## 4. 알림 카탈로그

### 4.1 재료 부족

| 항목 | 정책 |
| --- | --- |
| 대상 | 활성 재료 중 `pending` 발주 후보이며 아직 발주하지 않은 항목 |
| 시점 | 다음 영업일 예정 시작 3시간 전 |
| 빈도 | 영업일당 한 번, 여러 재료를 한 건으로 묶음 |
| 재확인 | 비활성·발주 완료·후보 제외·재고 회복 항목 제거 후 0건이면 취소 |
| 이동 | 발주 홈의 발주 후보 목록. 첫 재료를 강조하되 전체 후보가 보이게 함 |

- 1건 제목: `[재료명] 재고가 부족해요`
- 여러 건 제목: `[재료명] 외 N개 재료의 재고가 부족해요`
- 내용: `영업에 차질이 없도록 미리 발주를 진행해 주세요.`

`N`은 전체 건수가 아니라 첫 항목을 제외한 나머지 수다. 최소재고 경계는 제품 표시 규칙과 같이
`stock_total <= safety_stock`로 통일한다.

### 4.2 입고 확인

| 항목 | 정책 |
| --- | --- |
| 대상 | 예상 입고일이 지났고 남은 입고 수량이 있는 `ordered`·`partial` 발주 |
| 시점 | 영업 시작 2시간 전 |
| 빈도 | 현지 날짜당 한 번, 여러 발주를 한 건으로 묶음 |
| 재확인 | 입고 완료·취소·예상일 변경 건 제거 후 0건이면 취소 |
| 이동 | 발주 홈의 입고 대기 목록. 개별 건이면 해당 입고 화면으로 이동 |

- 1건 제목: `[재료명]의 도착 예정일이 지났어요`
- 여러 건 제목: `[재료명] 외 N건의 도착 예정일이 지났어요`
- 내용: `물건을 받으셨다면 잊지 말고 입고 처리를 완료해 주세요.`

배송 지연이 확인된 것이 아니므로 제목과 내용에서 `배송 지연`을 단정하지 않는다.

### 4.3 재고 확인

`재고 확인 알림`은 마이너스 재고가 남아 있을 때 주 1회 묶어서 알려주는 선택 알림이다. 판매 때문에
생긴 음수 재고는 허용된 원장 결과이며 오류로 바꾸거나 0으로 보정하지 않는다. 정기 전체 재고 실사
알림은 1차 범위에서 제외한다.

| 항목 | 정책 |
| --- | --- |
| 대상 | 발송 직전에 재고 추적 중인 활성 재료 중 `stock_total < 0`인 항목이 하나 이상 |
| 시점 | 매주 대표 정기 휴무일 13:00 |
| 휴무 없음 | 매주 첫 번째 영업일 예정 종료 2시간 후 |
| 빈도 | 매장당 주 1회, 여러 재료를 한 건으로 묶음 |
| 재확인 | 입고·판매 정정·개별 재고 수정·전체 실사로 0 이상 회복하거나 비활성·재고 추적 해제된 항목 제거 후 0건이면 취소 |
| 이동 | 1건이면 해당 재료 상세, 여러 건이면 재료 목록의 마이너스 재고 필터 |

- 1건 제목: `[재료명]의 재고 기록을 확인해 주세요`
- 여러 건 제목: `[재료명] 외 N개 재료의 재고 기록을 확인해 주세요`
- 내용: `빠진 입고나 판매 기록을 확인하고 실제 수량과 다르면 재고를 수정해 주세요.`

알림은 전체 실사를 자동 시작하거나 요구하지 않는다. 사용자는 누락된 입고·판매 기록을 먼저 확인하고
필요할 때 해당 재료의 재고 수정 기능을 사용한다. 전체 실사는 `pending_inventory_resolution`처럼
서버가 요구하는 기존 복구 흐름에서만 필수로 유지하며, 이 상태 자체는 푸시 사유에 넣지 않는다.

재료 부족 알림은 최소재고 기반의 **발주 업무**, 재고 확인 알림은 마이너스인 실제 수량과 원장 기록을
대조하는 **정합성 업무**다. 같은 발송 시각에 같은 재료가 겹치면 재료 부족 알림 한 건에
`마이너스 재고는 실제 수량도 확인해 주세요`를 함께 표시하고 별도 재고 확인 푸시는 보내지 않는다.
음수 재고도 실제 원장이므로 발주 후보 수량에서 제외하거나 0으로 잘라 계산하지 않는다.

### 4.4 목표 순이익률 미달 전환

| 항목 | 정책 |
| --- | --- |
| 대상 | 자동 재계산의 직전 판본은 `실제 순이익률 >= 목표`, 새 판본은 `실제 순이익률 < 목표`인 메뉴 |
| 제외 | 최초 계산부터 미달, 미산출→미달, 사용자가 목표 자체를 올린 결과, 계산 대기 중인 기준 |
| 시점 | 새 비용 기준이 실제 적용된 직후, 첫 전환부터 5분 뒤 묶음 발송 |
| 빈도 | 메뉴·계산 기준 판본·전환당 한 번 |
| 이동 | 해당 메뉴 상세의 손익 카드. 여러 건이면 목표 미달 메뉴 목록 |

- 1건 제목: `[메뉴명]의 순이익률이 목표치 아래로 떨어졌어요`
- 여러 건 제목: `[메뉴명] 외 N개 메뉴가 목표 순이익률에 미달했어요`
- 내용: `비용 기준 변경으로 순이익률이 낮아졌어요. 판매가와 비용을 다시 확인해 주세요.`

영업 중 저장되어 다음 영업일 경계에 적용되는 기준은 저장 시점이 아니라 **실제 적용 시점**에 판정한다.
입고 등 비용 기준 변경으로 여러 메뉴가 동시에 전환되면 같은 5분 묶음에 포함한다.

### 4.5 일간 매출 작성

| 항목 | 정책 |
| --- | --- |
| 대상 | 해당 영업일이 `미작성` 또는 `작성 중` |
| 시점 | 해당 영업일 예정 종료 2시간 후 |
| 빈도 | 영업일당 한 번 |
| 제외 | 휴무, 작성 완료, 편집 가능 기간 종료 |
| 이동 | 미작성은 해당 날짜 매출 작성, 작성 중은 기존 초안 이어쓰기 |

- 미작성 제목: `[M월 D일] 매출을 작성해 주세요`
- 미작성 내용: `매출을 작성하고 해당 영업일의 순이익을 확인해 주세요.`
- 작성 중 제목: `[M월 D일] 작성 중인 매출이 있어요`
- 작성 중 내용: `작성 중인 내역을 확인하고 매출 작성을 완료해 주세요.`

자정을 넘는 매장은 `오늘` 대신 영업일 날짜를 표시한다.

### 4.6 주간 매출 작성

| 항목 | 정책 |
| --- | --- |
| 대상 | 직전 완료 주의 기대 영업일 중 `미작성`·`작성 중` 날짜가 하나 이상 |
| 시점 | 이번 주 첫 정기 휴무일 13:00. 정기 휴무가 없으면 두 번째 영업일 종료 2시간 후 |
| 휴무 선택 | 정기 휴무가 여러 날이면 이번 주의 첫 번째 휴무일 |
| 빈도 | 기준 주당 한 번 |
| 이동 | 매출 작성 목록의 직전 주 필터. 미작성·작성 중 수를 함께 표시 |

- 제목: `지난주에 작성하지 않은 매출이 있어요`
- 내용: `미작성 또는 작성 중인 영업일이 남아 있어요. 정확한 손익 확인을 위해 작성을 완료해 주세요.`

알림 데이터에는 `미작성 N일 · 작성 중 N일`을 넣고 앱을 열었을 때 표시한다.

### 4.7 월간 매출 작성

| 항목 | 정책 |
| --- | --- |
| 대상 | 전월 기대 영업일 중 `미작성`·`작성 중` 날짜가 하나 이상 |
| 시점 | 익월 1일 영업 시작 3시간 전 |
| 1일 휴무 | 익월 첫 영업일 시작 3시간 전 |
| 월 경계 | 계산 시각이 전월이면 익월 1일 00:05 이후로 보정해 전월에 미리 보내지 않음 |
| 빈도 | 대상 월당 한 번 |
| 이동 | 매출 작성 목록의 전월 필터 |

- 제목: `지난달 매출 기록을 정리해 주세요`
- 내용: `지난달의 미작성·작성 중 내역을 완료하고 월간 손익을 확인해 주세요.`

월간 알림을 보내기 직전에 전월 상태를 다시 집계한다. 모두 완료되었으면 전송하지 않는다.

### 4.8 매출 작성 기한 임박

현재 매출 작성·수정 가능 범위가 이번 달과 지난달이므로 월간 알림만으로는 복구 불가능한 누락을
막기 어렵다. 지난달에 미작성·작성 중 날짜가 남아 있으면 편집 가능 기간 종료 7일 전과 1일 전에
알린다.

- 7일 전 제목: `지난달 매출 작성 기한이 7일 남았어요`
- 1일 전 제목: `지난달 매출 작성 기한이 내일까지예요`
- 내용: `기한이 지나기 전에 남은 매출 작성을 완료해 주세요.`
- 이동: 전월의 미작성·작성 중 목록

같은 날 같은 날짜들을 대상으로 월간·주간·일간 알림도 예정되어 있으면 기한 임박 알림만 보낸다.

`pending_inventory_resolution`은 푸시 대상에서 제외한다. 이미 완료된 전체 재고 실사 시점과 겹치는
과거 매출 증가분은 다음 전체 재고 실사가 흡수해야 하며, 현재 앱에는 매출 일자별 재고 확인 기능이
없다. 이 상태는 앱 안에서만 안내하고 일간·주간·월간 매출 알림의 `작성 중` 건수에도 포함하지 않는다.

### 4.9 고정 지출

고정 지출은 `fixed_cost_basis_result`가 요구하는 월을 모두 입력할 때까지 하나의 캠페인으로 관리한다.
입력 완료 즉시 남은 예약을 취소하고, 월이 바뀌어 새 필수 월이 생기면 새 캠페인을 시작한다.

| 시점 | 발송 조건 | 문구 |
| --- | --- | --- |
| 최초 인증 로그인 다음 영업일 시작 2시간 전 | 최초 설정 또는 필수 월 입력이 미완료. 다른 고정 지출 알림과 겹치면 한 번만 발송 | 제목 `순이익 계산을 위해 고정 지출을 설정해 주세요` / 내용 `임대료와 인건비처럼 매월 발생하는 고정 지출을 설정하면 비용이 빠지지 않은 순이익을 계산할 수 있어요.` |
| 매월 1일 영업 시작 2시간 전 | 월 변경으로 새 필수 월이 생겼고 미입력. 1일 휴무이면 첫 영업일, 월 경계 전이면 00:05 이후로 보정 | 제목 `지난달 고정 지출을 입력해 주세요` / 내용 `지난달 고정 지출을 입력하면 이번 달 메뉴와 매출의 순이익 계산에 반영돼요.` |
| 매주 첫 번째 영업일 종료 2시간 후 | 필요한 월이 여전히 미입력 | 제목 `고정 지출이 없어 순이익을 계산할 수 없어요` / 내용 `필요한 월의 고정 지출을 입력하고 메뉴와 매출의 순이익을 확인해 주세요.` |

최초 기준은 앱 설치나 재설치가 아니라 **매장에 연결된 인증 사용자의 첫 로그인 상태**다. 고정 지출은
입력되었지만 기준 월매출이 없거나 0원이라 계산할 수 없는 경우에는 입력 독촉과 분리한다.

- 제목: `고정 지출 계산 기준을 확인해 주세요`
- 내용: `고정 지출률 계산에 필요한 월매출이 없거나 0원이에요.`

### 4.10 세금 설정

세금 설정은 매월 작성하는 원장이 아니므로 정기 푸시에서 제외한다. 세금 프로필이 필수인데 준비되지
않은 경우 해당 계산 화면에서 지속 안내하고, 국가·지역·세금 정책 변경 직후에는 설정 흐름 안에서
확인한다.

## 5. 중복 제거와 우선순위

### 5.1 공통 멱등 키

```text
notification_type
+ store_id
+ recipient_id
+ subject_scope
+ subject_revision_or_period
+ scheduled_window
```

이 값을 해시한 `dedup_key`에 unique 제약을 둔다. Worker 재시도, Cron 중복 실행, 네트워크 응답 유실이
있어도 새 전송 의도를 만들지 않는다.

### 5.2 매출 알림 우선순위

같은 영업일 누락을 여러 알림이 가리키면 다음 한 건만 보낸다.

```text
작성 기한 1일 전
> 작성 기한 7일 전
> 월간
> 주간
> 일간
```

우선 알림이 전송되면 하위 알림에는 `suppressed_by`를 기록한다. 상위 알림이 전송 전에 조건 해소로
취소되었다고 하위 알림을 뒤늦게 보내지는 않는다.

### 5.3 묶음 규칙

- 재료 부족·입고 확인은 매장과 발송 시각 단위로 묶는다.
- 목표 미달은 첫 사건부터 5분 동안 같은 종류를 모은다.
- 5분은 계산을 늦추는 시간이 아니라 푸시를 한 건으로 줄이는 대기 시간이다.
- 제목에는 첫 항목과 나머지 건수만 넣고, 전체 목록은 앱 안에서 보여준다.
- 월간 매출과 고정 지출은 서로 다른 업무이며 사용자가 정한 시각을 유지해 자동 병합하지 않는다.

## 6. 알림 설정 화면

MY-06에는 다음 6개 상위 항목을 이 순서로 표시한다. 화면 제목이 `알림 설정`이어도 사용자가 기능을
바로 구분할 수 있도록 행 이름에는 `알림`을 유지한다.

| 상위 항목 | 화면 설명 | 하위 설정 | 기존 값 이관 |
| --- | --- | --- | --- |
| 재료 부족 알림 | 최소재고 이하의 발주 후보가 있으면 다음 영업일 시작 3시간 전에 알려요 | 없음 | `alert_morning_summary` |
| 입고 확인 알림 | 예상 입고일이 지난 발주가 있으면 영업 시작 2시간 전에 알려요 | 없음 | `alert_inbound_delay` |
| 재고 확인 알림 | 마이너스 재고가 남아 있으면 주 1회 알려요 | 없음 | 신규 |
| 순이익률 변동 알림 | 자동 재계산으로 목표 달성에서 목표 미달로 바뀌면 알려요 | 없음 | `alert_target_miss` |
| 매출 작성 알림 | 미작성·작성 중 매출과 작성 기한을 알려요 | 없음. 일간·주간·월간·작성 기한 임박 시점은 하나의 정책으로 동작 | 신규 |
| 고정 지출 알림 | 순이익 계산에 필요한 고정 지출이 입력되지 않았을 때 알려요 | 없음. 최초·월간·주간 시점은 하나의 정책으로 동작 | 신규 |

각 상위 스위치는 해당 알림 종류 전체를 켜고 끈다. `매출 작성 알림`은 하위 스위치를 두지 않고
하나의 값으로 일간·주간·월간·작성 기한 임박 알림을 함께 제어한다. 현재 권위 저장소는
`settings`의 **매장 단위 열**이며, 같은 매장에 속한 사용자는 같은 값을 공유한다. 개인별 푸시 선호가
필요해지는 시점에는 별도 사용자 선호 테이블로 분리한다.

| 의미 키 | 현재 DB 열 |
| --- | --- |
| `material_shortage` | `alert_morning_summary` |
| `inbound_confirmation` | `alert_inbound_delay` |
| `negative_stock_check` | `alert_negative_stock_check` |
| `target_profit_miss` | `alert_target_miss` |
| `sales_entry` | `alert_sales_entry` |
| `fixed_cost_missing` | `alert_fixed_cost_missing` |

`순이익률 변동 알림`은 상승·하락 전체를 뜻하지 않는다. 화면 설명과 접근성 라벨에
`목표 달성에서 미달로 변경된 경우`를 함께 제공한다. `재고 확인 알림`은 마이너스 재고 확인 푸시만
제어하며 음수 표시나 `pending_inventory_resolution` 필수 안내를 끄는 설정으로 사용하지 않는다.
업무별 서버 선호와 이 기기의 OS 수신 권한을 분리한다. 화면 진입이나 업무별 스위치 조작만으로 OS
권한 팝업을 띄우지 않고, 상단 `이 기기 알림 켜기`를 누를 때만 요청한다. 권한이 거절된 상태에서는
업무 선호는 보존하되 `기기 설정에서 코스트킵 알림을 허용해 주세요`와 설정 열기 동작을 표시한다.

기존 `alert_price_spike`는 더 이상 화면에 노출하거나 알림 판정에 사용하지 않는다. 첫 마이그레이션에서는
열을 바로 삭제하지 않고 이전 앱의 순차 배포를 위해 RPC 읽기·쓰기를 한 배포 주기만 유지한다.
새 앱은 이 추가 응답 키를 무시한다. 활성 앱 판본이 모두 전환된 사실을 확인한 뒤 별도 정리 migration에서
RPC 호환 키와 열을 함께 제거한다. DB migration을 앱 배포보다 먼저 적용한다.

후속 작업: 운영 지표에서 구 앱 호출이 없고 강제 최소 앱 판본이 6종 알림 지원 판본 이상임을 확인한 뒤,
그 시점의 다음 migration 번호로 `get_settings`·`save_settings`의 `alert_price_spike` 호환 계약과 컬럼을
함께 제거한다. 제거 migration에는 구 앱 호출 차단 확인, 새 앱 6종 응답, 판본·무변경 저장 회귀시험을 넣는다.

인앱 필수 안내는 푸시 선호와 별개다. 세금 프로필 미완료, 손익 미산출, 전체 재고 실사 대기 같은
상태는 관련 화면에서 계속 보여주되 `pending_inventory_resolution` 푸시는 만들지 않는다.

## 7. 데이터와 서버 구조

### 7.1 권위 입력

| 알림 | 권위 데이터 |
| --- | --- |
| 재료 부족 | 활성 재료, `inventory_states`, `order_candidates` |
| 입고 확인 | `order_records.expected_at/status/received_qty` |
| 재고 확인 | 재고 추적 중인 활성 재료와 `inventory_states.stock_total` |
| 목표 미달 | 적용 완료된 `profit_trends`의 전후 판본과 목표값 |
| 매출 | `sales_calendar_days`, `sales_day_drafts`, 확정 판매 판본, 서버 편집 가능 기간 |
| 고정 지출 | `fixed_cost_basis_result`의 `missing_months`와 계산 불가 사유 |
| 시각 | 매장 시간대, 영업 규칙, 임시 휴무, 서버 `now()` |

앱이 백그라운드에서 같은 공식을 다시 계산해 로컬 알림을 예약하지 않는다.

### 7.2 저장 모델

기존 서버 확장 계획의 outbox·Queue·Consumer 구조를 재사용한다.

```text
권위 RPC 또는 예약 스윕
  → 조건 판정·전송 직전 재검증
  → integration_outbox_events에 notification.push.requested 기록
  → pg_cron dispatch_outbox(limit)
  → Queue
  → service-only Push Edge Function
  → Expo Push API
  → ticket·receipt를 integration_delivery_attempts에 기록
```

알림 구현에 필요한 최소 저장 책임은 다음과 같다.

| 저장 책임 | 필수 필드 |
| --- | --- |
| 기기 등록 | 사용자, 기기 설치 ID, 플랫폼, Expo token 원문, token fingerprint, 앱 판본, 활성·폐기 시각 |
| 매장 선호 | 매장, 알림 키에 대응하는 `settings` 열, revision, updated_at. 같은 매장 사용자가 공유 |
| 묶음 창 | 매장, 알림 종류, 최초 사건, due_at, 대상 ID·판본, 상태 |
| outbox 의도 | event_id, store_id, recipient, template_id/version, 최소 params, dedup_key, available_at |
| 전송 시도 | event_id, attempt, provider ticket, 결과 코드, 다음 재시도, 완료·폐기 시각 |

푸시 token 원문은 발송 서비스만 읽는다. 앱 role에 SELECT를 주지 않고 등록·폐기는 본인 범위를 검증하는
전용 RPC로만 수행한다. 로그와 관리자 화면에는 fingerprint 끝 일부만 표시한다.

### 7.3 예약 스윕

`pg_cron`은 1분마다 제한된 수의 매장을 스캔한다. 각 스윕은 다음 순서를 지킨다.

1. 서버 UTC 시각을 매장 현지 시각으로 변환한다.
2. 영업일·휴무·예정 시작/종료와 알림 종류별 기준 시각을 계산한다.
3. 사용자 선호와 현재 업무 상태를 조회한다.
4. 발송 대상이 있으면 unique `dedup_key`로 outbox에 넣는다.
5. 발송 Consumer가 한 번 더 현재 상태를 확인하고 조건이 해소되었으면 `canceled_resolved`로 끝낸다.

전체 매장을 한 트랜잭션에서 처리하지 않는다. 커서·batch limit·`FOR UPDATE SKIP LOCKED`로 경합을
막고 오래 걸리는 외부 호출은 Cron 트랜잭션 밖의 Consumer가 처리한다.

### 7.4 사건 기반 알림

목표 미달은 주기 스캔으로 변화 원인을 추측하지 않는다. 손익 기준 적용 RPC가 업무 판본과 알림 묶음
대상을 같은 트랜잭션으로 기록한다. 원장 저장은 성공했지만 푸시 이벤트만 사라지는 dual-write를
금지한다.

## 8. 모바일 전달과 이동 계약

알림 payload에는 임의 URL 문자열 대신 버전이 있는 이동 계약을 넣는다.

```json
{
  "schemaVersion": 1,
  "destination": "sales.write",
  "storeId": "uuid",
  "businessDate": "2026-09-21",
  "entityId": "optional-uuid"
}
```

| destination | 기본 이동 |
| --- | --- |
| `orders.candidates` | `ORD-01` 발주 후보 |
| `orders.inbound` | `ORD-01` 입고 대기 또는 `ORD-03` 개별 입고 |
| `ingredients.negative` | 음수 재료 1건 상세 또는 재료 목록의 음수 필터 |
| `menu.profit` | 메뉴 상세 손익 |
| `sales.write` | `/sales/write?date=YYYY-MM-DD` |
| `sales.missing` | 매출관리 목록의 지정 기간 |
| `fixed_costs` | `/recipes/fixed-cost` |

앱이 종료된 상태에서는 인증과 매장 scope를 복원한 뒤 이동한다. 사용자가 매장 권한을 잃었거나 대상이
삭제·비활성화되었으면 잘못된 상세 화면을 열지 않고 해당 목록으로 이동해 상태 변경 안내를 보여준다.

## 9. 전송 실패와 보존

- 일시적 timeout·429·5xx는 지수 백오프로 최대 5회 재시도한다.
- 영구 payload 오류와 최대 시도 초과는 dead letter로 보내 관리자 재처리 대상이 된다.
- `DeviceNotRegistered`는 해당 기기 token을 즉시 폐기한다.
- 로그아웃은 현재 기기 등록 폐기를 먼저 시도하되 네트워크·만료 세션 때문에 로그아웃 자체를 막지 않는다.
  폐기 실패는 기기 SecureStore의 보류 표식으로 남기고, 다음 인증 세션에서 OS 권한을 묻기 전에 같은
  설치 ID를 먼저 폐기한다. 계정이 달라도 설치 ID를 가진 실제 기기가 이전 계정 알림을 계속 받지 않게
  한 뒤, 권한이 허용된 경우 현재 사용자·매장으로 다시 등록한다. 계정 탈퇴는 해당 계정의 모든 기기를 폐기한다.
- 성공 outbox·시도 상세은 90일, dead letter는 180일 보관 후 집계만 남긴다.
- 최종 제목·본문 전체 대신 `template_id/version`과 최소 치환값을 저장한다.
- 푸시 실패를 이유로 업무 원장 RPC를 rollback하거나 다시 실행하지 않는다.

## 10. 관측·운영

필수 지표:

- 종류별 생성·억제·조건 해소 취소 건수
- 예약 시각 대비 outbox 생성 지연 p50·p95·p99
- Queue depth와 oldest age
- 공급사 ticket 성공률, receipt 성공률, 429·5xx·영구 실패율
- 활성 token 수와 `DeviceNotRegistered` 비율
- dedup 충돌 수와 중복 푸시 신고 수
- 알림 열기율과 목적 화면 도착 실패율
- 매출·고정 지출 알림 후 완료 전환율

운영자가 볼 수 있는 것은 매장, 알림 종류, 예약·전송 상태, template version, token fingerprint,
오류 코드다. 매출액·순이익액·전체 token 원문은 표시하지 않는다.

## 11. 구현 순서

### N0. 계산 계약 정렬

- 재료 부족 경계를 `stock_total <= safety_stock`로 통일한다.
- 재고 확인 대상을 발송 시점의 `stock_total < 0`인 재고 추적 활성 재료로 고정한다.
- 최소재고 부족·메뉴 1인분 부족·`pending_inventory_resolution`과 재고 확인 사유를 구분한다.
- 같은 발송 시각의 재료 부족 알림과 겹치면 별도 푸시를 만들지 않고 확인 문구만 합친다.
- 목표 미달 전환의 이전/현재 판본과 `null` 처리 계약을 고정한다.
- 매출 미작성·작성 중·완료와 편집 마감일 조회 계약을 고정하고, `pending_inventory_resolution`은
  알림 후보에서 제외한다.
- 고정 지출 `missing_months`와 `sales_missing_or_zero`를 구분한다.

### N1. 선호와 기기 등록

- [x] 신규 알림 선호 키와 설정 revision 저장을 추가한다.
- [x] 기존 네 키를 손실 없이 이관한다.
- [x] Expo SDK 54 호환 알림·기기·상수·암호 모듈을 추가한다.
- [x] 명시적 권한 요청, token 등록·교체·로그아웃 폐기 RPC와 화면 상태를 구현한다.
- [x] 설치 ID 동시 생성을 단일화하고, 로그아웃 폐기 실패의 보류·다음 로그인 선처리를 구현한다.
- 실제 원격 푸시 N1 증빙은 Expo Go가 아니라 EAS development/production build의 실제 iOS·Android 기기에서 수집한다.

### N2. 알림 후보 생성

- 공통 순수 스케줄 함수와 서버 SQL 판정을 만든다.
- 사건 기반 묶음 창과 예약 기반 스윕을 구현한다.
- 우선순위·dedup·조건 해소 취소를 DB 제약과 시험으로 고정한다.

### N3. 전달 경로

- generic outbox·Queue·delivery attempt·dead letter를 서버 확장 계획대로 추가한다.
- service-only Edge Function에서 Expo batch 전송과 receipt 확인을 구현한다.
- raw token·service key가 Data API, 로그, 앱 번들에 노출되지 않게 ACL을 검사한다.

### N4. 모바일 UX

- MY-06의 6개 독립 스위치, 권한 거절 안내, OS 설정 이동을 구현한다.
- foreground·background·cold start 알림 탭을 같은 이동 계약으로 처리한다.
- 목록 fallback, 다른 매장 scope 차단, 삭제된 대상 처리를 구현한다.
- 잠금 화면 문구의 민감 수치 비노출과 글자 확대·스크린리더를 확인한다.

### N5. 스테이징과 운영

- 스테이징에서 실제 전송 대신 dry-run으로 7일간 후보·중복·시각을 기록한다.
- 내부 테스트 기기만 허용하는 canary flag로 실제 전송한다.
- 429·5xx·잘못된 token·Queue 중복·Cron 중단 복구 훈련을 수행한다.
- 운영 지표와 kill switch를 확인한 뒤 매장 비율을 단계적으로 늘린다.

## 12. 시험 행렬

### 12.1 시간·영업일

- Asia/Seoul과 DST가 있는 시간대 각각에서 시작 전·종료 후 시각
- 자정을 넘는 영업, 월말·연말, 윤년, 1일 휴무, 임시 휴무
- 영업시간 변경 직전·직후, 예정 후 실제 조기·지연 종료
- 월 시작 전으로 계산되는 `시작 - N시간`의 00:05 보정

### 12.2 상태

- 재료 재고가 최소재고보다 큼·같음·작음·0·음수
- 발주 후보 생성 후 발주·제외·재고 회복
- 재고가 음수·0·양수인 재료와 비활성·재고 추적 해제 재료 제외
- 입고·판매 정정·개별 조정·전체 실사로 발송 직전 0 이상 회복
- 한 건·여러 건 묶음과 `외 N개` 계산, 매장별 주 1회 중복 방지
- 같은 시각의 재료 부족 알림과 합쳐질 때 별도 재고 확인 푸시 미생성
- 발주 `ordered/partial/received/canceled`, 예상일 null·오늘·과거
- 목표 달성→미달, 미달→미달, null→미달, 미달→달성
- 매출 0원 완료, 미작성, 작성 중, 마감 만료, 전체 재고 실사 대기 상태의 알림 미생성
- 고정 지출 전부 입력, 일부 월 누락, 매출 0원, 월 변경

### 12.3 멱등·경합·실패

- Cron 두 세션 동시 실행과 같은 `dedup_key` 삽입

- 알림 탭 직전에 권한·매장 scope·대상 상태 변경

## 13. 완료 기준

다음 조건을 모두 만족해야 실제 업무 알림 수신을 완료로 판정한다.

- 모든 알림 종류가 이 문서의 권위 상태와 서버 영업일로 판정된다.
- 예약과 전송 직전 재검증, 우선순위, 묶음, unique dedup이 시험으로 고정된다.
- 사용자가 완료한 업무의 늦은 알림과 같은 업무의 중복 푸시가 없다.
- 푸시 실패가 재고·발주·입고·매출·손익 원장에 영향을 주지 않는다.
- 앱이 닫혀 있어도 정확한 매장과 목적 화면으로 이동하고 scope가 바뀌면 안전한 목록으로 물러난다.
- 서비스 키와 token 원문이 앱 role·로그·관리자 일반 조회에 노출되지 않는다.
- `verify` 전체 필수 게이트와 스테이징 전송 검수가 통과한다.
- 기능정의서, 화면 인벤토리, 작업큐, AppMap의 상태와 문구가 같은 판본으로 갱신된다.

## 14. 검토 결론

2026-09-21 제품 흐름과 Astra Ultra·Claude 독립 자문을 반영한 결론은 다음과 같다. 완료 검수
플러그인은 필수 전체 게이트가 제한 시간 이후 반환되지 않아 `REVIEW_BLOCKED`이며, 아래 결론은
두 읽기 전용 제품 자문과 로컬 문서 검사 결과다.

- 설정 화면은 재료 부족·입고 확인·재고 확인·순이익률 변동·매출 작성·고정 지출 알림의 6개
  독립 스위치로 구성한다. 매출 작성 스위치 하나가 일간·주간·월간·작성 기한 임박 알림을 함께 제어한다.
- 재고 확인 알림은 마이너스 재고가 남은 경우만 매장당 주 1회 묶어서 보내며 누락 기록과 개별 재고
  확인으로 연결한다. 정기 전체 재고 실사 푸시는 1차 범위에서 제외한다.
- 월간 매출은 사용자가 확정한 `익월 1일 영업 시작 3시간 전`을 사용한다.
- 복구 불가능한 누락을 막기 위해 매출 작성 기한 7일·1일 전 알림을 추가한다.
- `pending_inventory_resolution`은 일반 작성 중과 분리하고 푸시 대상에서 제외한다.
- 입고 단가 급등 알림과 기존 `alert_price_spike` 설정은 사용자 알림 범위에서 제거한다.
- 세금 설정 요청 푸시는 제외하고 화면 안의 필수 안내로 처리한다.
- 구현은 알림 UI부터 시작하지 않고 N0의 도메인 계약 정렬부터 진행한다.
