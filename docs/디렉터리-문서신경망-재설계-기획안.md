## 0. 목적과 권위

이 문서는 사람과 여러 AI 채팅이 저장소의 어느 위치에서 시작하더라도 같은 권위·Task·소스·시험·
검수 증거로 수렴하도록 디렉터리와 Markdown 배치를 설계한다. 파일 수를 늘리는 것이 목적이 아니라,
가까운 문맥은 가까이에 두고 단일 권위는 한 곳에만 두며 관계를 기계적으로 검증하는 것이 목적이다.

이 문서는 `DRAFT`다. 사람 승인으로 `ACTIVE`가 되고 `AGENTS.md` 책임 목록에 등재되기 전에는 현재
경로를 옮기거나 새 문서 규칙을 강제하지 않는다. 현재 권위 경로는 `AGENTS.md`와 팀 구성안 §0이
소유한다. 본 문서는 승인 뒤 진행할 경계 재설계의 목표와 이관 절차만 정의한다.

## 1. 핵심 판단

사용자가 제안한 “MD가 디렉터리 안에 신경망처럼 적재적소에 퍼지는 구조”는 방향이 맞다. 다만 모든
폴더에 설명 파일을 두면 복제·노후화·충돌이 급증한다. 권장 구조는 다음 두 층이다.

```text
중앙 권위 노드       정책·계산·작업·결정·위험·감사 규약의 단일 소유자
가까운 안내 노드     해당 디렉터리의 책임·진입점·금지 경계·시험·상위 권위 링크
```

가까운 안내 노드는 중앙 내용을 복사하지 않는다. “무엇을 여기서 찾는가, 무엇은 다른 곳의 권위인가,
어떤 시험으로 확인하는가”만 말한다. 이 구조가 문서 신경망의 기본 단위다.

## 2. 설계 원칙

1. **주제 하나, 권위 하나** — 같은 정책을 루트 문서·도메인 README·작업큐에 세 번 쓰지 않는다.
2. **소스와 설명을 가깝게** — 도메인 경계·진입점·시험 지도는 소스의 가장 가까운 README가 가진다.
3. **정책과 인스턴스를 분리** — 운영 정책은 기획안, 배포 결과는 `docs/deployments/`, 작업 상태는
   `docs/작업큐.md`가 가진다.
4. **채팅이 아니라 저장소가 기억한다** — 여러 채팅은 비식별 conversation reference로 같은 Task에
   연결되고 원문 대화 기억에 의존하지 않는다.
5. **사용자 파일을 자동 흡수하지 않는다** — 요청받지 않은 미추적 파일과 사용자 변경은 그래프 입력·
   이동·스테이징 대상에서 제외한다.
6. **한 번에 다 옮기지 않는다** — 인벤토리→링크 검사→파일군별 이동→동등성 검사 순으로 진행한다.
7. **임시 재수출로 과거 경로를 살리지 않는다** — 이동 뒤 모든 참조를 같은 변경에서 바꾸고 옛 경로
   재수출 파일은 두지 않는다.
8. **생성 색인은 권위가 아니다** — 자동 생성 인덱스는 원본을 찾는 보조물이며 사람이 직접 편집하지 않는다.
9. **빈 문서를 만들지 않는다** — 소유할 계약·진입점·시험이 없는 폴더에는 README를 만들지 않는다.
10. **정확한 SHA에서만 완료한다** — 이동·링크·시험·CI 결과를 같은 commit에 묶는다.

## 3. 현재 구조의 장점과 문제

### 유지할 장점

- `apps/mobile/src/features/<domain>` 중심의 제품 도메인 분리
- `packages/core`, `packages/db`, `packages/types`의 계산·DB·계약 경계
- `docs/ai-review/tasks/<TASK-ID>`의 검수 원본 격리
- `docs/deployments/`의 환경 적용 증거 분리
- 루트 `AGENTS.md`·`ARCHITECTURE.md`의 전역 권위
- `apps/mobile/src/features/README.md`의 화면·라우트 인벤토리

### 해결할 문제

- `docs/` 루트에 제품·플랫폼·AI 운영 기획안이 혼재해 시작점이 불명확하다.
- 도메인 README가 일부 경계에만 있어 새 채팅이 소스 전체를 검색한 뒤에야 책임을 파악한다.
- Task 상태·검수 증거·문서 관계가 링크는 있으나 기계적으로 그래프 검증되지 않는다.
- 여러 채팅의 edit owner·lease·다음 안전 행동을 한눈에 복원할 생성 뷰가 없다.
- 문서 이동 시 깨지는 링크·앵커·코드 주석을 전수 검사하는 전용 게이트가 없다.
- 기존 `components/kit` 내부 순환처럼 경계상 기술 부채와 계획 문서가 한 흐름으로 연결되지 않는다.

├─ core/                            순수 공식·미리보기·SQL parity

파일군만 별도 Task로 이동한다. 화면 ID와 expo route는 이동 여부와 무관하게 유지한다.

### 5.2 가까운 README 생성 기준

다음 중 두 가지 이상을 만족할 때만 로컬 README를 둔다.

- 외부 호출자가 알아야 할 공개 진입점이 3개 이상이다.
- 금지된 역참조 또는 계층 경계가 있다.
- 전용 시험·사보타주·배포 절차가 있다.
- 책임자가 다른 하위 영역이 2개 이상이다.
- 여러 채팅에서 반복적으로 잘못 탐색한 기록이 있다.

현재 우선 후보는 `apps/mobile/src/features/international-tax/`, `apps/mobile/src/components/kit/`,
`packages/core/`, `scripts/fable-review/`다. 실제 문서 생성은 인벤토리에서 임계값을 증명한 뒤 한다.

`docs/team/roles/*.md`는 이 기준의 예외적 필수 manifest다. 다만 주제별 정책·설계를 다시
쓰지 않고, 다음 필드만 소유한다: 역할 ID·활성 컨텍스트 ID/version/hash·허용 route·
입력 allowlist·권위 링크·필수 산출·인계 대상·중단 조건·검증 체크리스트. 활성화는
`ROLE_CONTEXTS.md`의 동일 판본·hash·자율성 Decision과 일치해야 한다.

### 5.3 로컬 README 최소 템플릿

```md
# <경계 이름>

## 책임
- 이 경계가 소유하는 것
- 소유하지 않는 것과 상위 권위 링크

## 진입점
- 공개 파일·함수·route

## 의존 규칙
- 허용 방향
- 금지 역참조

## 검증
- 가장 작은 시험
- 전체 게이트

## 변경 시 함께 볼 문서
- Decision·Architecture·Task 링크
```

다른 문서가 소유한 수치·정책·Task 상태를 복사하지 않고 권위 링크만 둔다. §5.1에 명시된 중앙 권위
README는 검사 allowlist이며 자신이 소유한 화면 ID·route·구현 상태를 기록할 수 있다. 일반 로컬
README에는 “현재 구현 완료” 같은 변동 상태를 넣지 않는다.

### 5.4 루트와 중첩 AGENTS 규칙

초기에는 루트 `AGENTS.md` 하나만 유지한다. 중첩 `AGENTS.md`는 도구별 우선순위 차이와 숨은 규칙을
만들 수 있으므로, 단순 안내는 README로 해결한다. 향후 중첩 규칙이 필요하면 다음을 모두 만족해야 한다.

- 루트에서 위임한 좁은 경계만 소유한다.
- 상위 규칙을 복사하거나 약화하지 않는다.
- 적용 경로와 precedence를 자동 시험한다.
- Codex와 Claude가 같은 파일을 선택하는지 사보타주로 확인한다.

## 6. 문서 신경망 관계

온톨로지의 노드·관계를 그대로 사용한다. 본 문서는 관계를 새로 정의하지 않는다. `ACTIVE` 문서가
아직 `DRAFT`인 후속 문서에 상세화를 맡기는 전이 링크는 `DELEGATED_PENDING`으로 표시하고, 활성
문서 안에 최소 게이트가 있을 때만 허용한다. 승인 뒤에는 `AUTHORITY_REF`로 전환한다.

관계 방향 사후조건은 다음 표를 기계 검증한다. 왼쪽이 주체, 오른쪽이 대상이며 역방향을 허용하지 않는다.

| 관계 | 정방향 계약 |
|---|---|
| 요청 정규화 | `NORMALIZED_REQUEST ─NORMALIZES→ REQUEST_INPUT` |
| Task 라우팅 | `NORMALIZED_REQUEST ─ROUTES_TO→ TASK` |
| Task 의존 | `TASK ─DEPENDS_ON→ DECISION` |
| 결정 구현 | `SOURCE ─IMPLEMENTS→ DECISION` |
| 소스 검증 | `SOURCE ─VERIFIED_BY→ TEST` |
| Task 증거 | `TASK ─EVIDENCED_BY→ REVIEW_ROUND / DEPLOYMENT_EVIDENCE` |
| 가까운 안내 | `DOMAIN_GUIDE ─POINTS_TO→ 상위 권위와 가까운 SOURCE·TEST` |
| 학습 근거 | `LEARNING ─LEARNED_FROM→ Finding/Test` |
| 학습 적용 | `LEARNING ─APPLIES_TO→ 허용 route` |

문서 링크만 있다고 관계가 성립하지 않는다. 노드 ID·권위 위치·상태·대상 SHA를 검사할 수 있어야 한다.

핵심 다섯 문서의 권위 의존은 아래 기계 판독 블록 하나가 소유한다. 탐색용 Markdown 링크는 이
표에 의존성을 더하지 않는다.

<!-- authority-dag:start -->
| team | [] |
| ontology | [team] |
| orchestration | [team, ontology] |
| directory | [team, ontology, orchestration] |
| quality | [team, ontology, orchestration, directory] |
<!-- authority-dag:end -->

## 7. 여러 채팅의 탐색·재개 흐름

새 채팅은 현재 채팅 요약을 기준으로 디렉터리를 고르지 않는다.

```text
루트 AGENTS.md
→ docs/작업큐.md의 Task ID·request_dispositions[]·edit lease
→ Task가 가리키는 중앙 권위 노드
→ 영향 디렉터리의 가까운 README
→ SOURCE·TEST·REVIEW/DEPLOYMENT 증거
→ exact SHA와 worktree 대조
→ next_safe_action 또는 stop_conditions
```

- conversation reference는 실제 thread ID가 아닌 비식별 값이다.
- 다른 채팅의 유효 lease가 있으면 읽기 전용 상태 확인과 인계 요청만 한다.
- 만료 lease를 자동 인수하지 않는다.
- Task 경로와 실제 Git 상태가 다르면 문서 탐색 결과를 믿고 편집하지 않는다.
- 사용자 추적 변경과 요청받지 않은 미추적 파일은 자동 색인·이동·스테이징에서 제외한다.

## 8. 생성 색인과 검사기

### 8.1 생성 산출물

다음은 소스가 아니라 파생 산출물이다.

- `docs/README.md`: 권위 문서·기획안·운영·감사·프로토타입 탐색 지도
- 문서 그래프 JSON: 노드 ID, path, status, owner, links, content hash
- Task resume view: 진행 Task의 last SHA, owner, lease, open Decision/Finding, next action
- 깨진 링크·고아 노드·중복 owner 보고서

생성 파일에는 “직접 편집 금지·권위 아님·생성 명령”을 표시한다. 원본과 다르면 생성 파일을 버리고
다시 만든다. 생성 산출물은 지식 그래프 노드가 아니라 그래프의 렌더링이며, 그래프 hash 입력에서
제외한다. 생성 파일에는 자기 hash가 아니라 입력 원본 집합과 그 content hash만 기록한다.

### 8.2 필수 정적 검사

- Markdown 상대 링크와 명시 앵커 존재
- 같은 authority topic의 ACTIVE owner 1개 이하
- DRAFT/REVIEWED 문서가 `AUTHORITY_REF`로 참조되지 않음. 전이 최소 게이트가 있는
  `DELEGATED_PENDING`만 예외
- Task의 필수 복원 필드와 비식별 conversation reference
- active edit lease 중 같은 artifact path 겹침 0건
- 가변 권위 문서·source·test·스크립트·CI·workspace 설정의 경로 존재와 옛 이동 경로 참조 0건
- 일반 README가 다른 권위의 정책·수치·Task 상태를 복사하지 않음. §5.1 중앙 권위 README는 소유
  주제만 허용
- generated index 직접 수정 탐지
- 역사 자료·프로토타입이 현재 권위로 연결되지 않음

### 8.3 동적·사보타주 검사

- 문서를 이동하고 한 링크만 옛 경로로 남기면 실패
- 셸 스크립트·GitHub Actions·workspace 설정에 옛 경로를 하나씩 남기면 각각 실패
- 같은 주제 ACTIVE owner를 둘로 만들면 실패
- 다른 채팅의 같은 artifact lease를 둘로 만들면 실패
- lease 소유자의 Task 갱신이 다른 채팅이 append한 `request_dispositions[]` 항목을 삭제·재정렬하거나
  chain prefix를 바꾸면 실패
- 요청받지 않은 미추적 파일을 이동 목록에 넣으면 실패
- Task에서 Decision 또는 시험 경로를 지우면 재개가 환경 미검증으로 멈춤
- 생성 색인을 손으로 고치면 원본 hash 불일치로 실패
- 로컬 README에 상위 정책의 낡은 수치를 복사하면 중복 규칙 검사 실패
- 누적 교차검수 집합의 문서 수·파일 목록을 오케스트레이션 기획안 §8.2 밖에서 복제하면 실패

## 9. 파일 이동 계약

하나의 이동 Task는 다음을 같은 commit에서 처리한다.

1. 원본과 목적지의 exact path 목록 고정
2. 사용자 변경·미추적 파일 겹침 확인
3. `git mv`로 이력 보존
4. import·Markdown 링크·코드 주석·검수 allowlist·문서 책임 지도·셸 스크립트·package.json·tsconfig·
   workspace 설정·GitHub Actions·verify 스크립트 경로 전수 갱신
5. 옛 경로 재수출·심볼릭 링크·복사본을 두지 않음
6. 경계·순환·링크·문서 그래프 시험
7. 제품에 영향이 있으면 기존 기능 시험과 `pnpm verify` 6/6
8. 같은 exact SHA의 `full-db-required`와 `protected-gate` 성공 뒤 완료

옛 경로 0건 검사는 가변 권위 문서·소스·시험·스크립트·설정만 대상으로 한다.
`docs/ai-review/tasks/*/rounds/`, `docs/ai-review/tasks/*/task.json`,
`docs/ai-review/tasks/*/collaboration.md`, `docs/ai-review/tasks/*/status.json`,
`docs/ai-review/evidence/`, `docs/deployments/`, `docs/source-v3/`의 불변·append-only·실행기 전용·
배포·역사 원본은 수정하지 않는다. “검수 allowlist 갱신”은 검수 실행기 설정과 앞으로 새로 발행할
`task.json`만 뜻한다. 진행 중 검수는 원본을 고치지 않고 후속 Task의 새 `task.json`으로 재발행한다.
이동 전·후 경로 매핑표는 이동 Task의 `evidence_paths`에 새 불변 증거로 남기고, 검사기는 이 매핑으로
봉인 원본의 옛 경로를 해석해 위반으로 세지 않는다.

이동 때문에 제품 동작을 바꾸지 않는다. 로직 수정이 필요하면 별도 Task와 commit으로 분리한다.

## 10. 역할과 편집 소유권

| 작업 | 제작 | 검증 | 독립 검수 | 승인 |
|---|---|---|---|---|
| 디렉터리 인벤토리 | SOLAR-ARCH | Codex 정적 분석 | 조건부 Fable/승계 fallback | AI 부 O |
| 문서 권위·관계 | AI 부 O | Codex graph check | Fable 아키텍처 | 사람 ACTIVE 승격 |
| 코드 이동 | 담당 SOLAR-DEV | Codex 동등성·전체 게이트 | 위험별 Fable route | AI 부 O/사람 |
| 운영·DB 경로 이동 | SOLAR-OPS/DB | Codex fresh·upgrade·deploy plan | Fable 보안·아키텍처 | 사람 |

`OPUS_DIRECT_ADVISORY`는 본 기획안의 누적 상호작용 자문이며 공식 독립 감사 칸을 대체하지 않는다.

## 11. 단계별 이관

### 단계 0 — 인벤토리와 동결

- 추적 파일·README·import·Markdown 링크·코드 주석·생성 파일을 목록화한다.
- 사용자 변경과 미추적 파일을 제외 목록으로 봉인한다.
- 현재 경로→목표 경로 매핑과 이동하지 않을 경계를 사람에게 제시한다.
- 이동 기간에는 같은 경로의 기능 작업을 병렬 실행하지 않는다.

### 단계 1 — 검사기를 먼저 만든다

- 문서 링크·중복 권위·고아 노드 검사
- Task 복원 필드·edit lease 검사
- 작업큐 전역 queue ledger lock과 Task lock의 고정 획득 순서 검사
- 옛 경로·역참조·순환 검사
- 각 검사에 실패 사보타주를 붙인다.

검사기 없이 문서부터 옮기지 않는다.

### 단계 2 — AI 운영 문서 파일군

- 오케스트레이션 기획안 §8.2가 정한 현재 누적 집합 전체와 team/ai-review 관계를 먼저 이동 후보로 검증한다.
- AGENTS·작업큐·검수 allowlist·모든 상호 링크를 같은 commit에서 바꾼다.
- 이동이 비용보다 혼란이 크면 현재 `docs/` 루트 경로를 유지하고 생성 인덱스만 도입한다.

### 단계 3 — 제품·플랫폼 기획안 파일군

- product/platform 구분이 실제 책임자·변경 주기와 맞는지 확인한다.
- 브랜치·DB·서버 기획안은 배포 스크립트·deployment evidence 링크를 함께 검증한다.
- 국제 출시 기획안은 앱·core·DB 계약 링크를 함께 검증한다.

### 단계 4 — 가까운 README

- §5.2 임계값을 만족한 경계부터 작성한다.
- README 내용 중 상위 권위와 겹치는 문장을 제거한다.
- 새 채팅 탐색 시험으로 필요한 파일 수와 잘못 선택한 경로 수를 잰다.

### 단계 5 — 제한된 코드 경계 리팩터링

- 확인된 중복·역참조·순환만 작은 Task로 해결한다.
- 이동 전후 공개 export·route·타입·동작을 동등성 시험으로 고정한다.
- DB migration과 제품 디렉터리 이동을 한 Task에 섞지 않는다.

### 단계 6 — 활성화

- 오케스트레이션 §8.2의 현재 사람 결정이 정한 외부 교차검수 유효 2회와 공식 필요한 Fable route를
  완료한다. 2026-09-02 결정 이후에는 공식 Fable 경로의 회차만 센다.
- graph checker와 사보타주가 같은 SHA에서 통과한다.
- 사람 승인 뒤 후속 네 기획안(온톨로지·오케스트레이션·디렉터리·평가)을 하나의
  activation commit에서 모두 `ACTIVE`로 바꾸고 AGENTS 책임 목록을 갱신한다. 부분
  `ACTIVE`는 거부한다.
- 첫 3개 실제 Task에서 다중 채팅 복원·탐색 비용을 관찰한 뒤 규칙을 조정한다.

## 13. 완료 조건

- 중앙 권위와 가까운 안내 문서의 책임이 분리된다.
- 여러 채팅이 저장소 Task·권위·README·증거만으로 같은 다음 행동을 복원한다.
- source/domain/test/audit/deployment 경로가 명시적 관계로 연결된다.
- 사용자 변경·미추적 파일과 동시 edit lease가 이동 도구에 의해 보호된다.
- 링크·권위 중복·고아 노드·옛 경로·순환을 자동 검사한다.
- 이동은 작은 파일군 단위이고 동작 변경과 분리된다.
- 오케스트레이션 기획안 §8.2가 정한 현재 누적 집합 전체의 책임·입력·출력·상태가 누적 교차검수에서 모순 없이 연결된다.
- exact SHA의 로컬·보호 원격 게이트와 사람 `ACTIVE` 승격이 기록된다.
