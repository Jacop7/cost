# 부자재 재고 관리 범위 검토

상태: 2026-09-13 사용자 판단을 위한 검토 초안. 구현 승인이나 확정 제품 정책이 아니다.

최신 검토안: **식품·포장용기를 사용자 화면에서 ‘재료’로 통합하고, 메뉴 원가 반영과 품목별 재고 관리 여부를 분리하는 방향을 권한다.** 사용자는 가스·임대료 등을 고정 지출에 두는 경계를 제시했다. 상세 전환·단가·데이터 이전 규칙은 미확정이다. 아래 최초 보류 권고와 후속 재판정은 검토 경위다.

## 검토 질문

수기 입력 식당 관리 앱에서 부자재를 식재료와 같은 입고·판매 차감·취소·실사·폐기 원장으로 관리할 필요가 있는가? 지금 전면 구현, 현재 비용 관리 유지, 향후 선택형 도입을 비교한다. 사용자 입력 부담, 품절 방지 가치, 비용 정확도, 기존 원장과의 관계를 함께 평가한다.

## 현재 확인된 사실

- `materials`는 기준 단가·단위명·카테고리·메모를 가진 마스터다. `inventory_events`·`inventory_states`는 식재료를 참조한다(`packages/db/src/database.types.ts`).
- 메뉴 부자재 연결은 `recipe_extra_costs`의 `material_id`, `qty`, `amount_per_serving`으로 표현한다. 부자재 단가와 메뉴별 사용량이 비용 계산에 쓰인다(`packages/db/supabase/migrations/20260911000204_recipe_write_contract.sql`).
- 부자재 추가·수정의 구매 수량·구매 가격은 개당 단가 계산에 사용하며 현재 재고를 등록하지 않는다(`apps/mobile/src/features/recipes/screens/MaterialFormScreen.tsx`).
- 식재료 재고 원장은 판매·취소·입고·취소·실사·폐기 등에 연결돼 있다. 영업 중 원가 기준 보존과 실제 재고 전파의 적용 시점은 구분한다(`ARCHITECTURE.md`).
- 사용자는 부자재 상세·추가·수정의 공통 디자인을 요청했고, 재고 기능까지 확장하면 과도한지 독립 검토를 요청했다. 부자재 재고 구현은 아직 승인하지 않았다.

## 독립 검토에서 답할 항목

1. 현 시점의 권고안과 이를 뒤집을 반례.
2. 일정하게 소비되는 포장 용기, 주문당 공유하는 봉투, 사용량을 측정하기 어려운 가스 등을 한 규칙으로 처리할 수 있는지.
3. 매장·배달·포장에 따른 사용 여부와 메뉴당/주문당 소비 단위의 구분이 필요한지.
4. 식재료와 부자재에 같은 실물을 중복 등록했을 때 원가·재고 이중 반영을 어떻게 피할지.
5. 현재 최소 조치와 향후 도입의 관찰 가능한 판단 신호.

실제 수요 빈도·투입 기간·시장 통계는 확보하지 않았다. 수치를 임의로 추정하지 않고 설계 판단과 확인 사실을 구분한다.

## 이번 검토의 권고 — 사용자 미확정

Codex와 이번 요청에 한정한 Astra Ultra 독립 검토는 **지금 전면 재고 관리는 보류하고, 필요가 확인된 품목에 추후 선택형으로 도입**하는 쪽으로 일치했다. Astra는 저장소를 읽기 전용 검토했으며 제품 변경·외부 호출을 하지 않았다.

- 보류의 근거는 부자재 단가가 낮아서가 아니다. 전용 용기 부족으로 주문을 처리하지 못한다면 재고 관리 가치는 클 수 있다. 실제 부족 문제와 지속적인 입고·실사 기록 가능성을 확인해야 한다.
- 메뉴마다 일정하게 쓰는 용기, 주문당 봉투, 선택 제공 소스팩, 공용 조리 가스는 소비 기준이 다르다. 메뉴별 사용량을 모든 부자재의 실제 판매 차감 규칙으로 확대할 수 없다.
- 현재 `recipe_extra_costs`에는 판매채널 조건이 없다. 배달·포장 전용 비용과 매장 판매의 관계를 먼저 점검해야 한다. 평균 배분을 의도한 경우에도 실제 소비 재고와 구분해야 한다.
- 재고 도입 시에는 판매 취소가 사용한 용기의 물리적 복구를 뜻하는지, 음식 폐기 시 포장재를 사용했는지 등 별도 소비 계약이 필요하다. 식재료 원장을 그대로 복사하는 방식은 피한다.
- 같은 실물을 식재료·부자재 양쪽에 등록하거나 가스를 고정 지출과 메뉴 부자재비로 동시에 계산하지 않도록 비용 출처를 정해야 한다. 구매금액을 판매당 부자재비에 더해 다시 손익에서 차감해서도 안 된다.
- 지금 최소 조치는 단가 계산용 수량의 의미를 명확히 하고, 채널별 원가 적용과 중복 비용 위험을 확인하는 것이다. 잔량 숫자만 수동 수정하는 원장 없는 임시 기능은 권하지 않는다.
- 도입 신호는 특정 품목 부족이 반복되고, 잔량 확인이 구매 행동을 바꾸며, 실제 수량과 소비 규칙을 확인할 수 있는 경우다. 통합 구매 흐름이 필요하다는 요구와 전 품목 자동 재고 차감 요구는 별도로 판단한다.

Fable 정식 검토는 `MATERIAL-STOCK-SCOPE-20260913` r001에 요청했으나 `PROVIDER_HARD_CAP_UNAVAILABLE`로 외부 호출 전에 중단됐다(`.codex/material-stock-review.log`). 이후 아래 사용자 지정 Claude 브라우저 자문을 받았으나 정식 Fable 게이트를 대체하지 않는다. 현재 권고를 확정 정책이나 구현 승인으로 취급하지 않는다.

## 사용자 지정 Claude 브라우저 자문 — 2026-09-13

사용자가 지정한 Claude의 `앱 작업` 대화에 Codex 인앱 브라우저로 검토 요청을 직접 전송하고 응답 완료를 확인했다. 다른 검토자의 결론을 전달하지 않고 현재 구조와 선택지·반례를 제공했다. Claude는 코드·migration·실사용 데이터를 직접 확인하지 않았으며 전달한 구조 설명을 전제로 판단했다고 명시했다. 정확한 제공 모델명은 이번 화면에서 확인하지 못했으므로 Fable 모델 실행으로 단정하지 않는다.

Claude의 핵심 권고도 **현재 전면 도입은 보류하고 소비 단위와 판매채널 적용을 먼저 정리한 뒤 포장 용기 등 필요한 품목부터 선택형으로 검토**하는 것이다. 메뉴당 용기와 주문당 봉투를 같은 소비 규칙으로 처리할 수 없다는 점, 이미 사용한 포장재가 판매 취소만으로 복구되지 않는다는 점, 중복 비용 위험을 지적했다. 품절로 배달·포장 판매가 막히는 경우를 보류안의 강한 반론으로 제시했다.

Codex는 다음 제안·일반화를 그대로 채택하지 않는다.

- 마지막 구매일·수량만으로 월 구매금액은 계산할 수 없다. 기간 내 구매 기록 전체와 각 금액이 필요하다.
- 잔량·소진 경고를 제공하려면 관측 시점과 수량 변경 근거가 필요하다. 화면을 간소화하더라도 서버 원장·정정·취소 계약을 생략할 근거는 아니다.
- 주문당 소비 유형 필드만 추가해도 정확한 비용이 계산되는 것은 아니다. 주문 수와 실제 묶음 제공 정보를 확보할 수 있는지 먼저 확인해야 한다.
- 부자재는 상하지 않는다거나 재고 기능 가치가 품절 예방에만 한정된다는 주장은 품목 전체에 일반화할 수 없다. 보관·파손·유효기간·사용량 대사 등의 가치와 부담도 품목에 따라 달라진다.
- 실제 가스 소비는 품목·용도에 따라 다르다. 가스라는 이름만으로 고정 지출로 자동 이관하지 않는다. 대용량 소스와 별도 구매 소스팩도 이름이 비슷하다는 이유만으로 같은 비용으로 간주하지 않는다.
- 음수 재고는 프로젝트가 허용하는 상태이며 그 자체가 계산 오류는 아니다. 실제 소비와 장부 차이는 원장·실사 근거로 판단한다. 로스율은 표시 전용이라는 기존 계약도 유지한다.

세 검토의 큰 방향은 일치하지만 세부 제안 전체가 합의된 것은 아니다. 이번 결과는 제품 범위 자문이며 코드 검수 통과·정식 Fable 승인·사용자 구현 승인을 뜻하지 않는다.

## 사용자 반론 후 재검토 — 메뉴별 사용량과 순이익 연결

사용자는 부자재가 이미 메뉴 구성과 메뉴별 순이익에 포함된다는 점을 지적했다. Codex·Astra Ultra의 코드 재검토와 같은 Claude 대화의 후속 자문을 통해 **메뉴별 실제 소비량을 정할 수 있는 부자재의 재고 도입까지 일괄 보류한 판단을 수정**한다. 후속 요청 시 브라우저 모델 선택 표시가 `Opus 5 중간`임을 확인했다. Claude 답변은 제공한 구조에 대한 자문이며 코드 검수는 아니다.

확인 근거:

- `MaterialSearchScreen.tsx:37`에서 N인분 입력량을 N으로 나눈 `qty`와 1인분 금액을 함께 저장한다. 판매 차감에 사용할 때 다시 N으로 나누지 않는다.
- `20260911000204_recipe_write_contract.sql:53`의 원가 저장 계약은 `unit_cost × qty`를 계산한다. `20260912000213_zero_cost_material_links.sql`은 후속 v3 계약으로 0원 품목도 양수 사용량 연결을 보존한다. 초기 v2만 보고 0원 연결 누락을 현재 결함으로 판정하지 않는다.
- `20260912000206_effective_menu_business_basis.sql:64`는 이후 영업일 스냅샷에 `material_id`·`qty`를 보존한다. 예전 스냅샷을 최신 구성으로 임의 보충해서는 안 된다.
- `20260820000058_day_basis_everywhere.sql:158`은 영업일의 1인분 부자재 비용과 판매 수량으로 판매 부자재 비용을 집계한다. 현재 부자재 잔량 차감은 구현돼 있지 않다.

비용에 포함된다는 사실만으로 모든 품목에 재고가 필수인 것은 아니다. 그러나 메뉴당 용기 1개처럼 실제 사용량이 정해져 있다면 이미 입력된 사용량과 판매 증감분을 재사용할 수 있다. 판매마다 부자재 수량을 다시 입력해야 한다는 부담을 전제하지 않는다. 주문당 공용품·기간 비용의 예외는 해당 품목의 적용 범위를 정할 이유이며 모든 부자재를 미룰 이유는 아니다.

최신 권고 범위:

1. 기존 메뉴 원가·판매 손익 반영은 계속 유지한다. 실제 수량 관리가 필요한 메뉴 연결 품목에서 재고 기능을 선택적으로 켜는 방향을 권한다.
2. 관리 시작 수량·입고·수량 정정은 서버 원장으로 기록한다. 기존 단가 계산용 구매 수량을 실제 입고로 소급 취급하지 않는다. 단위와 구매 묶음 환산을 명시한다.
3. 판매 차감은 당시 사용량·적용 채널·판매 증감분에 결속하고 중복 요청·수량 감소·취소·동시 수정에 대응한다. 모든 채널에서 쓰는 품목은 그 범위를 명시하고, 특정 채널 전용 품목만 해당 판매를 계산한다.
4. 입고 비용이나 재고 차감 비용을 기존 판매당 부자재 비용에 더해 다시 손익에서 빼지 않는다. 입고가 기준단가를 갱신할지와 영업 중 적용 시점은 별도 확정할 계약이다.
5. 조리 폐기와 포장재 훼손은 동일하지 않다. 실제 훼손·추가 제공·취소 후 미복구 수량을 기록할 방법은 필요하다. 폐기가 드물다는 가정으로 변경 근거를 생략하지 않는다.
6. UI는 공통 기본 정보 수정과 재고 수정 요소를 재사용하되 필요한 입력만 제공한다. 탭 구성·최근 내역 개수·전체 품목 활성화는 아직 확정하지 않았다.

Claude 후속 자문도 수량형·메뉴 연결 품목의 도입을 타당하다고 수정했다. 다만 자동 차감 구현이 공짜라는 표현, 품목명만으로 봉투·가스를 일괄 제외하는 제안, 부자재 폐기는 드물다는 일반화는 채택하지 않는다. 실제 소비 규칙과 서버 계약으로 판단한다. 이번 작업은 재검토 문서만 갱신했으며 제품 기능 구현은 시작하지 않았다.

## ‘재료’ 통합·품목별 재고 선택안 검토

사용자는 식재료와 부자재를 ‘재료’로 통합하고 식품·포장용기를 자율 등록하는 안에 대해 Astra Ultra와 Claude 검토를 요청했다. Astra Ultra는 읽기 전용 코드 검토를 수행했고, 지정 Claude 대화의 Opus 5 중간은 제공한 구조에 기초한 설계 답변을 완료했다. 서로의 결론을 전달하기 전에 독립 요청했다. 검토 중 사용자가 **가스·임대료 등은 고정 지출**에 둔다고 경계를 정했다. 기존 데이터를 자동 이관하라는 요청은 아니다.

### 검토 결과

- Astra: 통합 UX와 품목별 재고 선택을 추천한다. 단가 출처·재고 추적·메뉴 비용 반영을 별도로 정의하고, DB를 즉시 물리 통합하지 말 것을 권했다.
- Claude: 명칭·등록·검색 통합에는 찬성하지만, 재고 스위치가 단가 산출 방식까지 바꾸는 설계에 반대했다. 영업일 경계 전환·시작 실사·과거 추적 상태 보존을 권했다. 신규를 ingredient로 일원화하고 기존 material을 동결하는 구체안도 제시했으나 코드·이전 비용을 검증한 제안은 아니다.
- Codex: 사용자 화면의 재료 통합과 재고 선택 방향에 찬성한다. 재고 OFF여도 단가·메뉴 사용량에 따른 원가와 순이익 반영은 유지한다. 재고 ON/OFF만으로 단가를 지우거나 바꾸지 않는다. 가스·임대료는 사용자 결정에 따라 고정 지출로 분리한다.

### 코드 확인으로 보완한 조건

1. 단가 출처는 현재도 단순 이분법이 아니다. `20260912000214_current_ingredient_cost.sql:8`은 식재료 메뉴 단가의 직접 수정값을 우선하고 다음 입고·취소에서 가중평균으로 돌아가는 경로를 가진다. 현재 `IngredientFormScreen.tsx:107`은 `profileOnly: true`로 기본 정보를 저장하므로 이 RPC 가능성과 현재 폼의 노출 기능을 구분한다.
2. 기존 부자재 폼은 `MaterialFormScreen.tsx:49`에서 구매가격/수량을 정수로 반올림하고 자유 단위 이름을 받는다. 이를 모든 g/ml 재료의 공통 폼으로 그대로 쓰면 소수 단가·단위 환산 계약을 훼손할 수 있다. 새 통합 입력은 최소단위·소수 정밀도를 유지해야 한다.
3. 현재 원장과 메뉴 연결 테이블은 구분돼 있다. 화면 통합이 ID 병합·원장 재작성·기존 품목 동결을 뜻하지 않는다. ID 출처를 보존하고 양쪽 메뉴 비용을 정확히 한 번씩 계산해야 한다. 이름만 같은 품목을 자동 병합하지 않는다.
4. OFF→ON은 실제 확인한 시작 수량을 새 기록으로 남기고, ON→OFF는 원장·과거 잔량을 보존한다. 전환 전 판매가 당시 차감됐는지 확인하지 않고 취소 재고를 복구하면 안 된다. 영업 중·브레이크 전환을 제한하는 초기안이 적절하나 아직 구현 결정은 아니다.
5. 재고 OFF의 미확인 단가와 명시적 0원을 구분한다. 부족·소진·발주 알림은 추적 품목에만 적용하고, 모든 메뉴 연결 재료의 비용은 계속 계산한다. 과거 스냅샷과 원가 변경 시점도 유지한다.

### 채택하지 않은 자문 확대

Claude의 ‘UI 통합만’ 제안에 포함된 신규 ingredient 일원화·material 읽기 전용 동결은 실제 저장·수정 동작 변경이므로 UI만의 변경이 아니다. 기존 부자재 수정 기능을 갑자기 막는 안은 채택하지 않는다. 물리 통합이 원칙적으로 불가능하다거나 특정 이전 방식이 유일하게 안전하다는 단정, 개발비가 압도적으로 저렴하다는 주장도 근거가 확인되지 않았다.

단가 출처와 재고 추적을 내부에서 분리하는 것에 동의하지만 사용자에게 두 복잡한 선택 메뉴를 반드시 추가해야 한다는 뜻은 아니다. 재고 OFF 구매내역 신설·월 구매금액 제공도 별도 요구사항이며 이번 통합안의 필수 범위로 임의 확대하지 않는다. 실제 사용자들이 분류를 어떻게 이해하는지는 관찰하지 않았으므로 UX 판단으로만 기록한다.

결과는 **통합 재료 관리 + 메뉴 원가 반영 유지 + 선택형 재고**, 고정 지출과의 명확한 구분을 추천하는 설계 자문이다. 제품 변경·DB 이전·기존 부자재 동결은 실행하지 않았다. 정식 Fable 게이트 통과로 취급하지 않는다.
