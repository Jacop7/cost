# 전체 페이지 흐름 프로토타입 변경 기록

작업 대상 적용본: `docs/prototypes/full-page-flow-prototype-ui-applied.html`  
보존 원본: `docs/prototypes/full-page-flow-prototype.html`

이 문서는 프로토타입 검토 중 확정하거나 실험한 화면 변경을 기록한다. 실제 Expo 앱과 공식 기획안에는 자동으로 적용하지 않는다. 프로토타입 검토가 끝나면 `기획안 반영 포인트`를 기준으로 공식 기획안에 옮기고, 반영 여부를 다시 확인한다.

## 기록 규칙

- 프로토타입을 수정할 때마다 새 항목을 추가한다.
- 디자인 작업마다 맥락 장부에서 새 `DS-YYYYMMDD-NNN` ID를 발급하고 최상단의 새 PRT 항목에
  같은 ID를 연결한다.
- `변경 이유`에는 사용자가 느낀 문제와 해결하려는 UX를 적는다.
- `기획안 반영 포인트`에는 화면 구성, 노출 조건, 이동 경로처럼 문서에 확정해야 할 규칙을 적는다.
- 실제 앱에 반영하기 전까지 상태는 `프로토타입 반영`으로 유지한다.
- 기획안 반영 후에는 대상 문서와 항목을 연결하고 상태를 `기획안 반영`으로 바꾼다.
- 완료 전 현재 확정안·적용 검수 기록·맥락 장부를 함께 갱신하고, 공통 변경은 UI 가이드·실행서까지
  갱신한 뒤 자동 동기화 검사를 통과한다.

## 변경 내역

### PRT-182 · 2026-09-04 @font-face 복원 · 스크립트 금지 굵기 제거 · 인벤토리 정정

- 날짜: 2026-09-04
- 디자인 동기화 ID: `DS-20260904-004`
- 적용 범위: 전 화면 공통 `<style>`·`<script>` 템플릿, UI 가이드 인벤토리, 검수 기록·맥락 장부
- 상태: 프로토타입 적용본·문서 반영 · 실제 Expo 미적용
- 근거: `PRT-181`에 대한 독립 검수 지적 3건(Major 2 · Minor 1) 반영. 반박 0건
- 변경 내용:
  - **Major 1** `PRT-181`의 굵기 재산출 스크립트가 `@font-face` at-rule까지 정규화 대상에 넣어,
    세 블록의 선택자 문자열이 모두 `@font-face`로 같다는 이유로 마지막 값이 전부에 덮였다.
    그 결과 `SemiBold 600` · `Bold 700` · `ExtraBold 800` 디스크립터가 모두 `800`이 되어
    요청 굵기 600·700이 해당 face를 선택할 수 없었다. 파일명 기준으로 `600/700/800`을 복원했다.
    **`PRT-181`에 기록한 face 대조 증거는 이 손상된 판본에 대한 것이므로 무효이며, 이 항목에서
    최종 파일로 전량 재측정했다.**
  - **Major 2** `<script>` 템플릿의 인라인 style에 금지 굵기 `850`이 2건 남아 있었다
    (`channelProfitCard()`의 `매출`·`순이익` 라벨). 이 함수는 매장·배달앱·포장에 각각 쓰이므로
    `SALES-04`에서 6개 요소가 렌더된다. face 보존값 `800`으로 교체했다.
    이전 회차 검사는 `<style>` 블록만 대상으로 삼아 이를 놓쳤다. 검사 범위를 **렌더된 모든 요소의
    computed 값**으로 넓혔다.
  - **Minor** UI 가이드의 인벤토리를 HTML 레지스트리 실측으로 정정했다.
    등록 `screen 62 / host 125 / 고유 ID 99` → **`62 / 123 / 98`**,
    활성 `screen 62 / host 120 / 고유 ID 97` → **`61 / 121 / 96`**.
    이전 수치는 `PRT-151`이 `recipe_target_help`를 두 호스트에서 제거하기 전 값이며,
    활성 화면 62는 숨김 화면 `discard`를 활성으로 계수한 오류였다. HTML이 권위다.
- 검증 (최종 파일 기준 전량 재측정):
  - 폰트 매칭 실측(100px 텍스트 폭) — `300·400·500 → 963.53` / `600 → 1003.28` /
    `650·700 → 1023.11` / `750·800·850·900 → 1043.08`. 네 face가 다시 구분된다.
  - 이전 판본(pre-PRT179) 대비 요소별 face 대조 — **동일 7,277건 · 의도한 변경 818건 ·
    의도하지 않은 변경 0건**.
  - 렌더 요소의 computed `font-weight`에 `300·500·650·750·850` **0건**.
    `900`은 183건 있으나 이는 `b·strong`의 브라우저 기본 `bolder`가 굵은 부모 아래에서
    계산된 값이며, **이전 판본과 집합이 완전히 동일**(183 = 183, 차집합 0)하고
    렌더 폭이 `800`과 같아 face도 동일하다(427.25 = 427.25).
    따라서 **선언된 금지 굵기는 0건**이고, computed `900`은 이번 작업이 만든 것이 아니다.
  - 숫자 요소 스케일 밖은 프로토타입 셸 2종만 남았다.
  - PC 1280px·320px·320px 200% 확대 × 185건 — 넘침 0건·콘솔 오류 0건·폰트 실패 0건.
- 기획안 반영 포인트:
  - CSS 일괄 변환은 **at-rule을 반드시 제외**한다. `@font-face`는 선택자가 아니다.
  - 검사 범위는 `<style>`이 아니라 **렌더된 요소의 computed 값 + 스크립트 템플릿 인라인 style**이다.
  - 굵기 검사는 `선언값`과 `computed 값`을 구분해 표기한다. 요소 기본값(`bolder`)은 별도 항목이다.
  - 인벤토리 수치의 권위는 HTML 레지스트리이며, 변경 시 가이드를 같은 작업에서 갱신한다.

### PRT-181 · 2026-09-04 굵기 face 보존 재산출 및 인벤토리 표기 정정

- 날짜: 2026-09-04
- 디자인 동기화 ID: `DS-20260904-003`
- 적용 범위: 전 화면 공통 `<style>` 레이어, 검수 기록·디자인 맥락 장부·변경 이력
- 상태: 프로토타입 적용본·문서 반영 · 실제 Expo 미적용
- 근거: `PRT-180`에 대한 독립 검수 지적 2건(Major 1 · Minor 1) 반영. 반박 0건
- 변경 내용:
  - **Major** `PRT-180`의 "정적 OTF이므로 굵기 정규화가 렌더를 바꾸지 않았다"는 결론이 틀렸다.
    `@font-face`는 `400/600/700/800` 네 face만 선언하고, CSS Fonts 4 폰트 매칭에 따라
    실제 렌더는 다음으로 묶인다 — 100px 기준 텍스트 폭 실측:
    `300·400·500 → 400 face(963.53)` / `600 → 600(1003.28)` /
    `650·700 → 700(1023.11)` / `750·800·850·900 → 800(1043.08)`.
    따라서 `PRT-179`의 `650→600`은 face `700→600`, `750→700`은 `800→700`,
    `500→600`은 `400→600`으로 **실제 굵기를 바꿨다**.
  - 매핑을 숫자상 근사값이 아니라 **원래 선택되던 face를 보존하는 값**으로 재산출했다.
    `650→700`, `750→800`, `500→400`, `850→800`, `900→800`, `300→400`.
    이러면 공식 굵기 `400/600/700/800`만 쓰면서 시각 변화가 없다.
  - `b,strong{font-weight:700}` 기본 규칙을 철회했다. 브라우저 기본 `bolder`를 덮어써
    굵은 부모 안의 중첩 `<b>`가 face `800→700`으로 가늘어지고 있었다(177건).
    `b,strong`에는 `font-variant-numeric: tabular-nums`만 남긴다.
  - `.prototype-input-shell>span:last-child`와 `.edit-form-box.numeric-value>span:last-child`의
    타이포 선언을 `:not(.chev)`로 좁혔다. suffix용 규칙이 chevron 아이콘까지 잡아
    크기 `20px→14px`, 굵기 face `700→600`으로 축소하고 있었다(4건).
  - **Minor** 검수 범위 표기를 공식 인벤토리 기준으로 정정했다.
    `총 스캔 185건 = 활성 182건 + 숨김 보존 3건`. 숨김 3건은 `screen=discard` 1개와
    그 host의 `discard_type`·`discard_period` 2개다.
- 검증(무효 · PRT-182에서 재측정): 이전 판본과 현재 판본을 185건 전수 렌더해
  요소별 실제 face를 대조했다. **face 동일 7,167건 · 의도한 변경 818건 ·
  의도하지 않은 변경 0건.** 의도한 818건은 `small,em` 600 정규화의 파생과 입력 suffix 통일이다.
- 검수 결과: PC 1280px·320px·320px 200% 확대 3조건 × 185건 — 넘침 0건·콘솔 오류 0건·폰트 실패 0건.
  굵기 분포 `400:6 / 600:33 / 700:140 / 800:143`, 금지 굵기 잔존 0건, `tabular-nums` 132건.
- 기획안 반영 포인트:
  - 굵기 정규화는 숫자 근사가 아니라 **선언된 `@font-face`가 실제로 선택하는 face**를 기준으로 한다.
  - 요소 태그의 브라우저 기본값(`b/strong`의 `bolder`)을 전역 규칙으로 덮지 않는다.
  - `:last-child` 기반 규칙은 장식 아이콘을 함께 잡을 수 있으므로 역할로 좁힌다.
  - 검수 범위는 `활성 + 숨김 보존`을 구분해 표기한다.

### PRT-180 · 2026-09-04 숫자·단위 통일 검수 지적 반영

- 상태: 프로토타입 적용본·문서 반영 · 실제 Expo 미적용

- 변경 내용:
  - **F01** 숫자를 담은 스케일 밖 선택자 16종을 정정했다. `PRT-179`의 분류기가 셀렉터의 마지막
    토큰이 `b·strong·small·em`인 경우만 다뤄, 클래스로만 스타일된 요소를 통째로 놓쳤다.
    `.tab`·`.sheet-preview-tab`·`.edit-form-box`·`.stock-add-select`·`.sales-menu-name`·
    `.past-actions button`·`.confirm-actions>button` 계열 `15px → 16px`,
    `.sales-menu-sub`·`.fixed-ledger-sub`·`.fixed-ledger-total-value span`·
    `.sales-section span:last-child`·`.expo-target`·`.detail-chip` `12px → 13px`,
    `.app-tab` `12.5px → 13px`.
  - **F02** 검수 증거를 재취득했다. 이전 회차는 `file://`로 렌더해 `/apps/mobile/assets/fonts/`가
    드라이브 루트로 해석되며 Pretendard가 로드되지 않았고, 대체 폰트로 측정한 결과였다.
    저장소 루트 HTTP 서버에서 네 굵기 로드를 `document.fonts.check`로 확인하고
    `document.fonts.ready` 이후 재측정했다. 검사 대상도 화면 62개에서
    **활성 popup/state host 123개를 포함한 185건**으로 넓히고 200% 확대를 추가했다.
  - **F03** 단일 편집 입력에서 `tabular-nums`를 제거했다(선언 139 → 132). UI 가이드 `1.3`과
    실제 Expo `components/kit`이 폰트 렌더 검증 전 제외를 규정하는데 `PRT-179`가 이를 어겼다.
  - **F04** `small,em` 기본 규칙이 크기 규칙 없는 요소를 덮는 부작용을 해소했다. 필수 표시 `*`와
    곱셈 기호가 부모 크기를 잃던 문제를 `.prototype-field-label em`·`.edit-form-label em`·
    `.stock-add-label em`·`.sales-menu-name em`에 `font-size/weight: inherit`으로 되돌렸다.
  - **F05** `tabular-nums` 집계를 138에서 실제 값으로 정정했다. F03 반영 후 최종 132건이다.
- 부수 확인: 이 프로토타입의 Pretendard는 정적 OTF 4종(400/600/700/800)이며 가변축이 없다.
  ~~따라서 `PRT-179`의 `650/750/850` 정규화는 실제 렌더를 바꾸지 않았다.~~
  **정정(PRT-181): 이 결론은 틀렸다.** face 매칭상 `650→600`·`750→700`·`500→600`은
  실제 굵기를 바꿨다. `PRT-181`에서 face 보존 매핑으로 재산출했다.
- 검수 결과: 185건(화면 62 + popup host 123) 전수. PC 1280px·모바일 320px·320px 200% 확대
  세 조건 모두 가로 넘침 0건, 콘솔 오류 0건, 폰트 요청 실패 0건.
  숫자 text node 기준 스케일 밖 요소는 프로토타입 셸 2종만 남았다
  (폰 목업 상태바 시각 `11px`, 카탈로그 화면 ID 배지 `10px` — 제품 UI 아님).
- 기획안 반영 포인트:
  - 타이포 검사는 태그가 아니라 렌더된 text node와 입력값을 대상으로 한다.
  - 검수 증거는 실제 폰트가 로드된 환경에서만 유효하다. `document.fonts.check`를 게이트에 넣는다.
  - 검수 범위는 화면뿐 아니라 활성 popup/state host를 포함한다.

### PRT-179 · 2026-09-04 숫자·단위 타이포 전수 통일

- 날짜: 2026-09-04
- 디자인 동기화 ID: `DS-20260904-001`
- 적용 범위: 전 화면 공통 `<style>` 레이어, 현재 확정안·UI 가이드·실행서·검수 기록·디자인 맥락 장부
- 상태: 프로토타입 적용본·문서 반영 · 실제 Expo 미적용
- 변경 내용:
  - 값 표시 선택자의 `15px`를 `16px`로, `17px`를 `16px`로 통일했다(48건).
  - 단위·보조 수치 선택자의 `12px`·`11px`를 `13px`로, `16px`·`17px`를 `14px`로 통일했다(39건).
  - 큰 핵심값 `25px`·`23px`를 `TYPE.display 22px`로 맞췄다(4건).
  - 굵기 `750→700`(46) `850→800`(40) `650→600`(16) `900→800`(3) `500→600`(2) `300→400`(2)로
    정규화해 공식 굵기 `400/600/700/800` 외 값을 0건으로 만들었다.

  - `b,strong`과 `small,em`에 낮은 특이도 기본 규칙을 추가해, 크기를 지정하지 않은 `<small>`이

- 기획안 반영 포인트:
  - 숫자와 단위는 화면별 하위 선택자가 아니라 `TYPE` 역할 토큰으로만 크기를 정한다.
  - 값에는 `tabular-nums`를 기본 적용해 목록에서 자릿수가 흔들리지 않게 한다.
  - 입력 필드의 suffix는 단일 규격을 쓰고 화면마다 별도 클래스를 만들지 않는다.

  - 합계와 권장 판매가를 좌우 정렬하고 `0원 / 적용하기`를 한 동작 영역으로 묶는다.
  - 입력이 완료되지 않은 추가 버튼은 Expo와 같은 비활성 파란색으로 표시한다.
  - 메모 분리, 카테고리·목표 순이익률 필수, 월평균 탭 숨김 등 최신 확정 규칙은 유지한다.
- 기획안 반영 포인트:
  - 레시피 추가 하단 카드의 정보 위계와 검색·합계·안내 푸터 공통 구조를 확정한다.

  - 레시피 상세·수정·판매가 시뮬레이션에서 월평균 탭을 제거하고 `10인분 · 1인분`만 제공한다.

- 기획안 반영 포인트:
