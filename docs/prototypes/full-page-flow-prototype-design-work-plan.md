> 현재 디자인 동기화 ID: `DS-20260908-011`

## 0. 목적

이 문서는 화면마다 폰트·여백·선·정렬·버튼·팝업이 달라지는 문제를 막기 위한 **작업 순서와 완료
판정표**다. 디자인 규격 자체는 `full-page-flow-prototype-ui-guide.md`, 화면 문구·기능은 현재 확정안,
실제 확인 결과는 `full-page-flow-prototype-ui-applied-review.md`를 단일 원천으로 사용한다.

이 실행서는 규칙을 다시 정의하지 않는다. 작업자는 반드시 아래 순서로 진행한다.

1. 공통 규칙 잠금
2. 공통 컴포넌트 수정
3. 화면별 적용
4. 화면 한 장씩 전수 검수
5. 같은 역할 화면끼리 교차검수
6. PC·모바일 재검수와 기록

현재 `full-page-flow-prototype-ui-applied.html`은 등록된 모든 screen·popup·조건 상태의 렌더·디자인·
국제화 감사를 통과한 적용본이다. Expo 공용 색 역할은 소유자 승인에 따라 S2에서 함께 적용했고,
화면 구조·기하는 S3a·S4·S3b와 네이티브 S4a 증거까지 완료했다.

Expo `S4` 후보는 `scrollStart/end/endWithFab`, Modal Sheet의 safe-area 포함, ListRow 60/76,
2줄 탭 라벨의 글꼴 배율별 동적 높이, `sales-menu-sub` 줄바꿈, 비중첩 44px 터치 영역을 적용했다.
소유자 결정 12-4에 따라 Button sm은 시각 44px, 헤더·시트 icon action은 투명 44×44,
Chip·SortChip은 기존 형상과 44px 이상 부모 줄을 쓴다. 정적 게이트와 Android·iOS 실제 frame·
탭 측정이 모두 통과했으며, W1·S4a·S4·P2는 `04eb1de9bc24e96b2e520b1d150c3e5b37edaf71`
Opus PASS와 2026-09-07 소유자 exact-SHA 위험 수용으로 최종 종결됐다.

### 1.1 같은 작업 안의 문서 동기화 게이트

프로토타입을 한 줄이라도 수정하면 최종 응답 전에 아래 문서를 같은 작업 안에서 처리한다. 하나라도
빠지면 상태는 `미완료`이며 사용자에게 완료했다고 답하지 않는다.

| 변경 종류 | 반드시 함께 갱신할 파일 |
|---|---|
| 모든 프로토타입 변경 | UI 적용 HTML + 현재 확정안 기존 항목 교체 + changelog 새 PRT + 적용·검수 기록 + 맥락 장부 |
| 두 화면 이상에 적용되는 공통 규칙 | 위 5개 + UI 가이드 + 이 실행서 C 규칙 |
| 화면 문구·노출 조건·업무 흐름 | 위 5개 전체. 현재 확정안과 최신 PRT에서 옛 결정을 대체 |
| 검수만 수행하고 코드 변경 없음 | 적용·검수 기록 + 맥락 장부에 새 ID·범위·결과·미검수 항목 기록 |

최종 응답 전 필수 확인:

- [ ] 변경된 화면·popup의 최종 문구와 구조가 현재 확정안에 있다.
- [ ] 대체된 옛 문구·비율·색상·상태가 현재 확정안에 남아 있지 않다.
- [ ] changelog 최상단에 새 PRT 항목과 변경 이유가 있다.
- [ ] 맥락 장부에 새 ID·영향 범위·다음 시작점이 있고 작업 중에는 `IN_PROGRESS`다.
- [ ] 공통 변경이면 UI 가이드와 실행서의 같은 역할 규칙이 갱신됐다.
- [ ] 적용·검수 기록에 PC·모바일 결과와 실제 측정값이 있다.
- [ ] 자동 동기화 검사를 `-Finalize`로 실행해 현재 ID를 완료 장부에 등록했고 결과가 `PASS`다.
- [ ] 위 검수 뒤에만 맥락 장부의 문서 동기화 상태를 `SYNCED`로 바꿨다.
- [ ] 실제 Expo 소스를 수정하지 않았다.

이 게이트는 “나중에 한꺼번에 문서화”할 수 없다. 화면 수정과 문서 동기화는 하나의 작업 단위다.

작업 시작 시 맥락 장부에 새 `DS-YYYYMMDD-NNN` ID를 발급하고 상태를 `IN_PROGRESS`로 둔다. 작업
완료 시 UI 적용본·현재 확정안·changelog 최신 PRT·검수 기록·맥락 장부에 같은 ID가 있어야 한다.
두 화면 이상에 쓰이는 공통 규칙을 바꿨다면 UI 가이드와 이 실행서도 같은 ID를 가져야 한다.

최종 응답 직전에 `full-page-flow-prototype-design-sync-check.ps1 -Finalize`을 실행한다. 스크립트 `PASS`, 실제
PC·모바일 검수, 직접 연결 상태 검수가 모두 끝난 뒤에만 맥락 장부를 `SYNCED`로 바꾼다. 과거 ID가
다른 절에 남아 있는 것만으로는 통과할 수 없으며, 현재 ID는 각 문서의 지정된 최신 위치에 있어야 한다.
완료 장부에 등록된 같은 ID의 필수 파일이 이후 다시 바뀌면 일반 재검사도 실패하며 새 ID 발급을 요구한다.

## 2. 변경 금지 원칙

- 공통 컴포넌트 오류를 화면별 선택자와 임의 숫자로 덮지 않는다.
- 같은 예외가 두 화면 이상이면 화면 예외가 아니라 공통 variant 후보로 다시 검토한다.
- `margin-top: 7px`, `font-size: 13.5px`처럼 토큰에 없는 값을 화면별로 추가하지 않는다.
- 입력값·계산값·상태값·버튼을 비슷하게 보인다는 이유로 같은 요소로 처리하지 않는다.
- Card 안에 Card를 중첩해 여백 문제를 가리지 않는다.
- 실제 Expo가 다르다는 이유만으로 확정된 프로토타입 정책을 되돌리지 않는다. Expo는 비교 근거이며
  확정안과 충돌하면 검수 기록에 차이로 남긴다.
- 화면의 일부만 보고 PASS 처리하지 않는다. 스크롤 끝, 빈 상태, 채워진 상태, 오류, popup까지 확인한다.

### 3.1 확정 색상 역할

Expo에서는 팔레트 `T.*`를 직접 고르는 대신 `COLOR.*` 의미 역할을 우선 사용한다. 아래 색상은 프로토타입 검수값이며 화면 CSS에 별도 팔레트를
만들기 위한 값이 아니다.

| 역할 | 토큰 | 프로토타입 검수값 | 사용 규칙 |
|---|---|---:|---|
| 앱 배경 | `T.bg` | `#F2F4F6` | 화면 바탕 |
| 기본 표면 | `T.surface` | `#FFFFFF` | Card·Field·Layer |
| 보조 표면 | `T.surface2` | `#F9FAFB` | 중립 결과·요약·비활성 행동 |
| 핵심 글자 | `T.ink` | `#191F28` | 제목·핵심값·유형명 |
| 강한 보조 글자 | `T.ink2` | `#333D4B` | 읽어야 하는 본문 |
| 보조 글자 | `T.sub` | `#4E5968` | 라벨·설명·맥락 정보 |
| 읽히는 보조 글자 | `COLOR.text.tertiary` | `#66717E` | 날짜·단위·설명 |
| 비활성 글자 | `COLOR.text.disabled` | `#8B95A1` | 실제 비활성 컨트롤만 |
| 외곽선 | `T.line` | `#E5E8EB` | Card 외곽·Field 경계 |
| 내부 구분선 | `T.line2` | `#F2F4F6` | 연속 Row·LayerFooter 상단 |
| 브랜드 | `COLOR.brand.primary` | `#3182F6` | 로고·비상호작용 브랜드 식별 |
| Primary | `COLOR.action.primary` | `#1470F5` | 대표 행동 배경·비텍스트 경계 |
| 비활성 Button | 각 variant의 기본 역할색 + `opacity: 0.4` | 별도 색 없음 | 역할색은 유지하고 비활성 표현만 공통 적용 · 대비 면제 |
| 링크 | `COLOR.text.link` | `#1465DB` | 밝은 표면 위 명시적 링크·강조 전경 |
| 강조 값 | `COLOR.text.accent` | `#1465DB` | KPI·양의 방향·읽어야 하는 강조값 |

| 정보 tint | `COLOR.action.primaryTint` | `#EBF3FE` | 대표 계산 결과·정보 Notice |
| tint 전경 | `COLOR.action.onTint` | `#1465DB` | 정보 tint 위 글자·아이콘 |

- 유형명 `입고 / 판매 소진 / 차감 / 폐기`처럼 정보 분류를 담당하는 제목은 상태색이 아니라
  `T.ink`를 사용한다. 변화량만 의미에 따라 파랑·빨강을 사용한다.
- 일반 숫자·합계·Card 경계에 Primary 파랑을 장식으로 사용하지 않는다.
- 상태는 색만으로 구분하지 않고 문구·부호·아이콘을 함께 사용한다.

### 3.2 확정 타이포그래피

| 역할 | 크기 / 굵기 | 적용 대상 |
|---|---:|---|
| Display | `22 / 800` | 화면당 가장 중요한 재고·매출·순이익 값 |
| Title | `20 / 800` | 화면·Sheet·Dialog 제목 |
| Header | `18 / 700` | 앱 헤더·Section 제목 |
| Body | `16 / 700` | 행 제목·강조 본문·핵심 입력값 |
| BodyWeak | `16 / 600` | 일반 본문 |
| Caption | `14 / 600` | FieldLabel·설명·단위 |
| CaptionSm | `13 / 600` | 날짜·Filter·Badge·짧은 메타 |

- 공식 굵기는 `400 / 600 / 700 / 800`만 사용한다. `650 / 750 / 850 / 900`은 금지한다.
- 제목·핵심값·최종 합계만 `800`을 사용하고 반복 Row 전체를 굵게 만들지 않는다.
- 숫자 목록·KPI·비교표에는 tabular numeral을 사용한다.
- 200% 글자 확대에서 핵심값·입력·행동을 숨기거나 말줄임하지 않는다.
- 같은 역할의 글자를 화면별로 더 작게 만들어 밀도를 맞추지 않는다.

### 3.3 확정 간격·크기·모서리

| `space.xs` | `4px` | 제목-보조문구, 값-단위 |
| `space.sm` | `8px` | 라벨-입력, 아이콘-텍스트, 버튼 사이 |
| `space.md` | `12px` | Card 사이, Row 기본 상하 |
| `space.lg` | `16px` | 모바일 본문 gutter, Card 내부, Field 사이 |
| `space.xl` | `20px` | FieldGroup·Section 사이 |
| `space.xxl` | `24px` | 큰 업무 구획·Layer 제목과 독립 본문 |

- 레이아웃 여백은 `4 / 8 / 12 / 16 / 20 / 24`만 사용한다.
- 형제 간격은 부모 `gap`이 소유하고 자식 margin으로 맞추지 않는다.
- 모바일 본문 좌우는 기본 `16px`, 320~359px에서는 `12px`를 사용한다.
- Field·Button·작은 표면은 `radius.md`, Card는 `radius.lg`, Sheet 상단은 `radius.xl`,
  Badge·Filter는 `radius.full`을 사용한다.
- 조작 영역은 시각 크기와 관계없이 최소 `44px`를 확보한다.

### 3.4 확정 선·Card·Row 규칙

- Card 외곽선은 `1px / T.line`을 컨테이너가 한 번만 소유한다.
- 내부 Row 구분선은 `1px / T.line2`를 부모 RowGroup이 한 번만 소유하고 마지막 행은 제거한다.
- Card 사이는 선이 아니라 배경과 `12px` 이상 간격으로 구분한다.
- 일반 Card에 강한 외곽선과 그림자를 동시에 사용하지 않는다.
- Card는 `Header / Body 또는 RowGroup / Footer`로 구성하고 Card 안에 Card를 넣지 않는다.
- Header 우측에는 상태 또는 행동 한 개만 둔다. 본문 값·건수·재고량을 다시 반복하지 않는다.
- 3줄 기록 Row는 최소 `92px / 상하 16px`, 2줄 관리 Row는 `76px / 14px`, 1줄 단순 Row는
  `60px / 12px`를 사용한다.
- Row 제목·유형은 검정, 보조 정보는 회색, 변화량·상태만 의미색을 사용한다.
- 이동 행에는 chevron 하나만 사용한다. chevron·연필·더보기 행동을 한 행에 함께 나열하지 않는다.
- 날짜·제목·보조 정보와 우측 값의 첫 줄 기준선을 맞춘다.

### 3.5 확정 Form·입력·계산 결과 규칙

- 구조는 `외부 라벨 → FieldControl 또는 ResultField → 필요할 때만 오류/도움말`이다.
- 라벨·도움말·오류·합계명을 입력칸 안에 placeholder처럼 넣지 않는다.
- 이름·메모·검색·URL은 start, 수량·용량·금액·비율은 end 정렬한다.
- 선택창 검색은 SearchBar 안에서 아이콘·입력·placeholder를 함께 제공하고 같은 의미의 외부 `검색`
  라벨을 반복하지 않는다. 실제 기본값이 없는 최초 상태에서는 첫 목록 행에 체크를 표시하지 않는다.
- 숫자와 suffix는 `1 개`, `200 g`, `28.00 원/g`처럼 같은 끝선의 한 묶음으로 두고 양끝으로
  분리하지 않는다. 통화 기호 위치는 locale formatter 결과를 따른다.
- placeholder도 실제 값과 같은 정렬을 사용해 입력 시 값이 움직이지 않게 한다.
- 공용 폼 helper가 만든 suffix 입력과 페이지 직접 입력을 모두 점검하며, 숫자 Field를 정적 span이나
  start 정렬 input으로 남기지 않는다. 공용 폼 생성기는 별도 input 구조를 복제하지 않고 같은
  `FieldControl` helper를 호출해 값·suffix·접근성 이름을 함께 만든다.
- 계산값은 Input이 아니라 ResultField를 사용한다. 라벨은 밖, 값은 안쪽 end에 둔다.
- ResultField는 전체 너비, 높이 `50px`, 좌우 `14px`, 값 `16 / 800 / 22px`를 사용한다.
- 같은 Form의 ResultField는 입력칸과 좌우 시작선·끝선을 맞추고 값 길이만큼 pill로 줄이지 않는다.
- 자동 계산 결과는 기본 중립 표면을 사용한다. 사용자가 방금 바꾼 대표 결과 그룹 한 곳만 파란 tint를
  사용할 수 있다.
- 의미 없는 입력 하단 설명은 제거한다. 오류·제약·저장 영향처럼 행동 판단에 필요한 문장만 Notice 또는
  FieldMessage로 남긴다.

### 3.6 확정 Button·Filter·Badge 규칙

- 한 화면·Layer의 대표 Primary는 원칙적으로 하나다.
- 페이지·Layer의 두 행동은 320px까지 `1:1` 2열, 최소 높이 `48px`, 반경 `12px`, 간격 `8px`를
  사용한다. 긴 번역은 내부 줄바꿈과 높이 확장으로 처리한다.
- 취소·닫기: 연한 회색 채움과 검정 글씨.
- 완료·저장·확인·적용: Primary 파란 채움과 흰 글씨.
- 별도 이동·추가·수정: 흰 배경, 파란 선, 파란 글씨.
- 삭제·철회: 연한 빨강 배경과 빨간 글씨.
- 번역문이 길어도 두 행동은 한 열로 쌓지 않고 내부 줄바꿈과 높이 확장으로 수용한다.
- 상단 Filter는 높이 `38px`, 흰 배경, `1px` 중립선, 검정 글씨, full radius, 우측 아래 화살표다.
- 선택된 Filter도 검정 채움으로 바꾸지 않고 라벨만 현재 선택값으로 교체한다.
- Picker 내부 선택 행은 Filter와 다르게 파란 체크로 선택을 표시한다.
- Badge는 상태·최저/최고·짧은 메타만 사용하며 카테고리·구매처를 습관적으로 Badge로 만들지 않는다.
- 카테고리 관리 Row는 `28px 세로 순서 이동 열 → 이름·사용 개수 → 삭제` 구조를 공용으로 사용한다.
  순서 이동은 위·아래 SVG 버튼 각 `28×20px`, 첫·마지막 경계 비활성으로 구현한다. 일반 독립
  IconButton의 `44×44px` 규격을 적용해 가로 `88px` 행동 묶음으로 만들지 않는다.
- 카테고리 추가는 실제 화면 계약에 따라 헤더 오른쪽 추가 아이콘과 하단 점선 추가 버튼이 같은
  추가 Sheet를 열어야 하며, 제목·행 단위는 식재료/메뉴/부자재 종류와 일치하는지 함께 검수한다.

### 3.7 확정 Notice·빈 상태·소계 규칙

- 읽어야 하는 안내는 Notice를 사용하고 좌측 `20px` 정보 아이콘, 최소 높이 `48px`, 아이콘-본문
  간격 `10px`를 사용한다.
- 아이콘만으로 의미를 전달하지 않고 본문 문장과 함께 사용한다.
- 중복 제목·작은 설명·이미 화면에서 알 수 있는 문구는 삭제한다.
- 최초 없음·검색 결과 없음·필터 결과 없음·기록 없음을 같은 문구로 합치지 않는다.
- 빈 상태의 추가 행동은 본문 링크가 아니라 Card Footer의 한 가지 행동으로 분리한다.
- 재료·부자재처럼 동급인 원가 그룹은 모두 소계 Footer를 제공한다.
- 소계는 좌측 항목명, 우측 금액과 비율이며 빈 상태도 `0원 / 0.0%`를 표시한다.

### 3.8 확정 Layer·확인창 규칙

- 선택·입력·정보·행동은 하단 Sheet, 상태 변경·삭제·철회 확인은 중앙 ConfirmDialog다.
- Sheet는 제목/닫기, 스크롤 Body, LayerFooter가 각자 여백을 소유한다.
- 팝업 제목 아래에 제목을 반복하는 작은 설명을 넣지 않는다.
- 두 행동은 공통 1:1 Footer를 사용하고 Body 안 임의 버튼 그룹으로 만들지 않는다.
- 확인 대상은 `이름 · 수량` 문장으로 나열하지 않고 중립 DetailBlock의 `라벨 + 값`으로 분리한다.
- 핵심 이름·수량·금액은 말줄임하지 않고 줄바꿈한다. 좁은 화면은 2열에서 1열로 전환한다.
- 변경 전 값이 없으면 `—`가 아니라 `없음`을 사용한다. 비교 행은 최소 `56px`, 중립 경계,
  `radius.md`의 독립 블록으로 표시한다.
- 위험 행동은 ActionSheet에서 즉시 실행하지 않고 ConfirmDialog를 한 번 더 거친다.

### 3.9 확정 날짜·숫자·글로벌 규칙

- 서버 시각과 매장 시간대를 권위로 사용하고 기기 locale은 표시 형식에만 사용한다.
- 실제 제품은 locale formatter를 사용한다. 프로토타입 fallback은 `YYYY-MM-DD · HH:mm`이다.
- 통화 위치·소수점·날짜 순서·요일·복수형을 문자열 이어붙이기로 만들지 않는다.
- 음수는 `−750g`, 변화량은 `+1kg / −700g`, 곱셈은 `1kg × 2개`, 단가는 `28.00원/g`로 표시한다.
- 핵심값에는 말줄임을 사용하지 않는다. 30~50% 긴 번역, 320px 화면, 200% 글자 확대를 검수한다.
- 2열이 핵심값을 보존하지 못하면 1열로 전환하고 글자를 축소하지 않는다.
- RTL에서는 논리 방향 start/end를 사용하되 숫자와 단위의 읽는 순서를 보존한다.

### 3.10 화면 정책과 공통 규칙의 경계

다음은 기존 작업에서 확정됐지만 공통 디자인 variant로 만들지 않는다.

- 목표 순이익률 도움말 제거
- 레시피 월 평균 판매량 입력 제거
- 폐기 내역 화면 숨김과 재고 내역 통합
- 구매 링크·기본 거래처·필터 항목의 업무 문구와 노출 조건
- 특정 화면의 빈 상태 문구·최근 기록 노출 기간·철회 가능 조건

이 항목은 현재 확정안과 화면별 검수 카드에 기록한다. 같은 문구를 여러 화면에 적용해야 한다는 이유만으로
타이포·Card·Button의 새 variant를 만들지 않는다.

### 공통 규칙 변경 절차

1. 문제 화면과 같은 역할의 다른 화면을 최소 두 개 찾는다.
2. 가이드에 이미 있는 규칙인지 확인한다.
3. 규칙이 있으면 공통 selector/renderer를 수정한다.
4. 규칙이 없고 두 화면 이상에 필요하면 기존 variant에 병합 가능한지 먼저 판단한다.
5. 병합할 수 없을 때만 새 variant를 가이드에 추가한다.
6. 대표 화면 세 개에서 회귀를 확인한 뒤 개별 화면 작업으로 이동한다.

## 4. 2단계 · 공통 적용 순서

공통 작업은 다음 순서를 바꾸지 않는다. 뒤 요소가 앞 요소의 크기와 여백에 의존하기 때문이다.

1. 색·타이포·간격·크기·radius·선 토큰
2. Page shell·Header·Tab·스크롤·Safe Area
3. Button·IconButton·FieldControl·Select·Filter
4. Card·Row·Table·Badge·KPI·ResultField·Notice
5. Sheet·Dialog·Popover와 LayerFooter
6. Empty·Loading·Error·Disabled·Negative 상태
7. locale·숫자·단위·날짜 formatter
8. 반응형·키보드·긴 번역·접근성

이 단계가 끝나면 대표 화면으로 공통 회귀를 먼저 수행한다.

| 공통군 | 비교 화면 |
|---|---|
| MainHeader·Filter | `ingredient_main`, `recipe_main`, `order_main`, `sales_main` |
| Form·ResultField | `ingredient_add`, `stock_change`, `recipe_add`, `order_receive` |
| 기록 목록 | `stock`, `ingredient_changes`, `recipe_changes`, `profit` |
| 관리 목록 | `options`, `recipe_materials`, `recipe_category`, MY 관리 화면 |
| FormSheet | `memo_edit`, 재료 사용량, 부자재 사용량, 발주 입고 |
| ConfirmDialog | 입고 확인, 판매 상태 변경, 삭제·철회 |

## 5. 3단계 · 화면별 작업 순서

공통 회귀가 끝난 뒤에만 화면별 작업을 시작한다. 작업 순서는 사용자 업무 흐름과 하단 탭 순서를 따른다.

1. 식재료
2. 레시피
3. 발주
4. 매출관리
5. MY

각 도메인은 `메인 → 추가 → 상세 → 수정 → 상세의 상세 → 목록/내역 → popup → 빈/오류 상태` 순서로
진행한다. 한 도메인의 기본 화면만 끝내고 다음 도메인으로 넘어가지 않는다.

### 화면 한 장의 필수 검수 순서

1. 화면 목적과 사용자의 첫 질문
2. 헤더·뒤로가기·검색·알림·상단 행동
3. 정보 우선순위와 읽는 순서
4. 제목·본문·보조·숫자·상태의 폰트 크기·굵기·색
5. 페이지·Section·Card·Row·Field의 상하좌우 여백
6. 외곽선·내부선·radius·배경·그림자
7. 입력값·단위·계산값·후행 행동의 좌우 정렬
8. 버튼·필터·Badge·Chevron·IconButton 역할
9. 빈 상태·채움 상태·음수·비활성·오류·긴 값
10. 연결되는 모든 popup과 popup 내부 스크롤·하단 버튼
11. PC와 모바일의 줄바꿈·overflow·Safe Area
12. 같은 역할 화면과의 교차비교

## 6. 화면별 검수 카드

아래 블록을 `screen:{key}`와 `popup:{id}@{host}`마다 하나씩 검수 기록에 사용한다. popup은 같은 ID라도
host가 다르면 별도 대상으로 기록한다.

```md
### screen:{key} 또는 popup:{id}@{host}

- 상태: TODO / IN_PROGRESS / PASS / FAIL / EXCEPTION
- 기준 화면·원본:
- 사용 공통 요소: C-01, C-02, ...
- 화면 전용 정책:
- [ ] 화면 전체와 스크롤 끝 확인
- [ ] 타이포 위계 확인
- [ ] 여백·선·radius 확인
- [ ] 값·단위·행동 정렬 확인
- [ ] 빈/채움/오류/비활성 상태 확인
- [ ] 연결 popup 전체 확인
- [ ] PC 확인
- [ ] 모바일 확인
- [ ] 같은 역할 화면 교차검수
- 발견 문제:
- 수정 내용:
- 회귀 대상:
- 증거 링크·화면 캡처:
- 최종 판정:
```

## 7. 비교 묶음 검수

개별 화면 PASS 뒤에는 아래 묶음을 다시 비교한다. 한 화면이 좋아 보여도 같은 역할 화면과 다르면 완료가
아니다.

| 비교 묶음 | 반드시 같아야 하는 항목 |
|---|---|
| 추가 ↔ 수정 | Field 높이·라벨·필수 표시·숫자 정렬·하단 행동 |
| 메인 ↔ 메인 | 헤더·카테고리 Tab·필터·카드 간격·FAB |
| 상세 ↔ 상세 | 핵심 KPI·Section 간격·전체보기·수정 진입 |
| 내역 ↔ 내역 | 기간 헤더·필터·날짜·Row 밀도·구분선·더보기 |
| 재료 ↔ 부자재 | 검색·사용량 입력·비용 결과·소계·빈 상태 |
| Picker ↔ Picker | 제목·선택 행·체크·즉시 반영·닫기 정책 |
| FormSheet ↔ FormSheet | Field·ResultField·키보드·오류·LayerFooter |
| Confirm ↔ Confirm | 중앙 위치·대상 요약·질문·1:1 행동 |

## 8. 완료 판정

다음 조건을 모두 만족해야 한 화면을 PASS로 표시한다.

- 공통 규칙 위반이 없다.
- 화면 전용 정책과 문구가 현재 확정안과 일치한다.
- 화면의 모든 상태와 연결 popup을 확인했다.
- PC·모바일에서 가로 overflow, 가림, 버튼 겹침이 없다.
- 같은 역할 화면과 비교해 불필요한 크기·색·간격 차이가 없다.
- 수정 때문에 영향을 받는 대표 화면을 다시 확인했다.
- 검수 기록에 실제값과 증거가 남아 있다.

전체 완료는 등록된 모든 `screen`, `popup@host`, 조건 상태가 PASS이고 숨김 보존 대상이 활성 메뉴에
노출되지 않을 때만 선언한다. 공통 CSS를 한 번 적용했거나 도메인 메인 화면만 확인한 것은 전체 완료가
아니다.
