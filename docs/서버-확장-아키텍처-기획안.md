Supabase CLI는 P1-2에서 `2.116.0`으로 고정하고 로컬 전환 절차를 완주했다.

저장소 문서와 공용 RPC 변환 경계의 기준선 동기화(P1-3)는 `01c5358`에서 완료했다. P1-1의

완료를 뜻하지는 않으며, 호스티드 프로젝트에서 `audit` 실측을 별도로 남겨야 한다.

이 문서를 작성했다는 이유만으로 Queue·Edge·공급사 테이블을 만들지 않는다. 실제 도입은 측정된 조건과
짝 문서의 작업 큐·검증·배포 게이트를 통과해야 한다.

## 1. 결론

현재와 초기 운영의 정답은 **Supabase 중심 모듈러 모놀리스**다.

```text
Expo 앱
→ Supabase Auth + Data API/RPC + RLS
→ 하나의 Primary Postgres
```

유료 Supabase 전환은 Spring Boot·NestJS·FastAPI 서버를 새로 만드는 시점이 아니다. 운영 DB,
백업, 관측성, 서버리스 실행, Queue와 비밀값을 안정적으로 운영하기 시작하는 시점이다.

확장 원칙은 다음 한 줄로 고정한다.

> Supabase 중심 모듈러 모놀리스 → 관리형 비동기 처리 → 필요한 Worker만 외부 분리 → 측정된 병목 뒤 읽기·분석 분리

지금부터 RabbitMQ·Kafka·Redis·ClickHouse·API Gateway·별도 App API를 모두 만들지 않는다. 대신
나중에 안전하게 분리할 **논리 경계와 이벤트 계약**을 지금 정한다.

## 2. 현재 서버 구조와 절대 불변식

### 2.1 현재 구조

```text
┌───────────────────────────────────────────────────────┐
│ Expo 모바일 앱                                        │
│ · Supabase Auth JWT                                   │
│ · Data API 조회                                       │
│ · 공개 RPC 호출                                       │
└──────────────────────┬────────────────────────────────┘
                       ▼
┌───────────────────────────────────────────────────────┐
│ Supabase                                              │
│                                                       │
│ Postgres Primary                                      │
│ · RLS와 store_id 매장 격리                            │
│ · 재고·입고·발주·판매·영업일 원장                    │
│ · 트랜잭션 RPC·행 잠금·판본 검사                      │
│ · 단가·손익·세금·고정지출 권위 계산                   │
│ · 스냅샷·감사·수정 이력                               │
│                                                       │
│ pg_cron                                               │
│ · 자동 영업 종료                                      │
│ · 자동 브레이크 전환                                  │
│ · 정기 청소                                           │
└───────────────────────────────────────────────────────┘
```

### 2.2 계속 지켜야 하는 불변식

1. **권위 계산은 DB RPC**에 둔다. Edge Function과 Worker가 단가·손익·재고 공식을 다시 구현하지 않는다.
2. DB 저장 단위는 g/ml/개 최소 단위와 1인분 기준을 유지한다.
3. 외부 연계가 추가돼도 업무 테이블을 직접 수정하지 않는다. 외부 발주는 E7, 실제 수령은 E1,
   취소·보정은 해당 E11/E12/E2/E5, 외부 판매 반영은 E10→E8/E9 권위 경로를 통과한다.
4. 발주 등록은 계속 기록 전용이며 입고 확정 전 재고·단가를 움직이지 않는다.
5. 재고 부족은 판매를 막지 않고 원장에 음수까지 기록한다.
6. 모든 다중 테넌트 업무 데이터는 `store_id` 범위를 갖고, 서버가 스코프를 검증한다.
7. 모바일 앱은 DB 비밀번호, service role, Queue 소비 권한, 외부 공급사 비밀키를 가지지 않는다.
8. 서버 구성 요소는 업무 테이블을 임의로 수정하지 않고 권위 RPC를 호출한다.

### 2.3 DB 안에 계속 남기는 작업

다음은 외부 Worker로 옮기지 않는다.

- 재고·단가·손익 확정
- 판매 수량 정합성과 재고 소진
- 영업일 열기·종료·브레이크 상태 전이
- 판본 검사와 행 잠금
- 원장과 현재 상태의 검산
- 자동 종료·브레이크처럼 짧고 결정적인 DB 트랜잭션

현재 `close_due_business_days()`와 `apply_due_breaks()`는 상태 재확인과 잠금이 핵심이므로 DB 내부
Cron과 트랜잭션 몸통을 유지한다. 외부 시스템을 호출하거나 긴 처리를 이 함수에 붙이지 않는다.

## 4. 단계별 서버 진화

### 4.1 단계 0 — 현재부터 출시까지

```text
Expo → Supabase Auth/Data API/RPC/RLS → Primary Postgres
                                      └→ pg_cron
```

해야 할 일:

- 현재 모듈러 모놀리스 유지
- 운영 Pro 프로젝트와 별도 스테이징 준비
- 운영 리전·MFA·Supabase 프로젝트 관리자 2명 이상·백업·SSL·네트워크 설정 검토
- DB 전체 검증을 CI 필수 체크로 옮길 준비
- Cron 실패와 핵심 RPC 오류 관측
- 계정 탈퇴와 매장·원장 삭제 정책 분리
- `REF-1`(`cceafb9`) 폴더 경계 리팩터링으로 business-day·settings·master-data·date·history 책임 분리 완료

도입하지 않는 것:

- 별도 App API 서버
- Redis·RabbitMQ·Kafka
- Read Replica·ClickHouse
- API Gateway·WAF
- 매장별 테이블 파티션

### 4.2 단계 1 — 초기 1~6개월 운영

단일 Postgres 안에서 다음을 먼저 강화한다.

- 인덱스와 slow query 개선
- 일·월 집계 read model — `store_id + business_date` 키, 증분 갱신, 원본에서 재생성 가능
- 백업·복구 훈련과 RPO/RTO
- Cron 실패 알림
- 서버·DB·앱 공통 `request_id`, `store_id`, 결과 코드
- 장기 로그가 필요할 때 Log Drain 또는 외부 알림

외부 API, 알림, Webhook처럼 서버 비밀키와 재시도가 필요한 첫 기능이 생길 때만 다음을 추가한다.

```text
Edge Function + Supabase Queue + outbox/inbox
```

### 4.3 단계 2 — 첫 식자재 공급사 연계

```text
앱 RPC
→ 업무 상태 + outbox를 같은 트랜잭션으로 저장
→ pending_dispatch 상태 반환
→ pg_cron dispatch_outbox(limit)
→ Supabase Queue
→ pg_cron이 service-only Edge Function Consumer를 제한된 batch로 호출
→ 공급사 API
→ 결과·재시도 기록
```

반대 방향:

```text
공급사 Webhook
→ Edge Function 서명 검증
→ ingest RPC가 inbox unique + 내부 outbox를 같은 트랜잭션으로 저장
→ durable commit 후 2xx
→ dispatcher → Queue → Consumer
→ 업무 적용 RPC
→ 주문 상태 또는 기존 입고 E1
```

이 단계에서도 모든 것을 별도 서비스로 분리하지 않는다. `core`, `integrations`, `notifications`,
`ops`, `analytics`라는 논리 경계를 같은 Postgres 안에 두고 권한과 계약을 분리한다.

공급사별 `enabled/paused/error` 연결 상태와 kill switch를 둔다. 외부 효과만 중단하고 앱의 판매·재고·
발주 기록은 계속 저장할 수 있어야 한다. Webhook 유실이나 응답 유실은 외부 ID와 정기 reconciliation
pull로 복구한다.

### 4.4 단계 3 — 외부 Worker 분리

다음 중 하나라도 실제로 발생하면 해당 작업만 외부 Worker로 분리한다.

- Puppeteer·Playwright 등 브라우저 자동화
- 고정 outbound IP·프록시·IP 회전
- 지속 실행·지속 폴링
- Edge Function의 CPU·메모리·실행 시간 한계 초과
- 네이티브 바이너리·멀티스레드 런타임
- Worker만 독립적으로 오토스케일해야 함

외부 Worker의 배포 기술은 이 시점에 선택한다. Cloud Run, ECS, Fly.io, Render 등은 후보일 뿐 지금
고정하지 않는다. Worker가 분리돼도 Queue 메시지와 RPC 계약은 유지해 교체 비용을 낮춘다.

Supabase hosted Edge Function의 현재 한도는 메모리 256MB, wall-clock 무료 150초·유료 400초,
요청당 CPU 2초다. 150초 안에 응답을 시작하지 못하면 request idle timeout으로 504가 발생한다.
Webhook은 서명 검증과 inbox commit 뒤 먼저 응답하고 본 처리를 Queue로 넘긴다. 수치는 구현 시 다시
확인하고 문서의 영구 규칙은 “한계를 넘으면 외부 Worker”로 둔다.
[Edge Function limits](https://supabase.com/docs/guides/functions/limits)

### 4.5 단계 4 — 읽기와 분석 분리

다음 순서로만 확장한다.

```text
쿼리·인덱스 개선
→ 일/월 집계·materialized read model
→ Primary compute 상향
→ Read Replica
→ CDC/복제 기반 외부 OLAP
```

Read Replica는 같은 Postgres의 비동기 읽기 복제본이며 OLAP가 아니다. 복제 지연 때문에 다음에는
사용하지 않는다.

- 재고 부족 판정
- 영업 상태 결정
- 저장 직후 재조회
- 쓰기 전에 최신값이 필요한 의사결정

복잡한 리포트 GET과 과거 분석에만 사용한다. [Supabase Read Replicas](https://supabase.com/docs/guides/platform/read-replicas)

ClickHouse·BigQuery·Redshift 같은 외부 분석 저장소는 집계·compute·Replica로도 운영 쓰기 부하가
해소되지 않거나 장기 시계열 분석 요구가 명확할 때만 도입한다. 앱이 Primary와 OLAP에 동시에 쓰지
않고 outbox 또는 CDC로 전달한다.

## 5. Supabase 구성요소의 책임

| 구성요소         | 책임                                                 | 하지 않는 일                    |
| ---------------- | ---------------------------------------------------- | ------------------------------- |
| Postgres/RPC     | 원장, 계산, 잠금, 판본, RLS, 트랜잭션                | 긴 외부 HTTP, 브라우저 자동화   |
| Cron             | 짧은 DB 작업, bounded outbox dispatch, Consumer 호출 | 무거운 배치 본체, 끝없는 재시도 |
| Queue            | 내구성 메시지, visibility, 재시도 기반               | 외부 효과의 중복 방지 자체      |
| Edge Function    | JWT·서명 검증, 짧은 BFF, Webhook, 짧은 I/O           | 권위 계산 재구현, 긴 CPU 작업   |
| 외부 Worker      | 브라우저, 긴 배치, 고정 IP, 독립 스케일              | 업무 테이블 직접 변경           |
| Database Webhook | 비핵심 변경 알림과 fan-out                           | 핵심 전달의 유일한 보증         |
| Storage          | 영수증·거래명세서·상품 이미지 파일                   | 업무 원장·금액 권위             |
| Vault            | SQL·Cron·DB Webhook에서 읽는 비밀                    | 모바일에 전달할 키              |
| Read Replica     | 지연을 허용하는 읽기·리포트                          | 쓰기, 최신 재고 판정            |
| OLAP             | 장기 분석·대규모 집계                                | 앱 트랜잭션의 진실의 원천       |

Supabase Queues는 `pgmq` 기반 Postgres 내구성 Queue다. 초기 비동기 처리에는 별도 RabbitMQ·Kafka가
필요하지 않다. [Supabase Queues](https://supabase.com/docs/guides/queues)

Cron은 시간 트리거이며 DB 함수 또는 HTTP 호출을 실행할 수 있다. 무거운 작업은 Queue에 넣고
Consumer가 수행한다. [Supabase Cron](https://supabase.com/docs/guides/cron)

PGMQ는 pull Queue이므로 Edge Function이 스스로 상주하지 않는다. 초기에는 Cron이 service-only Edge
Function Consumer를 주기 호출하고 Consumer가 정해진 개수·시간 안에서만 메시지를 처리한다. 외부
Worker 단계에서는 Worker가 Queue를 poll한다. `waitUntil`을 내구성 Consumer로 간주하지 않는다.

## 6. 동기 요청과 비동기 작업의 경계

### 6.1 동기로 처리할 것

- 판매 수량 저장과 재고 소진
- 입고 확정과 단가 갱신
- 영업 상태 전이
- 사용자에게 즉시 성공·실패를 알려야 하는 작은 설정 저장
- 하나의 DB 트랜잭션에서 정합성이 완결되는 작업

### 6.2 Queue로 보낼 것

- 외부 공급사 주문 전송
- 공급사 카탈로그·가격 동기화 — 매장별 작업과 provider 전역 작업의 scope를 구분
- Push·이메일·알림톡
- Webhook 재시도
- 대량 리포트 생성·파일 변환
- 사용자 응답을 기다리게 할 필요가 없는 외부 I/O

판단 규칙:

> 실패 시 재시도가 필요하거나, 외부 서비스 응답 때문에 사용자 저장이 지연되거나, 한 요청 안에서
> 끝난다고 보장할 수 없으면 먼저 Queue에 기록한다.

Edge Function의 `waitUntil`은 응답 뒤 짧은 작업에 사용할 수 있지만 함수의 실행 한도를 그대로 받는다.
유실되면 안 되는 주문·알림의 Queue 대체재로 사용하지 않는다.
[Background Tasks](https://supabase.com/docs/guides/functions/background-tasks)

## 7. Outbox·Queue·Inbox 계약

### 7.1 역할 분리

```text
integration_outbox_events       내부에서 외부로 보낼 의도
integration_inbox_events        외부에서 받은 이벤트와 중복 방지
integration_delivery_attempts   전송 시도·응답·다음 재시도
integration_dead_letters        자동 재시도 종료 후 수동 처리 대상
integration_sync_runs           카탈로그·가격 동기화 실행 단위
```

`integration_outbox_events`에는 최소 `dispatched_at`, `dispatch_attempt`, `last_error`, `available_at`을
둔다. outbox는 업무 의도와 재처리의 원장이고 Queue는 전달 transport다. 두 역할을 합치지 않는다.

현재 `entity_change_events`는 화면용 최근 수정 내역이며 별도 정리 정책이 있으므로 outbox, 영구 감사,
이벤트 버스로 재사용하지 않는다. `inventory_events`, `business_day_revisions`,
`business_state_transitions`는 각 도메인 원장 역할을 유지한다.

### 7.2 이벤트 envelope

공통 필수 필드:

```text
event_id              전역 UUID
event_type            supplier.order.requested 등
schema_version        명시 버전
scope_type            store | provider
aggregate_type        order · inbound · ingredient 등
aggregate_id          내부 리소스 ID
aggregate_revision    같은 aggregate의 단조 증가 판본
occurred_at           UTC 업무 사건 시각
available_at          소비 가능 시각
payload               필요한 최소 JSON
```

scope별 필수 필드:

```text
scope_type=store      store_id 필수
scope_type=provider   provider_id 필수, store_id는 없음
```

조건부 필드:

```text
connection_id         매장별 공급사 연결을 사용하는 경우
idempotency_key       외부 효과를 만드는 경우 필수
correlation_id        여러 이벤트가 한 사용자 흐름인 경우
causation_id          앞 이벤트에서 파생된 경우
sequence_no           공급사가 순서를 제공하거나 상태 전이가 순서에 민감한 경우
business_day_id       판매·영업 장부 사건인 경우
business_date         판매·영업일 귀속이 필요한 경우
store_local_date      입고·발주·재고의 매장 현지 날짜가 필요한 경우
```

큰 원문과 민감정보를 Queue payload에 반복 저장하지 않는다. `resource_id`를 넣고 권한 있는 Consumer가
필요한 원문을 조회한다. payload 변경은 `schema_version`을 올리고 구 Consumer와의 호환 기간을 둔다.

분석 파이프라인은 UTC `occurred_at::date`로 매출을 묶지 않는다. 판매·영업은 `business_date`, 입고·
발주·재고는 `store_local_date`를 권위 날짜로 사용한다. 과거 손익은 현재 레시피가 아니라 그날 snapshot과
`basis_quality`를 사용한다.

### 7.3 원자성

업무 RPC가 상태만 저장한 뒤 애플리케이션이 별도로 Queue를 쓰면 중간 실패 때 이벤트가 사라진다.
초기 구현 방식은 다음 하나로 고정한다.

```text
권위 RPC
  업무 상태 + integration_outbox_events를 같은 트랜잭션으로 commit

pg_cron dispatch_outbox(limit)
  unpublished outbox를 FOR UPDATE SKIP LOCKED로 제한된 수만큼 잠금
  → 같은 DB 트랜잭션에서 pgmq.send(event_id)
  → dispatched_at 기록

pg_cron
  service-only Edge Function Consumer 호출
  → bounded batch 소비
```

업무 저장 성공의 의미는 “외부 공급사가 처리 완료”가 아니라 **outbox가 원자적으로 기록되어
`pending_dispatch`가 됨**이다. Dispatcher 실패는 `dispatch_attempt/last_error`에 남기고 다음 실행에서
재시도한다. 오래된 미발행 outbox를 탐지하는 stuck recovery와 수동 재실행 경로를 둔다. 이 구조는
향후 PGMQ를 외부 Queue로 바꿔도 권위 RPC를 바꾸지 않게 한다.

수신 경로도 하나의 `ingest_partner_event` 계열 RPC에서 다음을 원자 처리한다.

```text
unique(provider_id, connection_id, external_event_id) inbox 저장
+ 내부 처리용 outbox 저장
```

중복 Webhook이면 기존 inbox를 반환하고 outbox를 다시 만들지 않는다. Edge Function은 서명 검증 후 이
commit이 성공한 뒤에만 2xx를 반환한다. Database Webhook은 `pg_net` 기반 비동기 fan-out에 쓸 수 있지만,
핵심 주문 전달의 유일한 보증으로 사용하지 않는다.
[Database Webhooks](https://supabase.com/docs/guides/database/webhooks)

### 7.4 멱등성과 재시도

- Queue 전달 보장과 외부 API 업무 중복 방지는 다른 문제다.
- 모든 Consumer는 같은 `event_id`가 다시 와도 결과가 같아야 한다.
- 공급사 주문에는 내부 `idempotency_key`와 외부 주문 ID를 함께 저장한다.
- Consumer는 `aggregate_revision/sequence_no`보다 오래된 상태 전이를 무시하거나 명시적으로 거부한다.
- Webhook이 유실되거나 공급사가 성공 응답을 보냈지만 우리 응답이 유실된 경우를 정기 reconciliation로 복구한다.
- HTTP 429·5xx·timeout은 지수 backoff와 jitter로 재시도한다.
- 인증 오류·계약 오류·필수 매핑 누락은 자동 무한 재시도하지 않고 수동 조치 대상으로 보낸다.
- 최대 시도 횟수 후 dead letter로 옮기되 메시지와 마지막 오류를 삭제하지 않는다.
- 운영자는 수동 재처리 전에 원인과 현재 외부 상태를 확인한다.

### 7.5 권한

- 모바일·anon·일반 authenticated 사용자는 Queue를 직접 읽거나 삭제하지 못한다.
- Producer RPC는 자기 매장의 허용된 event만 기록한다.
- `pgmq_public`과 integration/ops 원본 테이블을 모바일 Data API에 노출하지 않는다.
- 공개 `public` 스키마에는 검증된 facade RPC만 두고 원본 integration/ops schema에는 앱 GRANT를 주지 않는다.
- Consumer는 전용 integration identity와 허용 RPC 목록을 사용한다.
- 범용 service role을 외부 Worker의 기본 자격으로 사용하지 않는다.
- service role은 모바일·브라우저 번들에 절대 넣지 않는다.

## 8. API 접근 주체와 신뢰 경계

초기에는 Supabase Function 이름으로 책임을 드러낸다. 아직 별도 API Gateway 경로를 흉내 내지 않는다.

```text
owner-*                점주 JWT와 매장 권한 필수
partner-supplier-*     공급사 서명·timestamp·nonce·idempotency 검증
worker-*               내부 자격만 허용, 사용자 JWT로 호출 불가
admin-*                별도 관리자 역할·MFA·감사 로그
```

### 8.1 점주 앱

- Supabase Auth JWT
- Data API와 공개 RPC
- RLS와 서버의 `assert_my_store` 같은 스코프 검증
- publishable/anon 성격의 공개 키만 포함

### 8.2 공급사 API와 Webhook

- 공급사별 서명 검증
- replay 방지용 timestamp·nonce
- `provider_id + connection_id + external_event_id` unique
- inbox durable commit 이후에만 2xx, 긴 처리는 Queue로 전달
- 원문 보관 시 개인정보·비밀값 마스킹과 보존 기간 적용
- Webhook 유실을 복구하는 주기적 reconciliation

### 8.3 내부 Worker

- 공개 사용자 API와 다른 전용 integration identity
- 허용 Queue와 facade RPC allowlist
- 일반 업무 테이블과 integration 원본 테이블 직접 DML 금지
- 범용 service role을 기본 자격으로 사용하지 않음
- DB 직접 연결이 꼭 필요하지 않으면 worker-auth Edge facade 또는 Data API/RPC 사용
- 전용 DB role을 쓸 경우 no-login 소유자와 실행 role을 분리하고 최소 GRANT만 부여
- 직접 연결 시 연결 수·pooling·비밀 회전·감사 로그 정책 적용

### 8.4 관리자

- 점주 앱에 숨은 버튼만 추가하는 방식 금지
- 관리자 역할, MFA, 모든 변경 감사
- 파괴적 작업은 2단계 확인과 이유 기록
- service role을 클라이언트에 배포하지 않음

파트너가 mTLS·고정 IP·전용 WAF를 요구하거나 독립 API가 여러 개로 늘 때만 별도 API Gateway를
검토한다. 현재부터 VPN·mTLS·전용선이 채택된 것처럼 문서화하지 않는다.

## 9. 식자재 공급사 데이터 경계

### 9.1 기존 개념을 억지로 확장하지 않는다

- 현재 `vendors`는 매장별 구매처 메모로 유지한다.
- 현재 구매 옵션은 사장님이 저장한 구매 단위와 가격으로 유지한다.
- 현재 발주 기록을 외부 다품목 주문 헤더로 억지 확장하지 않는다.

글로벌 공급사·상품 카탈로그·실시간 가격은 별도 모델이다.

### 9.2 미래 canonical 모델

아래는 **개념 모델**이다. 첫 공급사 계약과 데이터 모양이 확정되기 전에 테이블을 선제 생성하지 않는다.

```text
suppliers
  공급사 조직·상태·지원 지역

supplier_products
  공급사 상품 식별자·이름·브랜드

supplier_offers
  공급사 지점·connection별 포장 규격·가격·최소 주문·가용성·유효기간

store_supplier_connections
  매장-공급사 계정 연결과 상태
  업무행에는 secret_ref만 저장

ingredient_offer_mappings
  내부 식재료 ↔ 공급사 offer
  포장 단위를 g/ml/개로 환산하는 계약

procurement_orders / procurement_order_lines
  외부 주문 헤더·라인·상태·금액·통화 스냅샷
  normalized_quantity와 mapping_version 스냅샷

receipts / receipt_lines
  실제 수령과 부분 입고

external_resource_refs
  provider + connection + resource_type + external_id unique
```

주문 라인에는 상품명·규격·가격·세금·통화를 주문 당시 값으로 굳힌다. 공급사 카탈로그가 바뀌어도
과거 주문이 바뀌지 않아야 한다.

- 공급사 공용 플랫폼 키는 Edge Project Secrets에 둔다.
- 매장별 OAuth refresh token·connection secret은 Vault 또는 외부 Secret Manager에 두고 업무행에는
  `secret_ref`만 둔다.
- 구매 세금·공급사 송장 세금은 판매 세금 `tax_of()`와 다른 계약이다. `tax_of()`를 구매 세금에
  재사용하지 않는다.
- 서로 다른 통화는 환율 출처·시점·반올림 계약 없이 합산하지 않는다.

### 9.3 기존 도메인과 연결

- 외부 주문 요청은 발주 기록이며 재고·단가를 바꾸지 않는다.
- 외부 주문 라인마다 기존 E7 경로로 내부 `order_records`를 만들거나 연결하고
  `procurement_order_lines.order_record_id`로 관계를 보존한다.
- 실제 수령은 그 `order_record_id`를 사용해 기존 E1 입고 확정 RPC를 호출한다. 부분 수령이 여러 번
  필요하면 E1 어댑터를 별도 설계하되 주문 상태 권위를 두 벌 만들지 않는다.
- 공급사 박스·팩·망 같은 단위는 offer의 포장 규격이다.
- 내부 원장에는 계속 g/ml/개 최소 단위로 환산한다.
- 외부 Worker는 `inventory_states`나 단가 테이블을 직접 수정하지 않는다.

외부 주문 상태의 최소 의미:

```text
pending_dispatch → submitted → confirmed → partially_received → received
                                  ├→ failed
                                  └→ canceled
```

공급사가 주문을 받았지만 응답이 유실된 상태는 새 주문을 만들지 않고 같은 idempotency key와
reconciliation으로 확인한다.

## 10. 멀티테넌트와 조직 확장

### 10.1 현재 1차 계약

현재 `stores.owner_id UNIQUE`는 한 계정당 한 매장인 초기 계약이다. 초기 1~6개월에는 유지할 수 있다.
그러나 모든 업무 데이터의 `store_id`는 계속 필수이며 사용자 ID만으로 테넌트를 구분하지 않는다.

### 10.2 다매장·직원 전에 필요한 이관

첫 직원 초대 또는 두 번째 매장 지원 전에 다음 구조로 확장한다.

```text
organizations
organization_memberships
roles / permissions
stores.organization_id
```

이관 순서:

```text
새 조직·멤버십 추가
→ 기존 owner를 조직 owner로 backfill
→ 앱과 RPC가 membership으로 권한 확인
→ dual-read 검증
→ owner_id UNIQUE 의존 제거
→ 구 권한 경로 정리
```

### 10.3 매장 격리

- 모든 업무 쿼리와 이벤트에 `store_id`
- RLS + 서버 함수 내부 스코프 검증을 함께 사용
- 기본 인덱스는 `(store_id, occurred_at)` 또는 실제 조회 순서
- 캐시·Queue·로그·파일 경로에도 `store_id`
- 다른 매장 ID를 payload로 넘겨도 서버가 거부하는 회귀 시험

매장별 파티션은 지금 만들지 않는다. 파티션 수가 매장 수만큼 증가하면 운영 복잡도가 커진다.
실제 테이블 크기와 쿼리 계획이 요구할 때 연월 같은 시간 파티션을 우선 검토한다.

### 10.4 계정 탈퇴와 데이터 보존

0173부터 인증 계정 삭제가 매장과 원장 전체의 물리 삭제로 이어지지 않는다.

- `auth.users` 삭제는 `stores.owner_id`만 `SET NULL`로 바꾸고 매장은 `archived` 상태가 된다.
- 탈퇴·폐점 직후 `my_store_ids()`와 RLS에서 제외되어 앱 접근은 끊기고 거래 원장은 보존된다.
- `store_lifecycle_events`가 계정 삭제·폐점·삭제 예약·물리 삭제를 append-only로 남긴다.
- 물리 삭제는 service role 전용이며 보존 종료 시각·승인 주체·승인 근거·복구 백업 근거를 요구한다.
- MY-10은 원장 보존 사실과 접근 종료를 먼저 알리고 ‘탈퇴’ 확인 문구를 받은 뒤 공식 RPC를 호출한다.

이 항목은 확장 기능이 아니라 첫 실사용자 전 운영 안전 과제다.

## 11. 구독·컴퓨트·분리 승급 조건

달력 기준만으로 인프라를 늘리지 않는다. 다음 조건과 측정값으로 결정한다.

| 승급               | 도입 조건                                                      | 먼저 확인할 것                                   |
| ------------------ | -------------------------------------------------------------- | ------------------------------------------------ |
| 운영 유료 프로젝트 | 첫 실매장·복구 불가 데이터 이전                                | 리전, MFA, 백업, 프로젝트 관리자, 예산 알림      |
| 별도 스테이징      | 첫 실매장, 첫 외부 연계, 두 번째 개발자 중 가장 이른 시점      | 합성 시드, 운영 비밀 분리, 배포 권한             |
| Compute 상향       | CPU·메모리·IO·연결·p95가 지속 임계치 초과                      | slow query, 인덱스, N+1, 불필요한 폴링           |
| Queue              | 외부 I/O·재시도·대량 비동기 작업 최초 발생                     | 같은 트랜잭션 outbox, 멱등성, DLQ                |
| Edge Function      | 서버 비밀키·Webhook·짧은 BFF 필요                              | JWT/서명, timeout, invocation/runtime 비용, 로그 |
| 외부 Worker        | 브라우저·고정 IP·지속 실행·Edge 한계 초과                      | Queue 계약과 RPC 경계                            |
| PITR               | 하루치 판매·재고 손실을 감당할 수 없음                         | 복구 훈련, RPO/RTO, 비용                         |
| Read Replica       | 분석 읽기가 Primary 쓰기 지연을 유발하거나 해외 읽기 지연이 큼 | 쿼리·집계·compute 개선, 복제 지연 허용           |
| 외부 OLAP          | 집계·compute·Replica로도 분석 부하가 해소되지 않음             | CDC/outbox, 데이터 보존·비용                     |
| 외부 Queue         | Postgres Queue 쓰기·보관이 Primary를 실제 압박                 | 소비 최적화, 보관 정책, 분리 비용                |
| API Gateway/WAF    | 여러 파트너·관리자 API가 별도 보안·속도 제한·mTLS를 요구       | Edge 경계로 충분한지, 운영 인력                  |
| Log Drain          | 기본 로그 보존·검색·알림으로 장애 대응 불가                    | 로그 양, 개인정보 마스킹, 보존 비용              |

각 승급 작업은 측정값과 이 절의 조건을 `docs/작업큐.md`에 기록하고
[운영 기획안 §13](./브랜치-DB-운영-기획안.md#13-서버-단계-변경과-이-문서의-상호작용)의
절차로 배포한다.

## 12. 비밀값·연결·파일

### 12.1 비밀값 위치

| 소비자                         | 저장 위치                                   |
| ------------------------------ | ------------------------------------------- |
| 모바일 앱                      | 공개 가능한 Supabase URL·publishable key만  |
| Edge Function 공용 공급사 키   | Supabase Project Secrets                    |
| 매장별 OAuth·connection secret | Vault 또는 외부 Secret Manager              |
| SQL·Cron·DB Webhook            | Vault                                       |
| 외부 Worker                    | 배포 플랫폼의 Secret Manager 또는 동등 기능 |

Vault는 DB 함수·Trigger·Webhook이 사용할 비밀을 암호화해 저장한다.
[Supabase Vault](https://supabase.com/docs/guides/database/vault)

비밀값 원문을 일반 업무 테이블, Git, 로그, Queue payload, 앱 번들에 넣지 않는다. 비밀 교체 시 새 값을
먼저 배포하고 소비자를 전환한 뒤 구 값을 폐기한다.

### 12.2 DB 연결

- 모바일: Data API만 사용
- 마이그레이션·dump·restore: direct connection
- 짧은 serverless/Edge SQL 연결: transaction pooler 검토
- 장기 Worker: direct 또는 session pooler, 연결 수 제한
- Worker가 Data API/RPC로 충분하면 직접 SQL 연결을 만들지 않음

세부 연결 방식은 Supabase 공식 연결 가이드를 구현 시 다시 확인한다.
[Connect to Postgres](https://supabase.com/docs/guides/database/connecting-to-postgres)

### 12.3 Storage

- 영수증·발주서·상품 이미지 같은 파일만 저장
- DB에는 object path, checksum, 업무 리소스 ID, 보존 상태를 저장
- bucket·`storage.objects`에 매장 RLS
- signed URL 만료와 다운로드 권한 시험
- DB 백업과 파일 객체 복구가 같은 범위라고 가정하지 않음
- 중요한 증빙은 별도 내보내기·보존 정책 적용

## 13. 관측성과 운영 지표

### 13.1 공통 로그 필드

```text
request_id
event_id
job_id
store_id
function_name
function_version
schema_version
attempt
duration_ms
result_code
```

로그에 인증 토큰, 비밀키, 카드·계좌 원문, 영수증 원문, 불필요한 개인정보를 남기지 않는다.

### 13.2 최소 지표

- Data API/RPC p50·p95·p99, 4xx·5xx
- DB CPU·메모리·IO·disk·connection
- slow query·lock wait·deadlock·index 사용
- Cron 마지막 성공·실패·지연
- Queue depth·oldest age·attempt·DLQ
- Edge/Worker duration·timeout·memory·5xx
- 공급사 Webhook 중복·서명 실패·처리 지연
- 원장 합계 불일치 수
- Read Replica 사용 시 replication lag
- 월별 DB·Storage 증가량과 egress
- Edge invocation·runtime, Queue 보관량·oldest age
- Auth MAU·Realtime 사용량(사용할 경우)
- 월 예상 비용과 예산 알림 임계치

초기 운영의 RPC 관측은 `0176`의 앱 보고 버킷을 사용한다. 이는 정상 업무 거절을 제외한
**client-reported 예상 밖 오류 건수**이며, 전체 요청 분모가 없으므로 오류율·p95로 부르지 않는다.
`ops-health` Edge Function은 Cron 3종의 마지막 성공·실패·지연과 이 건수만 전용 토큰으로 내고,
GitHub Actions가 10분마다 외부에서 호출해 장애 이슈를 열고 회복 시 닫는다. 트래픽이 커져 정확한
Data API/RPC 오류율이 필요할 때 Supabase Log Drain 또는 동등한 원천 로그 수집을 별도 비용 검토 후
도입한다.

### 13.3 알림 우선순위

P0:

- 판매·입고 저장 불가
- 원장 불일치
- 인증·매장 격리 우회
- 자동 종료·브레이크 Cron 장시간 실패
- 운영 백업 실패

P1:

- Queue oldest age 임계치 초과
- 공급사 주문 반복 실패
- DB 자원 지속 포화
- Edge/Worker 5xx 급증

P2:

- 단일 동기화 실패
- 일시적인 파트너 429
- 재시도로 자동 회복된 작업

## 14. 저장소의 논리 경계

당장 별도 서비스로 쪼개지 않고 다음 책임만 코드와 DB에서 분리한다.

```text
apps/mobile
  점주 UX·조회·명령 요청

packages/core
  순수 계산 미리보기·검산

packages/types 또는 contracts
  앱·RPC·이벤트 envelope 계약

packages/db
  원장·권위 RPC·RLS·Cron·Queue schema

packages/db/supabase/functions  필요할 때 생성
  owner-* · partner-* · worker-*

services/integration-worker    분리 조건 충족 시 생성
  브라우저·긴 배치·고정 IP
```

DB 내부도 물리 DB를 나누기 전에 논리 영역을 구분한다.

```text
core/domain       현재 공개 업무 테이블·RPC
integration       outbox·inbox·supplier mapping
ops               job·attempt·dead letter·idempotency
analytics         read model·집계
```

스키마 이름을 실제로 나눌지는 Supabase Data API 노출·RLS·권한·타입 생성 영향을 검토한 뒤 별도
마이그레이션으로 결정한다. 문서의 논리 이름만 보고 즉시 스키마를 생성하지 않는다.

실제 스키마로 분리하면 integration/ops/analytics 원본은 Data API 비노출·앱 role no-grant를 기본으로
하고, 검증된 facade RPC만 `public`에 둔다.

## 15. 도입하지 않는 구조와 재검토 조건

| 지금 도입하지 않음          | 이유                                   | 재검토 조건                                           |
| --------------------------- | -------------------------------------- | ----------------------------------------------------- |
| Spring/Nest/FastAPI App API | 현재 Auth/RLS/RPC가 기능을 충족        | 여러 클라이언트 BFF가 복잡해지고 Edge로 부족          |
| Redis                       | 캐시 무효화·정합성 비용이 더 큼        | 측정된 hot read 또는 rate limit 상태 필요             |
| RabbitMQ/Kafka/SQS          | Supabase Queue로 초기 비동기 처리 가능 | Queue 부하가 Primary를 압박하거나 별도 조직 운영 필요 |
| ClickHouse/Spark            | 초기 데이터량과 팀 규모에 과함         | Replica·집계로도 분석 SLA 불충족                      |
| Read Replica                | 비용과 복제 지연                       | Primary 읽기 병목 실측                                |
| 매장별 파티션               | 파티션 폭증·운영 복잡도                | 실제 테이블 규모와 쿼리 계획이 요구                   |
| API Gateway/WAF             | Edge 경계로 충분                       | mTLS·고정 IP·복수 파트너 정책 필요                    |
| 다중 마이크로서비스         | 분산 트랜잭션·관측·배포 비용           | 독립 팀·독립 SLA·독립 스케일이 실제로 필요            |

금융 등 먼 미래 도메인은 현재 구축하지 않는다. 다만 core 원장과 integration 계약을 섞지 않아 향후
별도 보안·데이터 경계를 만들 수 있게 한다.

## 16. 단계별 완료 기준

### 단계 0 완료

- 운영 Pro·별도 스테이징 준비
- 백업·복구 훈련
- DB 6단계 CI 또는 관리 러너
- 계정 탈퇴와 원장 보존 분리
- Cron·핵심 RPC 관측
- 대형 브랜치 `main` 병합과 문서 동기화

### 단계 1 완료

- 첫 Queue/Edge 기능에 outbox·멱등성·재시도·DLQ
- bounded outbox dispatcher와 service-only Consumer 호출
- 비밀값이 Project Secrets/Vault에만 존재
- 중복 Webhook·timeout·429·5xx 시험
- 운영자가 실패 작업을 조회·재처리 가능
- 전용 integration identity·RPC allowlist·자격 회전·감사 로그
- 일반 업무 테이블 직접 DML과 범용 service role 사용 금지

### 단계 2 완료

- 공급사·상품·offer·매핑·외부 주문 모델 분리
- 포장 규격을 g/ml/개로 정확히 환산
- 발주는 재고 불변, 입고 확정은 E1 사용
- 주문 시점 스냅샷과 외부 ID unique
- 공급사 장애가 앱 핵심 저장을 막지 않음
- provider/connection kill switch와 정기 reconciliation

### 단계 3 완료

- 외부 Worker가 Queue/RPC 계약만 사용
- 고정 IP·브라우저·장시간 작업의 독립 관측
- Worker 중단 뒤 재시작해도 중복 효과 없음
- 배포·회전·비밀 교체 절차 문서화
- 전용 integration identity 외 자격으로 원본 테이블 접근 불가

### 단계 4 완료

- Read Replica/OLAP 도입 근거 지표 기록
- 최신값이 필요한 경로는 Primary 유지
- 분석 파이프라인 재처리·backfill 가능
- 앱 dual-write 없음
- 비용·보존·복제 지연 모니터링
- read model은 파생·재생성 가능하며 새 업무 권위가 아님

## 17. 운영 기획안과의 상호작용

서버 구조 변경은 다음 순서로 두 문서를 함께 사용한다.

```text
이 문서
  문제와 측정값으로 단계·구성요소·책임 경계 결정
        ↓
브랜치·DB 배포 운영 기획안
  작업 큐 → 세로 브랜치 → 검증 → 스테이징 → 운영 배포 → 전진 복구
        ↓
이 문서와 ARCHITECTURE.md
  실제 채택 단계·데이터 흐름·지표 갱신
```

상호 참조 규칙:

- 서버 단계 변경 → 운영 기획안 §13 절차 필수
- DB/RPC 변경 → 운영 기획안 §4 검증·마이그레이션 규칙
- Edge·Queue·Worker 추가 → 이 문서에서 책임 결정, 운영 기획안 §5에서 배포 순서 결정
- 비밀값 → 이 문서가 소비자와 저장 위치 결정, 운영 기획안이 배포·교체·검증
- 모니터링 → 이 문서가 지표·승급 조건 결정, 운영 기획안이 배포 전후 점검
- 장애 → 이 문서의 책임 경계를 유지하고 운영 기획안 §7로 전진 복구
