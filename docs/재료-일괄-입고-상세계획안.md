# 재료 일괄 입고 상세 계획안

> 상태: Fable·Astra 독립검수 READY · 구현 대기
> 작성일: 2026-09-21
> 대상 기능: `FN-ORD-003 직접 입고·초기 재고 입력` 확장
> 신규 화면: `ING-12 재료 일괄 입고`

## 1. 목적

여러 재료를 한 번에 입고하면서 각 재료의 구매처·결제금액·입고량을 기록하고, 저장 직전에는
서버가 계산한 `입고 후 단가`를 확인한다. 저장은 배치 전체를 하나의 원자 작업으로 처리해 일부
재료만 입고되는 상태와 재시도에 따른 중복 입고를 막는다.

이번 기능은 기존 단건 `재고 수정 > 입고`의 계산·원장 규칙을 바꾸지 않는다. 새 화면은 같은 E7
발주 기록과 E1 입고 원장을 여러 건 묶어 확정하는 진입점이다.

## 2. 확정된 사용자 요구사항

1. 재료 메인 우측 하단 버튼의 표시는 `+ 추가`로 바꾼다.
2. 버튼을 누르면 아이콘 없는 메뉴를 띄운다.
   - `재료 일괄 입고`
   - `재료 등록`
3. `재료 일괄 입고`를 누르면 별도 페이지로 이동한다.
4. 페이지는 입고 카드 추가·삭제 방식으로 구성한다.
5. 카드 하나는 헤더 없이 다음 4행을 사용한다.
   - 1행: 재료명
   - 2행: 구매처
   - 3행: 결제금액 | 입고 후 단가
   - 4행: 입고량
6. 3행만 2열이고 나머지는 전체 너비다.
7. 각 카드 아래에 삭제 버튼을 둔다.
8. 카드의 표면·테두리·입력 형태는 기존 메뉴 정보 카드와 단건 입고 입력을 재사용한다.

## 3. 화면 계약

### 3.1 재료 메인 진입 메뉴

- 기존 `재료 등록` FAB를 글자형 `+ 추가` 버튼으로 바꾼다.
- 현재 `FAB`가 항상 아이콘을 그리므로 공용 API에 `icon={false}`, 선택형
  `accessibilityLabel`, 선택형 `accessibilityState`를 추가한다. 버튼에는 별도 아이콘을 넣지 않고
  `+` 문자를 라벨 일부로 표시한다.
- 이 화면은 접근성 이름을 `추가 메뉴 열기`로 지정하고 펼침 상태를
  `accessibilityState.expanded`로 알린다. 기존 FAB 호출부의 기본 동작은 유지한다.
- 누르면 기존 `ActionSheet`의 floating 스타일을 사용한다. 메뉴 행에는 아이콘·설명 문구·우측
  화살표를 넣지 않는다.
- 메뉴 선택 결과:
  - `재료 일괄 입고` → `/ingredients/bulk-inbound`
  - `재료 등록` → `/ingredients/add`
- 바깥 영역, 시스템 뒤로가기, `닫기`를 누르면 아무 이동 없이 닫힌다.

### 3.2 `ING-12 재료 일괄 입고`

- 헤더: 뒤로가기 + `재료 일괄 입고`
- 본문은 세로 스크롤이며 최초 진입 시 빈 카드 1개를 표시한다.
- 카드 아래의 `재료 추가` 버튼으로 새 빈 카드를 추가한다.
- 한 번에 최대 20개 카드까지 허용한다. 한도를 넘으면 추가 버튼을 비활성화하고
  `한 번에 최대 20개까지 입고할 수 있어요`를 표시한다.
- 하단 고정 버튼은 `일괄 입고 완료`다. 카드가 없거나 유효하지 않은 카드가 하나라도 있거나,
  미리보기·결과 확인 중이면 비활성화한다.
- 시스템 뒤로가기나 헤더 뒤로가기를 눌렀을 때 입력된 값이 있으면 기존 이탈 확인 패턴을 사용한다.

### 3.3 카드 상세

카드에는 화면에 보이는 별도 번호나 카드 헤더를 두지 않는다. 보조기술에는 카드 순서를
`입고 항목 1`, `입고 항목 2`처럼 전달한다.

| 행 | 표시 | 입력·동작 |
|---|---|---|
| 1 | `재료명 *` | 활성 재료를 검색·선택한다. 선택 시 단위와 구매 옵션을 읽는다. |
| 2 | `구매처 (선택)` | `미선택` 또는 해당 재료에 등록된 구매 옵션을 선택한다. 표시값은 `구매처명 · 옵션명`이다. |
| 3 왼쪽 | `결제금액 *` | 실제 총 결제금액을 입력한다. 통화 설정의 숫자 형식을 적용한다. |
| 3 오른쪽 | `입고 후 단가` | 서버 미리보기의 `base_price_after`를 읽기 전용 회색 결과 칸으로 표시한다. |
| 4 | `입고량 *` | 이 카드에서 실제 들어온 총량을 재료 기준단위로 입력한다. |

- 저장된 구매 옵션을 고르면 결제금액과 입고량을 기본값으로 채우되 사용자가 수정할 수 있다.
- `미선택`은 구매처 없이 직접 입고하는 뜻이다. 구매처를 필수로 만들지 않는다.
- 재료를 바꾸면 이전 재료에서 선택한 구매처와 자동 입력값을 초기화한다.
- `입고량`은 포장 `용량 × 수량`이 아니라 카드 전체의 실제 입고량이다. 단건 구매 옵션 화면의
  포장 수량 UI를 이 화면에 넣지 않는다.
- 단위는 DB 기준단위인 g/ml/개로 보낸다. 화면에는 기존 규칙대로 kg·g·ml·L·개를 표시한다.
- 결제금액과 입고량은 0보다 커야 한다. 결제금액은 통화별 금액 입력 계약, 입고량은 기준단위
  환산·수량 정밀도 계약과 기존 `Input` 숫자 정규화 함수를 사용한다. `unit_price_digits`는 입력값을
  반올림하거나 절삭하지 않으며 읽기 전용 `입고 후 단가`의 `formatUnitPrice`에만 적용한다.
- 같은 재료를 여러 카드에 선택할 수 있다. 서로 다른 구매처·결제 건은 구매 이력과 E1 원장을
  각각 남긴다.
- 같은 재료가 반복되면 각 카드의 `입고 후 단가`는 화면 순서대로 앞 카드의 가상 입고를 누적한
  `base_price_after`다. 값이 없으면 `—`로 표시하고 기존 `formatUnitPrice`와 재료 기준단위 접미사를
  사용한다. 응답의 `inbound_unit_price`는 서버·시험 검산용이며 이 칸에는 표시하지 않는다.
- 카드 하단의 `삭제`는 위험색 텍스트 버튼으로 제공한다. 마지막 카드도 삭제할 수 있으며, 카드가
  0개면 빈 안내와 `재료 추가` 버튼만 남는다.

### 3.4 미리보기·오류·완료

- 앱에서 단가를 계산하지 않는다. `입고 후 단가`는 배치 미리보기 RPC가 반환한다.
- 미리보기는 카드 입력이 유효해진 뒤 짧은 지연을 두고 한 번의 배치 요청으로 갱신한다. 같은 재료가
  여러 카드에 있으면 화면 순서대로 반영한 각 카드 직후의 단가를 돌려준다.
- 미리보기 실패는 카드 결과 칸을 `확인 필요`로 표시하고 저장을 막는다. 0원이나 기존 단가로
  대체하지 않는다.
- 저장 전 클라이언트 오류는 해당 필드 아래에 표시한다. 서버가 특정 카드를 거절하면 응답의
  `client_item_id`를 이용해 해당 카드로 이동하고 같은 오류를 표시한다. 재고 실사 진행처럼 배치
  전체가 거절되는 오류는 화면 상단 안내 영역에 표시하며 어느 카드도 성공 처리하지 않는다.
- 서버 저장은 최신 원장을 다시 계산한다. 저장 응답의 최종 재고·단가가 미리보기와 달라졌다면
  성공 결과에는 최종값을 사용한다.
- 완료하면 `N건을 입고했어요`를 표시하고 재료 메인으로 이동한다. 재료·발주·메뉴·매출
  관련 캐시는 한 번만 묶어 무효화한다.

## 4. 서버·원장 계약

### 4.1 입력 형태

새 RPC의 외부 계약은 다음 의미를 갖는다. 실제 DB 식별자는 snake_case를 사용한다.

```text
record_current_quick_inbound_batch(
  p_store uuid,
  p_items jsonb,
  p_request_key uuid
)
```

각 항목은 다음 필드만 허용한다.

```json
{
  "client_item_id": "uuid",
  "ingredient_id": "uuid",
  "vendor_id": "uuid | null",
  "received_quantity": "positive numeric",
  "paid_amount": "positive numeric"
}
```

- `client_item_id`는 카드 생명주기 동안 유지하며 카드 오류·결과·재시도 매칭에 사용한다.
- 각 카드의 E1 멱등성 키는 `p_request_key::text || ':' || client_item_id`로 파생한다. 영수증에도
  이 카드 키를 저장해 동일 배치 안의 서로 다른 카드가 같은 `order_id`나 `inventory_event_id`를
  공유하지 않도록 한다.
- 구매 옵션 ID는 화면 자동 입력의 출처일 뿐 원장 권위 입력으로 사용하지 않는다. E7에는 선택한
  옵션의 구매처와 실제 입력한 양·금액을 저장한다.
- 서버 시각 `clock_timestamp()`와 `store_local_date()`가 발생시각·영업일을 정한다. 기기 날짜를
  쓰지 않는다.

### 4.2 선검증

RPC는 쓰기 전에 모든 항목을 검증한다.

1. 항목 수가 1~20개인지 확인한다.
2. `client_item_id`가 항목 안에서 유일한지 확인한다.
3. 재료가 현재 매장의 활성 재료이고 재고 관리 대상인지 확인한다.
4. 구매처가 있으면 현재 매장의 숨김 처리되지 않은 구매처인지 확인한다.
5. 입고량·결제금액이 유한한 양수이고 기준단위 규칙에 맞는지 확인한다.
6. 알 수 없는 필드, 잘못된 UUID, 중복 필드 의미를 거절한다.

검증 실패 시 어느 E7·E1도 기록하지 않는다. 오류에는 공개 가능한 `client_item_id`와 안정적인
`detail` 코드를 포함하되 다른 매장의 식별자 존재 여부를 노출하지 않는다.

### 4.3 원자 저장

- 배치 하나는 PostgreSQL 트랜잭션 하나에서 처리한다.
- 잠금과 검증 순서는 기존 단건 입고 계약을 따른다.
  1. `assert_my_store(p_store)`
  2. `lock_store_write_scope(p_store)`
  3. `store_id + p_request_key` 범위의 배치 advisory lock
  4. 닫힌 요청 키 확인
  5. 기존 배치 영수증 확인
  6. 전체 카드 선검증
  7. UI 카드 순서대로 E7과 E1 실행
- 별도의 재료 ID 정렬 잠금을 먼저 잡지 않는다. 기존 store write scope와 단건 입고의 잠금 순서를
  바꾸면 오히려 교착 위험이 생기므로 배치도 같은 순서를 유지한다.
- `record_current_quick_inbound`가 기대하는 기존 계약과 같이 배치 실행 시점 `v_now`로
  `costkeep.inventory_event_occurred_at`를 설정하고,
  `costkeep.inventory_stock_already_applied=on`을 배치에서 한 번 설정한 뒤 각 카드에 대해
  `public.quick_inbound(..., store_local_date(p_store, v_now), card_idempotency_key)`를 호출한다.
  카드 처리가 끝나거나 예외가 발생하면 두 GUC를 트랜잭션 범위에서 초기화한다.
- 해당 매장의 재고 실사가 진행 중이면 배치 전체 오류로 거절하고 모든 변경을 롤백한다. 이 판정은
  첫 카드만 확인하는 방식이 아니라 기존 재고 실사 잠금·거절 계약을 배치 전체에 적용한다.
- 각 카드는 `volume=received_quantity`, `amount=paid_amount`, `qty=1`인 직접 입고로 기록한다.
  따라서 포장 개수 추정 없이 실제 들어온 양과 실제 쓴 돈이 기준단가에 반영된다.
- 카드마다 별도 `order_records`와 `inventory_events(E1)`를 남긴다. 화면에서 E7과 E1을 나눠
  호출하지 않는다.
- 한 카드라도 실패하면 같은 배치의 모든 발주 기록·입고 원장·재고·단가 변경·영수증을 롤백한다.
- 기존 공식 `쓴 돈 ÷ 실제 들어온 양`과 연결 메뉴 원가 전파를 그대로 사용한다.
- 동일 재료 카드가 여러 개면 카드 순서대로 기록하되 최종 기준단가는 전체 실제 금액과 실제
  입고량의 가중 결과와 같아야 한다.

### 4.4 배치 멱등성과 결과 확인

새 `quick_inbound_batch_receipts`는 최소 다음을 저장한다.

- `store_id`, `request_key` 복합 기본키
- 서버 멱등 충돌 판정에 사용하는 요청 `jsonb` 원문. 키 순서를 정규화하는 PostgreSQL `jsonb`
  동등 비교를 기존 발주 영수증과 같은 권위 규칙으로 사용한다.
- 카드별 `ingredient_id`, 파생 멱등성 키, `order_id`, `inventory_event_id`, 최종 재고·단가 결과
- `created_by`, `created_at`

새 `quick_inbound_batch_closed_requests`는 resolve가 `not_recorded`로 확정한 키를 별도로 저장한다.

- `store_id`, UUID `request_key` 복합 기본키
- `actor_id`, `closed_at`

처리 순서는 다음과 같다.

1. store write scope 뒤 `store_id + request_key` 범위의 advisory lock을 잡는다.
2. 잠금 직후 닫힌 키를 확인하고 존재하면 SQLSTATE `45010`으로 거절한다.
3. 같은 키의 영수증이 있으면 payload가 같을 때 기존 결과와 배치 수준 `duplicate=true`를 반환한다.
   개별 카드가 중복인지로 배치의 `duplicate`를 판정하지 않는다.
4. 같은 키인데 payload가 다르면 SQLSTATE `45021`, detail
   `IDEMPOTENCY_PAYLOAD_MISMATCH`로 거절한다.
5. 최초 요청은 모든 E7·E1과 영수증을 같은 트랜잭션으로 저장한다.

응답 유실 복구용 `resolve_quick_inbound_batch(p_store, p_request_key)`를 추가한다.

- resolve는 닫힌 키를 기록하므로 `VOLATILE` 함수로 선언한다.
- writer와 같은 `assert_my_store` → store write scope → store+batch advisory lock 순서를 사용한다.
  진행 중 writer가 있으면 같은 잠금에서 기다린 뒤 결과를 판정한다.
- 잠금 획득 뒤 영수증이 있으면 `recorded`와 기존 카드별 결과를 반환한다.
- 영수증이 없으면 closed table에 요청 키·사용자·시각을 기록하고 `not_recorded`를 반환한다.
- 닫힌 키로 뒤늦은 쓰기가 도착하면 거절한다. 확인 뒤 새 저장은 새 요청 키를 사용한다.
- 앱은 전송 전에 작은 대기 기록만 영속화한다: 사용자·매장 범위, 요청 키, payload hash, 카드 수.
  앱의 payload hash는 대기 건 표시·로컬 진단용이며 서버 멱등 판정이나 재전송 허용 판단에 사용하지
  않는다. 서버의 영수증 `jsonb` 동등 비교만 payload 일치 여부의 권위다.
  전체 카드 payload를 SecureStore 한 값에 넣지 않는다.
- 대기 기록이 남아 있으면 새 배치를 보내기 전에 반드시 resolve한다. `recorded`면 재전송 없이
  성공 처리하고, `not_recorded`면 새 키로 사용자가 다시 저장할 수 있게 한다.

### 4.5 미리보기 응답

`quick_inbound_batch_preview(p_store, p_items)`를 추가한다. 쓰기 RPC와 같은 입력 검증·단가 공식을
사용하되 원장을 변경하지 않는다. 결과는 입력 순서를 보존한다.

```json
{
  "items": [
    {
      "client_item_id": "uuid",
      "stock_before": 0,
      "stock_after": 0,
      "inbound_unit_price": 0,
      "base_price_after": 0,
      "affected_recipes": 0
    }
  ]
}
```

같은 재료가 반복되면 앞 카드의 가상 입고를 다음 카드의 `stock_before`와 단가 분모·분자에 누적한다.
확정값은 쓰기 트랜잭션이 다시 계산해 반환하며 미리보기 응답을 신뢰해 저장하지 않는다.
`base_price_after`만 사용자 화면의 `입고 후 단가`로 사용하고 `inbound_unit_price`는 입력 금액과
입고량의 검산·서버 시험에만 사용한다.

### 4.6 RPC 권한·오류 계약

- 쓰기·resolve RPC는 `security definer`, `set search_path = public, pg_temp`를 사용한다.
- migration은 현재 패턴대로 함수 생성 → owner를 `costkeep_rpc_executor`로 변경 → 함수 생성 권한
  회수 순서를 지킨다. `public`·`anon`의 실행 권한은 회수하고 `authenticated`·`service_role`에만
  실행 권한을 부여한다.
- `assert_no_rpc_overloads`로 동일 이름 overload가 없음을 확인하고 PostgREST schema reload를
  알린다.
- preview RPC는 읽기 전용 `security invoker`를 우선 사용한다. definer가 꼭 필요하면 필요한
  SELECT 권한만 허용된다는 ACL 시험을 추가한다.
- `quick_inbound_batch_receipts`와 `quick_inbound_batch_closed_requests`는 RLS를 활성화하고 현재
  migration 계약에 맞는 owner를 지정한다. `public`·`anon`·`authenticated`의 직접
  SELECT/INSERT/UPDATE/DELETE 권한을 회수하며, 앱은 RPC로만 접근한다. 함수 owner에는 영수증 조회·
  생성과 닫힌 키 조회·생성에 필요한 최소 SELECT/INSERT만 허용하고 UPDATE/DELETE는 허용하지 않는다.
  모든 함수는 `assert_my_store`와 actor 범위를 검사해 다른 매장·다른 사용자의 키를 읽거나 닫지
  못하게 한다.
- 안정 오류 코드는 닫힌 키 `45010`, payload 불일치 `45021` +
  `IDEMPOTENCY_PAYLOAD_MISMATCH`, 일반 입력 검증 `22000` 계열로 고정한다.

## 7. 시험 계획

### 7.1 DB

1. 서로 다른 재료 2건 저장 시 E7·E1·재고·기준단가·구매 이력이 모두 일치한다.
2. 같은 재료 2건을 다른 구매처로 저장해 두 구매 기록과 두 E1 원장이 남고 최종 단가가 맞다.
3. 선검증 이후 첫 카드 E7·E1이 실행된 다음 두 번째 카드 실행 실패를 주입해 첫 카드의 발주·원장·
   재고·단가·추이와 배치 영수증까지 모두 롤백되는지 확인한다.
4. 같은 요청 키·같은 payload 재호출은 기존 결과만 반환하고 원장을 늘리지 않는다.
5. 같은 요청 키·다른 payload는 거절한다.
6. 응답 유실 뒤 resolve `recorded`가 기존 결과를 반환한다.
7. resolve `not_recorded` 뒤 늦게 도착한 요청은 닫힌 키로 거절된다.
8. 다른 매장 재료·구매처, 숨김 구매처, 비활성 재료를 거절한다.
9. 0·음수·무한값·형식 오류·0개·21개 항목을 거절한다.
10. 미리보기와 무경합 확정의 카드별 입고 후 단가가 일치한다.
11. 같은 배치의 두 카드가 서로 다른 파생 멱등성 키·`order_id`·`inventory_event_id`를 가진다.
12. 병렬 동일 키는 한 배치만 기록하고, 서로 다른 키는 기존 store write scope 잠금 순서로 교착
    없이 완료된다.
13. 진행 중 writer와 resolve가 경합하면 resolve가 같은 잠금에서 기다린 뒤 `recorded`를 반환한다.
14. 재고 실사 진행 중에는 배치 전체를 거절하며 E7·E1·재고·단가·영수증이 모두 롤백된다.
15. 앱 역할의 두 신규 테이블 직접 읽기·쓰기를 거절하고 RPC owner도 필요한 SELECT/INSERT 외
    UPDATE/DELETE를 수행하지 못한다. 다른 매장·다른 actor의 요청 키 resolve도 거절한다.
16. E1 뒤 현재 재고·현재 입고 평균과 적용 시점의 현재 메뉴 기준은 최신값을 반환한다. 영업 중·
    브레이크의 시작 원가 스냅샷과 과거 확정 손익은 보존하며 최신 입고 단가로 덮어쓰지 않는다.

### 7.2 모바일·웹

1. `+ 추가` 버튼에 아이콘이 없고 두 메뉴만 올바른 순서로 나온다.
2. `재료 등록`은 기존 경로, `재료 일괄 입고`는 ING-12로 이동한다.
3. 카드 추가·중간 삭제 뒤에도 나머지 입력과 오류가 올바른 카드에 남는다.
4. 카드가 정확히 4행이고 결제금액·입고 후 단가만 2열이다.
5. 구매 옵션 선택이 값을 채우고 사용자가 결제금액·입고량을 수정할 수 있다.
6. 미선택 구매처로 저장할 수 있다.
7. 같은 재료를 여러 카드에 선택할 수 있고 배치 미리보기 순서를 보존한다.
8. 카드 입력 수정·삭제 즉시 이전 미리보기 결과를 무효화하고, 요청 payload 판본이 현재 draft와
   일치하는 응답만 반영해 지연 응답이 다른 카드나 새 입력을 덮지 않는다.
9. 한 카드 오류가 전체 저장을 막고 해당 필드로 안내한다.
10. 재고 실사 중 같은 배치 전체 오류는 화면 상단에 표시하며 카드 일부를 성공 처리하지 않는다.
11. 저장 버튼 연타, 화면 중복 진입, 응답 유실 복구가 중복 입고를 만들지 않는다. 앱 재시작 뒤
    draft가 없어도 write/resolve 결과의 `ingredient_id`로 필요한 캐시를 무효화한다.
12. `unit_price_digits`를 바꿔도 결제금액·입고량 제출 payload는 같고 단가 표시 자릿수만 바뀐다.
13. 성공 문구는 중복 재료 카드도 포괄하도록 `N건을 입고했어요`로 표시한다.
14. 성공 후 재료 목록·상세·재고 내역·발주·연결 메뉴 원가가 다시 조회된다. 캐시 무효화는 서버의
    최신 응답을 다시 읽는 동작이며 영업일 원가 스냅샷을 현재 단가로 덮어쓰지 않는다.
15. 키보드 확대, 긴 재료·구매처 이름, 화면 읽기 순서, 44pt 터치 영역을 확인한다.

## 10. 수락 기준

- 사용자에게 보이는 4행 카드와 진입 메뉴가 2절 요구사항과 일치한다.
- N개 카드 저장은 N개의 구매 기록과 E1 원장을 만들며 일부 성공 상태가 존재하지 않는다.
- 같은 요청의 재시도·응답 유실 복구·동시 제출에서 재고가 한 번만 증가한다.
- 입고 후 단가와 최종 기준단가는 앱 계산값이 아니라 서버 응답이다.
- 저장 뒤 재료 재고·재고 내역·구매 내역·연결 메뉴 원가·매출 원가가 같은 확정 원장을 본다.
- 신규 RPC는 인증 사용자에게 필요한 실행 권한만 갖고 다른 매장 데이터를 읽거나 쓰지 못한다.
- 관련 시험과 전체 필수 게이트가 통과하고 독립 검수의 필수 Finding이 남지 않는다.
