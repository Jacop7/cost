## 1. 현재 코드와 교체 경계

현재 구현은 다음 결합 때문에 화면만 바꿀 수 없다.

- `SalesHomeScreen.tsx`가 오늘 판매 입력, `BusinessDayBar`, `useSaveSale`, 부족 확인, 기타 매출·지출 입력을 한 화면에서 수행한다.
- `SalesExpenseScreen.tsx`와 `SalesPastEditScreen.tsx`가 각각 `save_sale` 또는 `amend_ended_business_day`를 직접 호출한다.
- `queryClient.ts`의 `qk.businessDay`와 `invalidateOn.businessDay()`가 수동 영업 상태를 매출·재고·메뉴 갱신의 기준으로 사용한다.
- `business-day/businessDay.ts`와 `BusinessDayBar.tsx`가 `transition_business_state` 및 자동 마감 상태를 사용자 행동으로 노출한다.
- DB의 `save_sale`, `amend_ended_business_day`, `business_day_state`, `transition_business_state`, 자동 마감 함수는 `business_days.status=open|break|closed`를 전제로 한다.
- 기존 `sales_day`와 `sales_range`는 장부 없는 날짜를 작성 상태가 아니라 빈 결과로 취급한다.
- `change_stock_quantity`의 `deduct`는 단일 식재료 E5를 호출한다. 새 계약에서는 이 경로를 `relative_adjustment`로 분리해야 한다.

새 기능을 기존 함수 본문 문자열 치환으로 추가하지 않는다. 새 테이블과 새 RPC를 먼저 배포하고, 호환 조회를 거쳐 앱을 전환한 뒤 구형 공개 쓰기 RPC를 닫는다.

## 2. 데이터 모델

### 2.1 날짜·계산 기준

`sales_calendar_days`

- PK `(store_id, business_date)`
- `day_kind`: 제품 경로는 `expected | closed`. 기존 enum의 `unclassified`는 전환 호환 예약값이며 생성기·백필은 발행하지 않는다.
- `source`: 제품 경로는 `operating_rule | manual_extra | manual_closed | migrated_ledger`. `migrated_unknown`은 전환 호환 예약값이다.
- 생성 당시 `operating_rule_revision`, `timezone_id`, `local_date`, `sales_date`, `scheduled_open_at`, `scheduled_close_at`
- `revision`, `created_at`, `updated_at`
- 확정 장부나 활성 초안이 있으면 `closed` 전환을 거부한다.
- 수동 분류는 사유·실행자·시각·전후 kind/source/revision을 `sales_calendar_day_revisions`에 append-only로 남긴다.

`sales_basis_versions`

- 매장 단위 불변 매니페스트: 메뉴 판매가·판매 상태, 레시피 구성, 재료 평가 단가, 세금, 고정 지출률·근거 월
- `(store_id, effective_from_business_date, revision)` 유일
- `basis_quality`: `exact | legacy_unrecorded | estimated_current`
- 완성된 매니페스트 JSON의 SHA-256을 저장하고 초안·확정 판본은 ID로만 참조한다.
- 설정 저장과 월 경계 생성은 동일한 `resolve_sales_basis_version(store,date)`를 사용한다.

`sales_lifecycle_cutover_state`

- 매장당 한 행이며 `phase=legacy_active | draining | freezing | active | blocked`, phase revision, 계획한 freeze 시각, `inventory_reference_sales_date`, 전환 영수증 ID를 보존한다.
- `legacy_active → draining`과 조건부 `draining → legacy_active|blocked`, `draining → freezing`, `freezing → active|blocked`만 허용한다. 자동 복귀는 freeze 영수증·새 수명주기 원장·실사·컷오프 변경이 모두 없을 때 같은 공통 전환 잠금 안에서만 성공한다.

`publish_sales_basis_version(store,source_kind,source_id,source_revision,effective_from)`은 공통 매장 잠금 아래 대상 적용일에 유효한 source 판본들을 합성해 전체 매니페스트를 만든다. 현재값을 복사하지 않으며 더 이른 변경이 기존 미래 적용일 경계에 영향을 주면 그 경계에도 새 합성판본을 append한다. 기존 판본·고정 초안·확정 판본은 불변이다. `(store_id,source_kind,source_id,source_revision,effective_from)` 유일 제약으로 재시도를 멱등 처리하고 무변경이면 기존 판본을 반환한다. 조회용 `resolve_sales_basis_version`은 판본을 만들지 않는다. 매니페스트 입력을 바꾸는 모든 쓰기 RPC는 같은 트랜잭션에서 이 publisher를 호출해야 하며 아래 표는 최소 목록이다.

`sales_basis_publisher_state`는 매장·source kind·source ID별로 publisher가 마지막으로 처리한 최신 source revision과 처리 시각을 보존한다. `preview_sales_draft`·첫 `save_sales_draft`·`finalize`는 이 처리 revision을 현재 권위 source revision과 비교한다. 하나라도 다르면 `BASIS_STALE`로 거부하고 누락 publisher 경로를 감사 로그에 남긴다. 과거 적용일에 정상 고정된 매니페스트 revision이 현재 최신 source revision보다 오래됐다는 이유만으로 거부하지 않으며, 핀된 매니페스트는 해당 날짜의 as-of 유효성만 별도로 확인한다. 조회나 finalize가 자동으로 판본을 만들어 누락을 숨기지 않는다.

| 발행 쓰기 경계 | 발행 시점과 적용일 |
|---|---|
| 메뉴 등록·판매가·판매 상태·레시피 구성·복구·삭제 | 변경 RPC와 같은 트랜잭션, 서버 `next_sales_basis_effective_date` |
| E1 입고·E11 취소·흡수 경제 정정, 호환 `save_ingredient`의 구매가격·용량·`cost_scope`·단가 override 중 평가단가가 실제로 바뀐 경우 | 원가/수량 원장 확정 뒤 같은 트랜잭션, 다음 적용 영업일 |
| 매장 세금 프로필·가격 기준·메뉴 세금 override 등록·수정·복구 | 세금 설정 revision 확정 뒤 같은 트랜잭션, 서버 적용일 |
| 고정 지출 항목/평균기간 설정 완료, 마지막 대상월 재입력·취소·정정 | 고정 지출 basis revision 확정 뒤 같은 트랜잭션, 다음 적용 영업일 |
| 영업시간·휴무 규칙·시간대 설정 | 기존 날짜 원장은 보존하고 새 운영 규칙 적용일로 발행 |
| 매장 월 경계 | 예약 작업 또는 최초 읽기 전 `ensure_sales_month_basis` 명령이 직전 N개 완료 월 표본으로 멱등 발행 |

### 2.2 초안

`sales_day_drafts`

- `id`는 클라이언트 생성 UUID이며 불변이다.
- `(store_id, business_date, draft_kind, base_ledger_revision)`의 활성 행을 부분 유일 제약으로 보호한다.
- `draft_kind`: `initial | amendment`
- `status`: `editing | expired | discarded | finalized`
- `base_ledger_revision`, `basis_version_id`, `draft_revision`, `payload_hash`, `last_saved_by`, `last_saved_at`
- 초안은 확정 장부 테이블과 `inventory_events`를 참조하거나 수정하지 않는다.

초안 자식 테이블은 전체 목표값을 정규화해 저장한다.

- `sales_draft_menu_lines`: 메뉴, 매장·배달·포장 수량, 조리 후 폐기 수량, 안정적인 line UUID
- `sales_draft_etc_lines`: 항목명, 0 이상 단가, 수량, 채널, line UUID. 주문 단위 할인·환불·음수 매출은 이번 전환 범위에서 제외한다.
- `sales_draft_expense_lines`: 항목명, 금액, 메모, line UUID
- 각 배열은 `null=미전송`을 뜻한다. 최초 작성의 `[]`는 항목 없음이지만, amendment에서 기존 line이 있는 배열의 `[]`는 오류다. 전체 삭제도 기존 line별 `deleted=true` tombstone을 보내야 한다.
- amendment 생성은 서버가 최신 확정 판본의 모든 line을 복제한다. 저장 payload도 전체 집합이어야 하며 최신 line ID 누락은 거부한다. 삭제는 명시적 `deleted=true` 또는 메뉴 목표 수량 0으로만 표현한다.

`sales_command_receipts`

- PK `(store_id, command_kind, request_key)`
- `normalized_payload_hash`, `draft_id`, `result`, `created_at`
- 성공 영수증은 편집 기한보다 먼저 조회한다. 같은 키·같은 hash는 같은 성공 결과, 다른 hash는 충돌이다. 빠른 1차 조회 뒤 신규 후보는 공통 매장/요청 잠금을 얻고 영수증을 다시 조회한다. 두 번째 조회와 hash 판정이 revision·편집창·컷오프 검사보다 먼저여야 동시 동일 요청의 늦은 호출이 성공 영수증을 받는다.
- `get_sales_command_receipt(p_store,p_command_kind,p_request_key,p_payload_hash)`는 인증 사용자와 매장 소유권을 확인해 동일 hash의 성공 결과만 반환한다. 다른 사용자·매장·hash는 존재 여부를 누설하지 않고 거부한다.

### 2.3 확정 판본

`sales_day_versions`

- `(store_id, business_date, version_no)` 유일, 불변
- `source_draft_id`, `basis_version_id`, `basis_quality`, 사용자 입력 전체, 서버 계산 결과, 확정자·확정 시각
- 날짜 현재 판본 포인터는 `sales_day_heads(store_id,business_date,current_version_no,revision)`로 분리한다.
- 기존 `business_days.snapshot`, `daily_sales`, `business_day_revisions`는 전환 기간 호환 출력과 감사 입력으로 유지한다.
- 확정 금액은 `listed_total`, `customer_total`, `net_sales`, `tax`를 각각 저장한다. 사용자 표시 `매출`과 채널 배분 분자·분모는 `customer_total`, 손익 공식은 `net_sales`를 사용한다. 고정 지출률을 산출하지 못한 판본은 `fixed_rate=null`을 보존하고 0으로 바꾸지 않는다.
- 합계 불변식은 `day.customer_total = Σ channel.customer_total = Σ menu.customer_total + Σ 기타매출.customer_total`이다. 메뉴와 기타매출의 구성 항목별 서버 계산 결과를 통화 최소단위로 합산해 일·채널·행 합계를 정확히 일치시킨다. `range`는 날짜별 최신 확정 판본만 더한다. 고정 지출률 null 날짜가 있으면 고정 지출 포함 기간 지표를 null과 `uncomputed_day_count`로 반환한다. 이관 판본의 누락 `customer_total`은 `listed_total`을 `estimated_current`로 표시해 사용하고 `estimated_day_count`를 반환한다.

재고 사건에는 다음 식별자를 추가한다.

- `business_date`, `source_draft_id`, `from_version`, `to_version`, `source_line_kind`, `source_line_id`
- 유일 제약 `(source_draft_id,source_line_kind,source_line_id,ingredient_id,type)`
- `source_line_kind`는 적어도 `menu_sale_consumption`과 `menu_cooking_waste`를 별도 check/enum 값으로 강제해 같은 판매행·재료의 두 보정 사건이 충돌하지 않게 한다.
- E8은 재료 차감, E9는 재료 복원이며 같은 목표값은 새 사건을 만들지 않는다.
- `sales_inventory_delta_components`는 판매 line·ingredient·version별 증분 quantity, 불변 component ID, `stock_effect=normal|absorbed|resolved_by_count`, count batch 연결, 상쇄 quantity를 보존한다. 감소는 미상쇄 component를 최신 version/component ID 역순으로 배정해 흡수 component에는 stock 0, 정상 component에만 E9를 만든다.

### 2.4 전 매장 실사와 원장 컷오프

`inventory_count_batches`

- 불변 배치: `id`, `store_id`, `counted_at`, `cutoff_business_date`, `event_sequence_high_watermark`, `request_key`, `payload_hash`
- `inventory_count_lines`: 배치·활성 재고 추적 식재료별 `counted_quantity`, E5 사건 ID. 입력 확정 시각은 실제 계수 시각으로 간주하지 않는다.
- 한 배치는 활성 재고 추적 식재료 전체를 포함한다. 누락이나 중복이 있으면 전체 롤백한다.

`inventory_count_sessions`

- 상태는 `active | completed | cancelled | expired | invalidated`이며 매장당 active 하나만 허용한다. 서버 `expires_at=observation_started_at+4시간`, 명시 취소, 모든 관련 쓰기 진입점의 지연 만료 처리로 앱 종료 뒤 영구 차단을 막는다. CAS 실패는 예외 롤백 대신 세션을 `invalidated`로 보존한 구조화 결과를 반환한다.
- 실사 시작 시 `observation_started_at`, 공통 매장 쓰기 revision, 활성 대상 식재료와 미해결 모호 사건 재료의 합집합, 각 재고 revision, 사건 sequence 상한을 관측 토큰으로 고정한다. 화면과 시작·완료 확인은 관측 구간 동안 물리 입고·폐기·사용·이동을 멈추도록 요구하고, 활성 세션 중 일반 재고 쓰기와 판매 완료를 서버가 막는다.
- 완료 시 대상 집합·재고 revision·사건 상한을 모두 CAS 검증한다. 관측 뒤 입고·폐기·판매·조정·식재료 활성 변경이 하나라도 있으면 전체 실사를 다시 시작한다.
- 현재 추천 `sales_date`는 서버 매장 시각이 오늘 예정 시작 전이거나 오늘이 휴무이면 달력상 전날, 그 밖에는 오늘이며 예정 시작이 없는 날은 서버 날짜 전환 시각을 경계로 한다. 이 추천일이 이미 작성 완료 또는 휴무일 때만 관측 토큰을 발급한다. 미작성·작성 중·수정 중이면 발급하지 않는다.

`stores`에 `inventory_cutoff_business_date`와 `legacy_inventory_cutoff_business_date`를 둔다. `00108` expand 단계에서는 nullable로 추가하고 구형/신형 쓰기가 NULL을 안전한 보수 값으로 처리한다. `00111`에서 모든 기존 매장을 멱등 백필하고 누락 0건을 검증한 뒤 NOT NULL을 validate한다. 유효 컷오프는 두 값의 최댓값이다.

`inventory_events`에는 다음을 추가한다.

- `business_date`와 서버 단조 증가 `seq`
- `reported_count_delta`: 실제 발생량. 일반 사건은 `count_delta`와 같다.
- `absorbed_by_count_batch_id`: 실사 전 발생·실사 후 기록된 사건을 서버가 최초 후속 배치에 귀속한다. 흡수 후보 비판매 사건은 정확한 `occurred_at`이 필수이며 입력 시각이나 자정을 기본값으로 쓰지 않는다.
- 흡수 사건은 `count_delta=0`, `reported_count_delta=실제량`이다. 재고 합은 `count_delta`, 원가·폐기 손실·입고 감사는 `reported_count_delta`를 사용한다.
- `reported_count_delta`는 기준단위의 부호 있는 값이다. legacy NULL은 `count_delta`로 읽고, E2 `volume_delta=abs(reported_count_delta)`, 입고는 `received_qty×volume` 환산량과 주문 금액을 함께 보존한다.
- high-watermark 전에 정상 기록돼 뒤 실사에 포함된 사건의 취소도 재고를 역분개하지 않는다. 실제 반품은 현재 물리 사건, 기록 오류는 `count_delta=0` 경제 정정 사건이다.
- 일괄 E5와 흡수 사건은 수량 취소·역분개하지 않는다. 잘못된 경제 수량·금액·E2 손실은 불변 원본과 `absorbed_financial_correction` 차이 사건으로 전진 정정한다.
- `observation_started_at <= occurred_at <= counted_at`인 지연 입력은 흡수 여부를 확정할 수 없으므로 `ambiguous_during_count` 경제·감사 사건과 `inventory_recount_required`를 만든다. 재실사 전 일반 재고 쓰기는 막고 아래 복구 모드만 허용한다.

실사 관측 상한은 전역 sequence의 `currval`이 아니라 공통 매장 잠금 안에서 조회한 해당 매장의 **커밋된** `max(inventory_events.seq)`다. sequence gap과 다른 매장 사건은 CAS 실패 원인이 아니다. 별도 `inventory_store_write_state.revision`은 사건이 없는 활성 식재료 변경도 검출하도록 같은 잠금에서 증가한다.

재실사 필요 상태는 미해결 `ingredient_id` 집합을 보존한다. 복구 실사 대상은 활성 재고 추적 식재료와 이 집합의 합집합이며, 비활성화된 문제 재료도 포함한다. 전부 실측한 새 배치만 같은 트랜잭션에서 상태를 해제한다. 복구 모드는 실사 선행검사와 동일한 `유효 cutoff < D <= 현재 sales_date`의 편집 가능 날짜 전체에서 최초 초안 저장·완료와 활성 수정 초안 완료·폐기를 허용한다. 일반 재고 쓰기, 컷오프 이하 날짜, 편집 기간 밖 판매는 계속 막는다.

비판매 사건의 현재 입력은 서버 현재시각을 봉인하는 `record_current_*` facade로 저장하고, 실사 전 실제 발생·실사 후 입력은 exact `occurred_at`을 받는 `record_delayed_*` facade로만 저장한다. 최초 후속 실사보다 앞선 사건은 stock 0 흡수, 관측 구간 사건은 재실사 대상으로 분류한다. 판매 amendment는 delta 방향별로 판정한다. 감소분은 미상쇄 `sales_inventory_delta_components`를 최신순으로 배정하고 absorbed/resolved component는 seq와 무관하게 stock 0, 정상 component만 후속 batch watermark를 검사해 E9 여부를 정한다. 현재 제품은 판매 증가분의 실제 발생 시각을 신뢰할 수 있게 입력받지 않으므로 컷오프와 겹친 증가분을 모두 `pending_sales_inventory_resolution(draft_id,line_id,base_revision,basis_id,target_hash,delta,reported_at,status)`으로 저장하고 전체 재실사 뒤 stock 0으로 해소한다. exact 시각으로 즉시 E8을 게시하는 경로는 현 판본에 제공하지 않는다.

보류 delta가 있는 amendment는 목표 편집을 잠그고 재실사 후 완료 또는 폐기만 허용한다. `begin_inventory_count`는 이 읽기 전용 보류 초안을 실사 전제의 활성 수정 초안 예외로 인정한다. 후속 전체 실사는 동일 target hash의 보류행을 `resolved_by_count_batch_id`로 원자 연결하고 stock 0 해소한다. 같은 초안 finalize는 연결된 delta를 다시 게시하지 않고 회계 판본만 확정하며 target hash/base revision이 다르면 재사용하지 않는다. 폐기 시 pending은 `abandoned`로 남고 전체 실사가 끝나기 전까지 recount flag를 해제하지 않는다.

모든 재고 쓰기는 공통 `lock_store_write_scope(store_id)`를 가장 먼저 잡고 `날짜/원본 사건 → inventory_states → 발주·판매 상세` 순으로 잠근다. 이 함수는 현행 `lock_business_scope`와 정확히 같은 advisory key namespace를 사용하거나 그 함수를 직접 호출해 구형 쓰기와도 직렬화한다. 서로 다른 key를 쓰는 이름뿐인 공통 잠금은 허용하지 않는다. 트리거는 이 잠금을 처음 잡지 않고 보유 여부를 검증한 뒤 컷오프를 다시 읽는다.

## 3. 서버 RPC 계약

### 3.1 공통 순수 해석기

- `resolve_store_sales_clock(store_id, observed_at)`: 매장 시간대의 `local_date`, 추천 `sales_date`, 예정 시작·종료를 반환한다.
- `ensure_sales_calendar_range(store_id, from, to)`: 누락된 날짜만 멱등 생성하며 과거 행은 운영시간 변경으로 다시 쓰지 않는다.
- `resolve_sales_edit_window(store_id)`: `지난달 1일 ~ 추천 작성 영업일`을 서버 값으로 반환한다.
- `resolve_sales_basis_version(store_id,business_date)`: 날짜에 고정된 초안/판본을 우선하고, 아니면 적용일·revision이 가장 큰 매니페스트를 반환한다.
- `assert_inventory_event_after_cutoff(...)`: 매장 잠금 보유 상태에서 원본 역분개 체인과 유효 컷오프를 검사한다.

### 3.2 작성 RPC

`preview_sales_draft(p_store,p_date,p_draft_kind,p_payload)`

- 쓰기 전에도 서버 계산만 사용한다.
- 해석한 `basis_version_id`, 예상 매출·세금·원가·고정 지출·순이익, 부족 재고를 반환한다.
- 원장과 초안은 변경하지 않는다.

`save_sales_draft(p_store,p_date,p_draft_id,p_draft_kind,p_base_ledger_revision,p_base_draft_revision,p_basis_version_id,p_payload,p_request_key)`

- 영수증 확인 → 공통 매장 잠금 → 편집창·날짜 분류·revision 검사 → 기준 고정 → 초안/자식 전체 교체 → `draft_revision+1` 순서다.
- 초안 저장은 `daily_sales`, 확정 스냅샷, `inventory_events`, `inventory_states`를 바꾸지 않는다.

`discard_sales_draft(p_store,p_draft_id,p_base_draft_revision,p_request_key)`

- 최초 초안은 날짜를 `미작성`으로, 수정 초안은 기존 `작성 완료`로 되돌린다.
- 감사 메타데이터는 남기고 예약량을 즉시 제거한다.

`finalize_sales_day(p_store,p_draft_id,p_base_draft_revision,p_request_key)`

- 영수증 확인이 신규 요청 검증보다 먼저다.
- 공통 매장 잠금 → 날짜·초안·기준·편집창·재고 컷오프 재검사 → 전체 계산 → 확정 판본/E8/스냅샷/요약 → 초안 finalized → 영수증을 한 트랜잭션에서 처리한다. 구형 `save_sale`과 `close_business_day`를 조합해 구현하지 않는다.
- 세금 스냅샷은 초안에 고정한 매니페스트의 frozen tax payload로 만들며 완료 시점의 현재 프로필을 다시 읽지 않는다.
- 최초 작성은 초안의 전체 목표값을 그대로 확정한다. 구형 `apply_sale_items`의 부분 patch 의미에 전체 목표 배열을 그대로 넘기지 않는다.
- amendment 초안은 최신 확정 판본의 전체 line 복제로 시작하고 finalize는 최신 판본 line 집합이 모두 존재하는지 재검사한다. 삭제 표식/목표 0이 없는 누락 line은 오류이므로 네트워크 누락을 삭제로 오인하지 않는다.
- 부족 재고는 전체 필요량을 E8로 기록해 음수를 허용한다.

`finalize_sales_amendment(...)`

- 현재 head와 `base_ledger_revision`을 비교한다.
- 전후 전체 목표값 차이만 계산하며 증가분 E8, 감소분 E9, 동일량 무이벤트다.
- cutoff 이하 완료일도 편집 기간 안이면 회계 정정을 허용한다. 감소분은 component 상쇄로 E9 여부를 판정하고, 증가분은 실제 발생 시각 입력을 받지 않는 현재 제품 계약상 모두 `pending_inventory_resolution`과 전체 재실사로 보수적으로 해소한다.
- 새 불변 판본과 `business_day_revisions` 감사를 함께 기록한다.
- 무변경은 head·수정 시각을 올리지 않고 초안만 finalized 처리한다.

### 3.3 조회 RPC

`sales_feed(p_store,p_from,p_to,p_cursor,p_limit)`

- 서버 날짜, 추천 영업일, 편집창, 기간 요약, 상태 건수, 날짜 카드, 다음 커서를 한 응답으로 반환한다.
- 기간 요약은 최신 확정 판본과 독립 E2 손실만 포함한다. 초안 예상값은 날짜 카드에만 표시한다.
- 빈 날짜는 0원 완료로 만들지 않는다.

`sales_draft_detail(p_store,p_date)`는 활성 초안, 최신 완료 판본, 기준 품질, 예약 재료량, 가능한 행동을 반환한다. 기존 `sales_day`는 읽기 전용 상세 어댑터로 유지하되 새 앱은 이 RPC를 사용한다.

`get_sales_command_receipt(p_store,p_command_kind,p_request_key,p_payload_hash)`는 앱 재시작 복구 전용이다. JWT 사용자와 매장 소유권을 확인하고 같은 hash의 완료 결과만 반환하며 다른 범위의 receipt 존재 여부를 누설하지 않는다.

날짜 원장 보충처럼 쓰기가 필요한 작업은 `ensure_sales_calendar_range` 명령 래퍼로 분리한다. 순수 날짜 해석기와 분석 조회는 `STABLE`을 유지하고 내부에서 몰래 백필하지 않는다.

`begin_inventory_count`와 `commit_inventory_count_batch`는 실사 가능 날짜·미작성·활성 초안·만료 미작성 수와 관측 토큰 CAS를 서버에서 판정한다. 읽기 전용으로 잠긴 `pending_sales_inventory_resolution` amendment만 활성 수정 초안 예외로 두며, commit은 같은 target hash의 pending을 `resolved_by_count_batch_id`로 원자 연결한다. `record_delayed_inbound`·`record_delayed_discard`·`record_delayed_stock_adjustment`·`record_delayed_quick_inbound`는 사건 sequence가 배치 상한 뒤이고 실제 발생 시각이 `observation_started_at` 전이며 해당 식재료 count line이 있는 최초 후속 배치를 서버가 선택한다. 관측 구간 사건은 `ambiguous_during_count`와 재실사 필요 상태로 전환한다. 사용자의 배치 ID나 흡수 해제 값을 받지 않는다.

### 5.1 화면과 라우트

- `SalesHomeScreen.tsx`: 날짜 입력 화면에서 기간 피드 화면으로 교체한다.
- `SalesWriteScreen.tsx`: 새 날짜·초안 이어쓰기·완료 판본 수정의 공통 입력 화면이다.

- 기존 `SalesDayDetailScreen`은 상태별 읽기 전용 상세의 진입점으로 유지한다. 미작성·작성 중에는 빈 분석 대신 안내와 작성 행동을 표시한다.
- `SalesExpenseScreen`의 독립 저장과 `SalesPastEditScreen`의 독립 정정은 제거하고 `SalesWriteScreen` 안의 섹션으로 통합한다. 구 라우트는 새 화면으로 호환 redirect한다.

### 5.2 훅과 타입

`sales/lifecycleContract.ts`에 RPC 응답 파서를 두고 누락 필드를 0/false로 묵인하지 않는다.

- `useSalesFeed(range,cursor)` → `qk.salesFeed(from,to,cursor)`
- `useSalesDraft(date)` → `qk.salesDraft(date)`
- `usePreviewSalesDraft`, `useSaveSalesDraft`, `useDiscardSalesDraft`
- `useFinalizeSalesDay`, `useFinalizeSalesAmendment`

기존 `useSaveSale`, `useAmendPastSale`는 앱 전환 뒤 삭제한다. 쓰기 성공 시 `invalidateOn.salesFinalized(date)`가 `qk.sales`, 해당 날짜 초안/상세, 재고, 발주, 메뉴를 함께 무효화한다. 임시저장은 `qk.salesDraft`, 피드 상태, `qk.inventoryReservations`를 무효화한다. 확정 재고 원장은 갱신하지 않지만 예상 가용 재고와 부족 판정 소비자는 reservation key를 구독해 즉시 다시 계산한다.

`apps/mobile/app/(tabs)/_layout.tsx`의 `useBusinessDay` 관찰자는 삭제만 하지 않고 `useSalesLifecycleClock`으로 교체한다. 이 관찰자는 서버 `local_date`, 추천 `sales_date`, 편집 만료 경계, 현재 basis revision, 매장 ID를 60초와 앱 foreground 때 갱신한다. 날짜·월·basis revision이 바뀌면 feed/draft/entry context, 설정 적용 상태, 메뉴 quote를 해당 범위에서 무효화한다. `useStoreLocalDate`와 `useSalesBusinessDate` 소비자는 이 서버 시계로 통합하며 기기 날짜 계산을 추가하지 않는다.

클라이언트는 UUID 요청 키를 작업 세션 동안 유지한다. 응답 유실 재시도는 같은 키와 같은 payload를 사용하고, 사용자가 값을 바꾸면 새 요청 키를 만든다. `draft_revision` 충돌은 서버 초안을 다시 보여 주며 자동 병합하지 않는다.

완료·수정 완료처럼 원장을 바꾸는 진행 중 명령은 전송 전에 작은 불변 command envelope로 보존한다. envelope에는 사용자·매장·날짜·초안 ID·명령 종류·`p_base_draft_revision`을 포함한 expected revision들·payload hash·request key만 넣고 2,048바이트를 넘으면 전송하지 않고 오류로 처리한다. 전체 목표값은 이미 서버 초안에 있으므로 앱 재시작 뒤 draft ID·revision·hash로 다시 읽어 같은 RPC 인자를 재구성한다. 서버 초안이 없는 실사·경제 정정 명령은 먼저 부작용 없는 `prepared_mutation_commands` 행에 정규화 전체 인자를 저장하고 envelope에는 command ID만 둔다. 같은 사용자/매장 세션에서 `get_sales_command_receipt`로 성공을 복구하고 영수증이 없을 때만 서버 초안 또는 prepared command의 동일 hash를 검증해 재시도한다. 결과 확인 뒤 삭제하며 다른 사용자나 매장에서는 읽거나 재사용하지 않는다. `PendingSalesCommandStore` 어댑터의 native 구현은 작은 envelope만 `expo-secure-store`에, web은 사용자 세션 namespace에 저장하고 로그아웃 시 지운다. 두 플랫폼 모두 크기 상한·직렬화·격리·손상 envelope 폐기 시험을 둔다.

## 6. 이관·배포 순서

1. 새 스키마와 읽기/쓰기 RPC를 비활성 플래그 상태로 배포한다.
2. 날짜 원장과 기준선 v0를 멱등 백필한다. 이 단계는 `inventory_events`와 확정 장부를 쓰지 않는다.
3. 기존 장부와 새 어댑터의 일·기간 합계, 세금, E2, 고정 지출, 재고 checksum을 이중 읽기로 비교한다.
4. 계획한 freeze 후보 시각의 추천일이 작성 완료 또는 휴무가 될 수 있는지 먼저 검사한 뒤 매장 phase를 `draining`으로 바꿔 신규 `open`만 차단한다. 이미 열린 `open/break`에는 구형 save와 정상 close를 허용하고, 운영자가 해당 매장의 마지막 구형 장부를 정상 종료할 때까지 새 수명주기를 활성화하지 않는다. 24시간 매장은 고지한 전환 경계에서 마지막 저장·정상 종료를 한 번 수행한다. 마지막 세션 종료 뒤 서버가 freeze 후보 시각의 추천일을 다시 계산한다. 미작성 상태이면 공통 전환 잠금에서 freeze 영수증·새 수명주기 원장·실사·컷오프 변경이 모두 없음을 확인하고 phase와 구형 open/크론을 `legacy_active`로 원자 복귀한 뒤 전환을 연기한다. 이 무변경 조건이 깨졌으면 자동 복귀하지 않고 전진 복구한다.
5. 열린 세션 0건과 freeze 후보 추천일의 작성 완료/휴무를 모두 확인한 뒤에만 `00112`의 최종 공통 전환 잠금에서 phase를 `freezing`으로 바꾸고 구형 save/amend/E5/입고/폐기/설정 쓰기와 `costkeep-close-due`·`costkeep-apply-breaks`를 차단한다. snapshot, 최신 편집값, pending event ID와 source revision을 불변 전환 영수증에 봉인한다. 정상 종료된 마지막 영업일은 당시 snapshot·판매행·게시 E8 연결을 그대로 가진 완료판본으로 백필하며 초안이나 전량 E8을 만들지 않는다.
6. 같은 동결 구간에서 `00111` 예비 백필 뒤 바뀐 legacy head·snapshot·basis source와 최신 E5를 증분 재백필한다. 구형 부분 E5를 새 count batch로 가장하지 않는다. 모호 E5가 있는 매장은 freeze 시작 시점의 서버 시각으로 계산한 추천일을 전환 영수증의 `inventory_reference_sales_date`로 고정하고, 그 날짜까지를 보수적 legacy cutoff와 `inventory_recount_required`로 설정한다. 동결 구간 전용 전체 실사의 날짜 전제는 실시간 추천일이 아니라 이 고정값으로 판정하며, 전체 실사를 필수 완료한 뒤에만 격리를 해제한다. 봉인한 대기 설정을 적용일 판본으로 변환하고 원장합·재고·요약 checksum을 다시 검사한 뒤에만 phase를 `active`로 바꾼다. 활성화 이후 오늘 날짜는 정상 수명주기로 작성한다.
7. 날짜 보충 작업을 켜고 구형 공개 쓰기 RPC가 `APP_UPDATE_REQUIRED`를 반환하는지 확인한다.
8. 새 앱 피드·작성 화면과 새 RPC를 활성화한다.
9. 첫 새 판매 확정·실사 배치·흡수 사건·컷오프 쓰기 전까지만 플래그와 구형 크론을 되돌릴 수 있다. 그중 하나 이후에는 전진 migration으로만 복구한다.

`costkeep-purge-changes`는 변경 이력 보존 정책에 속하므로 이 전환에서 중단하지 않는다.

### 7.2 실사·경합

- 활성 식재료 누락 배치 거부와 전 식재료 원자 실사.
- 현재 추천 날짜 미완료·작성 중·수정 중일 때 실사 관측 토큰 발급 거부.
- 관측 뒤 재고 사건·식재료 집합 변경에서 완료 CAS 전체 거부.
- 관측 구간의 미기록 물리 사건을 나중에 입력하면 `ambiguous_during_count`·재실사 필요 상태가 생기고 재실사 전 쓰기가 차단되는지 확인.
- 실사 전 기록된 입고/폐기는 허용되고 실측값에 흡수되는지 확인.
- 실사 전 실제 발생·실사 후 입력된 입고/폐기/상대 조정은 자동 선택한 최초 후속 배치의 흡수 사건이며 재고에는 0, 원가·손실에는 실제량으로 반영.
- `occurred_at > counted_at`, 임의 배치 ID, 두 번째 배치 귀속, 흡수 사건 수정/취소 거부.
- 실사와 판매 완료, 실사와 입고, 실사와 폐기 두 세션 경합에서 매장 잠금 순서와 컷오프 가드 검증.
- 컷오프 이하 신규 판매 완료는 차단하되 편집 가능 완료일의 매출 수정은 허용한다. 감소분은 component 상쇄 결과만 E9로 게시하고, 증가분은 시각 추정 없이 보류되어 전체 재실사 뒤 stock 0으로 확정되는지 검증한다.
- 실제 계수 뒤 앱 입력 확정 전 판매처럼 관측 구간에 든 증가분은 즉시 흡수/E8로 단정하지 않고 pending이 된다. 시각 불명 +2 → amendment 잠금 → 보류 초안 예외로 전체 재실사 → 같은 target hash 완료가 재차감 없이 성공하고, 목표 변경·base revision 변경·중복 재시도는 해소 영수증을 재사용하지 못하는지 검증한다.
- 보류 amendment 폐기는 pending을 `abandoned`로 남기고도 전체 재실사를 진행할 수 있으며, 재실사 전 recount flag는 유지되는지 검증한다.
- 실사 전 누락 판매 +2를 absorbed로 추가한 뒤 다시 -2 정정하거나 pending +2를 재실사로 해소한 뒤 -2 정정해도 E9가 생기지 않는지 검증한다. 정상 소비 3과 흡수 소비 2가 섞인 목표를 4 줄이면 최신 component 우선으로 흡수 2는 stock 0, 정상 2만 E9가 되는지 확인한다.
- 컷오프 이하 지연 입고·폐기는 exact `occurred_at` 없는 저장을 거부하고 흡수 명령만 허용한다. 기본 시각·사용자 batch 선택이 없는지 검증한다.
- 일반 재고 역분개 체인 중 하나라도 컷오프 이하이면 차단하고, 판매 완료일 전용 amendment만 별도 흡수 판정으로 허용한다.
- 배치 high-watermark 전에 기록돼 배치에 포함된 사건의 사후 취소는 재고 역분개를 차단하고, 실제 반품과 경제 정정을 분리.
- 일괄 E5 취소·역분개 거부와 흡수 경제 오입력의 stock 0 차이 정정.
- 흡수 경제 정정은 원본 FK·전체 목표·economic_revision CAS·요청 영수증을 검증한다. 폐기 손실 500원→300원 정정은 재고 변화 없이 원본 귀속일 손실만 200원 줄어야 한다.
- 기존 `change_stock_quantity(deduct)`가 E5 컷오프를 만들지 않고 상대 조정 사건을 남기는지 확인.
- 모든 시험 뒤 `sum(inventory_events.count_delta)=inventory_states.stock_total` 검산.
- 실사 영수증 응답 유실 재시도와 다른 payload 충돌을 검증하고 재고 합과 손익을 함께 검산.
- `inventory_events.seq`의 전역 gap이나 rollback과 무관하게 매장 잠금 안에서 `max(committed seq for store)`를 관측 상한으로 쓰는지 검증한다.
- `00111` 예비 백필 뒤 구형 E5·정정이 발생한 업그레이드 fixture를 `00112` 최종 동결이 다시 포착하는지 검증한다.
- D0 실사 뒤 D1 미작성·최초 초안·수정 초안을 각각 둔 상태에서 D2 모호 사건이 생겨도 복구 모드가 검사 범위의 날짜를 완료/폐기/분류하고 전체 재실사로 해제할 수 있는지 검증한다.
- draining 중 legacy 세션은 저장·정상 종료할 수 있고 신규 open은 차단된다. 마지막 정상 종료판본의 snapshot·판매행·E8 연결을 보존해 같은 목표에서 추가 E8이 생기지 않으며, 열린 세션이 있거나 freeze 후보 추천일이 완료/휴무가 아니면 freezing/활성화하지 않는지 검증한다. 자정 뒤 추천일이 미작성으로 바뀌는 24시간 매장은 새 원장·실사·컷오프·freeze 영수증이 없을 때만 컷오버를 원자 취소해 `legacy_active`와 open/크론을 복구한다. 취소 검사와 동시 새 쓰기 경합은 취소 전체를 거부해야 한다.
- 모호한 구형 부분 E5가 있는 매장은 freeze 시작 시 고정한 `inventory_reference_sales_date`로 실사 전제를 판정해 실시간 추천일 변경으로 교착하지 않으며, 보수적 cutoff와 격리 상태에서 동결 구간 전체 실사를 완료하기 전 판매·일반 재고 쓰기를 열지 않는지 검증한다.

### 7.3 앱

- 피드 상태별 카드, 기간 필터, 커서 페이지, 요약에서 초안 제외.
- 미작성 작성, 임시저장 후 이어쓰기, 완료 확인, 완료 수정 초안, 기간 밖 읽기 전용.
- 상세 카드와 작성 버튼의 서로 다른 내비게이션.
- 임시저장 캐시 무효화가 확정 재고를 갱신하지 않으면서 reservation 기반 예상 가용 재고·부족 판정을 갱신하고, 완료만 확정 재고·발주·메뉴를 갱신.
- 오프라인/응답 유실 같은 요청 키 재시도와 revision 충돌 UX.
- 서버 도달 전 종료와 서버 성공 후 응답 유실 각각에서 native SecureStore/web 저장 어댑터의 2,048바이트 이하 command envelope로 영수증 조회 또는 서버 초안/prepared command 기반 동일 인자 재구성이 되는지 확인한다. `p_base_draft_revision` 보존, 크기 초과 전송 차단, 손상 envelope 폐기, 다른 사용자·매장 격리를 함께 검증한다.
- `BusinessDayBar`, `LateCloseSheet`, 상태 전이 호출, 독립 지출 저장 경로가 번들·라우트에서 사라졌는지 검사.
- 작은 화면, 글자 확대, 터치 영역, 상태/링크 대비를 확인한다.
