## 2. 재고 상태 (식재료)

| v3 스펙 | 구현 |
|---|---|
| 충분 / 부족 / 소진임박 (3단계) | **그대로 3단계** — 여유(초록) / 부족(노랑) / 소진 임박(빨강) |

- 한때 2단계로 줄였다가 되돌렸다. 두 번 틀린 자리라 남겨 둔다.
  - ① '부족'을 **'여유'로** 흡수 → 안전재고 미달인데 '여유'로 표시됐다.
    실측 7종. 애호박은 안전선 1,500g 에 재고 720g(48%) 인데 '여유' 였다.
    그게 걸려 옆에 ⚠ 아이콘을 따로 붙였고, '여유 ⚠' 라는 모순이 생겼다.
  - ② 흡수 방향을 뒤집어 '부족'을 **'소진 임박'으로** 보냈다 →
    진간장이 안전선의 **99%**(1,780/1,800) 인데 '소진 임박'이 됐다. 과장이다.
    62~99% 남은 7종이 전부 빨강이 되어 빨강이 의미를 잃었다.
- 둘은 다른 사건이다. 합치면 급한 것과 안 급한 것이 같은 색이 된다.
  - **소진 임박(빨강)** — 지금 없거나 사장님이 곧 없다고 표시했다. 오늘 사야 한다.
  - **부족(노랑)** — 안전선 아래로 내려왔다. 슬슬 시켜야 한다.
- 판정은 `@sikjae/core` 의 `stockBadge` 와 같은 규칙이고, 목록 카드·상세·정렬·
  상단 배너가 **한 함수**(`stockStateOf`)를 공유한다. 흩어지면 화면끼리 다른 말을 한다.
- 상단 빨강 배너는 '소진 임박'만 센다. '부족'까지 넣으면 배너가 늘 떠 있어 아무도 안 본다
  — 부족은 배너 둘째 줄에 건수로만 알린다.
- 발주 후보는 사유 뱃지(안전재고 미달 · 곧 소진) 별도 유지.

## 3. 단위 · 표기 규칙

- **화면 노출 단위는 kg · g · ml + 개수(개/모) 만.** 망 · 통 · 팩 · 박스 · 판 등 구매단위 라벨은 표기에서 제거하고 상품명/거래처로 분리.
  - 예: `양파 1망(1.2kg)` → `양파 · 1.2kg`, `앞다리살 5kg 냉장` → 상품명 `앞다리살 냉장` · 용량 `5kg`.
- **구매 옵션 표기 형식**: `식재료명 · 용량 · 금액` / `구매처 · 단가(원/g)`.
- **단가 미리보기(ING-03/05)**: 구매가 단가 + 실사용 단가(로스 반영) 2값 노출(`@sikjae/core` 계산).

## 7. 레시피 (RCP)

- 리스트 카드: '재료 원가율' → **재료비** 라벨. 숫자 15 / 퍼센트 13.5. **판매가·재료비=그레이, 순이익=블랙**.
- 추가 화면: 재료 행 = 우측 화살표(›) → **사용량 입력 시트(삭제/담기)**. 추가 지출 = 편집행([지출명][금액][X] + 추가).
- 재료 검색·담기(RCP-09): 식재료 리스트 카드 스타일 + 카드 탭 → 사용량 입력 시트(생산량 기준 / 1개당).

## 8. 세금 (0052~0055)

레시피_상세로직_v3 §168 대로 **부가세는 기본 항목이고, 그 밖의 세금·수수료를 사장님이 %로 더한다.**

- `recipes.tax_items` 는 원래 `text[]` 로 있었지만 아무도 쓰지 않았다(전 메뉴 `{}`). `jsonb`
  `[{"name":"카드 수수료","rate":2.5}]` 로 바꿔 살렸다. 계산은 `tax_of()` **한 곳**뿐이다 —
  전에는 다섯 함수가 각자 `10/110` 을 해서, 항목이 생기면 하나만 빠뜨려도 조용히 어긋났다.
- **그날 세금은 매출 줄의 `unit_tax` 에 굳는다.** 판매가·재료비·부자재와 같은 규칙이다.
  카드 수수료를 오늘 새로 넣어도 지난 장부의 세금은 안 움직이고, 다음 영업일 기준부터 반영된다.
- 화면: 레시피 추가/수정의 **세금 시트**에서 항목을 더하고 지운다(합계·비율 즉시 표시).
  레시피 상세의 '세금' 카드와 매출 메뉴 손익의 `(−) 세금` 은 항목별로 펴서 보여 준다.
- ⚠ **배달앱 중개 수수료는 여기 넣지 않는다** — 고정 지출에서 이미 빠진다(0043).
  두 곳에 넣으면 같은 돈이 두 번 빠진다. 시트에 그 안내를 박아 뒀다.
- 권장 판매가 분모도 세금 항목을 포함한다. 부가세만 넣으면 수수료만큼 권장가가 낮게 나온다.

## 9. 영업일 (0048~0050 · 0057)

사장님 결정: **영업 시작 시점의 값으로 하루가 고정된다.**

- 영업 시작 → 그 시점의 판매가·재료 구성(1인분량 + 단가)·부자재·고정지출·세금을
  `business_days.snapshot` 에 굳힌다. 행과 스냅샷이 **둘 다** 있어야 영업 중이다.
- 영업 중에 레시피·식재료를 고치면 **레시피 화면에는 새 값이 보이고**, 오늘 매출·원가·손익은
  시작 기준을 계속 쓴다. 두 화면은 다른 질문에 답한다 — 레시피는 "지금 팔면 얼마 남나",
  매출은 "그날 얼마 벌었나". 고친 값은 다음 영업일 기준부터 들어간다.
- 브레이크타임은 같은 영업일을 유지한다(기준값도 그대로). 영업 종료는 그날 집계를 함께 남기고
  잠근다. 빠뜨린 판매는 **다시 열기**로 넣는다 — 되돌려도 기준값은 시작 때 그대로다.
- 자동 종료는 예정 종료(설정 마감 시각) 뒤에도 활동이 있으면 **마지막 활동 + 1시간**으로 미룬다.
  22:00 마감인데 21:47 에 팔았으면 22:47 이다. 자동으로 닫힌 날은 다음 앱 실행 때 한 번 알리고
  [확인] / [기록 수정] 을 준다 — 사장님이 누른 게 아니라 시간이 눌렀기 때문이다.
- 화면이 네 함수를 따로 묻지 않도록 `business_day_state()` 하나로 모았다(0057).
  상태는 넷이다 — `none`(오늘 아직 시작 전) · `open` · `break` · `closed`.
- 매출 등록이 45001(영업 전)으로 막히면 오류가 아니라 **"오늘 영업을 시작할까요?"** 를 묻고,
  시작하면 방금 누른 판매를 이어서 저장한다. 45002(종료됨)는 다시 열기를 안내한다.

## 10. 매출 화면 전체가 그날 기준 (0058 · 0059)

사장님: "레시피에서 수정값이 매출페이지에 전부 반영되는 거지?"
재 보니 **여섯 군데가 따라 움직이고 있었다.** 메뉴 손익 상세만 고정돼 있고,
합계·분석·되짚기는 현재 값으로 다시 계산해서 같은 화면 안의 두 숫자가 다른 말을 했다.

| 새던 곳 | 원인 | 고침 |
|---|---|---|
| 오늘 손익 · 일 손익 상세 | 고정지출률이 **현재 월** 설정 | 날짜별 그날 률로 배분해 합산 |
| 매출 분석 | 위와 같음 | 위와 같음 |
| 지출 되짚기 · 재료 | 수량은 원장인데 **단가가 현재 값** | `day_unit_price()` — 그날 단가 |
| 지출 되짚기 · 부자재 | **현재 레시피** 구성을 읽음 (지우면 그날 내역에서도 사라짐) | 그날 스냅샷의 `extras` |
| 지출 되짚기 · 고정 | 현재 월 항목·금액 | 그날 `fixed_items` 로 날짜별 배분 |
| 폐기 손실 | 버린 양 × **현재 단가** | 버린 날 단가 |

- 스냅샷에 **재료 단가 맵**(`ingredients`)을 추가했다. 전에는 단가가 레시피 줄 안에만 있어서
  그날 안 팔린 메뉴의 재료와 식재료 폐기(매출과 무관)의 단가를 알 수 없었다.
  0058 이전 스냅샷은 레시피 줄에서 찾고, 그것도 없으면 현재 단가로 떨어진다.
- 덤으로 **되짚기 합계 = 손익의 재료비**가 됐다. 전에는 160,203 대 159,934 로 어긋나 있었다.
- **기간 조회는 평균이 아니라 합이다**(0059, `range_menu_detail`). 사장님: "a재료 값을 10번
  수정했어. 합계해서 보여준다고 해둬 — 어떤 합도 보여줘야 하잖아." 날마다 그날 기준으로 계산해
  더한다. 개당 값은 합 ÷ 수량이라 화면이 '기간 평균'이라 부른다.
- **판매가가 여러 가지였던 기간**은 `price_points` 로 몇 원짜리가 며칠 몇 개였는지 늘어놓는다.
  9,300 / 9,800 / 12,000 을 평균 하나로 뭉개면 사장님이 확인할 방법이 없다.
- 하루짜리 기간 조회 = 그날 조회. 두 함수가 같은 하루를 다르게 말하면 화면이 어느 쪽을
  믿어야 할지 알 수 없다 — 테스트로 못 박았다(12_day_basis).

## 11. 2차 범위 잔재 제거 (0060)

**ORD-04 레시피 계산기(E6)** — 7h-worklog §1132 에서 "P2 — 2차 범위. 구현하지 않는다"로
정했는데 스키마·RPC·타입·발주 후보 사유에는 자리가 남아 있었다. 화면이 없어 아무도 실행할 수
없는데, 발주 후보 사유 목록에는 **'레시피 계산'이 떠 있었다** — 사장님이 고를 수 없는 것을
보여 주고 있었다.

- DB: `e6_recipe_calc` RPC · `recipe_calc_runs` 테이블(행 0) 삭제,
  `candidate_reason` enum 에서 `recipe` 제거.
  ⚠ Postgres 는 enum 값 하나만 못 지운다 — 타입을 다시 만들고 컬럼을 옮겼다.
  `using` 절에는 서브쿼리를 못 써서(`cannot use subquery in transform expression`)
  `reasons::text[]::candidate_reason[]` 원소 단위 캐스팅으로 옮긴다.
- core: `requiredByIngredient` · `shortage`(E6 역산), `PropagationEvent` 의 `E6` 제거.
- types: `RecipeCalcRun` 엔터티, `CandidateReason` 의 `recipe` 제거.
- 앱: 발주 후보 사유 라벨 '레시피 계산' 제거. 서버가 옛 값을 주더라도 화면이 걸러 낸다.

**⚠ 전파 이벤트 번호는 당기지 않는다.** E7(발주 등록)을 E6 으로 옮기면 지금까지 쓴
문서·주석·커밋의 번호가 전부 어긋난다. E6 자리는 비워 둔다.

함께 지운 2차 잔재: Edge Function `alerts-daily`(일일 알림 푸시) · `ocr-parse-order`(발주서 OCR).
1차에서는 둘 다 쓰지 않는다.

1차 발주 후보는 **안전재고 미달**과 **곧 소진** 둘로 뜬다. '수동'은 사장님이 직접 담은 것이다.

## 12. 판매 입력 카드도 그날 기준 (0061)

돈 숫자를 전부 그날 기준으로 고정한 뒤(0051·0058·0059) 다시 훑었더니
**판매를 입력하는 카드 하나만** 현재 레시피를 보고 있었다.

| | 값 |
|---|---|
| 카드에 보이는 판매가 | 20,000원 (`recipe_list` = 지금 값) |
| 실제로 팔면 기록되는 값 | 12,000원 (스냅샷 = 영업 시작 시점) |

스냅샷 모델은 맞는데 **화면이 거짓말을 했다.** 12,000 → 20,000 으로 고친 뒤 그 카드를
눌러 팔면 장부에는 12,000 이 박힌다.

- `day_menu_basis()` — 오늘 팔면 잡히는 값 + 지금 값 + `changed` 플래그를 한 번에 준다.
  카드는 오늘 기준을 그리고, 달라졌으면 그 자리에서 **"수정한 값은 다음 영업일부터 적용돼요"**
  라고 밝힌다. 순이익순 정렬도 같은 기준을 쓴다 — 보이는 값과 정렬 기준이 다르면 안 된다.
- ~~영업 시작 뒤에 만든 메뉴는 '내일부터' 배지로 막는다~~ → **0062 에서 철회.** 아래 참조.
- ⚠ **기준이 굳는 시점은 자정이 아니라 영업 시작이다.** 사장님: "오늘 만든 메뉴라도 영업 전이면
  반영 가능해." 영업 전에는 아직 아무것도 정해지지 않았으므로 만들든 고치든 오늘 장사에 그대로
  들어간다. 막히는 것은 **영업을 시작한 뒤**에 만든 메뉴뿐이다.
  첫 판매가 영업 시작을 겸하는 흐름(45001 → "오늘 영업을 시작할까요?" → 시작 후 이어서 저장)
  에서도 방금 만든 메뉴가 그대로 팔린다 — 테스트로 못 박았다(12_day_basis).
- ⚠ 팔 수 있느냐(판매 중지·재료 부족)는 **지금** 상태로 본다. 재고는 지금 것이고 판매 중지도
  지금 결정이다 — e10 이 판매를 막을 때 쓰는 기준과 같아야 한다.

전수 측정(16개 경로: 입력 카드 · 오늘 손익 · 일 손익 상세 4종 · 매출 분석 · 메뉴 손익 하루/기간 ·
지출 되짚기 3종 · 채널별 매출 · 실제 기록값)에서 **레시피를 흔들어도 전부 고정**임을 확인했다.

## 13. 오늘 기준은 **더할 수 있다** (0062)

사장님: "내일부터 뱃지가 맞냐는거지?"

맞지 않았다. 스냅샷을 굳히는 이유는 **이미 기록된 숫자**가 뒤늦게 움직이지 않게 하려는 것이다.
그런데 오늘 새로 만든 메뉴는 오늘 기록이 하나도 없다 — 오늘 기준에 더해도 움직일 숫자가 없다.
순수한 추가다. 막을 이유가 없었는데, 스냅샷 모델의 부수효과를 규칙인 것처럼 만들어 놨다.

더 흔하고 더 나쁜 경우가 있었다:
> 재료가 떨어져 메뉴를 잠깐 꺼 둔 채 영업을 시작 → 스냅샷에 안 담김
> → 입고돼서 다시 켜도 **오늘 하루 종일 못 판다**

- 오늘 기준에 없는 메뉴는 팔 때 `add_to_day_basis()` 로 **그 시점 값으로 더한다.**
  기존 항목은 손대지 않으므로 이미 기록된 매출·원가·손익은 그대로다(테스트로 확인).
  한 번 더해지면 그 뒤의 수정은 여전히 다음 영업일부터다.
- ⚠ **종료된 영업일에는 더하지 않는다.** 그날 장부는 잠긴 것이다 — 다시 열어야 한다.
- 스냅샷의 레시피 한 벌을 `recipe_snapshot_entry()` 한 곳에서 만든다.
  `build_day_snapshot` 과 추가 경로가 각자 만들면 언젠가 어긋난다(세금 항목에서 이미 겪었다).
- 앱: '내일부터' 배지 제거. 막는 것은 판매 중지·재료 부족 둘뿐이다.

### ⚠ 곁가지로 잡은 것 — 예약 오류 코드

테스트를 쓰다 `exception when others` 가 오류를 못 잡는 걸 발견했다.

| 쓰던 코드 | 실제 뜻 |
|---|---|
| `P0003` | `too_many_rows` |
| `P0004` | `assert_failure` — **`others` 가 잡지 않는다**(Postgres 문서) |

남의 뜻을 가진 코드를 빌려 쓴 것이고, 그중 하나는 아예 잡히지 않아 서버 쪽에서 되돌리기·대체
처리를 넣을 수 없었다. 표준에서 쓰지 않는 45 클래스로 옮겼다 — `45001` 영업 미시작 ·
`45002` 종료됨. 앱은 코드가 아니라 문구로 가려내므로 화면은 그대로다.

## 14. 수정 내역 (0063~0068)

기획: `docs/식재료-레시피-수정내역-최종기획.md`. 식재료 상세와 레시피 상세가
**같은 원장·같은 컴포넌트·같은 판정**을 쓴다.

`↻ 최근 수정 08.18 09:10 · [현재 매출 반영] ›` — 한 줄, 행 전체가 눌리고 목록이 열린다.

- 기존 `price_trends` / `profit_trends` 로는 못 한다(확인함). 전자는 전후값·출처가 없고
  후자는 비율만 있고 금액이 없다. 역할을 가른다 — **trends = 그래프 · 변경 원장 = 읽는 내역**.
- **반영 여부는 저장하지 않는다.** 시간이 지나면 달라지는 값이라 굳히면 거짓말이 된다.
- ⚠ **값 비교로 판정하지 않는다.** 12,000 → 20,000 → 다시 12,000 으로 되돌리면 현재 값과
  스냅샷이 같아져 '반영됨'으로 보이지만 실제로는 둘 다 오늘 매출에 안 들어갔다.
  판정은 **언제 기록됐는가**다 — 그 영업일에 기록됐고 기준 확정 시각보다 나중이면 미반영.
- ⚠ 0062 이후 **기준 확정 시각이 항목마다 다르다**(영업 시작 때 담긴 것 vs 첫 판매로 더해진 것).
  스냅샷 항목에 `basis_at` 을 심어 가린다. 14:00 수정 → 15:00 첫 판매로 합류했으면 반영이다.
- ⚠ `now()` 가 아니라 **`clock_timestamp()`** 다(0068). 한 트랜잭션 안에서 `now()` 는 언제나
  같은 값이라 "영업 시작 직후 수정"이 반영됨으로 잘못 잡혔다 — 테스트를 쓰다 걸렸다.
- 한 번의 저장·입고·전파는 **카드 한 장**이고, 값이 실제로 달라진 필드만 담는다
  (`change_line()`). 같은 값 저장·재계산은 기록하지 않는다.
- 입고 확정 하나가 식재료 이벤트 1건 + 영향받은 레시피 N건을 **같은 `correlation_id`** 로
  남긴다. 그래야 "연결 레시피 2개를 재계산했어요"를 말하고 '일부 메뉴 미반영'을 판정할 수 있다.
  ⚠ 레시피 재료비는 **입고가 반영되기 전에** 잡아야 한다 — 뒤에 재면 전후가 같아진다.
- 커서는 `(occurred_at, id)` 복합이다. 전파는 한 트랜잭션에서 여러 건이 같은 시각으로
  들어가므로 시각만 쓰면 페이지 경계에서 새거나 겹친다.
- `recipes.memo` 추가 — 식재료에는 있는데 레시피에는 없었다. 매출 계산과 무관한 변경이다.
  ⚠ **컬럼과 화면·내역 비교까지 만들어 놓고 `save_recipe` 에 쓰는 자리를 빠뜨렸다**(0071).
  메모를 입력해도 값은 비어 있는데 수정 내역에는 "메모 (없음) → 점심 특선"이 남았다.
  저장이 안 된 것보다 **원장이 거짓말을 한 것**이 더 나쁘다 — 사장님은 내역을 보고
  저장됐다고 믿는다. 메모는 `tax_items` 와 같은 규칙이다 — **키가 있을 때만** 바꾸고,
  내역 비교도 같은 규칙을 쓴다(안 그러면 내역이 또 거짓말을 한다).
  `MemoEditSheet` 를 kit 으로 옮겨 식재료·레시피가 **같은 시트**로 고친다 —
  한쪽만 전체 수정 폼으로 튀면 같은 일을 하는데 손이 달라진다.
- **남은 자동 전파도 남긴다**(0069). 사장님이 직접 고치지 않았는데 숫자가 움직이는 경우:
  ① 고정지출 저장 → 고정지출률 → **전 메뉴** 순이익 ② 입고 **취소** → 단가가 되돌아감.
  고정지출은 담을 엔터티가 없어 영향받은 **메뉴 쪽에** 남기고 `correlation_id` 로 묶는다.
  ⚠ 직전 률은 **저장 직전**에만 알 수 있다(0070). 처음엔 그날 스냅샷의 `fixed_rate` 를
  "직전 값"으로 썼는데, 그건 그날 기준이지 저장 직전 값이 아니라서 **같은 값을 두 번 저장해도
  매번 기록이 쌓였다** — 테스트가 잡았다. `save_fixed_costs` 가 잡아 `e4` 로 넘긴다.
- ⚠ **재고 수정·폐기는 여기 담지 않는다**(기획 §5). 기준단가를 바꾸지 않고 재고 원장이 이미
  단일 출처다 — 두 곳에 적으면 어느 쪽이 맞는지 몰라진다. 내역 화면 맨 아래에서
  재고 변동·구매 이력으로 건너갈 자리만 준다.

## 15. 기준단가는 **양**으로 가중한다 (0072)

사장님: "양이 기본 아니야. 개수랑 이거는 구매 옵션 기록으로 남겨두고"

맞다. 개당 단가를 **팩 개수**로 평균 내면 1kg 짜리 한 개가 20kg 짜리와 같은 무게를 갖는다.

**결정적인 이유 — 이 불변식이 성립해야 한다:**
> 기준단가 × 총 입고량 = 그 재료에 쓴 돈

| 실측: 1kg 5,300원 + 20kg 80,000원 (쓴 돈 85,300 / 들어온 양 21,000g) | 21,000g 을 매기면 |
|---|---|
| 개수 가중 4.6500원/g | 97,650원 — **없는 돈 12,350원** |
| 양 가중 4.0619원/g | 85,300원 — **실제 쓴 돈** |

- **개수는 사라지지 않는다.** `order_records` 에 팩 용량·팩 금액·받은 개수가 그대로 남고
  구매 이력 화면이 보여 준다. **개수는 기록, 가중치는 양**이다.
- **재고도 같은 분모를 써야 한다.** 입고는 이제 **그 발주의 팩 용량**으로 환산한다.
  ⚠ 전에는 마스터 `per_volume` 을 썼다 — 마스터가 3kg 인데 5kg 짜리를 사 오면
  재고는 3,000g 만 늘고 단가는 5,000g 기준이라 **2,000g 이 증발**했다(실측).
  이건 빠른 입고 이전에도 있던 버그다. 마스터 `per_volume` 은 이제 **기본값**이다.
- `packages/core` 의 `weightedAvgUnitPrice` 도 같이 바꿨다(절대원칙 3). parity 테스트에
  팩 용량이 섞이는 경우를 추가했다 — 전에는 전부 같은 용량이라 두 공식이 구별되지 않았다.
- ⚠ **지금 데이터에서는 차이가 0** 이다. 모든 재료가 한 가지 팩 용량으로만 들어왔기 때문이다.
  빠른 입고로 여러 용량을 섞을 수 있게 되는 순간부터 갈라진다 — 그래서 검산값이 안 움직인다.
- 이동가중평균(입고마다 남은 재고 기준 갱신)은 1차에 넣지 않는다. 지금은 `order_records` 에서
  매번 재계산하는 무상태 구조라 입고 취소(E11)가 자유롭다. 상태를 저장하면 그게 흔들린다.

## 16. 안전재고도 기준단위로 (0073)

재고는 0056 에서 기준단위 총량으로 통일했는데 **안전재고만 개수**로 남아, 비교할 때마다
`safety_stock × per_volume` 로 환산했다. 0072 이후 `per_volume` 은 **기본값**일 뿐이라
그 환산이 설 자리가 없다(절대원칙 1: 저장은 항상 최소단위).

**실측된 피해** — 사장님이 "우리는 5kg 짜리 산다"며 **팩 용량만** 고쳤더니:
> 안전재고 기준이 3,000g → 5,000g 으로 소리 없이 바뀜. 안전재고는 건드리지도 않았다.

- `ingredients.safety_stock` 을 기준단위로 옮겼다(기존 값 × `per_volume`, 한 번만 도는 표식 포함)
- `refresh_order_candidate` · `order_board` 의 환산 제거, 앱 `belowSafety` 도 같이
- 입력 화면이 개수(`개`) 대신 **용량과 같은 단위**로 받는다 — 저장 직전 `displayToBase` 로 환산
- ⚠ **최소 발주량은 개수 그대로**다. 발주는 팩 단위로 하므로 개수가 맞는 단위다.
  추천 발주량을 낼 때 `per_volume` 으로 나누는 것도 그대로 — "몇 팩 사세요"의 기본값이다.

## 17. 재고 추가 · 빠른 입고 (0074, ING-03b)

프로토타입: `docs/prototypes/ingredient-stock-add.html`

지금 재고를 늘리는 유일한 길은 **발주 → 입고 확정** 2단계였다. 시장에서 그냥 사 온 걸
넣으려면 있지도 않은 발주부터 만들어야 했다 — 사장님 머릿속에 없는 단계다.

**⚠ 재고 수정에 녹이지 않았다.** 결과가 완전히 다르기 때문이다.

| | 재고 | 기준 단가 | 연결 메뉴 원가 |
|---|---|---|---|
| 재고 수정 (실사, E5) | 바뀜 | 그대로 | 그대로 |
| 재고 추가 (입고, E1) | 바뀜 | **바뀜** | **전 메뉴 바뀜** |

같은 시트의 탭으로 두면 "숫자를 올린다"는 같은 손짓이 한쪽은 아무것도 안 건드리고
한쪽은 전 메뉴 손익을 움직인다. 진입점을 가르고, 재고 수정 시트에는
*"새로 사 왔다면 → 재고 추가"* 한 줄을 뒀다.

- **한 RPC**(`quick_inbound`) — 화면에서 e7 → e1 을 두 번 부르면 중간에 끊겼을 때
  "발주는 있는데 입고는 안 된" 유령 발주가 남고 사장님은 정리할 방법이 없다.
- **멱등키** — 버튼을 두 번 누르면 두 번 입고된다. 같은 키면 발주를 만들기 **전에** 막는다
  (e1 안에서만 걸러도 발주는 이미 생긴 뒤다).
- **미리보기는 서버가 낸다**(`quick_inbound_preview`). 앱이 따로 계산하면 확정 후 숫자와
  갈리고, 4.81 을 보고 눌렀는데 4.85 가 되면 그 화면을 두 번 다시 안 믿는다.
  테스트가 `미리보기 = 확정 후`를 못 박는다.
- 발주 기록은 **남긴다**(`source='manual'`). 기준단가가 그 기록에서 나오므로 기록 없이
  재고만 늘리면 단가를 계산할 수 없다. 구매 이력에도 그대로 보인다.
- 구매 옵션을 고르면 용량·금액이 따라온다 — 사장님이 칠 건 **"몇 개"뿐**이다.
  실제 결제금액은 고칠 수 있다(할인·배송비가 붙는다).
- 지난 날짜로도 넣을 수 있다. ⚠ 그날 매출 원가는 안 바뀐다(0058, 스냅샷) — 화면이 밝힌다.

## 18. 기준 단가 + 구매 이력을 한 카드로 (ING-03)

프로토타입: `docs/prototypes/ingredient-price-inbound-history.html`

따로 있으면 "5.00원/g" 이 어디서 나왔는지 두 카드를 오가며 맞춰 봐야 한다.
숫자 바로 아래에 근거를 붙였다.

합치면서 **표시 오류 두 개**를 같이 고쳤다.

- ⚠ **금액이 팩 1개 값인데 총액처럼 보였다.** 화면은 "1kg × 3개 · 4,000원" 이라 했지만
  실제 결제는 **12,000원**이었다(실측). 이제 `팩 금액 × 받은 개수` 로 보여 준다.
- ⚠ **단가에 안 들어간 기록이 섞여 있었다.** 입고 대기·취소는 단가를 만들지 않는데
  같은 목록에 있으면 "이것도 반영됐나?" 를 만든다. `입고 완료 · 부분 입고`만 남기고
  머리말에 **"단가 계산에 포함된 기록"** 이라고 밝힌다.
- **표기는 `총 6kg (3kg × 2개) · 30,000원`** — 들어온 **양이 먼저**다.
  재고에 실제로 더해진 값이고 팩 구성은 그 근거다. 팩이 하나뿐이면 괄호를 뺀다
  (`총 3kg · 15,600원` — 같은 숫자를 두 번 말하지 않는다).
  `packSummary()` 한 곳에서 만든다 — 세 화면(기준 단가 카드 · 구매 이력 · 입고 예정)이
  각자 조립하면 언젠가 갈린다.
  ⚠ 입고 예정은 아직 안 받았으므로 `receivedQty` 를 넘기지 않는다 — 넘기면 `총 0kg` 이 된다.
- 부분 입고는 `총 3kg (3kg × 2개 중 1개) · 14,400원 반영` + `도착분만 반영` 로 도착분만
  셈에 들어갔음을 드러낸다(0038: 안 온 물량은 평균을 끌면 안 된다).
- 최저·최고를 만든 줄에 배지를 단다 — 어느 구매가 그 값이었는지 바로 보인다.

## 19. 수정 내역 보관 정책 (0076)

사장님 결정:
> 사용자는 최근 7일 확인 → 서버는 문제 확인을 위해 30일 보관 → **핵심 장부는 영구 보존**

| | |
|---|---|
| 화면 | 최근 **7일**만 표시 |
| `entity_change_events` | **30일** 뒤 자동 삭제 |
| `updated_at` | 계속 유지 |
| 재고 원장 · 구매/입고 이력 · 매출 장부 · 영업일 스냅샷 · 가격/손익 추이 | **삭제하지 않음** |

**이 정책이 안전한 근거는 하나다** — 수정 내역을 통째로 지워도 재고·단가·손익이
하나도 안 움직인다. 그게 사실인지 테스트가 확인한다(`16_change_retention`):
기준단가·재고·재료비·순이익·원장 건수·구매 이력·추이·그날 스냅샷 전부 불변.

- 청소는 **영업 시작**에 붙였다. pg_cron 도 쓸 수 있지만(미설치) 스케줄러를 하나 더
  들이면 그게 도는지를 또 봐야 한다. 영업 시작은 하루 한 번 자연스럽게 도는 자리다.
  며칠 쉬어 안 돌면 그동안 안 지워질 뿐, 잘못된 값이 생기지는 않는다.
  ⚠ 청소가 실패해도 영업 시작은 막히지 않는다 — 곁일이다.
- ⚠ **`security definer` 여야 한다.** 테스트를 쓰다 걸렸다 — `invoker` 로 두면 RLS 에
  막혀 **0건 삭제하고 조용히 성공**한다. 보관이 도는 줄 알았는데 아무것도 안 지워진다.
  그렇다고 DELETE 정책을 열지는 않았다. 이 원장은 append-only 이고, 지우는 길은
  **나이로만** 지우는 함수 하나뿐이어야 한다.
- 화면 아래에 정책을 밝힌다 — *"수정 내역은 최근 7일만 보여 주고 30일 뒤 지워져요.
  입고·재고·구매 기록과 가격·손익 추이는 그대로 남아요."* 없으면 "내 기록 어디 갔지?"가 된다.

### 전파 행을 1건으로 합치는 건 하지 않았다

식재료 단가 하나가 레시피 N개로 퍼질 때 행이 N+1개 생긴다. 합치자는 제안이 있었지만
**재 보고 접었다.**

| | |
|---|---|
| 실측 행 크기 | 식재료 304B · 레시피 432B |
| 30일 부피 (입고 5건/일 × 연결 5메뉴) | 약 **361 KB** |
| 레시피 행을 없앴을 때 절약 | 약 **316 KB / 월** |

보관 30일이 이미 증가를 묶어 놔서 절약이 월 0.3MB다. 반면 레시피 행이 담은
**재료비·순이익 전후값은 메뉴마다 다르다** — 복제가 아니라 서로 다른 데이터다.
그걸 버리면 "왜 이 메뉴 원가가 올랐나"에 답할 수 없다. 0.3MB 와 그 답을 바꾸지 않는다.

## 20. 메모는 수정 내역에 남기지 않는다 (0077)

사장님: "식재료 수정에 메모는 포함되지 말아야 해"

수정 내역은 **왜 값이 바뀌었나**를 답하는 자리다. 메모는 어느 계산에도 들어가지 않는
자유 기록이라, 거기 섞이면 진짜 변경을 밀어낸다 — 화면은 최근 7일치만 보여 준다(0076).

- 식재료·레시피 **둘 다** 뺐다. 한쪽만 빼면 같은 일을 했는데 한쪽은 남고 한쪽은 안 남는다.
- **저장은 그대로 된다.** 남기지 않는 것과 저장하지 않는 것은 다른 얘기다(0071).
  바뀌었다는 사실은 `updated_at` 이 가진다.
- 메모만 고치면 **기록 자체가 생기지 않는다**(`change_line` 이 빈 배열 → 행 없음).
  메모와 안전재고를 같이 고치면 안전재고 한 줄만 남는다.
- 기획서 §3 의 "메모 변경도 수정 내역에 남지만 매출 상태는 무관" 은 이 결정으로 대체됐다.

## 21. 수정 내역 공통 규격 (0078~0080)

기획 개정 + `docs/prototypes/unified-change-history-all-cases.html` 기준으로 맞췄다.
식재료와 레시피가 **같은 헤더·요약·목록·상세 시트**를 쓴다.

### 용어를 둘로 고정

화면에는 **직접 수정 / 자동 갱신** 둘뿐이다. `자동 반영`·`자동 전파`·`연관 변경`은 안 쓴다.

| 원인 | 제목 |
|---|---|
| 식재료 직접 저장 | 식재료 수정 |
| 레시피 직접 저장 | 레시피 수정 (← `메뉴 수정`) |
| 입고 확정 | 입고 단가 반영 (← `기준 단가 변경`) |
| 입고 취소 | 입고 취소 반영 |
| 식재료 단가 전파 | 식재료 단가 반영 (← `OO 기준 단가 자동 반영`) |
| 고정지출 전파 | 고정지출 반영 |

### 한 사건 안에서 값을 두 갈래로 (`change_kind`)

`direct` 사장님이 친 값 · `derived` 그 결과로 계산된 값. 상세 시트가 두 묶음으로 나눠 그린다.
지금은 한 덩어리라 "내가 세금을 고쳤나?" 로 읽혔다.

> ⚠ **부자재는 `direct`** 다 — 사장님이 직접 담고 빼는 값이다.
> 재료비는 `derived` — 구성을 고친 결과로 따라 움직인다.

한 줄 요약(`summary`)도 **직접 수정한 줄**로 만든다. 계산 결과를 대표로 내세우면
"내가 순이익을 고쳤나?" 가 된다.

### 상태 배지는 목록 전체에서 최대 두 건

과거 사건마다 '현재 매출 반영'을 붙이면 현재 값이 여러 개인 것처럼 보인다.
서버가 `latest_reflected_event_id` · `latest_unreflected_event_id` · `latest_unreflected_state`
를 정해 준다 — **앱이 고르면 식재료 화면과 레시피 화면이 다르게 고를 수 있다.**
매출과 무관한 사건은 언제나 `매출 계산과 무관`을 단다.

### 화면

- 헤더는 `수정 내역` 고정, 유형·이름은 본문에서
- `최근 7일 기준 N건` / `직접 수정 n건 · 자동 갱신 n건`
- 목록 우측의 **대표 금액 제거** — 식재료와 레시피의 단위가 다르고 한 사건에 여러 값이 섞인다
- 카드 여러 장이 아니라 **하나의 그룹 카드**와 행 구분선
- 상세 시트는 사건 제목으로 시작. `변경 내용` 헤더도, 하단 안내 문구도 없다 —
  항목이 많거나 영향이 섞이면 한 문장이 실제 상태와 어긋난다
- `last_change` 는 `{occurred_at, event_id, display_state}` 로 바뀌었다.
  ⚠ 목록의 사건과 **모양이 다르다** — `ChangeEvent` 로 읽으면 `display_state` 를 못 봐서
  상태가 조용히 '무관'이 된다. 전용 `LastChange` 타입으로 갈랐다.

### ⚠ 곁가지로 잡은 것 — 오버로드 가드가 오버로드를 놓쳤다

`change_line` 과 `record_entity_change` 에 인자를 하나씩 더하면서 **옛 시그니처가 남았다.**
`create or replace` 는 인자가 다르면 교체가 아니라 새 함수를 만든다.

```
ERROR: function change_line(unknown, unknown, text, text) is not unique
```

더 나쁜 건 `assert_no_rpc_overloads()` 가 이걸 **통과시켰다**는 것이다 — 가드가
전파 RPC 이름 패턴(`e1_`, `recompute_recipe`, …)만 보고 있었다. 오늘 두 번 "clean"
이라고 말해 놓고 두 번 다 오버로드가 남아 있었다. **public 전체를 보도록 넓혔다**(0080).

## 22. 레거시 내역 정리와 두 개의 가드 (0081)

### 이미 쌓인 행도 새 용어로

0079 는 **앞으로 쓰는** 제목만 바꿨다. 이미 커밋된 행이 남아 있고 보관이 30일이라
그동안 화면에 옛 표현이 그대로 떴다 — `고춧가루 기준 단가 자동 반영`, 바로 그 금지 표현이다.

- 제목을 새 용어로 옮기고, 원본 이름은 **요약으로 살렸다**(제목에서 잃지 않는다)
- ⚠ **`change_kind` 를 함께 채웠다.** 제목만 고치면 옛 행은 갈래가 없어 앱이 전부
  `direct` 로 읽는다 — 재료비·순이익이 '직접 수정'에 들어가 "내가 순이익을 고쳤나?" 가 된다
- 0077 이전 행의 **메모 줄**을 걷어내고, 그래서 빈 사건이 된 행은 지웠다
- ⚠ 대상은 `entity_change_events` 뿐이다. 재고 원장·입고·매출 장부·`price_trends`·
  `profit_trends`·영업일 스냅샷은 건드리지 않는다

정리 후 실측 — 갈래 없는 줄 **0개** · 옛 제목 **0건** · 메모 줄 **0개**.

### `display_state` 가 빠지면 조용히 넘어가지 않는다

`last_change` 모양이 바뀌었을 때 파서가 기본값 `irrelevant` 로 메꿔서, 화면이
"매출 계산과 무관"이라고 **없는 사실을 주장**했다. 두 겹으로 막는다.

- 앱: `parseLastChange` 가 개발 중에는 **바로 던진다**. 배포본에서는 `null` 을 주고
  화면은 **배지를 그리지 않는다** — 모르면 주장하지 않는다.
  (배지 하나 때문에 상세 화면이 통째로 죽으면 안 되므로 배포본에서는 던지지 않는다.)
- DB: `ingredient_detail` · `recipe_detail` 의 `last_change` 가 기록이 있든 없든
  `display_state` 를 담고 그 값이 아는 상태인지 테스트가 확인한다.

### 오버로드 가드가 **실제로 실패하는지** 본다

"지금 오버로드가 없다"만 확인하면 가드가 망가져도 통과한다. 테스트가 일부러
`change_line(int)` 를 만들어 가드가 터지는 것까지 보고, 치운 뒤 다시 통과하는지도 본다.
전파 RPC 이름이 아닌 함수(`business_day`)로도 확인한다 — **전에 뚫려 있던 자리**다.
