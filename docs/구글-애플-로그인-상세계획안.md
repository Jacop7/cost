# Google·Apple 로그인 상세 계획

- 상태: 모바일·탈퇴 서버 경로 구현 중. 제공자 콘솔 설정과 실기기 검증 전 출시 차단
- 기준일: 2026-09-22
- 범위: Expo 모바일 앱의 인증 수단 추가, 기존 매장·원장 접근 보존
- 선행 기준: `docs/기능정의서.md` §18, `docs/작업큐.md`의 `GROUP-MY-ACCESS`, `apps/mobile/src/lib/session.ts`, `apps/mobile/src/lib/SessionProvider.tsx`

## 1. 목표와 결정 경계

사용자가 Google 또는 Apple 계정으로 로그인해도 기존과 동일한 Supabase `auth.users.id`로 자신의 매장에 접근하고, 새 사용자만 명시적으로 첫 매장을 만든다. 인증 수단은 매장 소유권이나 재료·메뉴·발주·입고·재고·매출 원장의 식별자가 아니다. `stores.owner_id = auth.uid()`와 RLS·RPC 권위를 유지한다.

이번 구현 범위는 **소셜 로그인 추가**다. 현행 이메일·비밀번호 가입/로그인을 즉시 제거하지 않는다. 이미 이메일로 가입한 사용자의 유일한 접근 수단을 없애면 원장이 남아도 매장에 접근할 수 없기 때문이다. 향후 Google·Apple만 남기는 전환은 기존 사용자의 연결 완료율, 분실 계정 복구 경로, 운영 Auth 실측을 확인한 별도 결정으로 진행한다. 이 전환 전까지 이메일 계정에는 비밀번호 재설정/지원 경로가 필요하며, 소셜 전용 신규 사용자에게 앱의 아이디·비밀번호 찾기는 제공하지 않는다.

계정 합치기를 단순한 이메일 문자열 비교나 클라이언트의 `owner_id` 변경으로 구현하지 않는다. **같은 사람임이 확인된 로그인 상태에서 Supabase Auth identity linking**을 사용한다. Apple 비공개 릴레이 주소와 기존 이메일은 다를 수 있으므로 자동 연결을 전제로 해서는 안 된다. 이미 생성된 두 `auth.users.id`와 각각의 매장을 자동 병합하지 않는다.

## 2. 현재 구조와 영향 범위

현재 운영 진입은 이메일 `signUp`/`signInWithPassword` → `getUser()` 검증 → 활성 `stores` 조회 → 매장 없으면 `create_store`다. 개발 빌드는 시드 이메일 자동 로그인하므로 소셜 버튼의 실제 동작 시험은 개발 빌드에서 개발 자동 로그인을 우회하는 별도 시험 구성으로 수행한다. 인증 주체가 바뀌면 `sessionGeneration`과 쿼리 캐시 소유자 경계가 변경된다. 현행 `session.ts`는 `SIGNED_IN`·`USER_UPDATED`·`TOKEN_REFRESHED`에서도 같은 사용자 ID면 generation을 유지한다. 계정 연결 후에도 이 동작을 보존하고, 작성 중 초안이 초기화되지 않는지 시험한다.

| 경계 | 변경 계획 | 유지할 불변식 |
|---|---|---|
| `SessionProvider`/`session.ts` | Google·Apple 진입, 취소·오류·진행 중 상태, 기존 계정 연결 안내 | `getUser()`와 매장 재검증 전 업무 화면 차단 |
| `supabase.ts` | 현재 네이티브 SecureStore·웹 저장소 계약 재검증 | 브라우저 콜백/ID 토큰을 앱 로그·원장에 저장하지 않음 |
| MY 계정 관리 | 연결된 로그인 방식 표시와 연결 시작. 마지막 접근 수단 해제 금지 | 사용자 ID·매장 소유권 불변 |
| Supabase Auth/제공자 콘솔 | Google·Apple provider, 허용 client ID와 redirect URI 설정 | 서비스 키·Apple `.p8`·client secret은 저장소와 `EXPO_PUBLIC_*`에 금지 |
| DB·원장 | 원칙적으로 스키마 및 원장 변경 없음 | `stores.owner_id`와 모든 거래 FK를 소셜 provider ID로 재작성하지 않음 |

## 3. 플랫폼 및 인증 방식

| 플랫폼 | Google | Apple | 검증 환경 |
|---|---|---|---|
| iOS 앱 | 네이티브 Google 인증으로 ID 토큰 획득 후 `signInWithIdToken` | `expo-apple-authentication`으로 Apple ID 토큰 획득 후 `signInWithIdToken` | 실제 iOS 기기 개발/배포 빌드 |
| Android 앱 | 네이티브 Google 인증으로 ID 토큰 획득 후 `signInWithIdToken` | Apple OAuth 외부 브라우저 경로와 앱 복귀. Apple Developer Services ID·키 운영이 준비된 경우에만 노출 | 실제 Android 기기 개발/배포 빌드 |
| 웹 미리보기 | 공급자 OAuth 브라우저 경로를 별도 구현·허용 origin을 검증하기 전에는 이메일 개발 진입 유지 | 동일 | 현행 Expo web 회귀 확인 |

Google 네이티브 라이브러리는 Expo SDK 54·Android Credential Manager·iOS 빌드 호환성 시험을 거쳐 확정한다. Google 네이티브 SDK는 Expo Go에서 동작하지 않으므로 개발 빌드를 사용한다. iOS Apple은 `ios.usesAppleSignIn=true`와 config plugin/entitlement 및 Apple의 시스템 버튼을 사용한다. Android Apple은 iOS 네이티브 API를 재사용하지 않고, 정식 callback·앱 링크·상태/nonce 검증이 완료될 때만 제공한다. Android Apple의 범위가 준비되지 않았다면 버튼을 숨기고 iOS Google·Apple, Android Google부터 단계적으로 출시한다. 이는 전체 플랫폼 제공 완료로 표시하지 않는다.

ID 토큰은 Supabase Auth에 전달하고 앱은 자체 인증 서버나 독자 JWT를 만들지 않는다. 요청별 암호학적으로 안전한 nonce/state, provider의 토큰 검증, redirect allowlist, 콜백의 단일 처리·재생 방지를 설계한다. 성공 후 Auth 세션을 다시 `getUser()`로 확인하고 기존 `resolveStoreId()` 경로로만 업무에 진입한다. 취소·네트워크 실패·앱 복귀 누락은 계정 생성/연결 성공으로 표시하지 않는다.

네이티브 제공자별 nonce 계약은 사용 라이브러리 판본을 정한 뒤 실증한다. Apple은 원문 nonce와 Apple에 전달되는 SHA-256 값, Supabase에 전달되는 원문 nonce의 일치 여부를 실제 ID 토큰으로 검증한다. Google도 선택한 iOS·Android SDK의 nonce 전달 지원과 Supabase 검증 방식을 확인한다. 지원되지 않는 경로에서 검증을 조용히 생략하지 않으며, 예외 설정이 필요하면 해당 플랫폼의 위험·대체 재생 방지책·설정값을 별도 승인 기록에 남긴다.

브라우저 OAuth가 필요한 Android Apple 경로는 PKCE code 교환을 사용한다. 콜백 처리기는 `SessionGate` 바깥의 앱 시작 경계에서 초기 URL과 실행 중 URL을 모두 수신한다. 현재 `detectSessionInUrl=false`이므로 자동 URL 세션 감지에 의존하지 않는다. 인증 시도 ID·state·PKCE verifier를 안전하게 보존하고, 앱 재시작 후 복귀·중복/지연 복귀·다른 계정 로그인 중 복귀를 구분한다. verifier가 없거나 시도와 일치하지 않으면 세션을 열지 않고 다시 시작하도록 안내한다. 브라우저로 이동한 뒤 앱이 종료된 cold start를 실제 기기에서 시험한다.

## 4. 계정별 사용자 흐름

1. **신규 사용자**: 로그인 방식 선택 → 제공자 승인 → Supabase 사용자 검증 → 활성 매장 없음 → 매장 등록 선택 → 기존 `create_store`로 1회 생성 → 업무 진입. 매장 생성 전에 사용자는 다른 기존 계정으로 로그인할 수 있다.
2. **기존 이메일 사용자**: 이메일로 먼저 로그인 → MY/계정 관리에서 Google 또는 Apple 연결 → 제공자 인증 → Supabase의 수동 identity linking 설정을 확인한 뒤 `linkIdentity` 성공 → `getUser()`의 ID가 **연결 전과 동일한지** 확인 → 연결 방식 표시. 네이티브 토큰 연결과 브라우저 OAuth 연결은 SDK별로 별도 시험한다. 다음 로그인에 해당 제공자를 사용해도 같은 매장이 열리는지 검증한다.
3. **동일한 검증 이메일로 소셜 로그인**: Supabase 자동 연결이 일어날 수 있으나, 결과의 `auth.users.id`와 매장 ID를 재검증한다. Supabase는 미확인 identity를 연결 대상으로 안전하게 처리한다고 문서화하지만, 운영 이메일 확인 설정과 기존 미확인 계정을 실측한다. 미확인 이메일/비밀번호 계정이 같은 주소의 Google 로그인으로 안전하지 않게 승계되는 경우 제공자 출시를 차단한다. 자동 연결의 존재 자체를 성공 판정으로 삼지 않는다.
4. **Apple 비공개 릴레이·다른 이메일**: 기존 사용자는 **첫 소셜 로그인 전에** 이메일 계정으로 로그인하여 Apple identity를 연결하도록 안내한다. 이미 Apple 로그인으로 별도 Auth 사용자 B가 생긴 경우 B에 매장이 없어도 identity가 B에 귀속되므로 원래 사용자 A의 `linkIdentity`는 실패한다. 이때 A로 돌아와 단순히 연결을 다시 시도하라고 안내하지 않는다. B의 데이터·연결 상태를 읽기 전용으로 확인하고, 재인증을 거친 계정 정리·제공자 연결 해제 가능성·복구 순서를 별도 절차와 시험으로 확정하기 전까지 CS 충돌로 처리한다. A/B의 매장이나 원장을 자동 병합·이전하지 않는다.
5. **탈퇴·접근 차단**: 기존 `retire_my_account`만으로 Apple 탈퇴를 완료 처리하지 않는다. 이 RPC는 현재 Auth 사용자 삭제만 수행하며 Apple 제공자 토큰은 철회하지 않는다. Apple 로그인 도입 전에 서버에서 Apple authorization code를 교환해 철회에 필요한 유효 토큰을 안전하게 확보·보관하거나, Apple 공식 기술 문서가 허용하는 재인증·수동 철회 경로를 구현한다. 탈퇴 시 본인 재확인 → Apple 토큰 철회(또는 명시된 대체 경로) → 기존 매장 보관·Auth 삭제를 조정하고, 철회 실패·재시도·부분 완료 상태를 기록한다. 비밀과 토큰은 앱 저장소·로그·문서에 남기지 않는다. 제공자 앱 권한 철회만으로 코스트킵 탈퇴·원장 삭제를 추정하지 않는다. 탈퇴 뒤 동일 제공자 로그인은 이전 매장에 재접근하지 못해야 한다. **실기기 탈퇴·재로그인 시험이 통과하기 전에는 Apple 로그인을 출시하지 않는다.**

연결 해제 UI는 1차에 제공하지 않는다. 후속 제공 시 `getUserIdentities()`로 실제 연결 상태를 확인하고, 마지막 로그인 수단 해제 또는 활성 세션을 잃는 해제를 차단한다. CS가 임의의 이메일·제공자 표시명만으로 두 사용자 ID의 매장을 연결하는 관리자 기능도 범위 밖이다.

## 5. 화면·문구·보안 계약

- 로그인 화면에는 `Google로 계속하기`, iOS에서 사용 가능한 경우 시스템 `Apple로 계속하기`, 기존 `이메일로 로그인/회원가입`을 표시한다. 버튼별 로딩과 중복 탭 방지, 취소 시 조용한 원위치 복귀, 거절/네트워크/설정 오류의 구분을 제공한다.
- MY 계정 관리는 내부 사용자 ID와 연결된 방식(이메일·Google·Apple)을 읽기 전용으로 표시하고, 기존 사용자의 **연결** 동작을 로그인 동작과 구분한다. 제공자가 보낸 이메일·이름은 소유권 키가 아니며, Apple 이름은 최초 동의 때만 올 수 있으므로 필수 입력값으로 사용하지 않는다.
- 접근 가능한 버튼 크기·초점·스크린리더 문구를 기존 kit/tokens에 맞춘다. Apple 버튼은 Apple 시스템 컴포넌트 규칙을 따른다.
- `id_token`, `access_token`, `authorization code`, nonce, Apple 개인키, client secret, 개인 이메일·이름을 앱 로그·분석 이벤트·Git·검수 스냅샷에 넣지 않는다. 내부 관리자에는 사용자 ID, 제공자 종류, 연결 상태/시각 등 최소 진단 메타데이터만 표시한다.
- 제공자 인증 실패와 계정 존재 여부를 이용한 이메일 열거를 허용하지 않는다. 이미 로그인한 사용자와 새 provider의 연결 실패는 기존 세션을 보존한다.

## 6. 제공자 설정과 운영 전제

1. Google Cloud의 iOS bundle ID·Android package/SHA-1·웹 OAuth client ID, Supabase 허용 client ID 및 callback을 개발·스테이징·운영별로 구분한다. 실제 값은 비밀 저장소에 보관하고 계획 문서에는 기록하지 않는다.
2. Apple Developer에서 앱 ID의 Sign in with Apple capability와 iOS 번들 entitlement를 확인한다. **iOS 네이티브 로그인만 출시해도 계정 탈퇴 시 Apple 토큰을 서버에서 철회하기 위한 `.p8` 키·client secret 생성/보관·회전·장애 복구가 필요하다.** Android Apple OAuth를 제공할 경우 Services ID·return URL·서명 키 발급 및 6개월 secret 회전 절차와 책임자를 추가한다. iOS 네이티브 전용 경로와 OAuth 경로의 설정을 구분한다.
3. Supabase Auth provider·수동 identity linking 허용 여부·redirect allowlist·이메일 확인 필수 여부를 환경별로 설정한다. 현행 로컬 `config.toml`은 이메일 확인이 꺼져 있고 소셜 provider와 수동 연결 설정이 없으므로, 별도 시험 구성에 `[auth] enable_manual_linking`, `[auth.external.google]`, `[auth.external.apple]`과 비밀의 `env(...)` 참조를 추가해 실험한다. nonce 예외 설정은 판본별 실증 후에만 정한다. 자동 연결·미확인 이메일 충돌·연결 후 ID 불변을 로컬 및 스테이징에서 재현한다. 현재 DB migration 배포 가드는 Auth 콘솔 설정을 검증하지 않으므로, 환경별 프로젝트 식별자·변경 전후 provider 설정·허용 client ID/redirect URI·비밀 버전(값 제외)·적용 책임자·되돌리기 절차·적용 후 재조회 영수증을 별도 Auth 변경 기록에 남긴다. 스테이징 실기기 확인 뒤 운영에 반영하며 DB 가드 통과를 Auth 설정 검증 완료로 표현하지 않는다.
4. 기존 사용자 분포(이메일 사용자 수, 이메일 확인이 안 된 사용자·매장 소유자 수)와 Auth provider 설정을 개인정보 노출 없이 집계한다. 운영에서 이메일 확인을 필수로 전환할 때 기존 사용자 접근이 끊기지 않도록 전환·재확인 절차를 먼저 검증한다. 임의 계정 병합이나 기존 사용자 ID 재발급 없이 시험 계정으로 흐름을 확인한다.

## 7. 구현 순서와 수용 기준

| 단계 | 산출물 | 통과 조건 |
|---|---|---|
| A. 기준선 | 이메일 로그인/가입·탈퇴·캐시 경계 시험과 호스티드 Auth 설정 감사 | 기존 계정·매장 ID 확인, 자격정보 비노출 |
| B. 인증 어댑터 | 플랫폼별 제공자 토큰/콜백을 `session.ts` 경계에 연결 | 취소·거절·중복 콜백·만료/재생 차단, cold start 복귀와 `getUser()` 재검증 |
| C. 계정 연결 | 기존 사용자 로그인 상태의 provider 연결·결과 ID 검증 | 연결 전후 `auth.users.id`, `stores.id`, 원장 수량 불변; 이미 다른 사용자에 연결된 identity 충돌 검출 |
| D. UI | 로그인 선택 및 MY 연결 방식/안내 | 네이티브 접근성·웹 기존 진입 회귀 |
| E. 통합 | 실제 기기·스테이징 smoke, 소유권/RLS·푸시 등록·캐시 격리 | 다른 사용자/매장 데이터 노출 0건 |
| F. 탈퇴·출시 | Apple 토큰 철회/부분 실패 복구, 제공자별 기능 플래그와 운영 모니터링·롤백 | 실기기 탈퇴·재로그인, 실패율/중복 계정 징후 관측, 이메일 기존 접근 유지 |

필수 시나리오: 신규 Google/Apple, 기존 이메일→Google/Apple 네이티브 토큰 연결, 동일 검증 이메일 자동 연결, **미확인 이메일/비밀번호 계정과 동일 주소의 Google 로그인**, Apple 비공개 릴레이, **별도 사용자 B에 이미 연결된 Apple identity(매장 없음/있음 각각)**, Google·Apple 이메일 불일치, 기존 매장 보유자 재로그인, 다른 계정 A→B 전환, 로그인 취소/오프라인/타임아웃, 중복 탭/중복 callback, 브라우저 인증 중 앱 종료 후 복귀, 늦은 callback과 verifier 유실, 만료 토큰, 연결 실패 뒤 기존 세션 및 작성 중 초안 유지, Apple 철회 성공/실패 뒤 탈퇴·재로그인과 Apple 계정의 앱 연결 해제 확인, 푸시 기기 소유자 변경, 개발 자동 로그인과 소셜 시험의 분리, Android/iOS 실제 빌드, Expo web 기존 로그인 회귀. 각 경우 `auth.users.id`·매장 ID·원장 건수와 화면 상태를 함께 확인한다.

`corepack pnpm verify`의 필수 단계 및 인증 관련 모바일·DB 시험을 실행한다. 검수는 정확한 계획 판본과 변경 diff를 대상으로 독립 검수하고, 지적을 이 파일에 반영한 뒤 재검수한다. 시험 실패/건너뜀을 전체 통과로 표현하지 않는다. DB 변경은 기존 `docs/브랜치-DB-운영-기획안.md`의 대상별 가드를 따르고, Auth 제공자 콘솔 변경은 6절의 별도 감사·적용·되돌리기 영수증을 따른다.

## 8. 출시·복구 판단

처음에는 이메일 로그인을 유지한 채 제공자를 단계적으로 켠다. 제공자 장애 시 해당 버튼만 비활성화하고 기존 이메일 사용자의 로그인·매장·원장 접근을 유지한다. Apple 토큰 철회에 필요한 서버 비밀 운영이 불가능하면 iOS를 포함한 Apple 로그인을 출시하지 않는다. Android OAuth의 Services ID·비밀 회전 운영만 미완료라면 Android Apple만 제외한다. 소셜 전용 사용자를 위한 대체 로그인 수단과 CS의 본인 확인·복구 절차가 검증되기 전에는 이메일 경로를 전부 없애지 않는다.

미결정: (1) Android에서도 Apple 로그인을 첫 출시 범위로 요구할지, (2) 장기적으로 이메일 신규 가입을 닫을지, (3) 이미 분리된 두 Auth 사용자/매장의 수동 복구를 어떤 관리자 절차로 처리할지. 이 셋은 구현 편의로 자동 확정하지 않고, 단계별 출시 범위와 사용자 데이터 보호 기준으로 결정한다.

## 9. 현재 구현과 활성화 순서

- 네이티브 앱은 제공자 ID 토큰·nonce로 Supabase Auth에 로그인하거나 기존 사용자 ID에 identity를 연결한다. 웹은 기존 이메일 진입을 유지한다. Google 네이티브 플러그인은 CocoaPods 설정을 위해 항상 적용하고, 로그인 버튼은 `EXPO_PUBLIC_GOOGLE_WEB_CLIENT_ID`, `EXPO_PUBLIC_GOOGLE_IOS_CLIENT_ID`, `EXPO_PUBLIC_GOOGLE_IOS_URL_SCHEME` 세 값이 모두 있을 때만 연다. 값이 없으면 플러그인은 비기능성 iOS URL scheme을 사용한다. 값은 환경별 OAuth 클라이언트 식별자이며 비밀을 넣지 않는다.
- Apple 버튼은 iOS에서만 사용하며 `EXPO_PUBLIC_APPLE_ACCOUNT_DELETION_READY=true`와 실제 기기 가용성이 확인돼야 표시한다. iOS Google도 Apple 제공 조건이 충족된 뒤 연다. 이 플래그는 운영자가 아래 서버 배포·제공자 설정·실기기 탈퇴 검증을 끝냈다는 출시 신호이지, 보안 검증을 대체하지 않는다.
- Apple 계정 탈퇴는 `retire-apple-account` Edge Function에 **새 일회용 authorization code**를 보내 Apple `/auth/token` 교환 → 현재 사용자에 연결된 Apple subject 확인 → `/auth/revoke` → 기존 `retire_my_account` RPC 순서로 처리한다. 함수 비밀 `APPLE_TEAM_ID`, `APPLE_KEY_ID`, `APPLE_CLIENT_ID`(iOS App ID), `APPLE_PRIVATE_KEY`는 서버 전용으로 설정한다. Auth 사용자 조회에 필요한 Supabase URL·공개 키는 함수 기본 환경에 둔다. Apple 코드가 없거나 실제 철회가 실패한 경우에만 앱이 직접 연결 해제 안내를 명시적으로 선택하게 한 뒤 탈퇴할 수 있다. 사용자 취소·함수 설정/네트워크 오류에는 이 대체 버튼을 열지 않는다. 비밀·토큰은 앱, 원장, 로그에 저장하지 않는다.
- iOS에서는 이 기기에서 **Apple로 연 세션**만 Apple 자격 철회 알림·앱 복귀 상태 확인 대상으로 삼는다. 현재 로그인 방식과 사용자 ID만 기기 SecureStore에 보관하고 토큰은 별도 저장하지 않는다. 이메일·Google로 다시 로그인한 같은 사용자에게 Apple 철회를 이유로 로그아웃을 강제하지 않는다. 신규 보안 테스트는 `scripts/verify-contracts.mjs`의 필수 검사에 연결한다.
- 출시 전 Supabase Auth Google/Apple provider 및 수동 identity linking을 환경별로 설정하고, 함수 배포·Apple 키 회전·실기기 iOS/Android 빌드와 탈퇴 후 재로그인을 시험한다. Android Apple OAuth, 웹 소셜 로그인, 분리된 두 사용자 ID의 병합은 현재 구현되지 않았다. 개발 자동 로그인을 끄는 실제 인증 시험에는 `EXPO_PUBLIC_DEV_AUTO_LOGIN=false`를 사용한다.

## 10. 로컬 구현 검증 기록 (2026-09-22)

- 모바일 타입 검사, 인증·계정 관리 관련 모바일 시험 53개, Apple 탈퇴 함수 시험 4개, 터치 영역 회귀 시험 67개가 통과했다. `corepack pnpm verify --no-db`는 타입·core/mobile 시험·계약/ACL/디자인·웹 번들 4/6단계가 통과했다.
- 전체 `corepack pnpm verify` 재실행은 ① 타입, ② core/DB/mobile 시험, ③ 계약/ACL/디자인, ④ 새 DB, ⑥ 웹 번들이 통과했다. ⑤ 업그레이드 경로의 0240 사후조건은 전역 PostgreSQL 역할 `margincook_rpc_executor`가 남아 실패했다. 같은 시각 다른 `verify` 프로세스의 임시 DB 작업이 관측돼 전역 역할 경합이 원인 후보지만, 재현·격리 판정 전에는 확정하지 않는다. 별도 선행 전체 실행에서는 ⑤가 통과했다. 정확히 같은 실행의 6/6 통과 영수증은 아직 없다.
- Claude Fable과 Codex Astra Ultra의 수정본 독립 검수에서 미해결 P0~P2가 없다는 READY 판정을 받았다. 이는 제공자 콘솔 설정·iOS/Android 실제 빌드·Google/Apple 실계정 로그인·탈퇴 시험을 대체하지 않는다.
